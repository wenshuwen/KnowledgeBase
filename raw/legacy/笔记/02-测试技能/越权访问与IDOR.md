# 越权访问 / IDOR 测试

> 📌 来源：[[Test-测试经验总结-原文]] ｜ 安全测试章-越权访问 小节

攻击者通过修改请求中的标识符（如 ID、用户名等），访问或操作了本不属于自己的资源。分为水平越权（同级用户间）和垂直越权（低权限访问高权限功能）。核心逻辑：通过篡改资源标识，访问或操作不属于当前身份的数据。

|类型|攻击方向|通俗比喻|核心危害|
|---|---|---|---|
|水平越权|同级别用户之间横向跨越|普通员工 A 看到普通员工 B 的工资条|数据泄露（横向）|
|垂直越权|低级别用户向高级别提升|普通员工执行管理员的删除操作|功能滥用（纵向）|

> **测试详解与示例：**
> 
> 

- **场景： 用户查看个人订单详情 ****`GET /api/order/detail?id=10086`**

- **测试步骤：**

    - 使用账号 A 登录，获取自己的订单 ID（如 10086）。

    - 抓包修改请求中的 `id` 参数为其他值（如 10087）。

    - 观察响应：如果返回了账号 B 的订单信息，则存在水平越权。

    - 使用普通用户账号，尝试访问管理员接口（如 `/api/admin/user/delete`），若成功执行，则存在垂直越权。

- **关键检测点：**

    - 遍历自增/可预测 ID

    - 替换 UUID/Token 中的关联字段

    - 检查 API 是否仅依赖前端隐藏按钮做权限控制

- **修复建议：** 服务端必须校验当前 Session/JWT 所属用户与请求资源的归属关系，不能仅信任客户端传入的 ID。

    ---

    #### **1\.1 水平越权**

    服务端在处理请求时，仅根据客户端传入的资源标识符（ID、手机号、邮箱等）查询数据，未校验该资源是否属于当前登录用户。

    **示例 1：订单详情接口（经典 IDOR）**

    ```HTTP
    # 正常请求（用户A查看自己的订单）
    GET /api/v1/orders/ORD-2024-88721 HTTP/1.1
    Authorization: Bearer eyJhbGciOi...（用户A的Token）
    
    # ✅ 安全响应：返回用户A的订单信息
    # ❌ 越权响应：将ORD-2024-88721改为ORD-2024-88722后，返回了用户B的订单
    ```

    **示例 2：批量赋值导致的数据篡改**

    ```HTTP
    # 用户修改个人资料
    PUT /api/v1/user/profile HTTP/1.1
    Content-Type: application/json
    Authorization: Bearer eyJhbGciOi...（用户A的Token）
    
    {"nickname": "test", "avatar": "https://..."}
    
    # 攻击者额外传入其他用户的标识字段
    {"nickname": "test", "user_id": "U-10086", "email": "hacker@evil.com"}
    # 若服务端自动绑定了user_id字段 → 成功修改了用户U-10086的资料
    ```

    **示例 3：非自增 ID 的越权（UUID/GUID）**

    ⚠️ 误区： "使用 UUID 就安全了" —— UUID 只是增加了猜测难度，但如果存在以下泄露途径，仍可被利用：

    - 列表接口返回了完整 UUID

    - 分享链接中包含 UUID

    - 邮件/短信通知中暴露 UUID

    - 前端 JS 源码中硬编码或拼接了 UUID

    ---

    > **系统化测试方法**
    > 
    > 

    - 双账号对比法（黄金标准）

        - 同时登录账号 A 和账号 B

        - 用账号 A 抓取所有涉及资源 ID 的请求

        - 替换为账号 B 的资源 ID，使用账号 A 的 Token 重放

        - 关键判断： 响应状态码 200 ≠ 越权成功，必须对比响应体内容确认是否为 B 的数据

    - ID 遍历策略

        - 自增 ID：直接递增/递减遍历

        - 雪花算法 ID：分析时间戳\+机器 ID 规律，缩小爆破范围

        - UUID：从列表接口、历史记录、分享链接中收集已知 UUID 作为种子

    - 参数变体测试

    ```Plain Text
    # 不仅测试路径参数，还要测试：
    ?id=xxx          # Query参数
    {"id": "xxx"}    # JSON Body
    <id>xxx</id>     # XML Body
    X-Custom-Id: xxx # 自定义Header
    Cookie: session_id=xxx  # Cookie中的标识符
    ```

    - 关联对象链式越权

        - 用户 A 无权直接访问用户 B 的订单

        - 但用户 A 可以访问自己的"收货地址"

        - 收货地址接口返回了关联的 `order_id`

        - 通过该 `order_id` 间接获取用户 B 的订单 → 二阶 IDOR

    #### **1\.2 垂直越权**

    服务端未对用户角色/权限进行校验，或仅依赖前端隐藏菜单/按钮做访问控制，导致低权限用户可直接调用高权限接口。

    **示例 1：管理接口直接访问**

    ```HTTP
    # 普通用户尝试调用管理员接口
    DELETE /api/admin/users/U-10086 HTTP/1.1
    Authorization: Bearer eyJhbGciOi...（普通用户Token）
    
    # ❌ 越权成功：返回200，用户被删除
    # ✅ 安全响应：返回403 Forbidden
    ```

    **示例 2：前端隐藏 ≠ 后端校验**

    ```HTML
    <!-- 前端根据角色隐藏了按钮 -->
    <div v-if="user.role === 'admin'">
        <button @click="deleteUser(id)">删除用户</button>
    </div>
    ```

    > ⚠️ 攻击者无需点击按钮，直接构造 HTTP 请求即可调用 `/api/admin/users/delete`。前端控制仅是 UX 优化，绝非安全措施。
    > 
    > 

    **示例 3：角色参数篡改**

    ```HTTP
    # 注册/修改资料时传入角色字段
    POST /api/v1/user/update HTTP/1.1
    {"role": "admin", "is_verified": true}
    # 若服务端未过滤这些字段 → 直接提权为管理员
    ```

    **示例 4：JWT 角色声明篡改**

    ```JSON
    // 原始JWT Payload
    {"sub": "user123", "role": "viewer", "exp": 1720000000}
    
    // 攻击者修改role后重新签名（若密钥弱或算法混淆）
    {"sub": "user123", "role": "admin", "exp": 1720000000}
    ```

    ---

    > **系统化测试方法**
    > 
    > 

    - 权限矩阵枚举法

        - 梳理系统中所有角色（超级管理员、运营、客服、普通用户、游客）

        - 列出所有 API 端点，构建角色×接口矩阵

        - 逐格验证：每个角色对每个接口的实际访问结果是否与预期一致

    - 接口发现优先于权限测试

        - 爬取前端 JS/Swagger/OpenAPI 文档，提取全部 API 路径

        - 关注命名规律：`/admin/*`, `/internal/*`, `/manage/*`, `/config/*`

        - 使用目录爆破工具发现未文档化的管理接口

    - 降级测试

        - 使用高权限账号抓取请求

        - 逐步降低 Token 权限等级重放

        - 观察在哪一级权限开始返回 403 → 确认权限边界是否清晰

    - 功能级 vs 数据级垂直越权区分

        - 功能级： 能否调用某个接口（如删除用户）

        - 数据级： 能调用接口但只能操作自己管辖范围的数据（如区域经理只能看本区数据）

        - 两者需分别测试

    #### **1\.3 测试方法对比**

    |    测试步骤|    水平越权测试|    垂直越权测试|
    |---|---|---|
    |    准备账号|    准备两个同权限账号（A 和 B）|    准备一个低权限账号和一个高权限账号|
    |    抓取请求|    用 A 账号获取一个资源 ID（如订单号 12345）|    用管理员账号抓取一个敏感接口（如删除用户）|
    |    篡改身份标识|    将请求中的资源 ID 改为 B 的（如 12346）|    将 Cookie 或 Token 替换为低权限用户的凭证|
    |    重放请求|    用 A 的 Cookie \+ B 的 ID 发起请求|    用低权限用户的 Cookie \+ 管理员的接口路径发起请求|
    |    判定依据|    是否返回了 B 的数据|    是否成功执行了管理员功能|

    **📌 重要提醒：混合越权**

    实际业务中，更多是水平\+垂直的混合体。例如：

    - 一个普通用户通过修改 `role=admin` 参数，把自己提升为管理员（垂直）。

    - 然后利用管理员权限，导出所有用户的手机号（水平）。

    所以安全测试时，建议交叉组合测试：用低权限用户的凭证 \+ 高权限接口 \+ 高权限资源 ID，全方位排查。

    💡 实战心法

    - 越权测试的核心不是工具，而是业务理解。 测试前务必画出完整的用户角色图、数据实体关系图和业务流程图。不知道"应该怎样"，就无法发现"不该怎样"。

    - 水平越权测试务必使用两个真实账号。 单账号测试无法区分"正常返回自己的数据"和"越权返回他人的数据"。

    - 关注"间接引用"。 很多系统修复了直接 IDOR，但通过关联查询、导出功能、消息通知等侧面通道仍然泄露了跨用户数据。

    - 越权漏洞往往成群出现。 发现一个越权点，意味着整个模块的权限模型可能存在系统性缺陷，应扩大测试范围而非仅报告单个接口。
