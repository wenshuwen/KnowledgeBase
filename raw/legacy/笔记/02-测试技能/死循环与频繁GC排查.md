# 死循环与频繁 GC 排查

> 📌 来源：[[Test-测试经验总结-原文]] ｜ 业务知识章-死循环&频繁GC 小节

## **3\.1 死循环（Endless Loop）**

> **什么是死循环？**
> 
> 

死循环是指程序中的一个循环结构无法正常终止，导致程序陷入无限重复执行某段代码的状态。这通常是由于编程逻辑错误、缺少退出条件或循环条件永远为真引起的。

**常见表现形式：**

- 循环条件错误：如 `while(True)` 或 `for(;;)` 且内部没有 `break` 跳出机制。

- 变量未更新：循环体内没有改变循环变量的值，导致退出条件永远无法满足。

- 无穷递归：函数不断调用自身，且没有设置递归停止条件，最终导致栈溢出（Stack Overflow）。

**危害与影响：**

死循环会持续占用大量的 CPU 资源，导致程序“假死”、无响应，甚至引发整个系统崩溃。

**特殊情况（良性死循环）：**

在某些场景下，死循环是刻意设计的。例如操作系统中的消息循环、服务器监听客户端请求的事件驱动模型，以及嵌入式硬件控制中，都需要通过死循环来维持程序的持续运行。

## **3\.2 频繁 GC（Garbage Collection）**

> **什么是频繁 GC？**
> 
> 

在 Java 等带有自动内存管理的语言中，GC 负责回收不再使用的对象。如果 GC 触发得过于频繁，或者单次 GC 耗时过长，会导致应用出现严重的停顿（Stop The World），表现为响应变慢、接口超时或吞吐量急剧下降。

**核心分类与正常频率参考：**

- Minor GC（年轻代回收）：主要回收短生命周期对象。正常情况下，每分钟发生几次到几十次属于健康范围。如果每秒都在触发，说明内存分配压力极大。

- Full GC（全局/老年代回收）：影响面大，停顿时间长。理想情况下应非常少（例如每小时不超过 1 次）。频繁发生 Full GC 通常是系统出现严重问题的信号。

**频繁 GC 的常见原因：**

- 内存分配不合理：堆内存（Heap）设置过小，或新生代（Eden/Survivor 区）空间不足，导致对象频繁晋升到老年代，迅速填满老年代空间。

- 代码缺陷：存在内存泄漏（对象本应被回收却被错误地持有引用），或者代码中频繁创建大对象、短生命周期对象过多。

- GC 策略不当：选用的垃圾收集器（如 Serial GC）不适合当前的高并发业务场景，或者晋升阈值（MaxTenuringThreshold）设置不合理导致“过早晋升”。

---

## **3\.3 关联与优化建议**

在实际的线上故障中，死循环往往是导致频繁 GC 的“罪魁祸首”之一。如果代码陷入了死循环，并在循环体内不断创建新对象，内存会被迅速耗尽，从而疯狂触发 Full GC，最终导致服务完全瘫痪。

排查与优化建议：

- **监控先行：**利用 JVisualVM、Arthas 或 Prometheus 等工具，持续监控 GC 频率、单次耗时以及 CPU 占用率。一般建议 GC 总耗时不要超过总运行时间的 5%。

- **分析 GC 日志：**通过开启 `-XX:+PrintGCDetails` 等参数输出 GC 日志，观察是 Minor GC 还是 Full GC 频繁，以及 GC 前后的内存回收比例。

- **Dump 内存快照：**如果怀疑内存泄漏或死循环，可以使用 `jmap` 导出堆内存快照（Heap Dump），通过 MAT 等工具分析到底是哪些对象占用了大量内存且无法被回收。

- **代码与参数调优：**修复代码中的逻辑错误，减少无用对象的创建；同时根据业务特点适当增大堆内存（`-Xmx`），或更换更高效的垃圾收集器（如 G1、ZGC）。

## **3\.4 排查方法**

> **系统级排查（定位异常进程与线程）**
> 
> 

- 查看服务器整体资源与进程占用：

```Shell
top
```

- *作用：快速找到 CPU 或内存占用最高的 Java 进程 PID。*

---

- 查看指定进程下的所有线程 CPU 占用：

```Shell
top -H -p <进程PID>
```

- *作用：精准定位进程内哪一条线程（TID）在“烧 CPU”。按 **`P`** 键可按 CPU 占用排序。*

---

- 将十进制线程 ID 转换为十六进制：

```Shell
printf "%x\n" <十进制TID>
```

- *作用：JVM 线程堆栈中的线程 ID 是十六进制的（nid），此命令用于格式转换以便后续检索。*

---

> **JVM 级排查（定位死循环、GC 与内存问题）**
> 
> 

- 导出 Java 线程堆栈快照：

```Shell
jstack -l <进程PID> > /tmp/thread_dump.log
```

- *作用：排查死循环、死锁、线程阻塞。结合上一步的十六进制 TID，在日志中搜索 **`nid=0x...`** 即可精准定位到具体的业务代码行。*

---

- 实时监控 JVM GC 状态：

```Shell
jstat -gc <进程PID> 1000
```

- *作用：每秒打印一次 GC 状态。重点观察 **`YGC`**（Young GC 次数）、**`FGC`**（Full GC 次数）及 **`FGCT`**（Full GC 总耗时）。若 FGC 每分钟 ≥1 次，说明存在严重问题。*

---

- 查看堆内存详细使用情况：

```Shell
jmap -heap <进程PID>
```

- *作用：查看堆总配置、新生代与老年代的使用率。若老年代快满且持续增长，极大概率是内存泄漏。*

---

- 导出堆内存快照（OOM 或内存泄漏排查）：

```Shell
jmap -dump:format=b,file=/tmp/heap.hprof <进程PID>
```

- *作用：导出当前内存中的对象状态。⚠️ 注意：此操作会触发 STW（Stop\-The\-World），建议在业务低峰期执行，导出后使用 MAT 工具进行离线分析。*

---

- 查看 JVM 启动参数配置：

```Shell
jinfo -flags <进程PID>
```

- *作用：确认线上 JVM 参数（如 **`-Xmx`**, **`-Xms`**）是否符合预期，排查是否因参数配置不当（如新生代过小）导致频繁 GC。*

---

> **辅助分析命令**
> 
> 

- 快速统计线程状态分布：

```Shell
grep java.lang.Thread.State /tmp/thread_dump.log | sort | uniq -c
```

- *作用：快速评估系统健康度。若大量线程处于 **`RUNNABLE`** 且 CPU 满载，通常是死循环；若大量处于 **`WAITING`**，可能是锁竞争或阻塞。*

---

- 列出当前机器上所有 Java 进程：

```Shell
jps -l
```

- *作用：在不确定 PID 时，快速列出所有 Java 进程及其主类名称。*

> **💡 排查核心口诀：**
> ***CPU 飙高用 ******`top -H`****** 找线程，转十六进制后 ******`jstack`****** 抓代码；***
> ***频繁卡顿看 ******`jstat`****** 查 GC，内存泄漏用 ******`jmap`****** 导快照。***
> 
>
