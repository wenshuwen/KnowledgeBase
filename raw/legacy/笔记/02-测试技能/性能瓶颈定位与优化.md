# 性能瓶颈定位与优化

> 📌 来源：[[Test-测试经验总结-原文]] ｜ 业务知识章-性能瓶颈定位&优化 小节

## CPU 层瓶颈

|异常现象|健康范围|风险阈值|可能原因|排查工具/方法|优化建议|
|---|---|---|---|---|---|
|CPU 利用率持续 \> 80%|用户态 60%\~70%|\>85%|线程竞争、死循环、算法效率低|top \-Hp PID、jstack、火焰图|优化热点代码、减少锁竞争、增加 CPU 核心|
|上下文切换过高（\>3 万/秒）|\-|\>30,000/s|高并发多线程、线程频繁阻塞唤醒|vmstat、perf sched|减少线程数、使用协程池、异步非阻塞模型|
|运行队列长度持续增长|\-|r \> CPU 核心数\*2|CPU 算力不足、任务堆积|top/vmstat 查看 r 列|增加 CPU 资源、优化任务处理效率|

## 内存层瓶颈

|异常现象|健康范围|风险阈值|可能原因|排查工具/方法|优化建议|
|---|---|---|---|---|---|
|内存使用率 \> 95%，Swap 飙升|\-|使用率\>95%|物理内存不足、过度分配|free \-h、top|增加物理内存、优化内存使用、减少 Swap|
|Full GC 频繁（\>5 次/分钟）|\-|\>5 次/分钟|内存泄漏、JVM 参数不当|jstat \-gcutil、jmap \-histo:live|修复内存泄漏、优化 JVM 堆参数|
|GC 停顿时间过长|\-|STW \> 100ms|大对象分配、堆空间不足|GC 日志分析、jstat|调整 GC 策略、优化对象分配|
|内存持续上升不回落|\-|不回收|内存泄漏、缓存策略不当|堆快照分析、jmap|修复泄漏代码、优化缓存策略|

## 磁盘 I/O 层瓶颈

|异常现象|健康范围|风险阈值|可能原因|排查工具/方法|优化建议|
|---|---|---|---|---|---|
|磁盘 IO %util \> 90%|\-|\>90%|I/O 密集型操作、日志过多|iostat \-x 1、pidstat \-d|引入缓存、优化 I/O 模式、更换 SSD|
|磁盘读写速度远低于标称值|\-|低于标称 70%|磁盘老化、随机 I/O 过多|iostat、dstat|减少随机 IO、优化日志写入策略|
|I/O 等待时间（await）过高|\-|await \> 20ms|磁盘性能不足、并发 IO 过高|iostat \-x 1 查看 await|使用 SSD、RAID、减少同步 IO|

## 网络层瓶颈

|异常现象|健康范围|风险阈值|可能原因|排查工具/方法|优化建议|
|---|---|---|---|---|---|
|TCP 重传率过高|\-|重传率 \> 2%|网络拥塞、丢包|mtr、tcpdump 抓包分析|优化 TCP 参数、增加带宽|
|网络带宽饱和|\-|出入流量差 \> 带宽 70%|带宽不足|Prometheus\+NetFlow|增加带宽、CDN 加速|
|连接建立时间长（\>50ms）|\-|connecting \> 50ms|服务器距离远、TCP 开销大|监控连接时间指标|使用 CDN、连接复用|
|连接池耗尽导致请求阻塞|\-|blocked \> 100ms|连接池配置不当、连接泄漏|netstat 检查连接状态|增大连接池、启用 Keep\-Alive|

## 数据库层瓶颈

|异常现象|健康范围|风险阈值|可能原因|排查工具/方法|优化建议|
|---|---|---|---|---|---|
|慢查询比例过高|\-|占比 \> 5%|缺少索引、SQL 低效|EXPLAIN、慢查询日志|添加索引、优化 SQL|
|数据库连接池打满|\-|利用率\>80%|连接数不足、未复用连接|SHOW STATUS LIKE 'Threads\_connected'|增加连接池大小、优化连接复用|
|锁等待/死锁频繁|\-|锁等待 \> 1s|锁竞争、事务过长|SHOW ENGINE INNODB STATUS|优化锁策略、缩短事务、增加缓存|
|临时表使用过多/溢出|\-|溢出频繁|SQL 排序/分组不当|sys\.dm\_db\_file\_space\_usage|优化临时表使用、增加 TempDB 空间|
|连接池风暴|\-|连接数突增|连接池配置不合理|连接池监控|动态调整：max\_connections = \(核心数\*2\)\+磁盘 IOPS/100|
|索引缺失/失效<br>||逻辑读/物理读异常高|逻辑读/物理读异常高、执行计划走偏<br>|`EXPLAIN` 看 `type`、`key`<br>|补充索引、定期收集统计信息（`ANALYZE TABLE`），避免函数操作列、类型隐式转换、前导模糊匹配|

## 应用/JVM 层瓶颈

|异常现象|健康范围|风险阈值|可能原因|排查工具/方法|优化建议|
|---|---|---|---|---|---|
|线程池满（活跃数=最大值，队列持续增长）|\-|队列增长|线程阻塞（远程调用超时、慢 SQL）|检查线程池配置、jstack 分析阻塞|调整线程池参数、优化阻塞调用|
|TPS 波动大|\-|波动 \> 30%|核心业务逻辑慢、依赖服务不稳定|JMeter 报告、APM 链路追踪|优化核心逻辑、添加缓存、降级策略|
|服务超时/依赖故障|\-|超时率 \> 1%|依赖服务响应慢、配置不当|JMeter 错误报告、APM|优化超时设置、添加降级熔断|
|线程死锁|\-|检测到死锁|资源竞争、锁顺序不当|JStack 死锁检测|资源排序、超时机制|
|进程崩溃或频繁重启|\-|频繁|内存溢出、未捕获异常|应用日志、堆栈分析|修复代码缺陷、调整 JVM 参数|

## 中间件层瓶颈

|异常现象|可能原因|排查工具/方法|优化建议|
|---|---|---|---|
|消息队列积压（Lag \> 分区数\*1000）|消费能力不足|Kafka 消费者 Lag 监控|增加消费者、优化消费逻辑|
|Redis 连接池溢出|连接未释放、池大小不足|istioctl proxy\-config、Redis 监控|增大连接池、检查连接泄漏|
|容器 CPU Throttling|CPU Limit 过低|kubectl top pod|调整 CPU Limit、增加 Pod 副本|
|线程死锁|\-|检测到死锁|资源竞争、锁顺序不当|
|进程崩溃或频繁重启|\-|频繁|内存溢出、未捕获异常|

- **缓存层（Redis）**

|问题|排查方法|优化方法|
|---|---|---|
|缓存击穿|热点 Key 监控|热点 Key 永不过期、互斥锁重建|
|缓存穿透|查询日志看大量 null|布隆过滤器、空值缓存|
|缓存雪崩|大量 Key 同时过期|过期时间加随机偏移、多级缓存|
|大 Key|redis\-cli \-\-bigkeys|拆分大 Hash/List、压缩 value|
|热 Key|监控 QPS 集中度|本地缓存 \+ Redis、Key 拆分（如 key\_1\~key\_10）|
|Redis 单线程瓶颈|INFO 看 instantaneous\_ops\_per\_sec|集群分片、读写分离、Pipeline 批量操作|

## 🪙 诊断流程策略

```Plain Text
收到"系统慢了"反馈*
*    ↓*
*第一步：看磁盘 I/O（iostat -x 1）*
*    → %util > 80% 或 wa > 10%？→ 解决磁盘问题*
*    ↓ 否*
*第二步：看内存（free -h / vmstat）*
*    → Swap 活动？内存不足？→ 解决内存问题*
*    ↓ 否*
*第三步：看 CPU（top）*
*    → us 高？查 SQL/算法；sy 高？查锁/连接；wa 高？回到第一步*
*    ↓ 否*
*第四步：看网络（如有需要）*
*    → 带宽打满？延迟高？→ 优化拓扑/升级带宽
```

## 🕹️ 通用优化策略

|优化方向|核心思路|适用场景|
|---|---|---|
|减少需求|缓存热点数据、减少重复计算、合并请求|读多写少、重复计算多的场景|
|增加资源|扩容 CPU/内存/磁盘、升级存储介质|资源确实不足的"硬瓶颈"|
|改善分布|负载均衡、读写分离、分库分表|单点过载、集群环境|
|减少同步|异步化、消息队列解耦、无锁设计|高并发竞争场景|
|优化代码|算法优化、批量处理、减少 N\+1 查询|应用层逻辑瓶颈|

- 先测后优：没有基准测试的优化都是瞎猜。先压测出瓶颈点，再针对性优化。

- 二八定律：80% 的性能问题来自 20% 的代码，用火焰图找到热点。

- 空间换时间：缓存、索引、预计算是典型的空间换时间策略。

- 异步解耦：能异步的绝不同步（消息队列、事件驱动）。

- 批量操作：数据库批量插入、Redis Pipeline、接口批量查询。

- 避免过早优化：先保证代码正确、清晰，真的有性能需求时再优化。

- 监控闭环：优化后必须持续监控，防止回退。

## 🔍 核心排查原则

### **定位问题的核心思路**

|思路|说明|
|---|---|
|分层定位|从客户端 → 网络 → 网关 → 应用 → 数据库 → 基础设施，逐层剥离|
|对比分析|对比正常时段 vs 异常时段、压测环境 vs 生产环境、有缓存 vs 无缓存|
|瓶颈识别|找到系统中最慢的那一环（短板效应），优化它|
|量化验证|每次只改一个变量，用数据证明优化有效|

### 常用排查工具速查

|层面|工具/命令|看什么|
|---|---|---|
|系统资源|top/htop、vmstat、iostat、free、df|CPU、内存、磁盘 I/O、负载|
|网络|ss \-s、netstat、tcpdump、ping、curl \-w|连接数、延迟、丢包、TCP 状态|
|Java|jstack、jmap、jstat、arthas|线程、堆内存、GC、方法耗时|
|Go|pprof（CPU/内存/goroutine/block）|热点函数、内存分配、协程泄漏|
|数据库|EXPLAIN、SHOW PROCESSLIST、慢查询日志|SQL 执行计划、锁等待|
|全链路|SkyWalking、Pinpoint、Jaeger|调用链耗时分解|

```Plain Text
用户反馈慢
    ↓
压测复现 / 监控告警
    ↓
先看压测机/网络是否瓶颈（排除假问题）
    ↓
看系统资源（CPU/内存/磁盘/网络）
    ↓
看应用层（线程/GC/连接池/日志）
    ↓
看数据层（慢SQL/锁/缓存命中率）
    ↓
看代码层（算法/同步阻塞/序列化）
    ↓
定位根因 → 针对性优化 → 压测验证 → 上线监控
```

### 排查顺序建议

**3\.1 先排除"假问题"（5 分钟）**

- 压测环境是否干净 — 是否有其他流量干扰？是否用了生产环境？

- 压测工具本身是否瓶颈 — 单机压测时，先确认压测机（如 JMeter 所在机器）的 CPU/网络是否先被打满。很多"接口性能差"其实是压测机发不出请求。

- 网络带宽是否瓶颈 — 公网压测尤其要注意，带宽跑满后 RT 会飙升，但这与接口本身无关。

---

**3\.2 基础设施层（10 分钟）**

- **服务器资源监控**

    - CPU 利用率（是否被打满？用户态还是系统态高？）

    - 内存（是否 OOM？是否有频繁 GC/交换？）

    - 磁盘 I/O（日志是否狂写？是否有 swap？）

    - 网络连接数（`ss -s` / `netstat`，是否端口耗尽？`TIME_WAIT` 堆积？）

- **容器/中间件层**

    - 如果是 K8s，查看 Pod 的 CPU limit 是否被 throttle

    - Nginx/网关的连接数、超时配置、worker 进程数

    - 负载均衡器是否有健康检查异常或连接限制

---

**3\.3 应用服务层（核心）**

- **线程/协程状态**

    - Java：用 `jstack` 抓线程 dump，看是否有大量线程 BLOCKED 在锁上、等待池化资源（如数据库连接池耗尽）

    - Go：看 goroutine 数量是否暴涨，是否有大量阻塞在 channel/锁上

- **连接池是否耗尽**

    - 数据库连接池、Redis 连接池、HTTP 客户端连接池 — 这是最常见的隐形瓶颈。表现是 RT 稳定上涨、吞吐量上不去。

- **GC 行为**

    - Java：看 GC 日志，是否频繁 Full GC 或 GC 时间过长

    - Go：看 GC 频率和 STW 时间

- **日志级别与输出**

    - 压测时是否开了 DEBUG 日志？同步日志（如 Logback 同步 appender）在高并发下是性能杀手。

---

**3\.4 数据存储层**

- **数据库**

    - 慢查询日志：是否有未命中索引的 SQL？

    - 锁竞争：`SHOW ENGINE INNODB STATUS` 看是否有行锁、间隙锁等待

    - 连接数：数据库最大连接数是否被打满？

- **缓存（Redis 等）**

    - 是否有缓存击穿/穿透导致流量直接打到 DB？

    - 大 Key、热 Key 问题

---

**3\.5 代码与业务逻辑层（最后）**

- **同步阻塞调用**

    - 接口内部是否有同步调用外部 HTTP/RPC 接口？这是 RT 高的头号元凶。

    - 是否有大循环、复杂计算在主线程执行？

- **锁粒度**

    - 全局锁、分布式锁使用不当会导致并发度急剧下降

- **序列化/反序列化开销**

    - 返回数据量是否过大？JSON 序列化大对象很耗 CPU

**3\.6 快速定位口诀**

> "先看监控，再看日志；先查连接池，再看线程栈；先怀疑网络，再怀疑代码。"
> 
> 

- 如果压测时 吞吐量上不去但 CPU 很低 → 大概率是阻塞等待（连接池、锁、同步 IO）

- 如果压测时 CPU 打满 → 大概率是计算密集型或 GC 问题

- 如果压测时 RT 陡增但吞吐量骤降 → 大概率是下游依赖（DB/外部接口）拖垮

**3\.7 总结建议**

- 遇到性能问题时，建议遵循"先系统后应用，先资源后 SQL"的顺序排查，系统层亮了红灯，就别在应用层浪费时间。

> **磁盘 I/O → 内存 → CPU → 网络**
> 
> 按“用户侧 → 应用/JVM → 数据库 → 中间件 → 网络 → 硬件”分层梳理，覆盖全链路压测中 90%以上的典型瓶颈场景。
> 
> 

- 分层排查：按“用户侧 → 应用 → JVM → 数据库 → 中间件 → 网络 → 硬件”逐层下钻

- 数据驱动：所有结论必须有监控数据支撑，拒绝主观臆断

- 单一变量：每次只修改一个因素，验证效果

- 基线对比：与历史基线对比判断是否异常

- 先看用户侧：通过响应时间、TPS、成功率等指标确认“是否有瓶颈”，再向下钻取定位根因

> 专家提示：90%的性能问题源于数据库（索引缺失、查询效率低）和 CPU（算法效率低、锁竞争），排查时优先关注这两个层面。
>
