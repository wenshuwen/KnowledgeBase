# Linux 系统监控：内存

> 📌 来源：[[Test-测试经验总结-原文]] ｜ LINUX章-内存 小节

## 2\.1 free

- 常用命令：

```Shell
*free -h        # 以人类可读的 GB/MB 单位显示（强烈推荐）
free -m        # 以 MB 为单位显示
**free -s 3      # 每隔 3 秒持续刷新一次内存状态*
```

- 输出示例及含义：

```Shell
total        used        free      shared  buff/cache   available
Mem:           15Gi       3.2Gi       8.1Gi       252Mi       4.2Gi        11Gi
Swap:          19Gi          0B        19Gi

*total：系统总内存。*
*used：已经被程序使用的内存。*
*free：完全未被使用的空闲内存。*
*shared：多个进程共享的内存（如 tmpfs）。*
*buff/cache：系统为了加速文件读写而使用的缓冲区（Buffers）和缓存（Cache）。这部分内存虽然被占用，但如果应用程序需要，系统会立刻释放出来。（用于缓存数据以加速读写）*
*available：这是最关键的指标！ 它表示实际可供新应用程序立即使用的内存（包含了 free 空闲内存 + 可回收的 buff/cache）。*
```

> ***💡 核心提示******：******千万不要只盯着 ******`free`****** 列看！Linux 的内存管理机制是“不用白不用”，它会把空闲内存拿来做缓存（buff/cache）以提升系统性能。只要 ******`available`****** 充足，就说明内存资源是健康的。***
> 
> 

|内存问题场景|典型表现/现象|核心排查思路与工具方向|
|---|---|---|
|内存泄漏 \(Memory Leak\)|应用长时间运行后变卡、闪退；监控图上内存占用呈"锯齿状但整体持续上升"，且不回落到初始水平。|核心是找"不死的对象"。通过分析 Heap Dump（堆转储文件），找到 GC Root 并分析引用链。|
|内存过度消耗与 GC 压力|应用频繁卡顿（尤其在 Android 上），主线程被垃圾回收（GC）频繁中断；或 JVM 老年代内存持续增长。|核心是看"谁在不停分配"。使用内存分析工具抓取分配栈，定位频繁创建对象或集合容量不合理等代码。|
|内存抖动 \(Memory Churn\)|界面操作不流畅，尤其在滑动或动画过程中。常因短时间内大量创建临时对象，导致 GC 频繁触发。|核心是盯"临时对象"。利用工具的对象分配跟踪功能，找出循环或高频事件中反复创建的对象。|
|数据库内存与资源争用|数据库服务器内存占用极高（这是正常现象）；但查询响应变慢、出现死锁。|核心是分析慢查询与锁。关注索引有效性、锁等待情况，以及磁盘 I/O 性能（如队列长度）。|

## 2\.2 top

查看程序占用的内存：

- `top`：系统自带。运行 `top` 后，按下大写的 `M` 键，进程列表就会按照内存占用率（%MEM）从高到低排序，快速揪出“内存大户”。

进程内存字段解析：

- VIRT \(Virtual Memory\)：进程申请的虚拟内存总量（包含了它申请但还没实际使用的内存，以及共享库等）。

- RES \(Resident Memory\)：常驻内存。这是进程实际占用的物理内存大小，排查内存问题时主要看这个。

- %MEM：该进程使用的物理内存百分比。

## 2\.3 meminfo

输出内存指标：

- MemTotal：总物理内存。

- MemAvailable：估算的可用内存（`free` 命令的 `available` 就是读取的这个值）。

- Active / Inactive：活跃与非活跃内存（帮助内核判断哪些缓存可以被回收）。

- Slab：内核数据结构占用的缓存（如果小文件极多，这部分可能会偏高）。

```Shell
# 检查内存压力
 cat /proc/meminfo | grep -E "^(SwapTotal|SwapFree|SwapCached|Dirty)"
 # 如果 SwapCached 很大，说明有大量内存页在内存和swap之间来回移动
 
# 查看系统是否在频繁换页
 vmstat 1 5
 # 观察 si (swap in) 和 so (swap out) 列，如果数值持续大于0，说明swap活动频繁
```

## 2\.4 ps

- 命令行快速列出内存占用前 10 的进程

```Shell
# 按内存使用率（%MEM）降序排列
ps aux --sort=-%mem | head
```

## 2\.5 vmstat

- `vmstat`（Virtual Memory Statistics）是一个用于报告虚拟内存统计信息的强大工具。它可以收集和显示包括系统进程、内存、分页、块设备 I/O、中断、上下文切换和 CPU 活动等方面的信息，帮助管理员快速定位系统性能瓶颈。

```Shell
vmstat [选项] [时间间隔(秒)] [执行次数]

vmstat 1 10   *# 每秒刷新，观察 si 和 so 列*
```

- 时间间隔：指定每次报告之间的时间间隔。如果不指定，默认只显示一条自系统启动以来的汇总结果。

- 执行次数：指定生成报告的次数。如果只指定了时间间隔而未指定次数，命令将连续不断地生成报告。

**⚙️ 常用选项**

- `-a`：展示活跃和非活跃内存的信息。

- `-d`：展示磁盘相关的详细统计信息。

- `-p <分区>`：展示指定磁盘分区的性能统计信息（如 `vmstat -p /dev/sda1`）。

- `-s`：以列表形式展示关于内存、交换空间以及多种系统活动数量的详细统计信息。

- `-m`：展示 Slab 和内核 Malloc 工作的详细信息。

- `-f`：显示从系统启动至今创建的进程总数（forks）。

- `-S <单位>`：指定输出数据的单位，可选参数为 `k`、`K`、`m`、`M`，分别代表不同的字节换算标准。

- `-n`：只在开始时显示一次各字段名称（表头），避免刷屏时反复打印标题。

**🏀 核心输出字段解析**

直接运行 `vmstat` 或带时间参数运行时，输出的结果主要分为以下六个部分：

> **procs（进程状态）**
> 
> 

- r：等待运行的进程数（运行队列中的进程）。如果该值长期大于 1，说明 CPU 资源不足，需要考虑增加 CPU 或优化程序。

- b：处于不可中断睡眠状态的进程数（通常在等待 I/O 或内存交换等资源）。

> **memory（内存使用情况）**
> 
> 

- swpd：已使用的虚拟内存（Swap）大小。

- free：当前空闲的物理内存大小。

- buff：用作缓冲区（Buffer Cache）的内存大小，一般用于块设备的读写缓冲。

- cache：用作页面缓存（Page Cache）的内存大小，一般用于文件系统的缓存。

> **swap（交换分区活动）**
> 
> 

- si：每秒从磁盘交换到内存的数据量（Swap In）。

- so：每秒从内存交换到磁盘的数据量（Swap Out）。

```Shell
# 查看命令
cat /proc/sys/vm/swappiness

-- 默认值：60（绝大多数Linux发行版的默认值）
*含义：系统会平衡缓存回收和Swap使用。在内存压力开始出现时，它会偏向于回收文件缓存，但也会比较积极地动用Swap。*
*对性能的影响：这是一个中庸值，适合桌面环境和大多数通用服务器。*

-- 较低值：1 ~ 10（数据库服务器推荐值，如MySQL、PostgreSQL）
*含义：告诉内核“不到万不得已，别用Swap！”。系统会尽最大努力去回收文件缓存，甚至清理掉不重要的缓存页，也不愿意把进程内存搬到Swap。*
*对性能的影响：显著减少因Swap引起的I/O延迟。数据库通常有自己的缓存机制（如InnoDB Buffer Pool），不需要内核越俎代庖。这个值能让数据库的响应时间更稳定。*

- 极高值：100（极少手动设置，除非是某些定制化场景）
*含义：系统会非常激进地使用Swap。即使物理内存还有不少空闲，内核也会倾向于把不活跃的进程内存页先换出去，尽可能把物理内存留给文件缓存。*
*对性能的影响：如果你的应用是大量的文件读写（如文件服务器），这会提高缓存命中率，但会增加应用进程上下文切换和延迟的风险。*
```

*\(注：如果 si 和 so 的值长期不为 0，说明物理内存严重不足，系统正在频繁使用 Swap，会导致性能大幅下降。\)*

> **io（磁盘 I/O 活动）**
> 
> 

- bi：每秒从块设备读取的块数（Blocks In）。

- bo：每秒向块设备写入的块数（Blocks Out）。

> **system（系统活动）**
> 
> 

- in：每秒的设备中断数量。

- cs：每秒的上下文切换次数。如果该值比磁盘 I/O 和网络包速率高得多，应进一步调查是否存在过度切换的问题。

> **cpu（CPU 使用率百分比）**
> 
> 

- us：用户进程消耗的 CPU 时间百分比。如果长期较高（如大于 50%），需考虑优化用户态程序。

- sy：系统内核进程消耗的 CPU 时间百分比。通常 `us + sy` 的参考值为 80%，若超过此值说明可能存在 CPU 瓶颈。

- id：CPU 处于完全空闲状态的时间百分比。

- wa：CPU 等待磁盘 I/O 完成的时间百分比。参考值为 30%，若超过说明 I/O 等待严重，可能是磁盘带宽瓶颈或大量随机访问造成。

- st：CPU 被虚拟机管理程序（Hypervisor）强制“偷走”的时间百分比（Steal Time）。

**💡 实用技巧与注意事项**

- 常见用法示例：输入 `vmstat 1 5` 表示每 1 秒刷新一次，总共生成 5 次报告，非常适合观察短时间内的系统波动。

- 结合其他工具：`vmstat` 适合宏观排查，若发现 I/O 瓶颈可结合 `iostat` 深入分析磁盘；若发现 CPU 占用高可结合 `top` 或 `htop` 定位具体进程。

- 权限要求：运行该命令通常需要 root 用户权限，否则可能无法获取某些敏感的系统级信息。

- 性能考量：虽然 `vmstat` 本身开销极小，但不宜在自动化脚本中设置过高的采集频率，以免对系统产生不必要的负担。

## 2\.6 内存类型

**🖥️ 物理内存（Physical Memory / RAM）**

本质：就是你电脑主板上插的那根实实在在的内存条。

特点：读写速度极快（纳秒级），但容量有限（比如 8GB、16GB、32GB），而且一旦断电，里面的数据就会全部丢失。

作用：它是 CPU 的“短期工作台”。当你打开一个软件（比如浏览器），系统会立刻把相关数据从硬盘加载到物理内存里，这样 CPU 才能飞快地处理。

**☁️ 虚拟内存（Virtual Memory）**

- 本质：它不是一个硬件，而是操作系统玩的一个“障眼法”（一种**内存管理技术**）。它把一部分硬盘空间（比如 Windows 的页面文件、Linux 的 Swap 分区）伪装成内存来用。

- 特点：容量非常大（取决于你的硬盘还剩多少空间），但读写速度比物理内存慢得多（毫秒级，相差成千上万倍）。

- 作用：

    1\.扩充容量：当你的物理内存（办公桌）塞满时，操作系统会把暂时不用的数据挪到虚拟内存（仓库）里，腾出物理内存给当前急需的程序用。

    2\.安全隔离：它给每个程序都画了一个独立的“大饼”，让程序以为自己拥有连续且独占的内存空间，实际上这些数据可能散落在物理内存和硬盘的各个角落。

**🎈 核心区别对比**

|特性|物理内存 \(RAM\)|虚拟内存|
|---|---|---|
|**物理载体**|内存条（硬件芯片）|硬盘或 SSD 的一部分空间|
|**读写速度**|极快（CPU 的极速工作台）|较慢（受限于硬盘读写速度）|
|**容量大小**|较小（通常几 GB 到几十 GB）|很大（可达几百 GB，受硬盘限制）|
|**断电后**|数据全部丢失（易失性）|数据保存在硬盘上（非易失性）|
|**主要作用**|存放 CPU 正在高速处理的数据|扩展内存容量，作为物理内存的“蓄水池”|

**💡 总结**

物理内存决定了你电脑运行的“绝对速度”，而虚拟内存决定了你电脑能同时运行多少程序的“容量底线”。

## 2\.7 常见问题

- **内存溢出\(OOM\)**

根本原因在于系统内存资源不足，没办法继续满足新的内存申请，最常见的情况是内存资源被持续消耗，当某个进程不断地申请内存，系统会先使用物理内存，物理内存压力越来越大时再尝试通过回收缓存，使用 swap 等方式来释放空间，如果系统无法回收足够的可用内存来满足新申请，就可能触发 OOM Killer。

- **available 可用内存充足的情况下，swap 依然飙升**

根本原因在于：（内存冷热分级策略）Linux 内核的内存回收策略可能比你想象的更“积极”——它不会等到物理内存满了才用 Swap，它会在物理内存尚未耗尽时，主动将“冷门”内存数据换出到 SWAP，以腾出更多空间用于可能被频繁访问的“热门”数据（如文件缓存）使用。

- **Swap 使用量持续升高**

    - 现象：`free -h` 输出中，Swap 的 `used` 值持续增加。

    - 原因：物理内存严重不足，系统被迫将不常用的内存数据写入硬盘（Swap）。这会导致系统严重卡顿。

    - 解决：优先使用 `top` 或 `ps aux --sort=-%mem` 查找并排查占用内存最高的进程（可能是内存泄漏的程序）；长期解决方案为增加物理内存。

- **容器环境下的内存误判**

    - 现象：在 Docker 容器内执行 `free` 命令，显示内存充足，但应用却报内存不足。

    - 原因：容器内看到的通常是宿主机的内存信息，而非容器被分配的内存限制。

    - 解决：需通过读取 cgroup 文件来查看容器的真实内存限制和使用情况（如 `cat /sys/fs/cgroup/memory/memory.limit_in_bytes`）。

- **手动清理缓存（仅限测试环境）**

    - 如果发现 buff/cache 占用极高且需要临时释放内存进行测试，可执行 `sync && echo 3 > /proc/sys/vm/drop_caches`。注意：生产环境严禁频繁操作，系统会自动管理缓存。

- **内存还有，但应用报 OOM（内存溢出）**

    - 现象：`free -h` 显示 `available` 还有几个 G，但 Java 进程却抛出 `OutOfMemoryError`。

    - 推理：这是进程级限制，不是系统级。用 `ulimit -a` 查看进程最大内存限制，或用 `jmap -heap <PID>` 看 JVM 堆上限是否设得太小。

    - 举例：JVM `-Xmx` 只设了 512M，但应用峰值需要 800M。

- **Swap 的“致命弱点”**

    - 内存（RAM）：读写延迟约为 纳秒级（\~100ns），带宽可达几十 GB/s。

    - Swap（即使是 NVMe SSD）：读写延迟为 微秒到毫秒级（\~100μs \- 1ms），带宽仅为 GB/s 级别。

        - 在生产或压测环境中，不要只看`free -h`显示的 Swap used 大小，重点要追踪 Swap 的换入换出速率：

        ```Shell
        vmstat 1 10   # 每秒刷新，观察 si 和 so 列
        sar -W 1      # 专门查看每秒的换页数
        ```

        - `si`（Swap In）：每秒从 Swap 换入物理内存的数据量（KB）。

        - `so`（Swap Out）：每秒从物理内存换出到 Swap 的数据量（KB）。

        |        观察结果|        判断结论|        行动建议|
        |---|---|---|
        |        `si`和`so` 始终为 0|        系统运行稳定，Swap 只是静态占用，无性能影响。|        可忽略，属于正常优化。|
        |        `si`或`so` 持续 \> 几百 KB/s|        严重警告！内存带宽被 Swap 拖垮，系统响应时间会剧烈波动。|        立即检查是否有进程内存泄漏，或压测流量是否超出物理内存上限。|
        |        `si`/`so` 间歇性突发|        可能是某个定时任务或批处理进程在瞬间申请大内存。|        分析该任务的 JVM 堆或内存池设置，考虑调整其执行时间避开高峰。|
