# Linux 系统监控：磁盘

> 📌 来源：[[Test-测试经验总结-原文]] ｜ LINUX章-磁盘 小节

## 3\.1 df

功能说明：

- 查看文件系统整体磁盘使用情况（最常用）

- 常用命令：

```Shell
*df -h        # 以人类可读的 GB/MB 单位显示（强烈推荐）
df -T        # 显示文件系统的类型（如 ext4, xfs）
**df -i        # 查看 inode 使用情况（排查小文件过多导致的“空间不足”）*
```

- 输出详解（以 df \-h 为例）：

```Shell
*Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        50G   30G   18G  63% /
/dev/sdb1       100G   60G   40G  60% /data
**tmpfs           3.9G     0  3.9G   0% /dev/shm*

Filesystem：磁盘分区或文件系统的设备名称。
Size：分区的总大小。
Used：已使用的空间。
Avail：剩余可用的空间。
Use%：已用空间的百分比（超过 80%-90% 就需要重点关注）。
Mounted on：挂载点（该分区在系统中对应的目录，如 / 或 /data）。
```

## 3\.2 du

功能说明：

- 查看具体目录或文件的磁盘占用

- 常用命令：

```Shell
*du -sh /var/log          # 查看指定目录的总大小
du -sh * | sort -hr      # 查看当前目录下各子目录的大小，并按从大到小排序
**du -h --max-depth=1 / | sort -hr | head -10  # 找出根目录下占用最大的前10个目录*

# -s (summary)：只显示总计，不列出每个子文件。
# -h (human-readable)：以 GB/MB 等易读格式显示。
```

## 3\.3 lsblk

功能说明：

- 查看磁盘硬件与分区结构

- 常用命令：

```Shell
*lsblk          # 查看磁盘及分区的简要信息
**lsblk -f       # 查看更详细的信息（包含文件系统类型 FSTYPE 和 UUID）*
```

- 输出详解：

```Shell
*NAME   FSTYPE LABEL UUID                                 MOUNTPOINT
sda                                                      
├─sda1 ext4         5a2b9c8d-xxxx-xxxx-xxxx-xxxxxxx      /boot
└─sda2 ext4         7c4d5e6f-xxxx-xxxx-xxxx-xxxxxxx      /
sdb                                                      
**└─sdb1 xfs          9b2d5e8a-xxxx-xxxx-xxxx-xxxxxxx      /data*

NAME：设备名称（sda 代表第一块物理硬盘，sda1 是它的第一个分区）。
FSTYPE：文件系统类型（如 ext4, xfs）。
MOUNTPOINT：挂载点（如果为空，说明该分区尚未挂载使用）。
```

- **什么是挂载点？**

在 Linux 中，一切皆文件。硬盘分区不能直接被访问，必须将其"关联"到目录树上的某个节点（目录），这个目录就是挂载点。

> ⚠️ 核心概念：挂载后，该目录原有的内容会被"遮盖"，访问该目录实际访问的是分区内容。卸载后原内容恢复可见。
> 
> 

**常见挂载点规范 \(FHS 标准\)**

|挂载点|用途|说明|
|---|---|---|
|`/`|根分区|系统核心目录，必须存在|
|`/boot`|引导分区|存放内核和引导加载器，建议独立分区|
|`/home`|用户数据|个人文件，独立分区便于重装系统保留数据|
|`/var`|可变数据|日志、缓存、数据库，服务器建议独立分区|
|`/tmp`|临时文件|重启后可能清空|
|`/mnt`|临时挂载|管理员手动临时挂载外部设备|
|`/media`|自动挂载|桌面环境自动挂载 U 盘/光盘的位置|
|`/srv`|服务数据|Web/FTP 等服务的数据目录|
|`swap`|交换空间|无挂载点，作为虚拟内存使用|

## 3\.4 fdisk

功能说明：

- 可以用来查看磁盘的详细分区表信息（如磁盘总容量、扇区大小、分区表类型等）。

- 常用命令：

```Shell
*fdisk -l       # 列出所有磁盘的详细分区表信息（通常需要 root 权限）*
```

## 3\.5 iostat

功能说明：

- 分析磁盘性能的首选工具，可以直观地看到磁盘的读写速度、IOPS 以及利用率。

- 常用命令：

```Shell
iostat -dx 1 3   # 每秒刷新一次，共显示3次，-dx显示扩展的磁盘统计信息
iostat -dm 1     *# **以 MB 为单位查看磁盘吞吐量*

%util：磁盘利用率（核心指标）。如果该值持续接近 100%，说明磁盘 I/O 已经饱和，存在性能瓶颈。
await：I/O 请求的平均等待时间（毫秒）。数值越小越好，如果显著偏高（如超过 20-50ms），说明磁盘响应缓慢。
r/s 和 w/s：每秒的读、写请求次数（即 IOPS）。
rkB/s 和 wkB/s：每秒读取和写入的数据量（即吞吐量，单位为 KB）。
```

- **输出指标详解：**

|字段|含义|性能排查解读|
|---|---|---|
|r/s, w/s|每秒完成的读/写 I/O 次数|即 IOPS。反映磁盘每秒处理的请求数量。|
|rkB/s, wkB/s|每秒读取/写入的数据量 \(KB\)|即 磁盘吞吐量/带宽。反映单位时间内实际读写的数据大小。|
|await|平均每次 I/O 操作的等待时间 \(毫秒\)|核心延迟指标。包含在队列中等待的时间和实际处理的时间。SSD 正常应在 1ms 左右，机械硬盘在 10\-30ms。数值越高，说明磁盘响应越慢。\< 10ms 优秀；\> 20ms 警惕；\> 50ms 严重|
|avgqu\-sz|平均 I/O 队列长度|向磁盘设备发出的请求队列的平均长度。如果该值持续大于 10，说明有大量 I/O 请求在排队，磁盘处理不过来。|
|%util|磁盘 I/O 利用率|**核心瓶颈指标**。在采样周期内，磁盘处于活跃状态（有 IO 请求在处理）的时间占比。如果该值持续接近 100%，说明磁盘已经饱和，成为了系统性能的瓶颈。%util 高 ≠ 磁盘一定饱和；%util 低 ≠ 磁盘一定空闲。 它只表示"磁盘有多忙"，不直接等于"磁盘有多满"。|

💡 **如何判断磁盘 I/O 瓶颈**

在排查系统卡顿或性能问题时，可以结合以下逻辑进行判断：

- 磁盘饱和瓶颈：当 %util 持续接近 100%，且 await 显著升高时，说明磁盘本身的处理能力（IOPS 或带宽）已经达到上限，无法处理更多的请求。

- I/O 队列堆积：当 avgqu\-sz 持续大于 10 时，说明系统发出的 I/O 请求远远多于磁盘能处理的速度，大量请求在内存队列中等待。

- CPU 等待 I/O：在 iostat 输出的 CPU 部分，如果 %iowait（CPU 等待 I/O 完成的时间百分比）持续偏高（如超过 20%\-30%），说明 CPU 经常处于空闲状态，但不得不等待慢速的磁盘 I/O 操作完成，这也是存储性能不足的典型表现。

**关键看板（重点看 ****`sda`**** 等磁盘设备行）：**

- `%util`（磁盘繁忙度）：

    - \< 70%：正常。

    > - 80% 且持续：磁盘 I/O 已饱和，是性能瓶颈。
    > 
    > 

- `await`（平均 I/O 响应时间）：

    - \< 5ms（SSD）或 \< 10ms（HDD）：优秀。

    > - 50ms：明显延迟，应用会感知到卡顿。
    > 
    > 

- `r/s` vs `w/s`（读写次数） 与 `rkB/s` vs `wkB/s`（读写速率）：

    - 如果 `%util` 高但 `rkB/s` 很低 → 说明是大量的小文件随机读写，这是最坏的情况（比如频繁打日志、随机更新数据库索引）。

> ***💡 避坑提示：iostat 的第一次输出通常是系统自启动以来的平均值，往往掩盖了瞬时的性能波动。因此，在进行性能采样时，务必带上采样间隔和次数（如 iostat \-dx 1 5），并忽略第一次的输出结果，重点关注后续的实时采样数据。***
> 
>

## **📌**接口响应慢，CPU 不高，内存有余

- 现象：`top` 看到 `wa` 在 30% 左右；`iostat` 看到 `%util` 接近 100%，`await` 超过 200ms。

- 推理：磁盘 I/O 是性能瓶颈。可能是日志框架在同步刷盘，或数据库没有走索引导致全表扫描产生大量磁盘读取。

- 举例：一个查询接口每次都要扫描一张 10GB 的大表，且磁盘是机械硬盘，导致每个请求都触发大量随机读。

## **📌服务器 /tmp 目录空间占用达到 100% **

**`/tmp`**** 目录下有什么文件？**

这里面的文件五花八门，但主要可以归为以下几类：

- 程序运行时产生的临时文件：这是最主要的一类。例如，软件编译时的中间文件，用 `vim` 编辑文件时产生的 `.swp` 备份文件，以及 `wget` 等工具下载未完成时的部分文件。

- 进程间通信（IPC）文件：用于程序之间交换数据，最常见的是 Unix 套接字（Socket） 文件。比如 MySQL 等服务就可能会在 `/tmp` 目录下创建套接字文件用于本地连接。

- 锁（Lock）和进程 ID（PID）文件：这些文件用来防止同一个程序或资源被同时多次运行或访问，确保系统稳定。例如，一个程序启动时会创建一个 `.lock` 文件，如果该文件已存在，则说明程序已在运行。

- 临时脚本和缓存：一些脚本或程序运行时会生成临时的脚本文件，或者存放临时的缓存数据。软件包管理器（如 `apt`）在下载和安装软件时，也会将 `/tmp` 作为临时缓冲区。

- 其他 miscellaneous 文件：还包括一些临时的日志文件、系统或应用程序的自定义临时数据等等。

---

> **对系统造成的影响**
> 
> 

1. **系统运行缓慢与崩溃**：磁盘空间耗尽会导致服务器无法有效执行读写操作，系统响应变慢。极端情况下（如使用率达到 100%），可能导致操作系统崩溃或变得极不稳定，致使服务器进程全部 Down 掉。

2. **应用服务停止**：应用程序在运行中通常需要向 `/tmp` 写入临时文件或缓存。空间满后，应用无法创建新文件，会直接报错（如 `No space left on device`），导致服务假死、拒绝请求，甚至引发集群瘫痪。

3. **安全漏洞与数据丢失风险**：空间不足会导致系统无法生成必要的日志文件或备份文件，影响安全事件的监控与回溯，增加系统被攻击的风险。同时，文件碎片化或数据无法落盘也可能引发数据丢失。

**🛠️ 解决与释放空间的步骤**

处理 `/tmp` 空间爆满时，严禁直接盲目删除文件，因为某些进程可能正在使用这些文件，直接删除可能导致进程崩溃或空间无法真正释放。建议按以下步骤操作。

**1\. 诊断：查明原因**

首先，登录服务器，运行以下命令确认`/tmp`的使用情况：

```Shell
*# 查看 /tmp 的磁盘空间使用情况      *
*df -h /tmp*
```

- 如果`/tmp`是一个独立分区，`df -h`会显示其容量和使用率。

- 如果`/tmp`是`tmpfs`（挂载点显示为`tmpfs`），其大小通常受限于物理内存。

---

**2\. 快速恢复：清理空间**

在紧急情况下，首要任务是立即释放空间恢复业务。

- **方法一：清理旧文件（推荐）**
使用`find`命令安全地删除指定天数之前修改的文件，避免误删正在使用的文件。

```Shell
*# 例如，删除 /tmp 目录下 1 天前修改的所有文件
**sudo find /tmp -type f -mtime +1 -delete*
# 你可以根据需要调整+1为其他天数（如+5表示5天前）。
```

*注：如果担心误删正在使用的 **`.log`** 文件，可以将其内容清空而不是直接删除（如 **`> file.log`**），以防应用崩溃。*

- **方法二：排查并处理被占用的空间（文件已删除但空间未释放）**

如果清空了 `/tmp` 目录，但使用 `df -h` 查看空间依然是 100%，这通常是因为某些进程仍在持有已删除文件的句柄。

- *使用**** lsof \| grep "/tmp" ****或**** fuser \-u /tmp ****找出正在访问 /tmp 的进程。*

- *确认这些进程是否可以安全停止。如果是异常进程或脚本死循环产生的大量临时文件，可以手动 kill 掉对应进程，空间即可自动释放。*

- **方法三：手动检查并删除（需谨慎）**
可以先查看大文件，再决定是否删除。

```Shell
*# 查看 /tmp 目录下占用空间最大的前10个文件或目录
**sudo du -sh /tmp/* | sort -rh | head -10*
```

确认文件无用后，再使用`rm`命令删除。

---

**3\. 更改临时文件路径**

如果`/tmp`空间无法立即清理或扩容，可以临时将某些程序的临时目录指向其他有足够空间的位置，从数据盘中分出一部分空间，单独挂载为 /tmp 分区。这样即使 /tmp 被占满，也不会影响系统根目录 / 的正常运行。。

```Shell
*# 临时修改当前shell会话的临时目录
**export TMPDIR=/path/to/large/partition*
```

此方法仅对当前会话有效，适合临时绕过问题。

---

**4\. 根治：增加可用空间**

- **方案一：扩容 ****`/tmp`**** 分区**
如果`/tmp`是独立分区，需根据具体磁盘情况（如 LVM）进行扩容。

- **方案二：调整 ****`tmpfs`**** 大小**
如果`/tmp`是`tmpfs`，可以动态调整其大小。

```Shell
*# 将 /tmp 临时扩容到 4GB
**sudo mount -t tmpfs -o size=4096M tmpfs /tmp*
```

此调整在重启后失效。如需永久生效，需修改`/etc/fstab`文件。

- **方案三：检查 Inode 是否耗尽**
有时`df -h`显示空间充足，但依然报错，这可能是 inode（文件节点）耗尽了，导致无法创建新文件。使用以下命令检查：

```Shell
*df -i /tmp*
```

如果`IUse%`达到 100%，则需要清理大量小文件来释放 inode。

---

**💡 预防措施**

- 利用系统自动清理：现代 Linux 系统通常由`systemd-tmpfiles`服务管理`/tmp`清理。可以检查其配置（如`/usr/lib/tmpfiles.d/tmp.conf`）确保清理规则生效。

- 设置大小限制：在`/etc/fstab`中为`/tmp`挂载点设置`size`选项，防止其无限增长。

- 定期监控：设置监控告警，在磁盘使用率达到阈值（如 80%）时提前收到通知。

**⚠️ 重要提醒**

- 备份数据：执行删除操作前，请确认文件确实无用。虽然`/tmp`主要存放临时文件，但不能 100%保证没有重要数据。

- 识别进程：如果文件被进程占用，删除可能不会立即释放空间。可以用`lsof /tmp | grep deleted`查找被删除但未释放空间的文件，并考虑重启相关进程。

总的来说，处理`/tmp`空间占满问题的核心是“先诊断，后清理，再根治”。优先使用`find`命令按时间清理旧文件，这通常是恢复服务最快且相对安全的方法。
