# HTTPS 原理详解

> 📌 来源：[[Test-测试经验总结-原文]] ｜ 理论知识章-HTTPS 小节：概念与实现原理

## **1\.1 HTTPS 协议概念**

HTTPS（全称：Hypertext Transfer Protocol Secure，中文名：超文本传输安全协议）是 HTTP 协议的安全版本，用于在互联网上安全地传输数据。

- **核心定义**

HTTPS = HTTP \+ 加密 \+ 身份验证 \+ 数据完整性保护

它并非全新的协议，而是将 HTTP 协议运行在 SSL/TLS 协议（TLS 是 SSL 的继任者和升级版本）之上，通过安全层来保护数据传输。

- **主要特点**

    - 数据加密传输

        - 通过加密技术确保传输数据的机密性

        - 防止第三方窃听和获取敏感信息

    - 身份认证

        - 通过数字证书验证服务器身份

        - 防止中间人攻击和钓鱼网站

    - 数据完整性

        - 确保传输过程中数据不被篡改

        - 提供数据完整性校验机制

    - 防止重放攻击

        - 通过时间戳和随机数等机制防止数据被重复使用

## **1\.2 实现原理**

### **1\.2\.1 核心加密机制**

HTTPS 采用混合加密方式，结合了对称加密和非对称加密的优势：

1\. 对称加密

- 使用同一个密钥进行加密和解密

- 优点：加密速度快，适合大量数据传输

- 缺点：密钥分发困难，容易被窃听

2\. 非对称加密

- 使用公钥加密，私钥解密

- 优点：安全性高，解决了密钥分发问题

- 缺点：加密速度慢，计算开销大

3\. 混合加密策略

- 握手阶段：使用非对称加密安全地传输对称密钥

- 数据传输阶段：使用对称加密进行高效的数据传输

---

### **1\.2\.2 SSL/TLS 握手流程**

**阶段 1：TCP 连接建立**

客户端与服务器建立 TCP 连接（三次握手）

**阶段 2：Client Hello**

客户端发送：

- 支持的 TLS 版本

- 支持的加密套件列表

- 随机数（Client Random）

**阶段 3：Server Hello**

服务器回应：

- 选择的 TLS 版本

- 选择的加密套件

- 随机数（Server Random）

- 服务器证书（包含公钥）

**阶段 4：证书验证**

客户端验证：

- 证书是否由可信 CA 签发

- 证书是否在有效期内

- 证书域名是否匹配

- 证书是否被吊销

**阶段 5：密钥交换（TLS 1\.2）**

- 客户端生成预主密钥（Pre\-Master Secret）

- 使用服务器公钥加密预主密钥

- 发送给服务器

**阶段 6：密钥生成**

双方使用以下三个随机数生成会话密钥：

- Client Random

- Server Random

- Pre\-Master Secret

**阶段 7：加密通信开始**

- 客户端发送加密的"Finished"消息

- 服务器发送加密的"Finished"消息

- 双方确认握手成功，开始使用会话密钥加密传输数据

```Plain Text
*1.协商协议与加密套件
curl 向服务器发送一个 "Client Hello" 消息，其中包含它支持的 TLS 协议版本（如 TLS 1.2, TLS 1.3）和一系列加密算法（称为“加密套件”）。
**服务器回复一个 "Server Hello" 消息，从客户端提供的列表中选定一组双方都支持的协议和加密套件。*
*
2.服务器验证 (单向认证部分)
服务器将自己的证书（server.crt）发送给 curl。这个证书里包含了服务器的公钥和身份信息。
curl 会验证这个证书的有效性，比如检查它是否由可信的 CA 签发、是否过期、域名是否匹配等。
**为了证明自己拥有证书对应的私钥，**服务器会用它的私钥对之前握手的所有数据生成一个数字签名**，并发送给 curl。curl 用服务器证书里的公钥验证这个签名，如果验证通过，就确认了服务器的真实身份。*
*
3.客户端验证 (双向认证部分)
服务器验证完自身后，会向 curl 发送一个 "Certificate Request" 消息，要求客户端也提供证书。
curl 收到请求后，将你通过 --cert ./client.crt 指定的客户端证书发送给服务器。
服务器验证这个客户端证书的有效性（例如，检查它是否由服务器信任的 CA 签发）。
**为了证明 curl 确实拥有 client.crt 对应的私钥，**服务器会发送一段随机数据（挑战）**。curl 必须使用你通过 --key ./client.key 指定的私钥对这段数据进行数字签名，并将签名结果发回给服务器。
**服务器使用 client.crt 里的公钥来验证这个签名。如果验证通过，就确认了客户端的真实身份。*
*
4.生成会话密钥
**在双方身份都得到确认后，curl 和服务器会通过密钥交换算法（如 ECDHE）协商生成一个相同的、临时的“会话密钥” (Session Key)。这个密钥是对称密钥，将用于后续所有数据的加密和解密。*
```

### **1\.2\.3 证书机制详解**

**证书的作用**

- 验证服务器身份，防止中间人攻击

- 提供服务器的公钥

**证书验证流程**

1\.获取证书：客户端从服务器获取数字证书

2\.验证签名：

- 使用 CA 的公钥解密证书签名

- 对证书内容进行哈希运算

- 比较两个哈希值是否一致

3\.验证链：逐级验证证书链，直到根证书

**数字签名原理**

```Plain Text
*证书内容 → 哈希运算 → 哈希值 → 私钥加密 → 数字签名
验证时：数字签名 → 公钥解密 → 哈希值1
       证书内容 → 哈希运算 → 哈希值2
**       比较哈希值1和哈希值2是否相等*
```

---

### **1\.2\.4 数据传输过程**

**加密传输**

1. 客户端使用会话密钥加密 HTTP 请求

2. 发送加密数据到服务器

3. 服务器使用会话密钥解密数据

4. 服务器处理请求，加密响应数据

5. 发送加密响应到客户端

6. 客户端解密响应数据

**完整性保护**

- 使用 MAC（消息认证码）或 HMAC 验证数据完整性

- 防止数据在传输过程中被篡改

---

### **1\.2\.5 防止中间人攻击**

**攻击场景**

攻击者试图在客户端和服务器之间截获并篡改通信

**防护机制**

1. 证书验证：攻击者无法获得合法的服务器证书

2. 公钥加密：即使攻击者截获预主密钥，也无法解密（需要私钥）

3. 数字签名：证书被篡改会导致签名验证失败

---

### **1\.2\.6 性能优化**

**会话复用**

- Session ID：服务器保存会话状态，客户端下次连接时直接复用

- Session Ticket：将会话信息加密后发送给客户端，减少服务器存储压力

**0\-RTT 握手**

TLS 1\.3 支持 0\-RTT（零往返时间）握手，进一步减少延迟

### **1\.2\.7 工作流程图**

```Plain Text
客户端                    服务器*
*  |                        |*
*  |--TCP连接建立----------->|*
*  |--Client Hello--------->|*
*  |<--Server Hello---------|*
*  |<--证书-----------------|*
*  |--验证证书--------------|*
*  |--生成预主密钥-----------|*
*  |--公钥加密预主密钥------>|*
*  |--生成会话密钥-----------|*
*  |<--生成会话密钥----------|*
*  |--加密Finished--------->|*
*  |<--加密Finished---------|*
*  |--加密HTTP请求--------->|*
*  |<--加密HTTP响应---------|
```

非对称加密体系中最核心的设计原则：公钥用于验证签名或加密数据，私钥才用于生成签名或解密数据。

### **1\.2\.8 证书的构成**

- **证书的构成**

一张标准的服务器公钥证书（Digital Certificate）相当于服务器的“电子身份证”，它本身是一份明文文件，主要包含以下核心内容：

- 持有者信息：如网站的域名、公司名称等。

- 服务器公钥：这是最核心的部分，即服务器希望公开的公钥。

- 有效期：证书的起始和过期时间。

- CA 的数字签名：防止证书被伪造的核心防伪标志。

- **数字签名的生成过程（CA 的操作）**

当 CA 机构为您签发证书时，会执行以下操作来生成数字签名：

- 提取摘要：首先，CA 会使用哈希函数（Hash）计算整份证书明文内容（包括**持有者信息、服务器公钥、有效期**等）的哈希值（例如 Hash\_1）。

- 私钥加密（签名）：接着，CA 使用自己严格保密的 CA 私钥 对这个哈希值（Hash\_1）进行加密处理。这个加密后的结果就是“CA 的数字签名”。

- 打包发送：最后，CA 将这份包含了“服务器公钥”以及“CA 数字签名”的完整证书发送给服务器。

- **客户端如何验证（信任的建立）**

当客户端（如浏览器）收到服务器发来的证书时，会进行如下验证：

- 独立计算摘要：浏览器读取证书中的明文信息，并使用相同的哈希函数计算出新的哈希值（Hash\_A）。

- 解密签名：浏览器从操作系统或内置的受信任根证书库中，找到对应 CA 机构的公钥，并用该公钥去解密证书末尾的“CA 数字签名”，得到原始的哈希值（Hash\_B）。

- 对比确认：如果 Hash\_A 和 Hash\_B 完全相等，则说明两件事：第一，这份证书确实是由权威 CA 签发的；第二，证书上的“服务器公钥”等信息在传输过程中没有被任何人篡改过。

总结来说，不是把公钥加密变成签名，而是把包含公钥的整个证书信息进行哈希处理后，再用 CA 的私钥对哈希值进行加密，从而形成数字签名。这种机制确保了您拿到的服务器公钥是真实且未被篡改的。
