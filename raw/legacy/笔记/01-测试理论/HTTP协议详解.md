# HTTP 协议详解

> 📌 来源：[[Test-测试经验总结-原文]] ｜ 理论知识章-HTTP 小节：概念、状态码、请求方法

## **2\.1 HTTP 协议概念**

HTTP 是一种应用层协议，通常基于可靠的 TCP 协议来传输数据。

- **主要特点**

    - 请求\-响应模型：通信永远由客户端主动发起“请求”，服务器被动接收并返回“响应”。这就像在餐厅点餐，你（客户端）喊服务员点菜（发送请求），厨房（服务器）做好后由服务员端给你（返回响应）。

    - 无状态（Stateless）：服务器不会记住你上一次请求了什么。每次请求都是完全独立的“新对话”。为了解决这个问题（比如记住你的登录状态），后来衍生出了 Cookie、Session 等机制来辅助记录。

    - 支持多种数据格式：虽然最初是为传输超文本（HTML）设计的，但现在的 HTTP 可以传输任意类型的文件，比如图片、视频、JSON 数据等。

    - 明文传输：传统的 HTTP 协议在传输数据时是不加密的，内容容易被窃听或篡改。为了解决安全隐患，在 HTTP 基础上加入了 SSL/TLS 加密层的 HTTPS 协议成为了当今互联网的主流。

- **工作原理**

    - 建立连接：客户端首先通过 TCP 协议（通常是三次握手）与服务器建立一条可靠的通信连接。

    - 发送请求：连接建立后，客户端向服务器发送一个结构化的 HTTP 请求报文。

    - 处理与响应：服务器接收到请求后，根据请求的内容（如查找文件、查询数据库）进行处理，然后封装成 HTTP 响应报文返回给客户端。

    - 关闭或复用连接：数据传输完成后，连接可以选择关闭，也可以保持开启（Keep\-Alive）以便后续的请求复用，从而提高效率。

## **2\.2 版本对比**

|版本|核心特点|优势与改进|
|---|---|---|
|HTTP/1\.1|默认使用长连接（Keep\-Alive）|解决了 HTTP/1\.0 每次请求都要重新建立连接的开销，但同一连接下的请求仍需排队（队头阻塞）。|
|HTTP/2|二进制分帧、多路复用、头部压缩|允许在同一个连接上同时并行发送多个请求，互不干扰，大幅提升了网页加载速度。|
|HTTP/3|基于 UDP 的 QUIC 协议|彻底解决了底层的队头阻塞问题，在网络不稳定（如移动网络）的环境下表现更出色。|

## **2\.3 与 HTTPS 的区别**

|特性|HTTP|HTTPS|
|---|---|---|
|安全性|低，明文传输，易被窃听和篡改|高，加密传输，防窃听、防篡改|
|协议基础|直接基于 TCP|HTTP \+ SSL/TLS|
|端口|80|443|
|证书|不需要|需要向 CA 机构申请数字证书（通常付费或免费如 Let's Encrypt）|
|性能|较快（无加密解密开销）|略慢（需进行加密/解密运算，但现代硬件和优化如 HTTP/2/3 已极大缩小差距）|
|SEO 影响|无加分，甚至可能被标记为“不安全”|搜索引擎排名加权，浏览器标记为“安全”|

## **2\.4 HTTP 响应状态码**

### **1xx：信息性状态码（Informational）**

表示请求已被接收，继续处理。

- 100 Continue：客户端应继续发送请求体。

- 101 Switching Protocols：服务器同意切换协议（如从 HTTP 切换到 WebSocket）。

- 102 Processing（WebDAV）：服务器已收到请求并正在处理。

---

### **2xx：成功状态码（Success）**

表示请求已成功被服务器接收、理解、并接受。

- 200 OK：请求成功，响应体包含所请求的数据。

- 201 Created：请求成功并创建了新资源。

- 202 Accepted：请求已被接受，但尚未处理完成。

- 204 No Content：请求成功，但响应中不包含内容。

- 206 Partial Content：用于范围请求（如断点续传）。

---

### **3xx：重定向状态码（Redirection）**

表示需要客户端采取进一步操作才能完成请求。

- 301 Moved Permanently：资源已永久移动到新位置。

- 302 Found（临时重定向）：资源临时位于另一个 URI。

- 304 Not Modified：资源未修改，可使用缓存版本（用于条件请求）。

- 307 Temporary Redirect：临时重定向，要求保持原请求方法。

- 308 Permanent Redirect：永久重定向，要求保持原请求方法。

---

### **4xx：客户端错误状态码（Client Error）**

表示请求有误或无法完成。

- 400 Bad Request：请求语法错误或无法被服务器理解。

- 401 Unauthorized：请求需要用户认证（通常配合 `WWW-Authenticate` 头）。

- 403 Forbidden：服务器理解请求，但拒绝执行（权限不足）。

- 404 Not Found：请求的资源在服务器上未找到。

- 405 Method Not Allowed：请求方法对资源不被允许。

- 409 Conflict：请求与服务器当前状态冲突（如重复提交）。

- 429 Too Many Requests：客户端在单位时间内发送太多请求（限流）。

---

**🟥 400 Bad Request（错误请求）**

含义：服务器无法理解客户端发送的请求，因为语法有误、参数缺失或格式非法。

**常见原因：**

- JSON 格式错误（如缺少引号、括号不匹配）。

- 必填参数缺失或类型错误（如传字符串给需要整数的字段）。

- URL 编码错误（如包含未转义的特殊字符）。

- 表单数据格式不符合 `Content-Type`（如用 `application/json` 发送 `key=value`）。

**示例：**

你调用一个创建用户的 API：

```HTTP
POST /api/users*
*Content-Type: application/json*

*{ name: "Alice", age: "twenty" }
```

- `name` 未加双引号（非法 JSON）

- `age` 应为数字却传了字符串。

服务器解析失败，返回 400 Bad Request。

> ✅ 建议：使用 Postman 或 curl 测试前先校验 JSON；后端应返回具体错误字段（如 `"error": "age must be integer"`）。
> 
> 

---

**🟦 401 Unauthorized（未授权）**

含义：请求缺少有效的身份认证凭证（如 Token、Session、Basic Auth）。

**常见原因：**

- 未携带 `Authorization` 头。

- Token 过期、无效或格式错误。

- Session 已失效（如用户长时间未操作）。

**示例：**

你访问一个需要登录的接口，但没有带 Token，服务器返回：

```HTTP
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api"
```

> 🔐 注意：401 是“没证明你是谁”，而 403 是“你是谁但没权限”——这是关键区别！
> 
> 

---

**🟨 403 Forbidden（禁止访问）**

含义：服务器理解请求，但拒绝执行，通常因权限不足。

**常见原因：**

- 用户角色无权访问该资源（如普通用户尝试删除管理员数据）。

- IP 被防火墙或安全策略拦截。

- 文件系统权限限制（如 Web 服务器无权读取某目录）。

**示例：**

用户 A（ID=100）尝试删除用户 B 的文章：

```HTTP
DELETE /api/posts/500?user_id=200
```

后端校验发现当前用户不是作者，返回 403 Forbidden。

> ⚠️ 安全提示：不要暴露“资源存在但你不能看”，可统一返回 404 避免信息泄露（但语义上仍是 403）。
> 
> 

---

**⚪ 404 Not Found（未找到）**

含义：服务器找不到请求的资源（路径、ID 等不存在）。

**常见原因：**

- URL 拼写错误（如 `/user` 写成 `/uesr`）。

- 请求的资源已被删除。

- 路由未定义（前端路由 vs 后端 API 不匹配）。

**示例：**

你访问数据库中没有 ID 为 99999 的商品，服务器返回 **404 Not Found。**

```HTTP
GET /api/products/99999
```

> 🌐 前端注意：SPA 应用若使用 HTML5 History 模式，需配置服务器 fallback 到 `index.html`，否则刷新页面会 404。
> 
> 

---

**🟪 405 Method Not Allowed（方法不允许）**

含义：请求方法（GET/POST/PUT 等）对该资源不被允许。

**常见原因：**

- 对只读资源使用了写操作（如对 `/api/status` 发 POST）。

- 路由只注册了部分 HTTP 方法。

- Web 服务器（如 Nginx）限制了方法。

**示例：**

API 文档说明 `/api/login` 只接受 `POST`，但你误用了 `GET`：

```HTTP
GET /api/login?username=alice&password=123
```

服务器返回：

```HTTP
HTTP/1.1 405 Method Not Allowed
Allow: POST
```

> 💡 `Allow` 响应头会列出该资源支持的方法。
> 
> 

---

**🟩 409 Conflict（冲突）**

含义：请求与服务器当前状态冲突，通常因资源已存在或版本不一致。

**常见原因：**

- 创建已存在的唯一资源（如重复注册相同邮箱）。

- 并发编辑导致乐观锁失败（如两个用户同时修改同一篇文章）。

- 状态流转非法（如对“已完成”订单再次取消）。

**示例：**

注册新用户时：

```HTTP
{ "email": "alice@example.com" }
```

但该邮箱已被注册，服务器返回：

```HTTP
HTTP/1.1 409 Conflict
{ "error": "Email already exists" }
```

> ✅ 最佳实践：409 适合用于业务逻辑冲突，而非参数校验（后者用 400）。
> 
> 

---

**🟧 429 Too Many Requests（请求过多）**

含义：客户端在单位时间内发送了太多请求，触发限流（Rate Limiting）。

**常见原因：**

- 爬虫或脚本高频调用 API。

- 前端 bug 导致重复提交（如按钮未禁用）。

- 未遵守 API 的速率限制策略（如每分钟 100 次）。

**示例：**

你在 1 分钟内调用了某短信接口 101 次（限额 100），第 101 次返回：

```HTTP
HTTP/1.1 429 Too Many Requests
Retry-After: 60
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
```

> ⏳ 建议：客户端应监听 `Retry-After` 头，在指定秒数后重试。
> 
> 

**总结对比表：**

|状态码|名称|关键特征|典型场景|
|---|---|---|---|
|400|Bad Request|请求本身有语法/格式问题|JSON 错误、参数缺失|
|401|Unauthorized|缺少或无效身份凭证|未登录、Token 过期|
|403|Forbidden|有身份但无权限|角色不足、IP 被封|
|404|Not Found|资源不存在|URL 错、ID 无效|
|405|Method Not Allowed|方法不被该资源支持|对 GET 接口发 POST|
|409|Conflict|业务逻辑冲突|重复注册、并发修改冲突|
|429|Too Many Requests|触发速率限制|爬虫、高频点击|

---

### **5xx：服务器错误状态码（Server Error）**

表示服务器在处理请求时发生错误。

- 500 Internal Server Error：通用服务器内部错误。

- 501 Not Implemented：服务器不支持请求的功能。

- 502 Bad Gateway：作为网关或代理时，从上游服务器收到无效响应。

- 503 Service Unavailable：服务器暂时不可用（如过载或维护）。

- 504 Gateway Timeout：作为网关或代理时，上游服务器未及时响应。

---

**🔴 500 Internal Server Error（内部服务器错误）**

含义：服务器在处理请求时遇到了意料之外的情况，无法完成请求。这是一个“兜底”错误码，通常表示后端代码或配置出了问题。

**常见原因：**

- 后端程序抛出未捕获的异常（如 Python 的 `ZeroDivisionError`、Java 的 `NullPointerException`）。

- 数据库连接失败或 SQL 语句错误。

- 配置文件错误（如 `.env` 缺失、权限不足）。

- 第三方服务调用失败且未妥善处理。

**示例：**

你访问一个电商网站的商品详情页，后端在查询数据库时写错了字段名（比如把 `product_id` 写成 `prod_id`），导致 SQL 报错，服务器直接返回 500。

> 📌 开发建议：查看服务器日志（如 Nginx error log、应用日志）定位具体异常。
> 
> 

---

**🟠 501 Not Implemented（未实现）**

含义：服务器不支持请求中所要求的功能（通常是 HTTP 方法或协议扩展）。

**常见原因：**

- 客户端使用了服务器未实现的 HTTP 方法（如 `PATCH`、`PROPFIND`）。

- API 接口尚未开发完成，但路由已存在。

- Web 服务器（如 Apache/Nginx）未启用某些模块。

**示例：**

你向一个只支持 `GET` 和 `POST` 的 REST API 发送 `DELETE /api/user/123` 请求，但后端根本没有编写删除逻辑，于是返回 501。

> 💡 注意：501 是“功能未实现”，而 405（Method Not Allowed）是“方法不允许”——前者是能力缺失，后者是明确拒绝。
> 
> 

---

**⚪ 502 Bad Gateway（错误网关）**

含义：作为网关或反向代理的服务器（如 Nginx）从上游服务器（如应用服务器、API 服务）收到了无效响应。

**常见原因：**

- 上游应用崩溃或未启动（如 Gunicorn、Tomcat 没运行）。

- 上游返回了非 HTTP 格式的响应（如直接输出二进制或空内容）。

- 代理配置错误（如 upstream 地址写错）。

**示例：**

你访问 https://example\.com，Nginx 作为反向代理试图将请求转发给本地的 `127.0.0.1:8000`，但该端口上的 Django 应用已经宕机，Nginx 收不到有效 HTTP 响应，于是返回 502。

> 🛠️ 排查方向：检查后端服务是否运行、端口是否监听、防火墙是否放行。
> 
> 

---

**🟡 503 Service Unavailable（服务不可用）**

含义：服务器暂时无法处理请求，通常是由于过载或维护。

**常见原因：**

- 服务器负载过高，主动拒绝新请求（限流）。

- 正在进行系统维护（如数据库迁移）。

- 后端依赖服务（如 Redis、数据库）不可用。

- 自动扩缩容尚未完成（云环境常见）。

**示例：**

某抢购活动开始瞬间，大量用户涌入，服务器 CPU 打满，应用主动返回 503 并提示“系统繁忙，请稍后再试”。

> ✅ 良好实践：503 响应可配合 `Retry-After` 头告知客户端何时重试。
> 
> 

---

**🔵 504 Gateway Timeout（网关超时）**

含义：作为网关或代理的服务器在等待上游服务器响应时超时。

**常见原因：**

- 上游服务异常/未启动或处理太慢（如复杂计算、慢 SQL）。

- 网络延迟高或丢包。

- 代理服务器的超时设置过短（如 Nginx 默认 60 秒）。

**示例：**

你在上传一个大文件到网盘，后端需要调用 AI 服务分析内容，但 AI 服务花了 90 秒才响应，而 Nginx 的 `proxy_read_timeout` 设为 60 秒，于是 Nginx 主动断开连接，返回 504。

**总结对比表：**

|状态码|名称|关键特征|典型场景|
|---|---|---|---|
|500|Internal Server Error|后端代码/配置出错|未捕获异常、DB 连接失败|
|501|Not Implemented|功能未开发|使用了未实现的 HTTP 方法|
|502|Bad Gateway|上游返回无效响应|后端服务宕机、返回非 HTTP 内容|
|503|Service Unavailable|服务主动拒绝（过载/维护）|高并发限流、依赖服务不可用|
|504|Gateway Timeout|上游响应超时|慢查询、网络延迟、超时设置短|

## **2\.5 HTTP 请求方法**

|方法|说明|是否有请求体|幂等|
|---|---|---|---|
|GET|请求获取指定资源，最常用的方法，只读操作|否|✅|
|POST|向服务器提交数据，用于创建资源或触发操作|是|❌|
|PUT|用请求体中的内容整体替换指定资源|是|✅|
|DELETE|删除指定资源|否|✅|
|PATCH|对资源进行部分修改（区别于 PUT 的整体替换）|是|❌|
|HEAD|与 GET 相同，但只返回响应头，不返回响应体，常用于检查资源可用性|否|✅|
|OPTIONS|查询服务器支持的通信选项，跨域请求（CORS）时会先发 OPTIONS 预检请求|否|✅|
|TRACE|沿请求路径执行消息环回测试，用于调试和诊断|否|✅|
|CONNECT|建立隧道连接，通常用于 HTTPS 通过代理服务器通信|否|—|

**几个关键概念**

- 幂等性：同一个请求执行一次和执行多次效果相同。GET、PUT、DELETE 是幂等的，POST 不是（多次提交可能创建多条记录）。

> **幂等性的含义：同一个请求执行一次和执行多次，对服务器资源的最终效果是否相同。幂等 ≠ 返回值相同****，****而是指对服务器资源状态的影响相同****。**
> 
> 

- 安全性：GET 和 HEAD 是"安全方法"，不会修改服务器资源状态。

- 可缓存性：GET 和 HEAD 的响应可以被浏览器/CDN 缓存，POST 默认不可缓存。

**GET vs POST 快速对比**

|对比项|GET|POST|
|---|---|---|
|数据位置|URL 查询参数中|请求体中|
|数据长度|受浏览器和服务器限制|理论上无限制|
|安全性|参数暴露在 URL 中，不适合传敏感信息|数据在请求体中，相对更安全|
|缓存|可被缓存|默认不缓存|
|用途|获取数据|提交数据、创建资源|
|用途|获取数据|提交数据、创建资源|

**实际开发中的选择建议**

在 RESTful API 设计中，通常这样对应 CRUD 操作：

- Create → `POST`

- Read → `GET`

- Update → `PUT`（整体更新）/ `PATCH`（部分更新）

- Delete → `DELETE`
