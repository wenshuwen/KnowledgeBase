# TCP 与 UDP 详解

> 📌 来源：[[Test-测试经验总结-原文]] ｜ 理论知识章-TCP&UDP 小节

TCP（传输控制协议）和 UDP（用户数据报协议）是计算机网络传输层中最核心的两个协议。它们最本质的区别在于设计哲学的不同：TCP 是追求数据完整性的“完美主义者”，而 UDP 是追求极致速度的“极简主义者”。

## 4\.1 TCP（传输控制协议）详解

TCP 是一种面向连接、可靠、面向字节流的传输层协议。它的核心目标是确保数据能够无差错、不丢失、不重复且按序到达目的地。

核心机制：

- 连接管理：通信前必须通过“三次握手”建立连接，确认双方收发能力正常；通信结束后通过“四次挥手”安全断开连接。

- 可靠性保障：通过序列号与确认应答（ACK）机制追踪数据包。如果发送方超时未收到确认，会自动触发“超时重传”或“快速重传”。

- 流量控制：利用“滑动窗口”机制，接收方会根据自身处理能力动态告知发送方可以接收的数据量，防止接收方被淹没。

- 拥塞控制：TCP 能够感知网络拥堵情况，通过慢启动、拥塞避免、快重传和快恢复等算法动态调整发送速率，避免冲垮网络。

- 面向字节流：TCP 将数据看作一连串无结构的字节流，不保留应用层数据的边界，因此应用层需要自行处理“粘包/拆包”问题。

## 4\.2 UDP（用户数据报协议）详解

UDP 是一种无连接、不可靠、面向数据报的传输层协议。它的核心目标是提供低延迟、高效率的数据传输。

核心机制：

- 无连接：发送数据前不需要建立连接，知道目标 IP 和端口后直接发送，即发即走。

- 不可靠交付：UDP 只提供“尽最大努力交付”，不提供确认机制、重传机制或排序机制。如果网络发生抖动导致丢包或乱序，UDP 本身不会处理。

- 面向数据报：UDP 保留了应用层消息的边界。发送方发送一个多大尺寸的报文，接收方就会完整接收一个多大尺寸的报文，绝对不会发生粘包问题。

- 支持广播/组播：UDP 不仅支持一对一通信，还天然支持一对多、多对多的广播和组播功能。

## 4\.3 TCP 与 UDP 的核心区别对比

|对比维度|TCP \(传输控制协议\)|UDP \(用户数据报协议\)|
|---|---|---|
|连接方式|面向连接（需三次握手、四次挥手）|无连接（直接发送数据）|
|可靠性|极其可靠（不丢包、不重复、不乱序）|不可靠（尽力交付，丢包不管）|
|传输形式|面向字节流（无边界，存在粘包问题）|面向数据报（保留消息边界）|
|传输速度|较慢（有复杂的确认、重传和拥塞控制机制）|极快（无多余握手和控制逻辑）|
|首部开销|较大（固定头部 20 字节，最多 60 字节）|极小（固定头部仅 8 字节）|
|通信对象|仅支持一对一（点对点单播）|支持一对一、一对多、多对多（广播/组播）|
|典型应用场景|网页浏览（HTTP）、文件传输（FTP）、邮件收发（SMTP）|音视频通话、实时游戏、视频直播、DNS 查询|

- 选 TCP：当你的业务对数据准确性要求 100%，能容忍一定延迟时（如下载文件、网页加载、在线支付），丢一个比特位都会导致文件损坏或乱码，必须选择 TCP。

- 选 UDP：当你的业务对实时性要求极高，且能容忍少量丢包时（如射击游戏、语音通话），丢包只会导致画面轻微卡顿或声音丢失，但如果使用 TCP，重传旧包反而会导致严重的画面卡死，此时 UDP 是更好的选择。

|选择原则|推荐协议|
|---|---|
|要求数据完整、不丢失|TCP|
|允许丢包但要求低延迟|UDP|
|需要可靠的顺序传输|TCP|
|广播/组播场景|UDP|
|文件传输、网页、邮件|TCP|
|通信对象|仅支持一对一（点对点单播）|
|典型应用场景|网页浏览（HTTP）、文件传输（FTP）、邮件收发（SMTP）|

## 4\.4 常见面试题

### Q1: TCP 如何保证可靠传输？

- 校验和：检测数据损坏

- 序列号：解决乱序和重复

- 确认应答（ACK）：确认收到

- 超时重传：未收到 ACK 则重传

- 流量控制：滑动窗口防止接收方溢出

- 拥塞控制：慢启动、拥塞避免、快重传、快恢复

### Q2: 为什么 TCP 是面向字节流，UDP 是面向报文？

- TCP：将数据看作连续的字节流，发送方可能将多次 write 的数据合并发送，接收方需要多次 read 才能完整接收（无边界）

- UDP：应用层每次 write 的数据作为一个完整的报文发送，接收方一次 read 读取完整报文（有边界）

### Q3: 为什么 TCP 连接需要三次握手，而不是两次或四次？

- 两次不安全：无法防止已过期的 SYN 报文造成错误连接

- 三次足够：确认双方收发能力正常，同步初始序列号

- 四次浪费：第三次握手已将 ACK 和 SYN 合并

### Q4: TIME\_WAIT 状态的作用？

- 确保最后一个 ACK 能到达对方（如果丢失，对方会重发 FIN）

- 让旧连接的残留报文在网络中消失（2MSL 时间）

### Q5: 什么时候用 UDP 而不是 TCP？

- 实时性要求高、允许少量丢包（音视频、游戏）

- 广播/组播场景（DHCP、视频会议）

- 简单请求\-响应模式，单次交互（DNS）

- 自己实现可靠性且希望避免 TCP 队头阻塞

### Q6: 三次握手四次挥手详解

**🔍 详细步骤解析**

**第一挥手：客户端发起关闭**

- 动作：客户端发送 `FIN` 报文。

- 状态变化：客户端进入 `FIN-WAIT-1` 状态。

- 含义：客户端告诉服务端：“我的数据发完了，不再发送数据了，但我还能接收数据。”

**第二挥手：服务端确认收到**

- 动作：服务端收到 FIN 后，发送 `ACK` 确认报文。

- 状态变化：

    - 服务端进入 `CLOSE-WAIT` 状态。

    - 客户端进入 `FIN-WAIT-2` 状态。

- 含义：服务端告诉客户端：“你的 FIN 我收到了，但我可能还有数据没发完，请稍等。”

- ⚠️ 关键点：此时连接处于半关闭状态。客户端不能再发数据，但还能收数据；服务端还能发数据。

**第三挥手：服务端发起关闭**

- 动作：服务端处理完剩余数据后，发送自己的 `FIN` 报文。

- 状态变化：服务端进入 `LAST-ACK` 状态。

- 含义：服务端告诉客户端：“我的数据也发完了，我也准备关闭了。”

**第四挥手：客户端确认收到**

- 动作：客户端收到 FIN 后，发送 `ACK` 确认报文。

- 状态变化：

    - 服务端收到 ACK 后，立即关闭连接，进入 `CLOSED` 状态。

    - 客户端进入 `TIME-WAIT` 状态。

- 含义：客户端告诉服务端：“你的 FIN 我收到了，我们可以彻底断开了。”

---

**❓ 核心疑难点解答**

**挥手为什么是四次，而不是三次？**

因为 TCP 是全双工的。

- 当客户端发 FIN 时，仅代表客户端不再发数据，但服务端可能还有数据没发完。

- 所以服务端不能立刻发 FIN \+ ACK（像三次握手那样合并），必须先回一个 ACK 表示“收到”，等自己数据发完后，再发 FIN。

- 结论：ACK 和 FIN 在时间上被拆开了，所以多了一次。

**握手为什么不能是两次？（核心原因）**

两次握手无法防止“历史失效的连接请求”突然传到服务端，从而造成资源浪费。

经典场景推演：

1. 客户端发送了第一个连接请求（SYN），但因为网络拥堵，这个报文在网络中滞留了很久。

2. 客户端迟迟收不到回应，超时后重新发送了一个新的连接请求（SYN）。

3. 这次网络顺畅，服务端很快收到并回复了确认（SYN \+ ACK），连接成功建立，双方正常通信并关闭。

4. 突发状况：就在此时，步骤 1 中那个滞留的旧 SYN 报文突然到达了服务端。

**如果只有两次握手：**

- 服务端收到这个“旧 SYN”，会以为客户端又想建立连接，于是直接回复确认（SYN \+ ACK）。

- 此时，服务端已经分配了内存、端口等资源，进入了 `ESTABLISHED` 状态，傻等客户端发数据。

- 但客户端知道这是旧报文的回应，根本不会理会。

- 结果：服务端的资源被白白占用，甚至可能被大量这种旧报文攻击导致瘫痪（类似 SYN Flood 攻击的变种）。

**有了三次握手：**

- 服务端回复（SYN \+ ACK）后，进入 `SYN_RCVD` 状态，此时连接并未真正建立。

- 客户端收到后，必须再发一个确认（ACK）。服务端收到 ACK 后，才真正进入 `ESTABLISHED` 状态。

- 回到上面的场景：服务端发出（SYN \+ ACK）后，迟迟等不到客户端的 ACK，超时后就会自动释放资源。完美避坑！

**握手为什么不能是四次？（效率问题）**

三次已经足够完成“双方确认”的逻辑，第四次纯属多余。

- 第一次：客户端 \-\> 服务端 （客户端证明自己的发送能力和服务端的接收能力正常）

- 第二次：服务端 \-\> 客户端 （服务端证明自己的发送能力和接收能力正常，同时确认了客户端的发送能力）

- 第三次：客户端 \-\> 服务端 （客户端确认了服务端的发送和接收能力）
