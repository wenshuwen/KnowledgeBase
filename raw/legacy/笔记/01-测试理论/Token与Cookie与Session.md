# Token / Cookie / Session 鉴权机制

> 📌 来源：[[Test-测试经验总结-原文]] ｜ 理论知识章-Token&Cookie&Session 小节

Token、Cookie 和 Session 是 Web 开发中用于解决 HTTP 协议“无状态”特性的核心技术。HTTP 协议本身不会记住用户的任何信息，每次请求都是独立的。为了让服务器能够“记住”用户身份和状态，这三种技术应运而生。

## 3\.1 核心概念详解

> **Cookie（客户端状态记录）**
> 
> 

Cookie 是服务器发送给浏览器并保存在客户端（浏览器）的一小段文本数据。浏览器在后续访问同一域名时，会自动携带这些 Cookie 发送给服务器。

- 特点：存储容量极小（通常限制在 4KB 左右），安全性较低（数据明文存储在客户端，易被篡改或窃取），但浏览器会自动管理其传输。

**包含内容：**

- Session ID（会话标识符）： 这是最常见的内容。Cookie 里只存一个类似 `JSESSIONID=xyz123` 的编号，真正的用户状态数据（如权限、登录时间等）都保存在服务器端。

- 用户偏好设置： 一些非敏感的配置信息，如语言选择、主题颜色、字体大小等。

- 追踪标识： 用于统计分析或广告投放的设备标识符、点击流数据等。

- 限制： Cookie 只能存储字符串类型的数据，且有严格的大小限制（通常约 4KB）。

---

> **Session（服务端状态记录）**
> 
> 

Session 是服务器端用于保存特定用户会话信息的机制。当用户首次访问时，服务器会创建一个 Session 对象，并生成一个唯一的 Session ID。这个 ID 通常通过 Cookie 发送给客户端，后续请求中客户端只需携带该 ID，服务器即可通过 ID 找到对应的 Session 数据。

- 特点：数据存储在服务器端（内存、Redis 或数据库），安全性高，理论上没有存储大小限制，但会占用服务器资源。

**包含内容：**

- 用户 ID： 如 `userId = 10086`。

- 账号信息： 如 `username`（用户名）、`email`（邮箱）。

- 角色与权限： 如 `roles = ["admin", "editor"]`，用于后续的接口鉴权。

- Session ID： 这是 Session 的唯一标识符（通常是一长串随机字符串）。它本身不存储在服务器端，而是作为 Cookie（如 `JSESSIONID`）发送给客户端，用于客户端和服务器之间的“对暗号”。

- 创建时间： 记录 Session 何时生成。

- 最后访问时间： 服务器通过对比当前时间与这个时间，来判断 Session 是否超时（例如 30 分钟无操作则自动销毁）。

- 安全标记： 例如记录用户登录时的 IP 地址或 User\-Agent（设备信息）。如果后续请求发现 IP 突然改变，服务器可以判定为异常并强制注销。

---

> **Token（自包含的认证凭证）**
> 
> 

Token（如常见的 JWT，JSON Web Token）是一种加密签名的字符串。用户登录成功后，服务器生成一个 Token 返回给客户端。客户端在后续请求中手动将其放入请求头（如 Authorization 字段）发送给服务器，服务器只需验证签名即可确认身份，无需查询数据库。

- 特点：服务器无需保存任何会话状态（无状态），天然支持分布式和跨域，安全性较高（防篡改），但需要前端手动携带，且一旦签发难以主动作废。

**包含内容：**

- 用户身份与权限信息： 如用户 ID \(`userId`\)、用户名 \(`username`\)、角色 \(`roles`\)、权限范围等。

- 时间戳与有效期： 包含 Token 的签发时间 \(`iat`\) 和过期时间 \(`exp`\)，服务器据此判断凭证是否失效。

- 其他业务声明（Claims）： 开发者可以根据需要放入任何非敏感的业务数据。

- 安全警告： 虽然 Token 可以防篡改，但载荷部分的数据通常是 Base64 编码的，可以被解密查看。因此，绝对不能在 Token 中存放密码等敏感信息。

> ***Payload 里放的字段不同，直接决定了 Token 的用途——比如只放用户 ID 的 Token 和放用户 ID\+角色\+权限的 Token，在后端的校验逻辑和防伪造策略上差别很大。***
> 
>

## 3\.2 核心区别对比

|维度|Cookie|Session|Token \(JWT\)|
|---|---|---|---|
|状态类型|客户端状态|服务端状态（需维护会话记录）|无状态（服务器只负责验签）|
|存储位置|客户端（浏览器）|服务器（内存/Redis/DB）|客户端（浏览器/App/本地存储）|
|数据容量|4KB|无限制|适中|
|安全性|低（明文易被篡改/窃取，可被劫持）|中（敏感数据存储在服务端）|高（加密签名，防篡改）|
|XSS 防护|需 HttpOnly|天然防护|需谨慎存储|
|CSRF 防护|需 SameSite 属性 \+ 双重 Cookie|需 CSRF Token（服务端生成随机 Token 验证）|无需（不使用 Cookie）|
|扩展性|差|差（需共享存储）|好（无状态）|
|性能|每次请求携带|需查询存储|验证签名（快）|
|注销处理|删除 Cookie|删除 Session|需黑名单或短过期|
|移动端支持|❌|❌|✅|
|跨域支持|受同源策略限制|受同源策略限制，集群需共享 Session|极佳（跨域无压力，天然支持分布式）|
|传输方式|浏览器自动携带|自动携带 SessionID（依赖 Cookie）|前端手动放入请求头|

**🛡️ CSRF 防护对比详解**

> **Cookie：CSRF 的“重灾区”**
> 
> 

- **为什么危险？**
CSRF 攻击的核心就是利用浏览器的自动携带 Cookie 机制。只要用户登录了网站 A，访问恶意网站 B 时，B 发出的请求如果指向 A，浏览器会自动带上 A 的 Cookie，服务器无法分辨这是用户自愿的还是被伪造的。

- **如何防护？**

    - SameSite 属性（首选）：设置 `SameSite=Strict`（完全禁止跨站携带）或 `Lax`（仅允许顶级导航 GET 请求携带）。这是目前最推荐的防御手段。

    - 双重 Cookie 验证：在 Cookie 中存一个值，同时在页面表单/JS 变量中存一份。提交时比对两者是否一致。因为恶意网站无法读取目标网站的 Cookie，所以无法伪造这个比对值。

> **Session：本质上还是 Cookie 问题**
> 
> 

- 误区澄清：很多人认为 Session 在服务器端就很安全。错！ Session 只是存储状态的方式，它依然需要一个 SessionID 来标识用户。这个 ID 通常还是通过 Cookie 传递的。

- 防护逻辑：

    - 既然依赖 Cookie，就面临同样的 CSRF 风险。

    - CSRF Token：这是 Session 架构下的标准解法。服务端生成一个随机字符串绑定到 Session，前端每次请求必须带上这个 Token。攻击者虽然能带上 Cookie，但拿不到这个随机 Token，从而被拦截。

> **Token \(JWT\)：天生免疫？**
> 
> 

- 为什么安全？
JWT 通常存储在 `localStorage` 或通过 JS 手动管理。浏览器不会像对待 Cookie 那样自动把它加到请求头里。前端代码必须显式地写 `headers: { Authorization: 'Bearer ...' }`。恶意网站没法控制你的前端代码去读 localStorage 并发送请求，所以天然防 CSRF。

- 注意陷阱：

    - 如果你把 JWT 错误地 存在了 Cookie 里，并且设置了自动发送，那它就和普通 Cookie 一样危险了。

    - XSS 才是大敌：虽然防住了 CSRF，但 JWT 放在 localStorage 容易受到 XSS（跨站脚本攻击）窃取。一旦 XSS 发生，Token 泄露，攻击者可以直接冒充用户（这比 CSRF 更严重）。

**💡 总结建议**

- 传统后台管理系统：推荐 Session \+ CSRF Token，或者 Cookie \(HttpOnly \+ SameSite\)。安全性最高，逻辑最成熟。

- 移动端 / 前后端分离 / 微服务：推荐 Token \(JWT\)。扩展性好，天然防 CSRF，但必须做好 HTTPS 和 XSS 防护。

- 最佳实践：现在流行一种混合模式——JWT 存放在 HttpOnly Cookie 中。既利用了 Cookie 的 HttpOnly 防 XSS，又配合后端中间件做 Referer 校验或双重 Cookie 校验来防 CSRF，兼顾了安全和体验。

## 3\.3 典型使用场景

**Cookie 适用场景**

- 轻量级非敏感数据存储：如记住用户名、保存用户的个性化偏好设置（如网站主题、语言选择）、追踪标识（用于统计分析或广告投放的设备标识符、点击流数据等）。

- 配合 Session 使用：作为载体存储 Session ID，实现传统的登录状态保持。

**Session 适用场景**

- 传统单体 Web 应用：如传统的后台管理系统、内网系统，无需跨域或分布式部署。

- 存储敏感/复杂的临时数据：如用户登录信息、购物车详情、多步骤表单的中间数据、验证码等。

**Token 适用场景**

- 前后端分离架构：前端为 SPA（单页应用），后端提供 RESTful API。

- 移动端与小程序：App 和微信小程序无法像浏览器那样自动管理 Cookie，使用 Token 更为方便。

- 微服务与跨域认证：多个服务之间需要共享用户身份，Token 的无状态特性使其成为最佳选择。

## 3\.4 使用场景选择

**场景 1：传统 Web 应用（服务端渲染）**

```Plain Text
✅ 推荐：Session + Cookie
✅ 可选：Cookie（轻量级状态）
```

**场景 2：前后端分离应用（SPA）**

```Plain Text
✅ 推荐：Token (JWT) + localStorage
✅ 推荐：Token (JWT) + HttpOnly Cookie
```

**场景 3：移动端应用（iOS/Android）**

```Plain Text
✅ 推荐：Token (JWT)
❌ 不推荐：Cookie/Session
```

**场景 4：单点登录（SSO）**

```Plain Text
✅ 推荐：Token (JWT)
✅ 可选：Session + 共享存储
```

**场景 5：微服务架构**

```Plain Text
✅ 推荐：Token (JWT)
✅ 可选：Session + Redis（需要状态）
```

**场景 6：安全要求极高的场景（银行、支付）**

```Plain Text
✅ 推荐：Session + Cookie（HttpOnly + Secure + SameSite）
✅ 配合：CSRF Token、双因素认证
```

## 3\.5 常见面试题

### Q1: Cookie 和 Session 的区别？

|Cookie|Session|
|---|---|
|存储在客户端|存储在服务端|
|大小限制 4KB|无大小限制|
|可被用户修改|用户无法直接修改|
|安全性较低|安全性较高|
|不占用服务器内存|占用服务器内存|

### Q2：为什么有了 Cookie 还需要 Session？

- Cookie 存储在客户端，不安全（用户可篡改）

- Cookie 大小有限（4KB），无法存储大量数据

- Session 数据在服务端，更安全可控

### Q3: Token 和 Session 的区别？

|Session|Token|
|---|---|
|服务端存储|客户端存储|
|有状态|无状态|
|需要共享存储才能扩展|天然支持水平扩展|
|可以随时注销|注销需要额外机制|
|移动端不支持|移动端友好|

### Q4：JWT 的安全注意事项？

1. 不在 Payload 存放敏感信息（密码、身份证号）

2. 使用 HTTPS 防止中间人攻击

3. 设置合理的过期时间（Access Token 短期，Refresh Token 长期）

4. 存储安全：推荐 HttpOnly Cookie，避免 localStorage XSS

5. 使用强签名算法（HS256、RS256）

### Q5：分布式 Session 如何实现？

```Plain Text
方案1：Session 粘滞（Sticky Session）
   - 负载均衡根据用户 IP 或 Cookie 固定到同一台服务器
   - 缺点：节点故障会丢失 Session

方案2：Session 共享存储（推荐）
   - 所有服务器共享 Redis/数据库
   - Spring Session + Redis

方案3：无状态（Token/JWT）
   - 彻底放弃 Session
```
