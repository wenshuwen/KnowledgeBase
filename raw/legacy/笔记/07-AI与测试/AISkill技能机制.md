# AI Skill 技能机制

> 📌 来源：[[Test-测试经验总结-原文]] ｜ AI章-Skill 小节

**大模型很聪明，但有个天生缺陷：它不了解你团队的代码规范、设计标准或工作流程。每次对话都需要你从头教一遍，低效且不稳定。Skill 正是为解决这个问题而生。核心理念：像对待 Prompt 一样对待 Skill。**

## **3\.1 含义详解与实现原理**

Skill 是给 Agent 的“工作手册”\+“工具箱”——它是一个结构化的文件夹，把专业知识、操作流程、脚本工具和参考资料打包在一起，Agent 需要时自动加载并照章执行。

打个比方：MCP 解决的是“Agent 能用什么工具”（给你扳手、螺丝刀、电钻），Skill 解决的是“Agent 该怎么用这些工具”（拧螺丝用十字螺丝刀，先顺时针转三圈）。两者是协作关系，而非替代。

Skill 的底层实现原理基于模块化设计与渐进式加载机制，其核心架构通常包含三个部分：

- **元数据（Metadata）**：相当于技能的“名片”，包含名称和描述。它体积轻量，始终加载在系统中，帮助大模型快速识别该技能的功能及触发时机。

- **行动指南（Action Guide）**：技能的核心操作手册，详细定义了任务的执行流程、输入输出格式及规则。采用“触发式加载”，仅在用户请求匹配时才被读取，以节省上下文资源。

- **资源文件（Resources）**：可选的辅助模块，包含可执行脚本（如 Python 代码）、参考文档或模板，用于支撑更复杂的操作逻辑。

**Skill 的核心设计：三级渐进式披露**

> 这是 Skill 最精妙的设计，核心思想是 “按需加载，不浪费上下文”：
> 
> 

|层级|内容|加载时机|
|---|---|---|
|第一级|YAML 中的 `description` 字段（技能名\+一句话描述）|始终在系统提示词中，作为索引|
|第二级|`SKILL.md` 完整正文（工作流程、核心指令）|Agent 判断任务相关时才读取|
|第三级|`references/`、`scripts/`、`assets/` 中的详细文件|执行过程中确实需要时才调用|

**工作流程：**

```Plain Text
用户消息 → Agent 识别需要 Skill（匹配 description）
→ [工具调用: 读取 SKILL.md] → Agent 获得完整指令
→ [工具调用: 执行脚本 / 读取 references] → 返回结果
```

> ***Skill 激活本身会消耗 1\-2 步工具调用，所以 description 写得准不准，直接影响响应速度和 Token 消耗***
> 
> 

---

## **3\.2 Skill vs MCP vs Projects**

|功能|核心用途|触发方式|持久性|
|---|---|---|---|
|Skills|固化专业流程和操作规范|自动匹配触发|永久保存|
|Projects|提供静态背景知识|始终加载|永久保存|
|MCP|连接外部工具和数据源|显式调用工具|按需连接|
|Subagents|处理动态复杂子任务|委派调用|临时生成|

> ***简单说：Projects 是“背景知识”，Skills 是“操作规程”，MCP 是“工具箱”***
> 
>

## **3\.3 Skill 快速上手指南**

### 3\.3\.1 环境准备

- 确认你用的平台支持 Skill：Claude Code、Codex、Cursor、Windsurf、VS Code、OpenCode 均已支持

- （Claude Code 用户）安装：

```Shell
npm install -g @anthropic-ai/claude-code
```

- Skill 存放位置（以 Claude Code 为例）：

    - **项目级（仅当前项目）**：`.claude/skills/`

    - **全局级（所有项目）**：`~/.claude/skills/`或`C:\Users\你的用户名\.claude\skills`（windows）

---

### 3\.3\.2 目录结构

最小结构只需要一个文件。复杂 Skill 可以这样组织：

```Plain Text
my-skill-name/              # 文件夹必须用 kebab-case
├── SKILL.md                # 必须，入口文件（全大写）
├── scripts/                # 可选，可执行脚本（Python/Shell）
│   └── helper.py
├── references/             # 可选，参考文档
│   └── api-guide.md
└── assets/                 # 可选， 输出时使用的文件模板、图标logo、图片等资源
    └── template.docx
```

⚠️ 命名坑点：

- 文件夹名：`my-cool-skill` ✅；`My Cool Skill` ❌；`my_cool_skill` ❌

- 入口文件：必须是 `SKILL.md`，全大写，大小写敏感；`skill.md` ❌；`SKILL.MD` ❌

- 不要放 `README.md`，所有说明写在 `SKILL.md` 或 `references/` 里

---

**标准 Skill 的内部结构：**

1. `SKILL.md` \(必选\)：这是 Skill 的“大脑”和“说明书”。它采用 Markdown 格式，顶部通常包含 YAML 格式的元数据（如 `name`, `description`），下方则是详细的执行流程、决策规则、角色定位和输出标准。AI 首先读取此文件来判断是否触发该技能。

2. `scripts/` \(可选\)：存放可执行的脚本文件（如 Python, Shell, JavaScript）。当 Skill 需要执行具体操作（如格式化文件、调用 API、运行测试）时，AI 会调用这些脚本，而不是自己生成代码，从而保证操作的准确性和安全性。

3. `references/` \(可选\)：存放外部规范、API 文档、模板或最佳实践指南。当 AI 在执行任务中需要查阅特定领域的详细知识时，会从这里获取信息，避免在 `SKILL.md` 中塞入过多内容导致臃肿。

4. `assets/` \(可选\)：存放不可变的静态资源，如图片、图标、配置文件或预定义的模板文件。这些是 Skill 执行任务时可能需要的“原材料”。

---

> ***标准的核心思想是：将“专业知识”从“对话提示词”中解耦，变成可复用的、模块化的文件系统资产。***
> 
> 

- **标准化格式：**所有遵循该标准的工具都要求 Skill 以一个文件夹形式存在，且必须包含一个名为 `SKILL.md` 的核心文件。

- **渐进式披露：**AI 不会一次性加载整个 Skill 文件夹的内容，而是先读取 `SKILL.md` 中的元数据（如名称、描述），判断是否需要调用该技能。只有在确认需要后，才会按需读取其中的脚本、参考文档或资源文件。这极大地节省了宝贵的上下文 Token。

- **跨平台兼容：**由于结构统一，你在 Claude Code 中编写的 Skill，理论上可以直接复制到 OpenCode 或 Trae IDE 中使用，只需调整一下存放路径即可。

---

**统一结构带来的核心价值**

- **专业化：**让通用大模型瞬间变身领域专家。例如，一个 `excel-analysis` Skill 可以让 AI 熟练掌握数据透视表、VLOOKUP 等复杂操作，而无需每次对话都重新解释。

- **可复用与可维护：**一次编写，处处使用。当业务流程变更时，只需更新 `SKILL.md` 或相关脚本，所有使用该 Skill 的场景都会自动同步最新逻辑。

- **降低幻觉：**通过提供精确的执行步骤和参考文档，大幅减少了 AI “自由发挥”的空间，确保输出结果符合预期。

- **生态互通：**开发者可以构建一个 Skill 库，在不同的 AI 工具间共享，加速了优质能力的沉淀和传播。

### 3\.3\.3 编写 SKILL\.md

`SKILL.md` 分两部分：**YAML Frontmatter \+ Markdown 正文**。

```Markdown
---
name: code-review-helper
description: 执行代码审查，按安全→性能→规范→可维护性顺序检查，生成表格报告。当用户说"帮我review这段代码"或"代码审查"时使用。
allowed-tools: Read, Grep  # 可选：限制该Skill能用的工具
version: 1.0.0             # 可选
---

# Code Review Helper

## 角色定位
你是一个资深代码审查专家，专注于后端代码质量。

## 核心规则
1. 安全第一：检查硬编码密钥、SQL注入风险
2. 性能第二：检查N+1查询、内存泄漏
3. 规范第三：命名、注释、代码格式
4. 可维护性：函数不超过50行，单一职责

## 工作流程
1. 读取用户提供的代码片段
2. 按上述四个维度逐项检查
3. 生成表格报告：问题等级 | 问题描述 | 修复建议

## 输出格式
| 等级 | 问题 | 建议 |
|------|------|------|
| 严重 | ... | ... |
| 一般 | ... | ... |

## 注意事项
- 不要直接修改用户代码，只提建议
- 不确定的地方标注"需人工确认"
```

**Frontmatter **必填字段：`name` 和 `description`\.

**description** 是整份 Skill 最关键的部分——它决定 Agent 什么时候触发。好的 description 要同时回答：能做什么、核心能力、什么时候触发（含用户关键词）。

❌ 反面案例：`description: Helps with projects.` ——太模糊，什么都匹配

✅ 正面案例：`description: 分析 Figma 设计稿并生成开发交付文档。当用户上传 .fig 文件或要求"设计规范"、"组件文档"时使用。`

---

### 3\.3\.4 核心规范

一个标准的 Skill 通常以文件夹形式存在，其核心是必须包含的 `SKILL.md` 文件。编写时需遵循以下规范：

- 元数据定义：在文件头部使用 YAML 格式定义 `name`（技能名称）和 `description`（功能及使用时机描述），这是决定 AI 能否精准触发的关键。

- 职责边界清晰：保持 Skill 颗粒度稳定，只解决单一或高度相关的问题，避免试图用一个 Skill 包含所有逻辑。

- 结构化执行步骤：将自然语言流程改写为机器可执行的步骤，每一步需明确动作（Action）、产出物（Output）、检查点（Checkpoint）及失败处理机制（Fallback）。

- 辅助文件配置：若涉及复杂操作，可在同级目录下建立 `scripts/` 文件夹存放执行脚本，或建立 `references/` 文件夹存放参考文档，并在 `SKILL.md` 中明确调用规则。

> ***Skill 不是一次性工作——把它当代码一样持续迭代：把 AI 经常犯错的点记下来，整理成“错题本”补充到 ******`references/`******，Skill 会越用越好用。***
> 
> 

---

### 3\.3\.5 编写优质的 Skill

> ###### **优质 Skill 的核心规范与结构**
> 
> 

一个标准的 Skill 通常是一个包含 `SKILL.md` 核心文件的文件夹。编写时需遵循以下规范：

1. **顶部元数据（L1 元数据层）**

这是 Skill 的“身份证”，始终加载在上下文中，用于意图匹配。

- name：必须使用纯英文小写加连字符（kebab\-case），作为唯一标识。

- description：这是决定 Skill 能否被精准触发的灵魂。必须一句话闭环，清晰说明“做什么”、“触发场景”和“前置条件”，避免使用“处理文件”等模糊表述。

2. **核心指令（L2 指令层）**

触发后加载，是 AI 的强制执行手册。

- 输入要求：明确所需参数（必填/选填），若信息不足应要求 AI 追问而非硬编。

- 操作步骤：流程要“傻瓜化”，像给新人写 SOP 一样，明确“做什么、用什么工具、预期输出什么”，关键节点要有条件分支（如果\.\.\.则\.\.\.）。

- 输出格式与质量标准：明确最终输出的结构（如表格、JSON、代码），并定义“好结果”的标准，避免 AI 生成看似完成但无用的废话。

- 失败处理与安全边界：补充异常场景的兜底策略（如工具失败、信息缺失怎么办），并划定红线（不编造事实、不越权）。

```Markdown
# Skill 名称

## 1. 核心原则 (画底线)
- 明确什么能改，什么不能改。例如：“忠于用户原意，不擅自添加信息。”[citation:3]

## 2. 前置条件
- 执行前需要满足的条件，如“需要项目已安装依赖 X”。

## 3. 处理步骤 (线性执行)
- **Step 1:** 先去 references/api.md 读取 API 规范。
- **Step 2:** 基于规范生成代码。
- **Step 3:** 输出结果，不添加任何解释。[citation:3]

## 4. 验证清单 / 常见问题
- [ ] 检查项 1
- Q: 遇到 X 情况怎么办？A: 执行 Y 操作。
```

3. **三个“克制”原则**

- 克制写废话：默认 AI 已经够聪明，省去背景知识科普，直接给步骤、示例和边界条件。

- 克制追求全面：坚持单一职责（原子性），一个 Skill 只做一件事并做透，不要试图做成全能工具箱。

- 克制越界设计：Skill 只负责“告诉 AI 怎么做”，不要塞入 CHANGELOG 等人类阅读文档。

---

> ###### **减少 Token 消耗的优化策略**
> 
> 

Token 消耗不仅关乎成本，更影响 AI 的响应速度和准确率。可通过以下方式优化：

1. **采用“渐进式披露”架构（核心）**

Skill 的加载分三层：**元数据常驻 \-\> 正文触发时加载 \-\> 脚本/参考资料按需引用**。
不要将所有细节塞进 `SKILL.md`，应采用三层加载机制：

- L1 元数据层：仅包含 name 和 description，占用极少 Token（约几十到上百），用于快速筛选。

- L2 指令层：`SKILL.md` 正文保持精简（建议 5000 词以内），只写核心工作流。

- L3 资源层：将详细的 API 文档、示例代码、长篇模板放入 `references/` 目录，AI 仅在需要时按需读取，平时不占上下文。

2. **结构化信息表达**

对于配置项、参数说明、错误码等结构化信息，一律使用 Markdown 表格替代长段落描述。AI 读表格的效率更高，提取信息更准确，能显著减少冗余 Token。

- 控制长度：正文建议不超过 500 行，Token 消耗在 2,000\-5,000 左右为宜。

- 具体化：与其写“语气自然一点”，不如写“不使用破折号，不使用冒号，不加小标题”。AI 对越具体的要求，执行偏差越小。

- Rule：是“底线”，每次对话都必须遵守（如“SQL 必须参数化”），始终占用上下文，宜短。

- Skill：是“技能”，只在特定任务时才加载，可长。

3. **优先使用脚本执行而非代码生成**
对于复杂的验证或数据处理，尽量在 `scripts/` 目录下提供可执行脚本（如 Python/Bash）。AI 调用脚本时，脚本代码本身不会进入上下文窗口，只有执行结果会消耗 Token，这比让 AI 实时生成等效代码更省 Token 且更稳定。

4. **控制启用的 Skill 数量**

每个启用的 Skill 都会占用上下文空间。定期审查并禁用不常用的 Skill；如果安装了数十个 Skill，建议将相关技能打包或按需开启，避免元数据层在系统提示中竞争注意力，导致误触发或 Token 浪费。

---

### 3\.3\.6 复杂 Skill 的内容拆分

如果 Skill 很复杂，不要把什么都塞进 `SKILL.md`。利用渐进式披露：这能有效减少 Skill 在不相关场景下被加载。

```Markdown
## 附加资源
- 详细 API 文档：参考 `references/api-guide.md`
- 评分细则：参考 `references/rubric.md`

## 脚本使用
运行数据校验：
```bash
python scripts/validator.py --input <文件路径>
```

```Plain Text

这样详细文档和脚本代码**不占主上下文**，Agent 需要时才去读[citation:1][citation:8]。

## 5.2 防止误触发：负向触发

在 description 中加入“不要用于什么场景”：

```yaml
description: CSV 文件的高级数据分析，包括统计建模、回归分析。
不要用于简单的数据浏览（那个用 data-viz skill）。
```

- **异常阻断机制**

    在工作流中加入兜底逻辑：

    > ***如果用户的需求在现有组件库中无法找到对应模式，必须停止生成并向用户提问，绝对禁止自行硬编码。***
    >

### 3\.3\.7 调试评测迭代

- **核心理念：像对待 Prompt 一样对待 Skill**

    Skill 的 Description 是系统提示词的一部分，Body 是任务执行时的指令集。这使得 Skill 开发和 Prompt 开发面临相似的挑战，而 Prompt 开发有一个被反复验证的基本事实：你无法靠直觉判断一段指令的好坏，只能靠在真实场景中反复测试来验证。

    这引出三个关键原则：

    > **原则一：分层评测**
    > 
    > 

    Description 和 Body 解决的是完全不同的问题，前者决定"什么时候用"，后者决定"用起来效果如何"。它们的评测方法、评测标准和迭代策略完全不同，必须分开处理。

    > **原则二：对照实验** 
    > 
    > 

    "好不好"是相对概念。一个 Skill 的输出质量，只有和某个基线对比才有意义。这个基线可以是没有 Skill 时的裸跑效果，也可以是上一个版本的 Skill。没有对照组，改进就无从衡量。

    > **原则三：人类参与**
    > 
    > 

    自动化评分能覆盖格式、结构、字段完整性这类客观检查，但 Skill 真正的价值，比如审美判断、业务适配度、专业深度，只有人能评估。评测流程的设计必须让人的判断能高效地注入迭代循环。

---

- **评测 Description：触发的精准度**

    Description 评测要回答一个简单的问题：Agent 在该用这个 Skill 的时候用了吗？在不该用的时候没用吧？

    > **理解触发机制**
    > 
    > 

    在动手测之前，先理解两个关于触发的事实：

    **事实一：Agent 只在觉得自己搞不定时才找 Skill。** 简单的一步操作（比如"读一下这个文件"），即使 Description 完美匹配也可能不触发，因为 Agent 判断自己直接就能完成。这意味着你的测试用例必须足够复杂，不然你测的不是 Description 好不好，而是任务够不够难。

    ---

    **事实二：Agent 天生偏向欠触发（under\-triggering）。** Description 要写得主动一点，把边界往外推。比如不只写"分析 Figma 设计稿并生成交付文档"，而是追加"当用户提到设计规范、UI 组件文档、设计转代码交付，甚至只是上传了 \.fig 文件但没明说要干嘛时，都应该使用"。

    还有一个常见错误：把"什么时候该用这个 Skill"的信息写在 Body 里。Body 是触发之后才加载的，写了也没有任何帮助。所有触发相关的信息，必须且只能写在 Description 中。

### 3\.3\.8 Skill 存放管理

在实际的工程化协作中，“**项目级 Skill**”比“**全局 Skill**”具有更高的优先级和不可替代的优势。

以下是为什么业界更推荐将 Skill 放在项目目录中的核心原因：

1. **保证团队一致性与开箱即用**

项目专属的 Skill 是跟着代码仓库走的。当你把 Skill 提交到 Git 仓库后，团队里的任何成员只要 `clone` 了项目，就会自动获得这套 AI 技能。

- 对比：如果放在全局，新入职的同事必须手动配置自己的本地环境，一旦漏配，AI 的表现就会和团队其他人不一致。

2. **实现能力的精准隔离**

不同的项目往往需要完全不同的 AI 行为。

- 对比：如果你把前端 Vue 的规范和后端 Java 的规范都塞进全局配置，AI 在处理 Java 项目时可能会被前端的规则干扰，导致上下文混乱。放在项目目录里，AI 就能做到“专事专办”。

3. **支持项目级的版本控制**

项目专属的 Skill 可以像代码一样进行版本管理。如果项目的架构发生了重构，对应的 Skill 也可以随之迭代。

**总结来说：**

工具本身完全支持全局部署。把 Skill 放进项目目录，并不是为了“方便个人使用”，而是为了“方便团队协作”和“保持项目环境的纯粹”。如果是你个人的通用技能，完全可以放心地部署在工具的全局配置目录中。

### 3\.3\.8 Skill 带来的优势

#### **极致的性能与成本优化（省钱、提速）**

- 降低 Token 消耗：通过“按需加载”机制，避免了每次对话都向大模型输入几万字的背景知识，大幅降低了 API 调用的 Token 消耗和费用。

- 提升响应速度：模型处理的上下文更精简，推理速度更快，用户等待时间缩短。

- 缓解“注意力迷失”：模型不再被无关信息干扰，能够精准聚焦于当前任务，提升了复杂任务的处理准确率。

---

#### **工程化与资产化（好管、好用）**

- 跨平台兼容：Skill 采用标准化的格式（如 YAML \+ Markdown），这意味着你在 Cursor 里写好的技能，可以直接复制到 Copilot 或其他支持该规范的 Agent 框架中，打破了工具壁垒。

- 版本控制与追溯：Skill 以文件形式存在，可以完美接入 Git 等版本控制系统。团队可以清晰地看到谁在什么时候修改了 AI 的某项能力，方便回滚和审计。

- 能力复用：一次编写，处处可用。不需要每次开新对话都重复输入长篇大论的提示词。

---

#### **开发效率与体验提升（好写、好调）**

- 结构化编写：相比于在纯文本里写 Prompt，Skill 提供了清晰的目录结构（如包含描述、触发条件、执行步骤、示例等）。这种结构化让编写和阅读都更加直观。

- 降低调试难度：当 AI 表现不佳时，开发者可以像排查代码 Bug 一样，精准定位到 Skill 文件中的某个步骤或规则进行微调，而不是盲目地重写整段提示词。

---

#### **业务能力的标准化（专业、稳定）**

- 沉淀企业最佳实践：团队可以将内部的业务流程、代码规范、沟通话术封装成 Skill，让新入职的员工或新接入的 AI 瞬间具备“老员工”的专业水平。

- 执行结果的一致性：通过内置的异常处理、重试机制和严格的输入输出约束，Skill 确保了 AI 在处理相同任务时，每次都能给出符合预期、格式统一的标准化结果，减少了“幻觉”和随机性。
