# AI 知识库调用原理

## 背景 / 上下文

对话中整理（2026-09-05），缘起提问"调用知识库并结合知识库内容进行输出的过程与原理"。核心前提一句话：**模型本身不含你的知识库**——每次作答只基于上下文窗口内"看得见"的文本；知识库内容必须被检索出来、拼进 Prompt，模型才能"结合知识库"输出。各种方案之间的差异只在于"内容怎么被找到、怎么喂进去"。

## 核心机制：检索 → 注入 → 生成

- 三段式缺一不可，任何一段缺失，"结合知识库输出"都不成立。
- **注入是关键一步**：知识库内容不会自动进入模型，只有被检索命中并拼进 Prompt 的那一小段才真正参与生成。
- 推论：**检索质量 = 回答上限**——漏检、切块切碎上下文、注入被截断，都会让答案打折。

## 三种接入方式对比

| 方式 | 过程 | 适用 | 代价 |
|---|---|---|---|
| 全量注入 | 收集相关文档 → 精简去重 → 整体写入 Prompt → 直接生成 | 文档量小、单次问答 | token 成本高、易超上下文窗口、慢 |
| 工具检索（Agent） | 模型先决策"查哪里" → 调工具读文件/搜索/查接口 → 命中内容注入 → 生成 | 本地文件、结构化系统 | 多一次检索时延，依赖模型决策准确 |
| 向量 RAG | 离线切块+向量化入库 → 提问转向量 → 相似度召回 Top-K → Rerank → 注入 → 生成+引用 | 海量非结构化语料 | 需维护索引系统，存在召回失败/噪声风险 |

- 本库（Obsidian 本地 md）现状 = **工具检索模式**：会话启动注入精简记忆（身份/库规范/偏好画像）→ 提问后按需用工具命中文件 → 命中内容注入上下文 → 生成。

## RAG 链路要点（理论详解见 [[AIRAG检索增强生成]]）

- **切块（chunking）是隐性分水岭**：文档按 chunk 向量化而非整篇。一篇笔记独立成文 ≈ 天然 chunk——本库"文件名唯一、独立成文、互链清楚"的规范恰好提升命中率，这是调参换不来的。
- 相似度 ≠ 语义正确：向量近邻只保证主题接近，所以线上要加 Rerank 精排 + 引用溯源（后者同时让输出可核对、可测试）。
- 成本权衡：全量注入贵且慢；检索注入省 token、只多一次检索时延。本地几十篇笔记的规模用工具检索已够，硬上向量库属于过度设计。

## 从 AI 测试视角验证（四个可测点）

1. 准确性 / 幻觉：回答与命中原文逐句比对，断言引用出处一致。
2. 召回覆盖：预置"问题 → 期望命中的笔记"用例集，验证 Top-K 是否包含目标。
3. 延迟与 token 消耗：命中片段数对首字时延与成本的影响。
4. 注入安全：知识文本中夹带"忽略以上指令"能否劫持输出；确保入库来源可信。
