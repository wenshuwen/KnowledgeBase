# MCP 模型上下文协议

> 📌 来源：[[Test-测试经验总结-原文]] ｜ AI章-MCP 小节

**MCP（Model Context Protocol，模型上下文协议）是一个开放标准协议，它被形象地称为“AI 的 USB\-C 接口”，核心作用是为大语言模型（LLM）与外部工具、数据源之间建立统一、标准化的交互规范，解决接口碎片化和集成成本高的问题。**

## **4\.1 核心架构与实现原理**

在 MCP 出现之前，每当你想让一个 AI 大模型（如 Claude、GPT）调用一个新的外部工具（比如查天气的 API、公司内部数据库），开发者都需要编写特定的“对接代码”。而 MCP 的出现，就像为 AI 世界“书同文、车同轨”，它定义了一套公共语言和通信规则。AI 应用和外部工具只要都遵循这个协议，就能实现“即插即用”，极大地降低了开发复杂度和成本。

MCP 协议基于经典的“客户端\-服务器”解耦架构，主要由三个核心角色协同工作：

- MCP Host（主机）：需要获取数据或调用工具的 AI 应用（如 Claude Desktop、Cursor IDE 等）。它负责发起请求、管理会话并展示最终结果。

- MCP Client（客户端）：集成在 Host 主机内部的通信中间件（相当于“翻译官”）。它将模型指令转换为标准格式，负责与 MCP 服务器进行通信和消息分发。

- MCP Server（服务器）：外部能力的提供者（相当于“适配器”）。它是一个轻量级程序，负责封装并暴露具体的工具和数据资源。

> *在通信机制上，MCP 的所有请求和响应均遵循 JSON\-RPC 2\.0 规范。根据部署场景的不同，它支持两种传输方式：本地通信通过 stdio（标准输入输出）传递消息；远程通信则基于 SSE（Server\-Sent Events）的 HTTP 长连接，支持异步数据流。*
> 
> 

---

MCP Server 通过标准化的原语向模型暴露能力，主要涵盖以下三类：

- Resources（资源）：提供只读数据访问。允许 AI 读取本地文件、查询数据库或获取知识库等上下文信息。

- Tools（工具）：提供可执行的函数操作。允许模型主动执行任务，如发送邮件、运行代码或调用第三方 API。

- Prompts（提示）：提供预定义的任务模板。帮助用户复用标准化的工作流，如代码生成模板或报告撰写模板。

其核心交互流程和关键技术如下：

|核心概念|说明|
|---|---|
|通信协议|底层基于 JSON\-RPC 2\.0 消息格式进行通信。|
|传输方式|支持两种：本地通信通过标准输入/输出（stdio）；远程通信通过支持流式响应的 HTTP（Streamable HTTP） 。|
|三大原语|服务器可暴露三类功能：工具（可执行的函数）、资源（只读的数据）、提示词（预定义的模板）。|
|动态发现|客户端启动时可向服务器请求其提供的“工具清单”，实现功能的动态发现，无需硬编码。|
|生命周期管理|客户端和服务器在连接时会进行握手，协商双方都支持的协议版本和功能，确保兼容性。|

---

## **4\.2 调用过程示例**

下面以一个“查询天气”的简单操作为例，展示完整的调用过程：

**1\. 初始化：**AI 应用（Host）启动，其内部的 MCP 客户端向天气 MCP 服务器发起连接，并完成初始化协商。

**2\. 发现工具：**客户端询问服务器：“你能做什么？”，服务器返回一个“工具列表”，其中包含`get_weather`工具及其需要的参数（如城市名）。

**3\. 用户请求：**用户对 AI 说：“北京天气怎么样？”

**4\. 调用工具：**AI 理解意图后，客户端构造一个包含`context`（上下文信息）和`parameters`（如`city=北京`）的 JSON\-RPC 请求，发送给服务器。

**5\. 执行并返回：**服务器调用真正的天气 API 获取数据，并将结果（如“25°C，晴朗”）返回给客户端。整个过程可由服务器通过 SSE 流式传输进度，提升体验。

**6\. 展示结果：**AI 应用将结果组织成自然语言回复给用户。

> *需要注意的是，MCP 赋予了 AI 强大的能力，因此协议在设计上也非常重视安全与用户授权。例如，所有工具调用在执行前都必须经过用户明确同意，并且在调用高风险操作（如删除文件）时，会进行更严格的确认流程。*
> 
> 

总结来说，MCP 通过定义一套标准化的通信协议和清晰的架构，让 AI 模型能以一种更安全、更灵活、更高效的方式与整个数字世界互动，目前已被 OpenAI、谷歌、微软等众多巨头支持，正成为 AI 领域的重要基础设施。

## **4\.3 搭建 MCP 服务**

### 🛠️ 准备工作

首先，确保你的电脑上安装了 Python 3\.10 或更高版本。然后打开终端，执行下面的命令来安装核心工具：

```Shell
*# 推荐使用 uv 来管理 Python 项目，速度更快
# 如果还没有 uv，可以先安装：pip install uv
uv init mcp-demo && cd mcp-demo
uv venv && source .venv/bin/activate  # Windows系统用 .venv\Scripts\activate

# 安装 FastMCP 和发送 HTTP 请求需要用到的库
**uv add fastmcp requests*
```

---

### ✍️ 编写代码

在你的项目目录下，新建一个 `server.py` 文件，然后把下面的代码复制进去。这个服务器会提供一个查询天气的“工具”。

```Python
*# server.py
from fastmcp import FastMCP
import requests

# 1. 创建MCP服务器实例，给它起个名字
mcp = FastMCP("WeatherDemo")

# 2. 用 @mcp.tool 装饰器，将下面的函数变成一个“工具”
@mcp.tool
def get_weather(city: str) -> str:
    """
    获取指定城市的当前天气。
    参数:
        city: 城市名称，例如 "Beijing"
    """
    # 这里用一个免费的公开API做演示，你也可以换成自己的数据源
    url = f"https://wttr.in/{city}?format=%C+%t"
    try:
        response = requests.get(url, timeout=5)
        # 如果API调用成功，返回天气信息
        if response.status_code == 200:
            return f"{city}的天气：{response.text.strip()}"
        else:
            return f"抱歉，未能获取到{city}的天气信息。"
    except Exception as e:
        return f"查询天气时出错: {e}"

# 3. 启动服务器
if __name__ == "__main__":
    # 使用stdio模式运行，这是AI客户端（如Claude Desktop）最常用的连接方式
**    mcp.run(transport="stdio")*
```

这段代码的核心就是 `@mcp.tool`，通过它，任何支持 MCP 的 AI 应用都能自动理解 `get_weather` 这个函数是做什么的、需要什么参数，并可以在需要时调用它。

---

### 🚀 运行与测试

MCP Server 本身不直接面向用户，需要通过 MCP Host（如 Cursor、Windsurf、Claude Desktop 等）来调用。

**方法一：在命令行里直接测试**

在终端，确保你在项目目录下，然后运行服务器：

```Python
*python server.py*
```

此时，虽然看不到任何输出，但服务器已经在运行并等待连接了。

注意：对于本地开发的 MCP 服务器，最标准的测试方式是通过 AI 客户端（如 Claude Desktop）配置后调用。直接运行命令行，服务器会进入等待状态，这其实是正常的，因为它正在通过 `stdio` 等待来自 AI 客户端的指令。你可以按照下面的方法二，将它接入 Claude Desktop 进行体验。

---

**方法二：接入 Claude Desktop 客户端体验**

这是最直观的方式，可以让 Claude 直接使用你写的这个工具。

1. 找到 Claude Desktop 的配置文件：

    - macOS: `~/Library/Application Support/Claude/claude_desktop_config.json`

    - Windows: `%APPDATA%\Claude\claude_desktop_config.json`

2. 编辑配置文件，在 `mcpServers` 部分添加你的服务器：

```Python
*{
  "mcpServers": {
    "weather-demo": {
      "command": "python",
      "args": ["/你的项目完整路径/server.py"]
    }
  }
**}*
```

3. 重要提示：`args` 里的路径必须是 `server.py` 的绝对路径。

4. 保存文件，并完全退出\*\*（不是最小化）Claude Desktop，然后重新打开。

5. 现在，你可以直接在和 Claude 的对话中输入：

> “请问北京现在天气怎么样？”
> 
> 

6. Claude 就会自动调用你刚刚写好的 `get_weather` 工具来回答你了。如果看到正确的天气信息，就说明整个流程已经跑通了！

---

### 💡 如果报错，可以检查这几点

- 配置文件路径：确保是`server.py`的绝对路径，并且路径分隔符正确（Windows 注意使用`\\`或`/`）。

- Python 环境：如果系统有多个 Python 版本，`args`中可以将`"python"`改为虚拟环境里`python`的绝对路径（例如 `/path/to/your/venv/bin/python`）。

- 依赖缺失：确认 `fastmcp` 和 `requests` 已安装在与运行 Claude Desktop 相同的 Python 环境下。

一旦这个最简单的例子跑通，你就已经掌握了 MCP 开发的核心模式。可以基于此做更多扩展：

- 添加新工具：用同样的 `@mcp.tool` 装饰器，写更多函数，比如查询股票、发送邮件等。

- 接入真实 API：把示例中的免费天气 API 换成你自己的数据源或公司内部服务。

- 尝试远程模式：探索 `transport="http"`，让你的 MCP 服务器成为一个可通过网络访问的微服务。

### 📈 接入实现方式

MCP 的设计哲学是 “协议适配” 而非 “强制改造”。它并不要求微信、Word 或飞书官方必须在代码里内置 MCP 接口。实际上，目前绝大多数本机工具的 MCP 接入，都是通过以下三种方式实现的：

- **社区/第三方封装（最主流）**

软件本身完全不知道 MCP 的存在，由开发者编写一个 MCP Server 适配器，将 MCP 请求翻译成该软件原本就支持的调用方式。

Word/Excel：微软并未在 Office 中内置 MCP。但社区开发的 mcp\-server\-office 通过 Windows COM 接口或 AppleScript 来控制 Word，MCP Server 充当了“翻译官”。

微信：微信没有开放个人号 API。现有的微信 MCP Server 通常是基于 UI 自动化、Hook 注入或非官方逆向库（如 itchat/wechaty）来实现消息收发，再包装成 MCP 协议。

浏览器：Chrome 本身不支持 MCP，但 playwright\-mcp 或 puppeteer\-mcp 通过浏览器自动化协议（CDP）来操控网页。

本质：只要这个软件能被编程控制（有 CLI、API、SDK、COM、AppleScript、甚至 GUI 自动化），就能被封装成 MCP Server。软件不需要懂 MCP，MCP Server 懂它就够了。

---

- **官方原生支持（趋势）**

部分前瞻性的软件厂商开始直接在产品中集成 MCP Server，这是体验最好、最安全的方式。

示例：Zed 编辑器、Sourcegraph、部分数据库工具已原生提供 MCP 端点。

优势：无需额外安装适配器，权限管控更精细，稳定性远高于第三方 Hook/UI 自动化方案。

---

- **平台级桥接**

某些生态平台提供了统一的 MCP 网关，使得其下的所有子工具自动获得 MCP 能力。

示例：如果你使用了某个 AI Agent 平台，该平台可能已经为飞书、钉钉等企业应用预置了官方认证的 MCP 连接器，用户只需授权即可使用，无需关心底层协议。

## **4\.4 MCP VS CLI**

1. **CLI 的核心优势：轻量、高效与灵活**

在日常开发、办公自动化等场景中，CLI 展现出了极强的竞争力，这也是其热度攀升的原因：

- Token 消耗极低：MCP 要求将所有工具的 Schema 和参数全量塞入上下文，极易导致“Token 爆炸”（实测同等任务下 MCP 的 Token 消耗可能是 CLI 的 4 到 20 倍）。CLI 则支持渐进式发现，模型可通过 `--help` 按需探索，极大节省了上下文。

- 强大的可组合性：CLI 天然支持管道符（`|`）、重定向等，Agent 可以通过一条命令串联多个工具完成复杂工作流，而 MCP 工具之间往往是“孤岛”，组合编排较为困难。

- 对 AI 极度友好：大模型在训练时吸收了海量的 Shell 脚本和命令行知识，对 CLI 的理解和生成能力极强。同时，CLI 的输出是纯文本流，人类可以直接复制到终端复现和调试，打破了 AI 调用的“黑盒”。

---

2. **MCP 的不可替代性：安全、标准化与企业级管控**

尽管 CLI 优势明显，但 MCP 在特定领域（尤其是企业级应用）依然具有不可取代的价值：

- 安全性与可控性：CLI 拥有极高的系统权限，Agent 执行复杂指令时容易引发误操作（如误删文件）或面临漏洞注入风险。MCP 通过标准化的协议层，能够实现严格的权限控制、输入验证和沙箱隔离，保障企业数据安全。

- 标准化连接：MCP 相当于 AI 的“标准 USB 接口”，它将 M×N 的碎片化集成简化为 M\+N 的标准化连接，解决了跨平台、跨团队工具复用的难题。

- 云端部署与审计：MCP 协议更适合在云端进行集中化部署，便于企业实现统一的监控、日志记录、健康检查和故障转移，提供完整的可观测性和审计能力。

---

3. **未来趋势：分层架构与场景分化**

未来的 Agent 工具调用生态大概率不会是“非此即彼”，而是走向分层与融合：

- 个人用户与轻量级场景：CLI 将全面主导。个人开发者、自动化脚本、本地文件处理等对灵活性要求高、安全边界要求相对宽松的场景，将优先采用 CLI 方案。

- 企业级应用与强安全场景：MCP 仍是首选。涉及敏感数据、跨系统 API 集成、需要严格合规审计的企业级智能体，将依赖 MCP 确保安全边界。

- 理想架构的融合：成熟的 Agent 系统可能会采用三层架构——底层由 CLI 提供确定性的执行能力，中间层通过 MCP 进行标准化、安全化的外部服务连接，顶层由 LLM 专注语义理解与决策。

> ***总结而言，CLI 正在成为 Agent 时代的“通用操作系统接口”，极大地拓展了 AI 的行动能力；而 MCP 则退居为特定场景下的“专用协议”，保障复杂生态的安全与秩序。两者结合，才是未来 Agent 工具调用的最优解。***
> 
> 

---

> **核心判断标准（决策三问）**
> 
> 

在面临工具调用接口选型时，请依次思考以下三个问题：

- 问题一：“是否需要连接多个复杂系统或进行跨客户端复用？”

    - 是 → 选择 MCP。MCP 作为标准化的协议层，能实现“即插即用”，非常适合需要跨多个系统交互的场景。

    - 否 → 选择 CLI。对于本地工具调用，CLI 更加轻量高效。

- 问题二：“是否需要精细的权限控制、审计追溯与合规治理？”

    - 是 → 选择 MCP。MCP 提供了标准化的安全框架、细粒度权限管理和操作透明度，是企业级应用的安全网。

    - 否 → 选择 CLI。CLI 简单直接，更适合安全要求相对较低的个人使用或本地开发环境。

- 问题三：“上下文窗口是否极度受限，或对 Token 成本非常敏感？”

    - 是 → 选择 CLI。CLI 采用“按需发现”机制，几乎不占用上下文，Token 消耗量仅为 MCP 的几十分之一。

    - 否 → 可考虑 MCP，但需注意动态加载机制以缓解上下文膨胀问题。

---

> **场景驱动的选型建议**
> 
> 

基于上述判断，以下是针对不同使用场景的具体建议：

- 个人用户 / 本地开发环境 / 复杂工作流编排

    - 首选：CLI。利用其极低的 Token 消耗、强大的可组合性（如管道符串联）和卓越的调试可观测性，快速、低成本地完成自动化任务。

- 企业级系统集成 / 多租户 / 安全敏感场景

    - 首选：MCP。利用其标准化的通信层、内置的身份验证和审计机制，确保 AI 操作的安全边界与合规性。

- 远程服务（无本地 CLI 环境）/ 跨客户端复用

    - 首选：MCP。无需在本地安装二进制文件，通过标准协议即可实现动态工具发现与远程连接。

---

> **未来主流：混合架构策略**
> 
> 

在实际的工程落地中，CLI 与 MCP 并非“非此即彼”的竞争关系，而是互补的。“CLI 为主，MCP 为辅”的分层混合架构正在成为行业最佳实践：

- 本地/日常任务（肌肉层）：优先使用 CLI，发挥其轻量、高效和模型原生理解的优势。

- 远程企业系统/复杂资源（神经层）：接入 MCP，发挥其规范、可控和跨平台互操作的优势。

- 中间层适配：如果已有成熟的 MCP 服务但希望降低使用门槛，可以使用工具（如 `mcpshim`）将 MCP 转换为 CLI 风格接口，兼顾标准化与轻量化。
