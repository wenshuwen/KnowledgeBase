# JMeter 使用详解

> 📌 来源：[[Test-测试经验总结-原文]] ｜ 测试工具章-Jmeter 小节（核心组件/流程/实战，内容较长）

## 🧩 核心组件

> **标准执行顺序：**
> 
> 

**配置元件 → 前置处理器 → 定时器 → 取样器 → 后置处理器 → 断言 → 监听器**

JMeter 的组件各司其职，按照特定的顺序协同工作。以下是各个组件的通俗解释：

### **1\.**** ****测试计划 \(Test Plan\)**

> **它是整个测试的“总指挥部”或“总文件夹”。你所有的测试脚本、用户配置和结果收集，都必须放在测试计划这个容器里。**
> 
> 

### **2\. 线程组 \(Thread Group\)**

> **线程组是测试执行的入口点，它定义了一组虚拟用户（线程）的行为。**
> 
> 

- 线程数：模拟的并发用户数量。例如，设置为 200 表示模拟 200 个用户同时操作。

- Ramp\-Up 时间：启动所有线程所需的总时间。例如，线程数为 200，Ramp\-Up 为 10 秒，意味着每秒会启动 20 个线程，避免瞬间压垮服务。

- 循环次数：每个线程执行测试脚本的次数。性能压测时通常勾选“永远”，并配合“调度器”设置测试持续时间（如 300 秒）。

- **标准线程组（Thread Group）**

    - 核心特点：最基础的类型，支持配置线程数（虚拟用户数）、启动时间（Ramp\-Up）、循环次数和调度器。

    - 适用场景：适用于绝大多数的并发测试、基准测试和压力测试。它是生成负载的核心载体。

    - 配置逻辑：Ramp\-Up 时间代表启动所有线程的总耗时。例如，100 个线程设置 Ramp\-Up 为 10 秒，意味着每秒启动 10 个线程，平滑模拟用户进入。

- **setUp 线程组（Setup Thread Group）**

    - 核心特点：具有最高执行优先级，在所有普通线程组之前执行，且全局仅运行 1 次（与线程数无关）。

    - 适用场景：用于测试前的初始化操作，如创建测试数据、预热 JVM、或执行登录获取全局 Token 等。

- **tearDown 线程组（TearDown Thread Group）**

    - 核心特点：执行优先级最低，在所有普通线程组执行完毕后运行，同样仅运行 1 次。即使测试中途手动停止，该线程组仍会执行。

    - 适用场景：用于测试后的清理工作，如删除测试数据、关闭数据库连接、执行登出操作等。

### **3\. 配置元件 \(Config Element\)**

> **用于提供共享的配置数据，避免在每个请求中重复设置，父级元件的配置会作用于所有子级元件。**
> 
> 

- **HTTP 请求默认值：**设置全局的协议（http/https）、服务器 IP/域名、端口号等。后续的 HTTP 请求只需填写不同的路径即可。

- **HTTP 信息头管理器：**添加自定义请求头。例如，测试 JSON 接口时，必须添加` Content-Type: application/json` 鉴权时添加` Authorization: Bearer ${token}`。

- **HTTP Cookie 管理器：**自动管理 Cookie，模拟浏览器的会话保持行为（如登录后自动携带 Cookie）。

- **CSV 数据文件设置：**实现参数化（数据驱动）测试。通过读取外部 CSV 文件（如存放不同的用户 ID、商品 ID），让每个线程使用不同的测试数据，避免缓存干扰。

    **💡 变量引用与实战小贴士：**

    1. 引用语法：配置好变量名后，在 HTTP 请求的参数、Body 或 Header 中，使用 `${变量名}` 的语法进行动态引用（例如 `${username}`）。

    2. 路径排查：如果在非 GUI 模式（命令行）下运行提示找不到文件，请检查文件路径是否相对于执行命令的目录，或确认路径中是否包含空格与中文字符。

    3. 大小写敏感：JMeter 的变量名是严格区分大小写的，引用时务必确保拼写与 `Variable Names` 中完全一致。

    |    界面参数|    含义解释|    配置示例/注意事项|
    |---|---|---|
    |    Filename|    CSV 文件的路径。支持绝对路径和相对路径。|    `./data/users.csv`<br>    最佳实践：推荐使用相对路径（如 `./` 前缀），并将文件与 `.jmx` 脚本放在同级目录，以增强脚本的可移植性。|

### **4\. 前置处理器 \(Pre\-Processor\)**

> **在请求发送前执行，用于修改请求设置或生成动态参数。比如在发送请求前，先生成一个随机的时间戳或加密签名。**
> 
> 

#### **用户参数**

这是最简单的参数化前置处理器。

- 作用：为同一线程组的不同线程（虚拟用户）分配不同的参数值。

- 与 CSV 数据文件设置的区别：

    - CSV：是配置元件，从外部文件顺序读取，更适合大规模、结构化的数据驱动。

    - 用户参数：是前置处理器，直接在脚本里定义少量几组参数，更直观。

- 性能测试场景：模拟几个特定的 VIP 用户，他们的账号密码固定且各不相同。

- 配置示例：

    - 添加变量：`username`

    - 添加用户：`user_vip1`，`user_vip2`，`user_vip3`

    - 在 HTTP 请求里使用 `${username}`，3 个用户并发时会自动分配这些值。

#### **JSR223 前置处理器 \(最重要的通用处理器\)**

这是功能最强大的前置处理器，因为你可以直接写 Groovy 代码。

- 作用：实现任何自定义的、复杂的请求前逻辑。

- 典型性能测试应用：

    - 生成动态签名：很多接口需要在 Header 里传一个签名字段，比如 `sign = MD5(timestamp + token)`。可以在这里用代码计算签名，再存入变量。

    - 构造当前时间戳：`${__time(,)}` 函数很简单，但想生成特定格式的字符串，如“yyyyMMddHHmmss”，写 Groovy 更灵活。

- 代码示例 \(生成签名\)：

```Groovy
*import java.security.MessageDigest

// 假设 token 已通过后置处理器从登录接口提取
String token = vars.get("token")
// 生成时间戳
long timestamp = System.currentTimeMillis()
// 计算签名
String sign = MessageDigest.getInstance("MD5")
    .digest((timestamp + token).getBytes())
    .encodeHex()
    .toString()
// 将生成的值存入JMeter变量，供后续请求使用
vars.put("timestamp", timestamp.toString())
**vars.put("sign", sign)*
```

- 为什么推荐 JSR223 而不是 BeanShell：Groovy 脚本会被编译，执行效率远高于解释执行的 BeanShell，高并发下对压力机性能影响更小。

#### **JDBC 前置处理器**

- 功能：在发送请求前，先执行 SQL 语句操作数据库。

- 核心场景：

    - 数据准备：在压测前，向数据库中插入一条测试订单，并获取其订单 ID 供后续接口使用。

    - 环境清理：在测试开始前，清理掉数据库中过期的测试数据。

### **5\. 定时器 \(Timer\)**

> **真实用户操作之间会有停顿，定时器可以在请求之间加入延迟（思考时间），让压测场景更贴近真实情况。**
> 
> 

#### **固定定时器 \(Constant Timer\)**

- 功能：在每个请求执行前，固定等待一段指定的时间（单位：毫秒）。

- 使用场景：适用于需要固定间隔的轮询任务，或者简单的固定思考时间模拟。

- 参数：只需填写“线程延迟（毫秒）”。例如填入 `3000`，表示每次请求前固定等待 3 秒。

#### **高斯随机定时器 \(Gaussian Random Timer\)**

- 功能：生成符合正态分布的随机延迟时间。实际延迟 = 固定延迟偏移 \+ 随机偏差。

- 使用场景：最贴近真实人类操作习惯的定时器。大部分用户的操作间隔会集中在某个均值附近，但偶尔会有快有慢。

- 参数：

    - 固定延迟偏移：延迟的基准值（如 `2000` 毫秒）。

    - 偏差：正态分布的标准差（如 `300` 毫秒）。

    - 实际效果：大部分请求的延迟会在 1700ms 到 2300ms 之间波动。

#### **均匀随机定时器 \(Uniform Random Timer\)**

- 功能：在固定延迟的基础上，再加上一个 0 到指定最大值之间的随机数。

- 使用场景：模拟操作间隔差异较大的场景。

- 参数：

    - 固定延迟偏移：基准值（如 `1000` 毫秒）。

    - 随机延迟最大值：随机范围上限（如 `5000` 毫秒）。

    - 实际效果：每次请求的延迟会在 1000ms 到 6000ms 之间随机产生。

#### **定时器的核心使用规则与避坑指南**

- 作用域规则：
定时器对其作用域内的所有采样器（Sampler）生效。如果放在某个 HTTP 请求的子节点下，仅对该请求生效；如果放在线程组下，则对该线程组内所有的请求生效。

- 叠加效应：
如果在同一个作用域内添加了多个定时器，它们的延迟时间会叠加。例如同时加了一个 1000ms 的固定定时器和一个 2000ms 的随机定时器，实际等待时间会是 3000ms \+ 随机数。

- 执行顺序：
定时器总是在其所属的采样器（请求）之前执行。

- 事务统计失真：
如果你使用了事务控制器 \(Transaction Controller\) 来统计某个业务流程的总耗时，建议将模拟思考时间的定时器放在事务控制器的内部。如果放在外部，可能会导致事务的响应时间统计不准确（包含了不必要的等待时间）。

- 同步定时器的误区：
同步定时器控制的是“并发用户数”，而不是精确的“每秒请求数（RPS）”。且设置“模拟用户组数量”时，不能超过线程组的总线程数，否则永远凑不齐人，只能等待超时。

### **6\. 取样器 \(Sampler\)**

#### **HTTP 请求 \(HTTP Request\)**

- 基本配置：选择请求方法（GET、POST、PUT、DELETE 等），填写接口路径。

- 参数（Parameters）：适用于 GET 请求的 Query 参数或 POST 的表单数据（x\-www\-form\-urlencoded）。

- 消息体数据（Body Data）：适用于 POST/PUT 请求发送 JSON 或 XML 格式的数据。

#### **JDBC 请求 \(JDBC Request\)**

用于直接向数据库发送 SQL，测试其查询、更新性能\(数据库性能测试\)。这在定位瓶颈、独立压测数据库时很关键。

- 前置步骤：必须先添加 JDBC 连接配置（配置元件），填入数据库 URL、驱动类和连接池大小。

- 配置核心：

    - Variable Name：绑定到 JDBC 连接池的名称。

    - Query Type：`Select Statement`（查单行）、`Callable Statement`（存储过程）、`Update Statement`（增删改）等。

- 场景：

    - 验证数据库上限：构造复杂的 `SELECT` 查询，用 200 并发直接跑，看数据库 IOPS 和 CPU。

    - 压测存储过程：模拟后端业务逻辑在数据库层的执行效率。

- 参数化：在 SQL 中用 `?` 作为占位符，在下方参数值中填入 `${csv_user_id}`，实现不同用户查不同数据。

- 实战避坑小贴士：

    - 字符串引号问题：如果在 SQL Query 中直接使用 `${变量}` 拼接（而非使用 `?` 占位符），且该变量是字符串类型，必须手动加上单引号（如 `'${name}'`）。但如果使用的是 `Parameter values` 传参，则不需要加引号，只需在 `Parameter types` 中声明为 `VARCHAR` 即可。

    - 驱动配置：使用 JDBC Request 前，务必确保已将对应数据库的驱动 Jar 包（如 `mysql-connector-java-x.x.x.jar`）放入了 JMeter 的 `lib` 或 `lib/ext` 目录下，并重启 JMeter。

|界面参数|含义解释|配置示例/注意事项|
|---|---|---|

|Query Type|指定要执行的 SQL 语句类型。常见选项包括：<br>• Select Statement：执行普通的 SELECT 查询。<br>• Update Statement：执行 INSERT/UPDATE/DELETE 等更新语句。<br>• Callable Statement：调用数据库存储过程。<br>• Prepared Select/Update Statement：执行带参数的预编译 SQL，性能更好且防注入。|普通查询选 `Select Statement`；带 `?` 占位符的查询选 `Prepared Select Statement`。|

|Query timeout \(s\)|设置 SQL 查询的超时时间（单位：秒）。默认为 0，表示不限制超时时间。|`30`|
|Handle result set|定义如何处理由 `Callable Statements`（存储过程）返回的结果集。默认选项为 `Store as String`（存储为字符串），也可选 `Store as Object` 或 `Count Records`。|`Store as String`|

#### **调试取样器 \(Debug Sampler\)**

它不产生任何业务请求，纯粹是调试工具。

- 作用：在执行到此取样器时，打印当前上下文里所有可用的 JMeter 变量 和 属性。

- 查看方式：它的输出在“查看结果树”的响应数据中。

- 实战价值：当你的参数化、关联逻辑复杂，不确定变量是否正确生成时，在脚本关键位置插入一个“调试取样器”，能快速定位变量是否正确，比任何猜测都直接。

#### **Java 请求 \(Java Request\)**

当需要测试的接口不是标准 HTTP（如 Dubbo、gRPC、自研协议）时，可以使用它。

- 工作原理：它允许你编写 Java 代码，实现 `org.apache.jmeter.protocol.java.sampler.JavaSamplerClient` 接口，然后将代码打包成 JAR 包放入 `lib/ext` 目录，JMeter 就能识别并执行。

- 场景：压测 Dubbo 微服务。你可以在 `runTest` 方法中，用 Dubbo 客户端发起调用，JMeter 则负责并发调度、参数化和结果统计。

- 优缺点：非常灵活，几乎能测试任何协议，但需要一定的 Java 开发能力。

### **7\. 后置处理器 \(Post\-Processor\)**

> **在请求响应后执行，最常用的是正则表达式提取器或 JSON 提取器。用于从上一个接口的响应中提取动态值（如登录后的 token、下单后的 orderId），并将其保存为变量，供后续接口使用（即“接口关联”）。**
> 
> 

#### **JSON 提取器 \(JSON Extractor\)**

- 功能：专门针对 JSON 格式的响应数据，使用 JSONPath 语法提取字段值。

- 核心场景：接口测试中最常用的提取器。例如，从登录接口的响应 `{"code":200, "data":{"token":"abc123"}}` 中，通过表达式 `$.data.token` 提取出 `token` 值，并保存为变量供后续接口调用。

- 配置：

    - Names of created variables: `auth_token`

    - JSON Path expressions: `$.data.token`

- 引用：在后续接口的 Header 管理器中，添加参数 `Authorization: Bearer ${auth_token}` 即可。

#### **正则表达式提取器**

- 功能：使用正则表达式从任意格式的响应文本（HTML、JSON、纯文本等）中提取数据。

- 核心场景：万能提取器。当响应不是标准的 JSON 格式，或者需要提取 HTML 页面中的隐藏域（如 CSRF Token）、重定向的 URL 时非常有用。

- 配置要点：

    - 模板：`$1$` 表示取第一个捕获组。

    - 匹配号：为`-1`时取所有匹配值的随机一个。

- 特别提醒：如果能用 JSON 提取器，就不要用正则。正则编写难、调试慢、易出错，比如忘记转义 `[` `]`。

#### **JSR223 后置处理器**

- 功能：使用脚本语言对响应数据进行极其复杂的自定义处理。当你发现图形化提取器搞不定时，这就是终极方案。

- 核心场景：当内置的提取器无法满足需求时使用。例如，响应是一个复杂的 JSON 数组，需要遍历数组并根据特定条件筛选出某个 ID；或者需要对响应数据进行解密后再提取。

- 典型场景：处理复杂的、动态的响应逻辑

    - 场景 1：解密响应：服务端返回的数据整体加密了。在这里用 Groovy 解密后，再提取。

    - 场景 2：一次提取，多次使用：从列表接口响应中，随机提取一个可用的订单 ID。

    - 场景 3：数据清洗与转换：提取出一个数字字符串，把它乘 100 后传给下个接口。

- 代码示例 \(从响应中提取数据并处理\)：

```Groovy
*import groovy.json.JsonSlurper

// 获取当前取样器的响应数据（字符串格式）
String responseData = prev.getResponseDataAsString()
// 解析JSON
def json = new JsonSlurper().parseText(responseData)
// 获取订单列表
def orders = json.data.orderList
// 只取状态为“待支付”的订单ID
def pendingOrderIds = orders.findAll { it.status == "PENDING_PAY" }.id
if (pendingOrderIds) {
    // 随机选择一个ID，并存入变量
    String randomOrderId = pendingOrderIds[new Random().nextInt(pendingOrderIds.size())]
    vars.put("orderId", randomOrderId)
**}*

// prev 和 vars 是关键对象：prev 可访问取样器结果，vars 可存取JMeter变量。
```

#### **调试后置处理程序 \(Debug PostProcessor\)**

- 作用：它不提取数据，而是将当前 JMeter 中的所有变量、属性、系统信息打印到响应结果中。它不是用来写业务逻辑的，而是帮你调试脚本。

- 查看方式：添加后运行一次，配合“查看结果树”，在响应数据里就能看到所有变量和值。

- 最佳实践：提取变量不成功时，马上加一个“调试后置处理程序”来检查，用完后必须禁用或删除，否则会严重影响压测时压力机的性能。

- 核心场景：脚本调试神器。当你不确定前置处理器生成的变量、或后置处理器提取的变量是否正确赋值时，添加它并在“查看结果树”中观察，能极大提升排错效率。

#### **边界提取器 \(Boundary Extractor\)**

- 功能：通过设置“左边界”和“右边界”来提取中间的文本。

- 核心场景：当提取规则非常简单且固定时（例如提取 `<title>首页</title>` 中的“首页”），它比写复杂的正则表达式更简单、执行效率更高。

- 关键配置：

    - 名称（Name）：给这个提取器起个名字，比如“提取订单 ID”。

    - 要检查的响应字段（Field to check）：默认是 `Main sample only`（仅主样本），通常保持默认即可。如果是要提取子请求（如重定向）的数据，可以调整。

    - 左边界（Left boundary）：目标数据左边紧挨着的固定文本。

    - 右边界（Right boundary）：目标数据右边紧挨着的固定文本。

    - 匹配数字（Match No\.）：

        - 填 `0` 或留空：随机提取一个符合条件的值。

        - 填 `1`：提取第 1 个匹配到的值。

        - 填 `-1`：提取所有匹配到的值，保存为数组（如 `var_1`, `var_2`\.\.\.）。

    - 缺省值（Default Value）：如果没提取到数据（比如服务器报错，或者左右边界没对上），变量会被赋予这个默认值。通常建议填一个明显的错误提示，如 `extract_fail`，方便后续通过断言快速发现关联失败。

### **8\. 断言 \(Assertion\)**

> **用来检查服务器返回的结果是否符合预期（比如检查响应码是不是 200，或者返回的 JSON 里是否包含“成功”字样）。**
> 
> 

#### **响应断言**

这是最基础的断言，通过匹配响应的文本内容来判断。

- **核心配置：**

    - Apply to \(应用范围\)：`Main sample only` \(主请求\)。

    - Test Field \(测试字段\)：选 `Text Response` \(响应文本\)。如 `响应文本`（默认）、`响应代码`（如 200）、`响应消息`（如 OK）。

    - Pattern Matching Rules \(匹配规则\)：

        - `包括 (Contains)`：响应内容包含指定字符串即可（支持正则）。

        - `匹配 (Matches)`：响应内容必须完全等于指定字符串（支持正则）。

        - `等于 (Equals)`：响应内容完全等于指定字符串（不支持正则，区分大小写）。

        - `Substring`：响应内容包含指定字符串（不支持正则）。

    - Patterns to Test \(测试模式\)：填写你期望在响应里看到的文本，如 `"success":true`。

- **场景：快速验证一个静态页面或简单接口是否返回了预期内容。**

|界面参数|含义解释|配置示例|
|---|---|---|
|Apply to \(应用范围\)|指定断言的作用范围。`Main sample only` 仅作用于父节点取样器；`Main sample and sub-samples` 作用于父节点及子节点。|`Main sample only`|
|Field to Test \(测试字段\)|选择需要校验的目标字段。常用选项包括：`Text Response`（响应文本）、`Response Code`（状态码，如 200）、`Response Message`（响应信息，如 OK）、`Response Headers`（响应头）。|`Text Response`|
|Pattern Matching Rules \(匹配规则\)|定义比较方式。`Contains`（包括，支持正则）、`Matches`（匹配，支持正则）、`Equals`（相等，纯文本区分大小写）、`Substring`（字符串，纯文本部分匹配）。|`Contains`|
|Patterns to Test \(测试模式\)|填写预期的结果字符串或正则表达式。可添加多个模式，默认多个规则之间是“与\(AND\)”的关系，勾选“或者\(OR\)”则满足其一即可。|`success` 或 `"status":"success"`|
|Ignore Status \(忽略状态\)|勾选后，JMeter 会忽略返回的响应状态码（如 4xx/5xx 默认被视为失败），强制设置状态为成功后再进行断言判断。|视场景勾选|

#### **JSON 断言**

专门针对 JSON 格式响应，能精准定位字段进行校验。

- 核心配置：

    - JSON Path \(JSON 路径\)：`$.code`，代表取响应 JSON 里顶层的`code`字段。

    - Additionally assert value \(额外断言值\)：勾选后，填写期望值，如 `200`。

    - Expected Value：期望值。

    - 匹配规则：支持 `Equals`（等于）、`Contains`（包含）、`Matches`（正则匹配）等。

- 场景与技巧：

    - 验证业务成功：判断 `$.code` 是否等于 `0` 或 `200`。

    - 验证数据不为空：判断 `$.data.list.length()` 是否大于 `0`。这在查询接口中非常重要，能防止接口返回成功但数据为空的情况。

|界面参数|含义解释|配置示例|
|---|---|---|
|JSON Path|填写用于提取 JSON 节点的 JSON Path 表达式，类似于 XPath 之于 XML。|`$.status` 或 `$.data.userId`|
|Expected Value \(预期值\)|期望该 JSON 路径返回的具体值（支持字符串、数字、布尔值等）。|`success` 或 `200`|
|Validation \(验证模式\)|定义比较逻辑，常用的有 `==`（等于）、`!=`（不等于）等。|`==`|
|Additional assert value|勾选后，断言才会去校验 Expected Value 中的预期值；若不勾选，则仅验证该 JSON Path 节点是否存在。|勾选|
|Ignore case \(忽略大小写\)|勾选后，在进行字符串比较时将忽略大小写差异。|视场景勾选|

#### **大小断言**

不关注内容，只关注响应体的大小（Bytes）。

- 场景：

    - 防止异常大包：正常情况下响应包是 1KB，某次发布后变成了 10MB（序列化错误或逻辑 bug）。设置断言 `Size < 2048` \(2KB\)，能立即捕获这种性能灾难。

    - 检测空白响应：设置 `Size > 0`，防止接口返回 200 但内容是空白的。

|界面参数|含义解释|配置示例|
|---|---|---|
|Size to Assert \(预期大小\)|填写期望的响应数据字节数，并可选择比较类型（等于、大于、小于、不等于等）。|`1024` \(选择等于\)|
|Apply to / Response Field|指定要验证的数据部分，通常选择 `Full response`（完整响应体）或 `Response Headers`（响应头）。|`Full response`|

#### **JSR223 断言**

- 高级场景：

    - 复杂业务逻辑验证：比如断言 `响应里订单总额` 等于 `请求里的单价 x 数量`。

    - 响应数据验签：拿到响应体，用预设公钥进行验签，校验通过才算成功。

- 代码示例 \(验证计算逻辑\)：

```Groovy
*import groovy.json.JsonSlurper
// 1. 获取上一个请求发送的body (需要通过前置处理器先存好)
def requestPrice = vars.get("req_price") as double
def requestQty = vars.get("req_qty") as int
// 2. 解析响应
def json = new JsonSlurper().parse(prev.getResponseData())
def responseTotal = json.data.totalAmount as double

// 3. 核心断言逻辑
if ( (requestPrice * requestQty - responseTotal).abs() > 0.001 ) {
    AssertionResult.setFailure(true)
    AssertionResult.setFailureMessage("金额不匹配：期望${requestPrice * requestQty}，实际${responseTotal}")
**}*
```

#### **持续时间断言 \(Duration Assertion\)**

- 功能：验证接口的响应时间是否超过了设定的阈值（单位：毫秒）。

- 使用场景：在性能测试中，除了要求接口功能正确，还要求其响应速度达标。例如，要求核心接口的响应时间必须小于 500ms，超过即视为性能不达标。

- Duration in milliseconds：设定允许的最大响应时间阈值（单位：毫秒）。如果请求耗时超过此值，无论响应内容如何，均判定为失败。（`500` \(即要求响应时间 ≤ 500ms\)）

### **9\. 监听器 \(Listener\)**

> **负责收集测试数据，并以表格、树状图或图表的形式展示出来，比如“查看结果树”可以用来调试，“聚合报告”可以看整体的吞吐量和响应时间。****图形界面下的监听器非常耗费内存和 CPU****。**
> 
> 

#### **查看结果树 \(View Results Tree\)**

- 功能：显示每个请求的详细细节，包括请求头、请求体、响应数据以及断言结果。

- 使用场景：脚本调试阶段的神器。用于排查脚本编写错误、检查接口关联是否成功、验证断言是否生效。

- ⚠️ 避坑指南：在正式进行高并发压测时，务必禁用或移除该监听器。因为它会消耗极大的内存和 I/O 资源，严重影响 JMeter 本身的性能，导致压测结果失真。

#### **聚合报告 \(Aggregate Report\)**

- 功能：以表格形式汇总展示核心性能指标，是性能测试报告中最常引用的数据源。

- 核心指标：

    - Samples：发出的请求总数。

    - Average：平均响应时间。

    - 90% Line / 95% Line / 99% Line（百分位响应时间）：90% 或 95% 的请求响应时间低于该值（比平均值更能反映真实用户体验），这些尾部延迟指标比平均值更贴近真实用户体验。。

    - Error %：错误率。

    - Throughput：吞吐量（默认单位为请求数/秒，即 TPS/QPS）。

    - Received / Sent KB/sec（接收/发送速率）：每秒从服务器端接收或向服务器发送的数据量（千字节）。

- 使用场景：测试结束后，查看整体性能表现和瓶颈。

#### **响应时间图 \(Response Time Graph\) / 图形结果 \(Graph Results\)**

- 功能：以折线图的形式动态展示响应时间随时间的变化趋势。

- 使用场景：直观地观察系统在压测过程中，响应时间是否出现剧烈波动或逐渐攀升（可能存在内存泄漏或资源耗尽）。

#### **汇总报告 \(Summary Report\)**

- 功能：与聚合报告类似，但提供了更精简的汇总数据，且支持实时刷新。

- 使用场景：在长时间稳定性测试中，用于快速查看当前的整体概况。

#### **进阶插件监听器 \(需安装 JMeter Plugins\)**

- **PerfMon Metrics Collector（服务器性能监控数据采集器）**

    - 核心作用：在压测过程中，实时采集并展示被测服务器的各项硬件资源使用情况（如 CPU、内存、磁盘 I/O、网络带宽等），帮助快速定位系统瓶颈。

    - 核心参数详解：

        - Add Row：点击添加监控指标行，一行选择一种监控项。

        - Metric：选择要监控的具体指标（如 CPU Usage, Memory, Disk I/O 等）。

        - Host：被测服务器的 IP 地址。

        - Port：通信端口，默认使用 4444 端口（需在服务器端启动 ServerAgent 并保持一致）。

        - Params：附加参数，例如监控特定 CPU 核心或特定磁盘分区。

- **jp@gc \- Transactions per Second（每秒事务数 TPS 监控）**

    - 核心作用：在测试执行过程中，动态绘制 TPS 随时间变化的折线图，实时展示每秒事务数（TPS）的变化曲线，直观反映系统的整体处理能力和稳定性趋势。

    - 核心参数详解：

        - Sampler label selection：支持按取样器名称（Label）进行过滤，可使用正则表达式仅展示特定接口的 TPS 曲线。

        - Interval \(ms\)：X 轴的时间刻度间隔，默认通常为 1000ms（每秒更新一次）。

        - Graph size / X Axis / Y Axis：用于自定义图表的尺寸、横坐标日期格式及纵坐标最大值等显示样式。

- **jp@gc \- Response Times Over Time（响应时间趋势监控）**

    - 核心作用：实时监控每个请求的响应时间随时间变化的曲线，用于观察压测过程中是否存在性能衰减或瞬时峰值。

    - 核心参数详解：

        - Line settings：定义响应时间折线的宽度与颜色。

        - Scale maximum value：纵坐标（响应时间）的最大刻度值，防止个别极端长尾请求导致正常曲线被压缩。

        - Sampler label selection：同样支持通过正则表达式过滤特定接口的响应时间数据。

- **jp@gc \- Active Threads Over Time（活动线程数趋势）**

    - 核心作用：展示不同时间段内实际处于活动状态的用户数量，实时展示当前活跃线程数（并发用户数）的变化。

    - 适用场景：常与阶梯式加压线程组配合使用，用于验证压测脚本是否按照预期的阶梯曲线（如爬坡、稳态、降压）执行。

- **后端监听器（Backend Listener）**

    - 核心作用：生产级压测必备。它是一个异步侦听器，能够将 JMeter 的实时测试指标推送到时序数据库中，再结合 Grafana 生成极具视觉冲击力的全链路监控大屏。

    - 核心参数详解：

        - Backend Listener implementation：选择推送的实现类，常用 `InfluxdbBackendListenerClient` 或 `GraphiteBackendListenerClient`。

        - influxdbUrl：InfluxDB 数据库的写入地址（例如：`http://influxHost:8086/write?db=jmeter`）。

        - application：被测试的应用名称，作为标签存储，便于在 Grafana 中区分不同项目。

        - summaryOnly：设为 `true` 时仅输出请求的集合汇总数据；设为 `false` 时输出每条数据的详情报告。

        - samplersRegex：正则表达式，用于匹配需要发送到后端的样本名称（默认匹配所有）。

        - percentiles：发送到后端的百分位响应时间，多个值用分号分割（默认 `90;95;99`）。

        - Async Queue size：异步队列大小，默认为 5000，除非有特定性能问题否则不建议修改。

- **JSR223 监听器**

    - 核心作用：提供极大的灵活性，允许测试人员使用 Groovy、Beanshell 等脚本语言，对测试过程中的数据进行自定义处理、逻辑判断或生成定制化报告。

    - 核心参数详解：

        - Language：下拉选择脚本语言，强烈推荐选择 `Groovy`（执行性能高且功能丰富）。

        - Parameters：向脚本传递外部参数，脚本内可通过 `Parameters` 或 `args` 获取。

        - Script file / Script：可直接在界面编写脚本，或指定外部脚本文件路径（推荐长脚本使用外部文件以便版本管理）。

        - Cache compiled script if available：勾选后会缓存编译后的脚本，显著提高执行效率。

### **10\. 逻辑控制器 \(Logic Controllers\)**

#### **IF 控制器（If Controller）**

- 核心作用：根据设定的条件判断是否执行其下的子节点请求，类似于编程语言中的 `if` 语句。

- 实战示例：密码错误锁定逻辑。
在登录场景中，当用户连续输入密码错误 3 次后，账户会被锁定。可以通过定义全局变量（如 `${error_count}`），结合 `__jexl3` 函数（例如 \{\_\_jexl3\(\{error\_count\} \>= 3,\)\}）作为 IF 控制器的条件。只有当条件为真（错误次数大于等于 3）时，才会执行下方的“获取锁定提示”请求。

|界面参数|含义解释|配置示例|
|---|---|---|
|Expression \(must evaluate to true or false\)|条件表达式，结果必须为 true 或 false。推荐使用 `__jexl3` 或 `__groovy` 函数。|`${__jexl3(${error_count} >= 3,)}`|
|Interpret Condition as Variable Expression?|默认勾选。将条件解释为变量表达式。|保持勾选|
|Evaluate for all children?|是否对每个子项都评估条件。勾选表示每个子节点执行前都会重新判断；不勾选则只在控制器入口处判断一次。|视业务而定（默认不勾选）|

#### **循环控制器（Loop Controller）**

- 核心作用：指定其子节点下的请求重复执行的次数，或者设置为“永远（Infinite）”直到测试结束。

- 实战示例：批量数据提交。
如果线程组循环 1 次，但需要模拟用户连续提交 5 次表单，可以在 HTTP 请求外包裹一个 Loop Controller，将循环次数设置为 5。最终该请求将执行 1 × 5 = 5 次。

|界面参数|含义解释|配置示例|
|---|---|---|
|Loop Count|循环次数。可填写具体数字，或勾选 Infinite（永远循环）。|`5` 或勾选 `Infinite`|

#### **ForEach 控制器（ForEach Controller）**

- 核心作用：遍历读取具有相同前缀的变量列表，每次循环读取一个不同的变量值，通常配合正则提取器或 JSON 提取器使用。

- 实战示例：批量查询商品详情。
前置接口返回了多个商品 ID（如 `item_id_1`, `item_id_2`, `item_id_3`）。在 ForEach 控制器中设置输入变量前缀为 `item_id`，输出变量名为 `current_id`。控制器下的“查询商品详情”请求即可通过引用 `${current_id}` 逐个遍历查询。

|界面参数|含义解释|配置示例|
|---|---|---|
|Input variable prefix|需要遍历的输入变量前缀（如提取器生成的 `item_id_1`, `item_id_2`）。|`item_id`|
|Start index for loop \(exclusive\)|循环起始下标（不包含）。不填默认为 1。|`0`（实际从第 1 个元素开始）|
|End index for loop \(inclusive\)|循环结束下标（包含）。不填则遍历到最后一个。|留空或 `5`|
|Output variable name|输出变量名。遍历到的值会赋给该变量，供后续请求使用 `${变量名}`。|`current_id`|
|Add "\_" before number?|输入变量名称中是否使用 `_` 进行间隔。若变量为 `data_1` 则勾选，若为 `data1` 则不勾选。|勾选|

#### **Switch 控制器（Switch Controller）**

- 核心作用：根据“Switch Value”的值（数字索引或字符串名称）精准选择执行哪一个子节点，类似于编程语言中的 `switch-case`。

- 实战示例：多角色权限测试。
如果测试账号分为管理员（admin）和普通用户（user），可以通过前置脚本将角色存入变量 `${role}`。Switch Value 设置为 `${role}`，下方分别放置名为 `admin` 和 `user` 的取样器。JMeter 会根据当前登录用户的角色，精准匹配并执行对应的业务请求。

|界面参数|含义解释|配置示例|
|---|---|---|
|Switch Value|切换值。可填数字（执行第 N\+1 个节点）、字符串（全匹配节点名称）或变量。|`${role}` 或 `admin`|

#### **While 控制器（While Controller）**

- 核心作用：只要设定的条件为真（True），就会持续循环执行其下的子节点，直到条件变为 False 或请求失败才退出。

- 实战示例：异步任务结果轮询。
提交一个耗时较长的后台导出任务后，接口会返回一个任务 ID。在 While 控制器中设置条件为 ${__jexl3("$`{task_status}" != "completed",)}`，下方放置“查询任务状态”的请求。只要任务未完成，就会一直循环查询，直到状态变更为 `completed` 自动跳出循环。

|界面参数|含义解释|配置示例|
|---|---|---|
|Condition|循环条件。可填 `LAST`（上一个请求失败则退出），留空（失败退出），或 `__jexl3` 表达式。|`${__jexl3("${task_status}" != "completed",)}`|

#### **事务控制器（Transaction Controller）**

- 核心作用：将多个请求合并为一个“事务”，用于统计这一组请求的整体响应时间，常用于关键业务流程的性能分析。

- 实战示例：电商下单核心链路耗时统计。
将“搜索商品 → 加入购物车 → 提交订单 → 支付”这 4 个请求放入事务控制器中，并勾选 `Generate parent sample`。在聚合报告中，这 4 个请求会被折叠为一个父级事务，直接展示该完整业务链路的总耗时。

|界面参数|含义解释|配置示例|
|---|---|---|
|Generate parent sample|勾选后，在聚合报告中将所有子请求合并为一个父级事务展示；不勾选则分别展示。|勾选|
|Include duration of timer and pre\-post processors in generated sample|是否在生成的样本中包含定时器、前置/后置处理器的耗时。默认不勾选（仅统计请求本身）。|不勾选|

#### **吞吐量控制器（Throughput Controller）**

- 核心作用：按比例或固定次数控制其下子节点的执行频率，常用于模拟真实流量中不同业务的操作占比。

- 实战示例：模拟真实用户行为分布。
在电商场景中，真实用户的“浏览商品”与“下单购买”比例约为 7:3。可以添加两个吞吐量控制器，一个设置为 `Percent Executions: 70%` 放置浏览请求，另一个设置为 `30%` 放置下单请求，从而精准还原生产环境的真实负载模型。

|界面参数|含义解释|配置示例|
|---|---|---|
|Percent Executions / Total Executions|选择按“百分比”还是“总执行次数”来控制。|勾选 `Percent Executions`|
|吞吐量值|填写对应的百分比（1\-100）或固定执行次数。|`30` \(代表 30%\)|
|Per User|勾选时，百分比基于“单线程循环次数”，次数基于“单线程”；不勾选则基于全局。|视场景勾选|

#### **交替控制器（Interleave Controller）**

- 核心作用：在每次循环中，仅执行其下的一个子节点，下次循环执行下一个，依次交替。

- 实战示例：多页面轮询访问。
模拟用户在首页、分类页、个人中心之间切换。将这三个页面的请求放入交替控制器，线程组循环 3 次，则执行顺序严格为：首页 → 分类页 → 个人中心 → 首页 → 分类页 → 个人中心。

|界面参数|含义解释|配置示例|
|---|---|---|
|Ignore sub\-controller blocks|忽略子控制器。勾选后，无视其下的其他逻辑控制器，将每个取样器作为独立节点交替。|视嵌套场景而定|
|Interleave across threads|跨线程交替。勾选后，交替顺序会应用到所有线程和循环中迭代。|默认不勾选|

#### **仅一次控制器（Once Only Controller）**

- 核心作用：确保其下的子节点在整个线程的生命周期内仅执行一次，不受线程组循环次数的影响。

- 实战示例：用户登录初始化。
如果线程组需要循环 100 次来测试业务，但登录接口只需在测试开始时调用一次以获取 Token，将登录请求放入“仅一次控制器”即可。无论后续循环多少次，该请求都只会在第一次迭代时执行。

#### **随机控制器（Random Controller）**

- 核心作用：在每次迭代中，从其下的子节点中随机挑选一个执行。

- 实战示例：首页随机模块点击。
模拟真实用户打开 App 后，随机浏览推荐、热门或最新列表。将这三个列表的请求放入随机控制器，每次循环都会随机触发其中一个请求，增加测试的不可预测性和真实性。

### **🤖 生成测试报告**

1. 命令自动生成：压测命令直接带 `-e -o` 参数。

```Shell
*jmeter -n -t test.jmx -l result.jtl -e -o ./ReportFolder*
```

2. 事后手动生成：先跑压测拿到 `result.jtl`，再单独执行生成命令。

```Shell
*jmeter -g result.jtl -o ./ReportFolder*
```

- 读报告的关键图表：

    - Over Time \(时间趋势图\)：查看响应时间、TPS 等指标随时间的变化曲线。

    - Throughput \(吞吐量\)：直接看系统的处理能力上限。

    - Response Times Percentiles \(百分位响应时间\)：重点关注 90% Line、95% Line、99% Line，这比平均响应时间更能反映多数用户的真实体验。

> **总结一下断言和监听器的核心原则：**
> 
> 

断言要精准有效，用 JSON 断言验证业务，用持续时间断言设红线。

监听器要分场景，调试用“查看结果树”，压测用“简单数据写入器”输出数据，最终分析靠 HTML 报告。图形界面下的饼图、曲线图，一概不要用于正式压测。

|组件分类|组件名称|核心作用|使用要点|
|---|---|---|---|
|配置元件<br>|HTTP 请求默认值|统一管理公共的服务器地址和端口|当你有多个接口时，只需在这里填一次 IP，所有取样器自动继承，维护超方便。|
||用户定义的变量|定义全局常量，如测试环境 URL、版本号|一处定义（`${host}`），全局引用。环境切换时只改这一个值即可。|
||CSV 数据文件设置|实现参数化，用文件里的多组数据驱动测试|模拟多用户登录的核心技术。让 JMeter 逐行读取 CSV 文件中的用户名、密码进行测试。|
||HTTP 信息头管理器|设置请求头<br>|接口测试必用，用于设置`Content-Type: application/json`或认证 Token 等。|
||HTTP Cookie 管理器|自动管理 Cookie，维持会话状态|只要加上这个组件，JMeter 就会自动处理登录后的 Session ID，无需手动提取。|
|前置/后置处理器|JSON 提取器|从上个请求的 JSON 响应中提取数据给下个请求用|关联操作的核心。例如：从"登录"接口提取 Token，传给"查询余额"接口。|
|定时器|同步定时器 \(Synchronizing Timer\)|设定集合点，让虚拟用户"等"到一定数量后瞬间发力|用于制造绝对的并发压力。设置成和线程数一致，所有用户准备好后同时发请求。|
|断言|响应断言|校验返回结果是否符合预期|接口响应 200 不代表业务成功。用断言检查返回的 JSON 里是否包含`"success": true`才是真正的通过。|
|逻辑控制器|事务控制器|把多个接口（如登录、下单、支付）合并成一个事务|统计完整业务流程的总耗时，而非单个接口的时间。|

## 🚀 基本流程

当你安装好 JDK 并解压启动 JMeter 后，可以按照以下标准流程创建一个最基础的接口测试：

> **第一步：创建测试计划与线程组**
> 
> 

右键点击“测试计划” \-\> 添加 \-\> 线程\(用户\) \-\> 线程组。设置线程数为 1，Ramp\-Up 时间为 1，循环次数为 1（先跑通流程）。

> **第二步：添加 HTTP 请求（取样器）**
> 
> 

右键点击“线程组” \-\> 添加 \-\> 取样器 \-\> HTTP 请求。

- 填写协议（http/https）、服务器名称或 IP、端口号。

- 填写请求方法（GET/POST）和接口的路径。

- 如果是 POST 请求，可以在“消息体数据”中填入 JSON 参数。

> **第三步：添加监听器（查看结果）**
> 
> 

右键点击“线程组” \-\> 添加 \-\> 监听器 \-\> 查看结果树。这个组件能最直观地展示你发出的请求和服务器返回的响应，非常适合脚本调试。

> **第四步：添加断言（可选但推荐）**
> 
> 

右键点击“HTTP 请求” \-\> 添加 \-\> 断言 \-\> 响应断言。配置你要检查的文本（比如接口返回的 success: true），确保接口不仅通了，而且业务逻辑也是对的。

> **第五步：运行并分析**
> 
> 

点击工具栏上的绿色“启动”三角形按钮。点击左侧的“查看结果树”，如果图标是绿色的 ✔，说明测试通过；如果是红色的 ✘，则可以点击该条目查看具体的请求和响应数据来排查问题。

**🎈 脚本调试阶段**

在图形界面下执行，核心是验证脚本正确性。

- 监听器选择：务必添加查看结果树。能直观看到 Request Body、Response Body 是否乱码，断言是否通过。

- 调试技巧：仅设置线程数 1，循环 1 次，确保脚本跑通了再发压。

**✨ 负载执行阶段**

一定要切换为命令行模式，GUI 模式资源消耗大，会严重影响结果准确性。

非 GUI 运行命令：

```Shell
*jmeter -n -t [脚本名.jmx] -l [结果文件.jtl] -e -o [报告输出目录]*
```

- `-n`：无图形模式

- `-t`：指定脚本

- `-l`：生成测试结果文件

- `-e -o`：执行完毕后直接生成 HTML 可视化报告

## 📈 监控服务器

> ***PerfMon \(Server Performance Monitoring\)***
> 
> 

**核心原理：**

1. 服务端代理 \(ServerAgent\)：一个轻量级的 Java 程序，部署在被测服务器上，负责实时采集系统资源数据。

2. JMeter 监听器 \(PerfMon Metrics Collector\)：安装在你的 JMeter 客户端，负责向 ServerAgent 拉取数据并绘制成可视化图表。

**🛠️ 第一步：安装 PerfMon 插件到 JMeter 客户端**

推荐使用 JMeter 自带的插件管理器进行安装：

1. 打开 JMeter，点击顶部菜单栏的 `Options`（选项） \-\> `Plugins Manager`（插件管理器）。

2. 切换到 `Available Plugins`（可用插件）标签页。

3. 在搜索框输入 `PerfMon`，找到 PerfMon \(Servers Performance Monitoring\) 并勾选。

4. 点击右下角的 `Apply Changes and Restart JMeter`，等待下载完成并自动重启即可。

*\(注：如果你的环境无法联网，也可以手动下载 **`JMeterPlugins-Standard`** 插件包，将其中的 **`.jar`** 文件复制到 JMeter 安装目录下的 **`/lib/ext/`** 文件夹中，然后重启 JMeter。\)*

---

**🖥️ 第二步：在被测服务器上部署 ServerAgent**

你需要将监控代理程序放到你要压测的目标服务器（如 Web 服务器、数据库服务器）上：

1. 下载 ServerAgent 压缩包（例如 `ServerAgent-2.2.3.zip`），上传并解压到目标服务器的任意目录下。

2. 根据服务器操作系统启动 Agent：

    - Linux 系统：进入解压目录，执行命令 `./startAgent.sh`

    - Windows 系统：双击运行 `startAgent.bat`

3. 启动成功后，控制台会提示默认监听端口为 4444。请确保服务器的防火墙已放行该端口（TCP/UDP 4444），否则 JMeter 无法连接。

---

**📊 第三步：在 JMeter 测试计划中配置监控**

1. 在你的线程组（Thread Group）下右键，选择 `添加` \-\> `监听器` \-\> `jp@gc - PerfMon Metrics Collector`。

2. 在打开的界面下方，点击 `Add Row`（添加行）来配置要监控的服务器和指标：

    - Host/IP：填写被测服务器的 IP 地址。

    - Port：填写 ServerAgent 的端口，默认为 `4444`。

    - Metric to collect：选择需要监控的具体指标，常用的有 `CPU`、`Memory`（内存）、`Disk I/O`（磁盘读写）、`Network I/O`（网络流量）等。

3. 你可以通过多次点击 `Add Row`，同时监控多台服务器或多个不同的指标。

---

**🚀 第四步：运行压测并关联分析**

配置完成后，直接像往常一样点击绿色按钮启动 JMeter 压测。此时，在 `PerfMon Metrics Collector` 的图表区域，你就能实时看到服务器各项资源的消耗曲线了。

---

**💡 最佳实践与分析技巧：**

- 关联分析瓶颈：性能测试的核心在于“找瓶颈”。你可以将 JMeter 原生的“聚合报告”或“TPS 曲线图”与此处的资源监控图放在一起对比。例如，当发现 TPS 不再上升且响应时间飙升时，观察同一时间点的 CPU 是否达到 100%，或者内存是否耗尽，从而精准定位是计算瓶颈还是内存泄漏。

- 轻装上阵：在正式的高并发压测中，建议禁用“查看结果树”等消耗资源的监听器，但保留 `PerfMon Metrics Collector`，因为它的开销极小，且提供的数据对性能分析至关重要。

## 🏀 实战示例

### **测试场景一**：创建商品订单

> **业务流程为：先查询商品详情（GET），获取有效商品后创建订单（POST JSON）**
> 
> 

**步骤 1：创建测试计划与线程组**

1. 打开 JMeter，右键「测试计划」→ 添加 → 线程组。

2. 配置线程组参数：

    - 线程数：`50`

    - Ramp\-Up 时间：`10`

    - 勾选“调度器”，持续时间（秒）：`300`

**步骤 2：添加配置元件（简化配置）**

1. 右键线程组 → 添加 → 配置元件 → HTTP 请求默认值。

    - 协议：`http`，服务器名称：`192.168.1.100`，端口号：`8080`，编码：`UTF-8`。

2. 右键线程组 → 添加 → 配置元件 → HTTP 信息头管理器。

    - 添加一行：名称 `Content-Type`，值 `application/json`。

**步骤 3：编写第一个接口（查询商品详情）**

1. 右键线程组 → 添加 → 取样器 → HTTP 请求，命名为“查询商品详情”。

    - 方法：`GET`

    - 路径：`/api/goods/detail`

    - 参数：添加 `goods_id`，值设为 `10086`（或通过 CSV 参数化）。

2. 添加断言：右键该请求 → 添加 → 断言 → JSON 断言。

    - JSON 路径：`$.code`，期望值：`200`。

3. 提取商品库存（为下单做准备）：右键该请求 → 添加 → 后置处理器 → JSON 提取器。

    - 变量名：`stock_num`

    - JSON 路径表达式：`$.data.stock`。

**步骤 4：编写第二个接口（创建订单）**

1. 右键线程组 → 添加 → 取样器 → HTTP 请求，命名为“创建订单”。

    - 方法：`POST`

    - 路径：`/api/order/create`

    - 切换到“消息体数据 \(Body Data\)”，填入 JSON：

    ```Plain Text
    {
      "goodsId": "10086",
      "buyNum": 1,
      "stock": "${stock_num}" 
    }
    ```

    - *\(注：**`${stock_num}`** 即为从上一个接口提取的变量\)*

2. 添加断言：右键该请求 → 添加 → 断言 → 响应断言。

    - 测试字段：响应文本，模式匹配规则：包括，要测试的模式：`"success":true`。

**步骤 5：添加监听器并运行**

1. 右键线程组 → 添加 → 监听器 → 查看结果树（调试用）。

2. 右键线程组 → 添加 → 监听器 → 聚合报告（看性能指标）。

3. 点击工具栏的绿色启动按钮开始测试。

### **测试场景二**：电商登录接口

假设我们有一个电商登录接口：

- URL: `https://api.example.com/v1/login`

- Method: POST \(JSON\)

- Body: `{"username": "user${__Random(1,10000)}", "password": "123456"}`

- 目标: 500 并发用户，持续 10 分钟，TPS 目标 \> 1000，P99 响应时间 \< 200ms。

---

> **脚本构建与参数化 \(核心步骤\)**
> 
> 

**A\. 线程组设置 \(Thread Group\)**

- Number of Threads \(users\): 500 \(模拟 500 个并发用户\)

- Ramp\-Up period \(seconds\): 50 \(意味着每秒启动 10 个线程，平滑加压，避免瞬间击穿服务端\)

- Loop Count: 勾选 "Forever" \(永远\)，并配合 Scheduler 设置持续时间为 600 秒 \(10 分钟\)。

    - *注：* 若使用 Concurrency Thread Group 插件，可设置 Target Concurrency 为 500，Ramp\-Up 为 50s，Hold 为 600s，更为直观。

---

**B\. 参数化 \(CSV Data Set Config\)**
为了避免所有请求都使用同一个账号导致缓存命中或锁竞争，我们需要准备一个 `users.csv` 文件，包含 10000 个测试账号。

- Filename: `users.csv`

- Variable Names: `csv_user`

- Sharing Mode: All threads

- Recycle on EOF: True

- Stop thread on EOF: False

- HTTP Request Body: `{"username": "${csv_user}", "password": "123456"}`

---

**C\. 关联与动态值 \(Extractors\)**

如果登录后返回 Token 并用于后续请求，需使用 JSON Extractor：

- Names of created variables: `token`

- JSON Path expressions: `$.data.token`

- Default Values: `NO_TOKEN`

- 后续请求的 Header Manager 中添加：`Authorization: Bearer ${token}`

---

**D\. 思考时间 \(Think Time\)**

真实用户不会每秒点击 10 次。使用 Constant Throughput Timer 或 Uniform Random Timer：

- 例如：Constant Throughput Timer 设置 Target throughput 为 `60000.0` \(即每分钟 1000 个请求，分配到每个线程\)。

---

> **执行压测 \(Non\-GUI 模式\)**
> 
> 

绝对不要在 GUI 模式下运行大规模压测！ GUI 会消耗大量 CPU 和内存，导致测试机本身成为瓶颈。

```Shell
# -n: Non-GUI 模式
# -t: 测试计划文件
# -l: 结果日志文件 (.jtl)
# -e: 生成 HTML 报告
# -o: 报告输出目录
# -Jthreads=500: 通过命令行参数覆盖线程数
# -Jrampup=50: 通过命令行参数覆盖 Ramp-Up

jmeter -n -t login_test.jmx -l result.jtl -e -o ./report_20260823 \
       -Jthreads=500 -Jrampup=50 -Jduration=600
```

---

> **结果分析 \(HTML Dashboard Report\)**
> 
>

### **测试场景五**：阶梯式加压测试

阶梯式加压测试（Step Load Test）是模拟用户量逐渐增加的压测方式，能够清晰观察系统在不同负载下的表现。它遵循 “缓起步，快结束” 的原则，通过逐步、平稳地增加并发用户数来找到系统的性能瓶颈。核心是模拟真实场景中用户量缓慢上升的过程，避免瞬时高并发导致系统崩溃或数据失真。

与普通线程组“瞬间全量发起请求”的暴力测试相比，阶梯加压能清晰观察到：

- 系统性能拐点：在哪个并发级别，响应时间开始显著上升、错误率开始出现

- 资源消耗趋势：CPU、内存、IO 等系统资源随压力增加的变化

- 系统弹性与稳定性：压力逐步增加和维持阶段，系统是否保持稳定

|插件|特点|推荐度|
|---|---|---|
|Concurrency Thread Group|精确控制并发用户数，智能管理线程，自动增减以维持目标并发|⭐⭐⭐⭐⭐ 推荐|
|Ultimate Thread Group|支持复杂的线程调度计划，可配置多段阶梯|⭐⭐⭐⭐ 推荐|
|Stepping Thread Group|经典插件，功能完整但已标记为 deprecated|⭐⭐⭐ 可用|

#### **1\.**  **使用 Concurrency Thread Group（推荐）**

场景设计：模拟一个电商系统，在 10 分钟内逐步加压到 200 并发，保持 30 分钟，观察系统表现。

**配置步骤：**

1. 添加线程组：右键 Test Plan → Add → Threads \(Users\) → bzm \- Concurrency Thread Group

2. 核心参数配置：

|参数|含义|示例值|
|---|---|---|
|Target Concurrency|目标并发用户数|200|
|Ramp Up Time|从 0 达到目标并发的时间|10（单位选 Min）|
|Ramp\-Up Steps Count|分多少步达到目标（阶梯次数）|10|
|Hold Target Rate Time|保持目标并发的时间|30（单位选 Min）|

**计算：Steps Count = 10，意味着每 1 分钟增加 200/10 = 20 个用户。Steps Count 值越大，加压越平滑。**

3. 添加 HTTP 请求：在线程组下添加 HTTP Request，配置目标接口的 URL、方法、参数等

4. 添加监听器：

    - `jp@gc - Active Threads Over Time`：实时监控并发数变化

    - `jp@gc - Response Times Over Time`：响应时间趋势

    - `jp@gc - Transactions per Second`：TPS 变化趋势

    - `Aggregate Report`：汇总统计数据

配置示例（100 用户，1 分钟内启动 → 保持 2 分钟 → 30 秒释放）：

|参数|值|说明|
|---|---|---|

|Shutdown Time|30|30 秒内释放|

- Ultimate Thread Group 支持在 Threads Schedule 中添加多行，实现多段阶梯组合

#### **5\.**  **测试结果分析与瓶颈定位**

**5\.1 核心分析维度**

性能瓶颈分析应围绕 四条主线 展开：

- 吞吐量（TPS/QPS）

- 响应时间（RT）

- 错误率（Error%）

- 资源利用率（CPU、内存、磁盘 IO、网络）

**5\.2 关键指标解读**

**TPS（吞吐量）曲线**

TPS 是判断性能瓶颈最核心的指标：

- TPS 持续上升：系统还有余量，未到瓶颈

- TPS 增长停滞：达到当前配置下的处理上限

- TPS 开始下降：已过性能拐点，系统开始过载

> **拐点判断：随着负载升高，TPS 逐渐达到一个高点然后开始持平甚至下降，这个最高拐点就是性能瓶颈点。**
> 
> 

**响应时间曲线**

- 响应时间平稳：系统处理能力充足

- 响应时间缓慢上升：系统资源开始紧张

- 响应时间陡增：已过拐点，系统严重过载

> **重点关注 90 分位（90% Line） 和 99 分位（99% Line）。若 99 分位响应时间超过 2 秒，说明尾部用户体验极差。**
> 
> 

**错误率**

- 错误率 \< 1%：正常范围

- 错误率 \> 5%：系统已出现严重问题

> **必须低于业务可接受范围（如 0\.1%）。需分析错误类型，是超时、5xx 服务器错误还是 4xx 业务逻辑错误。**
> 
> 

**5\.3 瓶颈定位四步法**

当发现响应时间飙升、吞吐量下降或错误率上升时，可按以下步骤排查：

1. 观察业务指标曲线：在监控大盘上，观察核心业务（如下单成功率）是否从 100%开始下跌。一旦下跌，立刻查看对应时间点的响应时间曲线，定位是哪个服务开始超时。

2. 链路追踪定位：通过 SkyWalking 等链路追踪工具，找到耗时最长的请求链路，查看具体是哪个服务、哪个方法或哪条 SQL 执行缓慢。

3. 检查系统资源水位：

    - CPU/内存：是否某个服务的 CPU 被打满？是否存在频繁 GC 导致响应时间出现周期性尖峰？

    - 数据库：数据库 CPU/IO 等待是否很高？是否存在慢查询或死锁？

    - 连接池：Redis 或数据库连接池是否耗尽（如日志出现 "Too many connections"）？

4. 排查压测机自身瓶颈：如果服务端资源利用率正常，但响应时间依然异常偏高，需检查 JMeter 压测机本身。可能是 JVM 堆内存紧张引发频繁 GC、网络带宽饱和或单机压测能力达到上限。此时应优化 JVM 参数、关闭不必要的监听器，或采用分布式压测。

- **建立容量规划模型**

通过记录不同并发阶段（如 100、500、1000 并发）的 QPS、响应时间和资源水位，可以建立容量模型。例如，当并发从 1000 增至 1500 时，若响应时间急剧增加且错误率飙升，说明当前系统配置下的容量上限就在 1000 并发左右。据此可制定扩容阈值（如 TPS 达到上限 85%时触发自动扩容）或针对性优化瓶颈服务。

**5\.4 实战分析示例**

以下图为例（阶梯负载量 \+ 响应时间 \+ TPS 三合一视图）：

```Plain Text
TPS
  ↑    ╱────
  │   ╱  ↑
  │  ╱   │ TPS增长停滞区 → 瓶颈拐点
  │ ╱    ↓
  │╱─────→ 并发数
  │
  └─────────────────
```

**分析步骤：**

- 观察 TPS 变化：找到 TPS 从上升到停滞的转折点，此即为性能拐点区间

- 对比响应时间：在拐点处，响应时间是否出现明显上升

- 检查错误率：拐点附近是否有错误开始出现

- 定位拐点区间：例如，330 并发正常、360 并发异常，则拐点在\[330,360\]之间

**5\.5 监听器组合分析**

单一监听器难以全面分析，需要组合使用:

|监听器|作用|分析重点|
|---|---|---|
|Active Threads Over Time|查看实际并发数|确认阶梯是否按预期执行|
|Response Times Over Time|响应时间趋势|观察拐点出现时机|
|Transactions per Second|TPS 趋势|核心指标，判断瓶颈|
|Hits per Second|每秒请求数|与 TPS 对比，判断是否有请求丢失|
|PerfMon Metrics Collector|服务器资源监控|CPU/内存/磁盘 IO/网络|
|Aggregate Report|汇总统计|平均值、中位数、90%/95%/99%分位线|

**5\.5 系统化瓶颈排查流程**

当发现性能下降时，按以下顺序排查：

**第一层：检查 JMeter 压力机自身**

- 压力机的 CPU、内存是否饱和

- 网络带宽是否成为瓶颈

- 是否以非 GUI 模式运行（`jmeter -n -t test.jmx -l result.jtl`），避免 GUI 监听器消耗资源

- JVM 内存配置是否足够

**第二层：检查网络链路**

- 网络延迟和带宽

- 是否有丢包

**第三层：检查被测服务**

- Web/应用容器：线程池是否耗尽、连接数是否达到上限

- 数据库：连接池是否耗尽、慢查询、锁等待

- 缓存：命中率是否下降

- 外部依赖：第三方服务是否成为瓶颈

**第四层：检查系统资源**

- CPU：是否持续高于 80%

- 内存：是否有内存泄漏（持续上升不回落）

- 磁盘 IO：是否成为瓶颈

- GC：GC 频率是否过高

**5\.6 常见瓶颈案例**

> **案例 1：端口耗尽**
> 
> 

阶梯压测运行一段时间后请求报错，检查发现客户端端口耗尽。解决方法：关闭 Keep\-Alive 或调整操作系统端口范围。

> **案例 2：连接池耗尽**
> 
> 

TPS 在某个并发级别突然下降，检查应用服务器连接池配置，适当增大连接池大小。

> **案例 3：数据库慢查询**
> 
> 

响应时间随并发上升而急剧增加，检查数据库慢查询日志，优化 SQL 或增加索引。

> **案例 4：阶梯抖动过大**
> 
> 

阶梯加压过程中出现剧烈抖动，说明系统存在性能问题。需要检查是否有缓存失效、定时任务等周期性影响因素。

#### **6\.**  **总结与最佳实践**

1. 先小后大：先用小规模并发验证脚本逻辑，再逐步增加压力

2. 先探后精：先用 Stepping Thread Group 快速加压找到大概的性能拐点，再在拐点前选择一个负载水平（如拐点用户数的 80%）进行精细测试

3. 多维度监控：不仅看 JMeter 报告，还要配合服务器资源监控（PerfMon、Grafana\+Prometheus 等）

4. 闭环迭代：按“瓶颈定位 → 系统调优 → 再压测验证”的闭环迭代优化

5. 关注拐点区间：性能拐点不是单一数值，而是 TPS 稳定、响应时间可控、错误率\<1%的平衡区间

6. 严禁使用 GUI 模式：正式压测必须使用命令行（Non\-GUI）模式，GUI 模式会占用大量本地 CPU 和内存，导致压测结果不准确甚至 JMeter 崩溃。启动命令：`jmeter -n -t script.jmx -l result.jtl -e -o ./report`。

## 🧭 常用插件

### **各类线程组**

> **原生线程组**
> 
> 

1. **标准线程组（Thread Group）**

    - 核心特点：最基础的类型，支持配置线程数（虚拟用户数）、启动时间（Ramp\-Up）、循环次数和调度器。

    - 适用场景：适用于绝大多数的并发测试、基准测试和压力测试。它是生成负载的核心载体。

    - 配置逻辑：Ramp\-Up 时间代表启动所有线程的总耗时。例如，100 个线程设置 Ramp\-Up 为 10 秒，意味着每秒启动 10 个线程，平滑模拟用户进入。

2. **setUp 线程组（Setup Thread Group）**

    - 核心特点：具有最高执行优先级，在所有普通线程组之前执行，且全局仅运行 1 次（与线程数无关）。

    - 适用场景：用于测试前的初始化操作，如创建测试数据、预热 JVM、或执行登录获取全局 Token 等。

3. **tearDown 线程组（TearDown Thread Group）**

    - 核心特点：执行优先级最低，在所有普通线程组执行完毕后运行，同样仅运行 1 次。即使测试中途手动停止，该线程组仍会执行。

    - 适用场景：用于测试后的清理工作，如删除测试数据、关闭数据库连接、执行登出操作等。

> **插件线程组与阶梯式加压**
> 
> 

原生标准线程组虽然强大，但在模拟“逐步加压 → 稳定 → 逐步降压”等复杂真实流量模型时略显不足。此时需要借助第三方插件（如通过 JMeter Plugins Manager 安装的 Custom Thread Groups）来实现阶梯式加压。

阶梯式加压常用于负载测试（寻找系统性能拐点），通过梯度增加并发用户数，观察 TPS 和响应时间的变化，从而精准定位系统瓶颈。常用的阶梯式插件线程组包括：

1. **Stepping Thread Group（步进线程组）**

    - 核心逻辑：通过设定初始线程数、每次增加的线程数（Add）、增加的时间间隔（Every）以及满负载保持时间（Hold load），形成直观的阶梯状并发曲线。

    - 配置示例：测试开始后等待 10 秒，初始启动 10 个用户；之后每隔 60 秒增加 20 个用户（新增用户在 30 秒内平滑启动）；一直增加到 100 个用户后，保持压力运行 5 分钟；最后所有用户立即停止。

    |    界面参数|    含义解释|    配置示例（对应你的需求）|
    |---|---|---|
    |    This group will start|    当前负载最终要达到的最大并发用户总数。|    `100`|
    |    First, wait for|    测试开始后，启动第一个线程前需要等待的秒数。|    `10` \(等待 10 秒\)|
    |    Then start|    初始启动的并发用户数。|    `10` \(初始启动 10 个用户\)|
    |    Next, add|    每次阶梯需要增加的并发用户数。|    `20` \(每次增加 20 个用户\)|
    |    threads every|    每次增加线程的时间间隔（秒）。|    `60` \(每隔 60 秒加一次\)|
    |    using ramp\-up|    新增的这批用户在多少秒内平滑启动完毕。|    `30` \(新增的 20 个用户在 30 秒内启动\)|
    |    Then hold load for|    达到最大并发数后，持续保持该压力的运行时间（秒）。|    `300` \(保持 5 分钟\)|
    |    Finally, stop|    测试结束时，每次减少的并发用户数。|    `0` 或留空 \(表示不阶梯停止，直接结束\)|
    |    逻辑控制器|    事务控制器|    把多个接口（如登录、下单、支付）合并成一个事务|

2. **Ultimate Thread Group（终极线程组）**

    - 核心逻辑：允许定义任意复杂的线程生命周期，支持多阶段配置。每个阶段均可独立设置启动线程数、初始延迟、启动耗时、保持时间和停止耗时。

    - 适用场景：完美模拟大促开场、持续高峰、热度退散的全过程。例如：前 5 分钟每分钟增加 100 线程，达到 500 后保持 10 分钟，然后在 5 分钟内线性下降至 0。

    |    界面参数|    含义解释|    配置示例（大促场景）|
    |---|---|---|
    |    Start Threads Count|    当前阶段需要启动的并发用户数。|    阶段 1: `100`<br>    阶段 2: `500`<br>    阶段 3: `0`|
    |    Initial Delay \(sec\)|    当前阶段开始前的等待时间（秒），常用于阶段衔接。|    `0`|
    |    Startup Time \(sec\)|    从 0 增加到该阶段目标线程数的耗时（秒）。|    `300` \(5 分钟内加到 100\)<br>    `300` \(5 分钟内加到 500\)<br>    `300` \(5 分钟内减到 0\)|
    |    Hold Load For \(sec\)|    该阶段线程全部启动后，保持运行的持续时间（秒）。|    `600` \(保持 10 分钟\)|
    |    Shutdown Time \(sec\)|    当前阶段结束时，线程数降至 0 的耗时（秒）。|    `0` \(不降，直接进下一阶段\)|

3. **Concurrency Thread Group（并发线程组）**

    - 核心逻辑：更适合精确控制 TPS 而非固定线程数。它会根据实际吞吐量动态调整线程数，支持设置目标并发数、爬升时间、爬升步数（Ramp Up Steps）以及保持满负载的时间。

    - 配置示例：目标并发 200，总加压时长 1 分钟，分 5 个阶梯增加。效果为每分钟增加 40 个用户，阶梯状压力上升，达到目标后持续 2 分钟。

    |    界面参数|    含义解释|    配置示例（对应你的需求）|
    |---|---|---|
    |    Target Concurrency|    希望达到并维持的目标并发用户总数。|    `200`|
    |    Ramp Up Time \(sec\)|    从初始状态达到目标并发数所需的总爬升时间（秒）。|    `60` \(1 分钟内达到 200\)|
    |    Ramp\-Up Steps Count|    将总爬升时间分割为多少个阶梯（步数）。|    `5` \(分 5 个阶梯增加\)|
    |    Hold Target Rate Time \(sec\)|    达到目标并发后，持续保持该负载的运行时间（秒）。|    `120` \(持续 2 分钟\)|
    |    Thread Iterations Limit|    每个线程的循环次数限制（\-1 表示持续运行至压测结束）。|    `-1`|

> **阶梯式加压的结果分析关键点**
> 
> 

在使用阶梯式线程组进行压测时，可以通过以下指标寻找系统的性能拐点：

- TPS 拐点：当阶梯加压过程中，TPS（吞吐量）停滞或开始下降，表明系统已达到处理瓶颈。

- 错误率突增：当某个阶梯的错误率突然大于 1% 时，前一个阶梯的并发值通常即为系统的极限负载。

- 资源饱和度：若监控到服务器 CPU 利用率 \>80% 或内存 \>90%，该阶梯需标记为高风险点。

## 💡 避坑小贴士

- 调试与压测分离：在调试脚本时，可以开着“查看结果树”；但在进行正式的高并发压测时，一定要禁用或移除“查看结果树”，因为它极其消耗客户端内存，会影响压测结果的准确性。正式压测建议使用“聚合报告”或通过命令行模式运行。

- 执行顺序：JMeter 组件的执行顺序通常是：配置元件 \-\> 前置处理器 \-\> 定时器 \-\> 取样器 \-\> 后置处理器 \-\> 断言 \-\> 监听器。了解这个顺序有助于你正确放置组件。

## 📍 常见问题

### 高并发下 TPS 上不去 \(吞吐量瓶颈\)

现象： 增加线程数（并发用户），TPS 不再增长，甚至下降；响应时间显著变长。

排查方向：

- 应用层 \(Application\):

    - 线程池配置： 检查 Tomcat/Undertow/Jetty 的 `max-threads`。如果只有 200 个 worker 线程，而你有 500 个并发请求，多余的请求将在队列中排队等待。

    - 代码锁竞争： 是否存在全局锁 \(`synchronized`\)、数据库行锁或表锁？使用 `jstack <pid>` 查看线程状态，寻找大量 `BLOCKED` 或 `WAITING` 状态的线程。

    - 垃圾回收 \(GC\): 检查 GC 日志。频繁 Full GC 或长时间 Stop\-The\-World \(STW\) 会严重拖慢性能。使用 `jstat -gcutil <pid> 1000` 监控。

- 中间件层 \(Middleware\):

    - 连接池耗尽： 数据库连接池 \(HikariCP, Druid\) 或 Redis 连接池设置过小。例如，最大连接数设为 50，但并发有 200，导致大量 `Connection pool exhausted` 异常或长时间等待。

    - 消息队列积压： Kafka/RabbitMQ 消费者处理速度跟不上生产者，导致队列堆积。

- 系统层 \(OS/Network\):

    - CPU 饱和： 使用 `top` 或 `htop`。如果 User CPU 高，是业务计算密集；如果 Sys CPU 高，可能是系统调用（如锁竞争、上下文切换）过多。

    - 文件描述符 \(File Descriptors\): 达到 `ulimit -n` 上限，导致 `Too many open files` 错误。

### 响应时间偶尔极长 \(毛刺/Latency Spikes\)

现象： 平均响应时间尚可，但 P99 或 P99\.9 极高，图表上出现明显的尖峰。

排查方向：

- JVM Full GC: 最常见的原因。STW 暂停会导致所有请求卡顿。查看 GC 日志确认。

- 数据库慢查询： 偶发的全表扫描或未命中索引。检查 MySQL Slow Query Log。

- 网络抖动: TCP 重传、丢包。使用 `ping` 或 `mtr` 检查网络质量。

- 锁等待: 数据库死锁或长时间持有的行锁。

- 资源争抢: 同一宿主机上的其他容器/进程正在抢占 CPU 或 IO \(Noisy Neighbor 问题\)。

### 错误率飙升 \(Error Rate High\)

现象： 压测中后期，HTTP 500/502/503/504 错误增多，或出现连接超时。

排查方向：

- HTTP 502/503/504 \(Gateway/Timeout\):

    - 后端应用处理不过来，导致 Nginx/网关 等待超时。

    - 后端应用崩溃 \(OOM Kill\)。

    - 连接池耗尽，拒绝新请求。

- HTTP 500 \(Internal Server Error\):

    - 代码 Bug（如空指针异常，未处理特定边界条件）。

    - 数据库约束冲突（如唯一键冲突）。

    - 依赖服务超时（如调用第三方支付接口超时，且未做熔断降级）。

- Connection Refused / Reset:

    - 服务端端口未监听或防火墙拦截。

    - 服务端 backlog 队列满了 \(`tcp_max_syn_backlog` 设置过小\)，丢弃了新的 TCP 连接。

    - 达到最大文件描述符限制。

### 内存泄漏 \(Memory Leak\)

现象： 长时间稳定性测试 \(Endurance Testing\) 中，JVM 堆内存使用率呈锯齿状上升，且 Full GC 后内存无法回落到基线水平，最终 OOM。

排查方法：

- 监控: 使用 Prometheus \+ Grafana 监控 JVM Heap。

- Dump: 在 OOM 发生时自动 dump 堆内存 \(`-XX:+HeapDumpOnOutOfMemoryError`\)。

- 分析: 使用 MAT \(Memory Analyzer Tool\) 或 VisualVM 分析 `.hprof` 文件，查找 "Dominator Tree" 中占用内存最大的对象，定位代码中的静态集合类、未关闭的资源或 ThreadLocal 滥用。

### JMeter 客户端自身瓶颈

现象： 服务端资源利用率很低（CPU \< 20%），但 JMeter 报告 TPS 很低，且 JMeter 进程 CPU 100%。

原因与解决：

- GUI 模式运行: 切换到 Non\-GUI 模式。

- 监听器过多: 移除 "View Results Tree" 和 "Aggregate Report"，只保留 `.jtl` 输出。

- 单机性能不足: 使用 JMeter Master\-Slave 分布式架构。

    - *Master \(Controller\):* 不产生负载，只负责分发脚本和收集结果。

    - *Slave \(Server\):* 运行 `jmeter-server`，实际产生流量。

    - *命令:* `jmeter -n -t test.jmx -R slave1,slave2,slave3 ...`

### 仅一次控制器（Once Only Controller）对比 setUp 线程组

结论：视业务场景而定，大多数情况下不能直接替代。

虽然两者都能实现“只执行一次”的效果，但它们在并发上下文和数据隔离上存在致命差异：

**为什么【不能】替代的场景（最常见）**

场景：每个虚拟用户需要独立的登录凭证（Token/Session）

- 使用“仅一次控制器”：如果放在普通线程组内，100 个线程并发启动时，每个线程都会在自己的第一次迭代中独立执行一次登录请求。这样 100 个用户会获得 100 个不同的 Token，完美模拟真实场景。

- 使用“setUp 线程组”代替：setUp 线程组全局只执行 1 次登录。结果就是 100 个并发线程共享同一个 Token。这会导致：

    - 如果系统不支持多端/多 IP 共用 Token，后续 99 个用户的请求会全部报“Token 失效”或“账号异地登录”错误。

    - 无法测试高并发下的登录接口性能。

**为什么【可以】替代的场景**

场景：获取全局共享的公共数据

- 示例：获取系统配置字典、生成一个全局共享的只读 Token、或者提前往数据库插入一批测试订单供后续线程组查询。

- 分析：这种数据对所有虚拟用户都是通用的，只需要获取一次。此时，使用 setUp 线程组不仅完全可以替代“仅一次控制器”，而且更推荐，因为它能避免 100 个线程同时去请求同一个配置接口，减少了不必要的并发开销。

**💡 总结与最佳实践**

- setUp 线程组 = 全局共享的前置任务（1 次执行，所有线程共享结果）。

- 仅一次控制器 = 单用户的前置任务（每个线程各执行 1 次，数据相互隔离）。

实战建议：

如果你需要模拟 100 个真实用户并发，请将“登录”、“获取个人信息”等产生独立状态的操作放在普通线程组 \+ 仅一次控制器中；将“创建测试商品”、“获取公共配置”等全局操作放在 setUp 线程组中。两者配合使用，才是最严谨的压测架构。
