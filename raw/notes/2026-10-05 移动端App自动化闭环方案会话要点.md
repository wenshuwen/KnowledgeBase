# 2026-10-05 移动端 App 全链路自动化闭环方案 —— 会话要点

> WIKI-SCHEMA 5.1 的「对话回填例外」直接进入编译流程。
> 脱敏：无项目名、无真实域名、无账号与业务数据；提及的产品均为公开的通用工具。

## 用户原问

能否用一个独立的程序/脚本实现移动端 App 的自动化操作，部署后可持续后台运行，
把点击、页面跳转、返回等动作串成完整的全链路操作闭环？需要：可行方案、所需技术能力
与依赖条件、以及如何验证闭环稳定运行并覆盖主要路径。

## 后续澄清（三问三答）

| 问题 | 用户选择 |
|---|---|
| 目标平台 | Android + iOS 双端 |
| 运行档位 | A 档：设备本地跑（不接电脑） |
| 目标 App | 第三方 App，可能有反自动化 |

## 关键结论

1. **三条件互斥**：双端 + 设备本地跑 + 第三方 App 有反自动化，三者无法同时满足。
   松绑任意一条即可落地。
2. **iOS 的 A 档（非越狱）不成立**：一个 App 无法操作另一个 App 的 UI（沙箱前提）。
   所有现成方案的实质是「Mac 构建一次 WDA + 主机持续发指令」。
3. **Android 无隐身通道**：非 root 条件下产生一次点击只有两条通道——无障碍服务或
   adb/调试注入。图像识别只是「找目标」的方法，最终点击仍要落到这两条通道之一。
4. **「离线/后台常驻」有三个档位**：A 设备本地跑 / B 主机常驻调度 / C 云真机托管。
   三档的难度与代价完全不同，应先定义清楚。

## 闭环七阶段

前置检查 → 冷启动 → 就绪判定 → 单步动作 → 跳转与返回 → 异常分支 → 收尾与证据。
每阶段有「校验点」与「失败处理」两行，二者缺一不算闭环。

五条工程约定：不写死 sleep（锚点出现 + 快照连续一致）／定位优先级固定／每步都要到达确认／
返回用系统 back 并重校指纹／步骤幂等 + 从最近锚点重入且重试有上限。

## 验证六级阶梯

L1 单动作 → L2 单流程冒烟 → L3 全链路端到端 → L4 长稳运行 → L5 异常注入 → L6 覆盖度核对。
稳定性指标口径：全链路成功率、无故障连续轮次、假失败率、单步 P95 耗时、自动恢复成功率、定位漂移率。
覆盖度三步：页面-状态图 → 需求↔步骤映射矩阵 → 脚本日志/埋点日志/录屏三方交叉验证。

## 合规边界（对话中明确）

检测面（无障碍列表、悬浮窗、调试状态、输入法包名、事件来源与时间间隔、root/Hook 痕迹）
可以按技术原理讲清楚，用于判断方案为什么失败；但**不提供绕过风控的实施步骤**。

计算机信息系统相关的法律风险。合法路径：获取授权测试包、使用官方开放接口、或改用自有产品。
