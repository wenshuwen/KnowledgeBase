## 一、诉求原文

「在本地搭建一个基于 Karpathy llm-wiki 管理规范的自生长私有知识库」，服务软件测试领域，首要用途是**经验图谱**。

## 二、16 题澄清结论

| # | 维度 | 结论 |
|---|---|---|
| 1 | 用途优先级 | 经验图谱优先，其余用途长在上面 |
| 2 | 入库内容 | 实战复盘、技术选型与决策、外部输入、测试理论 / AI 测试 / 自动化测试 / 性能测试经验 |
| 3 | 存量素材 | 基本为零，从零开始 |
| 4 | 投喂节奏 | 不定时手动投喂 + 每周自动体检 |
| 5 | 规模预期 | 1000 页以上 / 不设上限 |
| 6 | 存放位置 | 当前工作区 `KnowledgeBase/`（原选 Obsidian 库后修正） |
| 7 | 交互入口 | 对话式提问为主 |
| 8 | 隐私边界 | 只存脱敏后的通用经验 |
| 9 | 内容粒度 | 混合制：概念原子化 + 复盘长文页，长文抽实体页 |
| 10 | 采集渠道 | 对话回填、丢文件/链接、口述要点、定时自动抓取（四渠道全开） |
| 11 | 编译模式 | 单源精读，禁止批量灌入 |
| 12 | 检索机制 | 分层索引 + 标签 + 全文搜索，预留向量接入位默认关闭 |
| 13 | 接入形式 | 包装成 skill |
| 14 | 写权限 | 可手改，改后由 LLM 执行 sync |
| 15 | 体检备份 | 每周自动 lint + 本地 Git |
| 16 | 命名约定 | 中文文件名 + 英文 kebab-case 标签，标签上限 30 |

## 三、澄清过程中的关键分歧与修正

1. **位置改了两次**：最初倾向放进 Obsidian 库以换取关系图谱视图，后修正为当前工作区。代价是失去开箱即用的图谱可视化，需要后续用 Obsidian「打开文件夹作为库」补上。
2. **规模选到 1000 页以上**，但没有因此引入向量库——结论是分层索引在千页量级仍够用，向量检索留接口不启用。
3. **「可复用资产」未勾选**：脚本片段被降级为 raw 层附件，不作图谱主干节点，理由是避免大量代码页稀释关系网。

## 五、设计过程中被否掉的方案

| 被否方案 | 否决理由 |
|---|---|
| 引入本地向量检索（Ollama + bge-m3） | 0 页起步时是纯负债：多一层模型依赖与索引重建成本，收益为零 |
| 批量灌入 + 事后 lint 收抬 | 交叉引用质量会崩，而交叉引用正是知识库存在的理由 |
| 全原子化页面 | 复盘类叙事内容被切碎后不可读 |
| 自动抓取直接入库 | 会在一周内灌进几十页低价值内容，改为落 `raw/inbox/` 人工确认 |

## 六、待验证项

- 分层索引在 800 页以上是否仍然够用（届时再评估向量接入）
- 每周 lint 的报告量是否会超出阅读意愿
