## 一、面试题精选

### 自动化测试

**Q：自动化用例集的「健康度」你会看哪几个指标？怎么发现「假绿」？**

四个指标：稳定性（连续 N 次执行的通过率方差，低于 98% 的用例单独挂出来）、有效性（注入已知缺陷能否被抓到）、执行时长（整批与单条趋势）、覆盖增量（新增需求是否带来对应用例）。

专治假绿的手段是**定期做变异测试或反向验证**：把一条已知的 bug 修复回滚掉，看用例是否变红，不变红就说明断言太弱。第二步是把断言从「状态码 + 关键字段」升级到**业务语义断言**（订单金额、状态流转是否真的对）。

**Q：自动化怎么并发执行又保证用例之间互不干扰？**

三条隔离线，缺一条就会出偶发失败：

1. **数据隔离**：每个 worker 用独立数据命名空间（账号加 worker 后缀、订单号带 traceId），或每条用例自备自回收数据；
2. **环境隔离**：避免改全局配置、缓存、开关这类「全局态」；必须改的用锁或串行；
3. **资源隔离**：浏览器实例、临时目录、日志文件按 worker 分开；DB 连接池按 worker 调小。

`pytest-xdist --dist loadfile` 可让同一文件的用例落在同一 worker，天然规避文件内顺序依赖。上线并发前必须先串行跑一遍、并发跑十遍比对差异。

**Q：用例之间存在先后依赖（A 建单、B 审单），你会怎么组织？**

顺序依赖是自动化最大的负债，能消就消，消不掉就显式声明。按优先级三种处理：

1. **用 API 直接造前置数据**（推荐）：B 不再依赖 A 的 UI 操作；
2. **合并成一条长用例**：业务流程天然不可拆时就老实写成端到端用例；
3. **显式声明依赖**：用 marker/fixture 声明顺序，让框架串行调度。

底线是**单条用例必须能独立跑通**，否则排查失败时分不清是这条坏了还是前一条坏了。

### 接口测试与数据处理

**Q：Webhook 回调接口怎么测？对方重试、乱序、重复投递怎么仿真？**

Webhook 是被动接收、无法控制发送方，测试重点是**抗异常投递**，用例分四组：

1. **正常路径**：合法签名 + 合法报文 → 正确处理并返回 2xx；
2. **重复投递**：同一事件 ID 发两次（对方超时重试很常见），必须**幂等**——按事件 ID 去重，第二次直接回 200 而不重复处理；
3. **乱序**：先收到「已支付」再收到「已创建」，业务状态机能否兜住；时间戳过旧的消息是否丢弃；
4. **安全**：签名篡改/缺失、时间戳过期、超大报文、非法 JSON。

仿真用 ngrok 或 WireMock 起假回调地址，把真实报文体存成夹具再改字段批量发送。易漏项：**回调处理超时怎么办**，同步处理重业务会拖垮对方，需确认是否异步化 + 落表补偿。

**Q：主从延迟导致「写完立刻读不到」，测试怎么设计用例暴露它？**

这类问题在测试环境经常因为读库少而测不出来，必须主动构造：

1. **写入后立刻读**：同一请求链路里写主库后马上从从库查，走真实路径（提交后跳详情页、下单后查订单列表）；
2. **强制放大延迟**：在从库注入延迟，把「偶发」变成「必现」——这是暴露问题的关键手段；
3. **并发下的一致性**：多线程同时写同一批数据后读，检查丢失更新或读到旧值；
4. **业务语义**：确认哪些读**必须走主库**（刚写的自己的数据、金额、状态机），哪些可容忍延迟——这是设计问题不是 bug。

做法上把「读写一致」写成持续性用例长期挂在 SIT，延迟类问题只有长期跑才能抓到。

### 质量工程

**Q：需求频繁变更时，测试怎么保证不被拖垮？**

需求变更本身不可怕，**未经评估的变更**才可怕。建立轻量变更闸门：

1. **变更要过影响评估**：必须回答「影响哪些模块、影响哪些已完成用例、要不要回归、要不要重估排期」；
2. **用例分层让变更成本可控**：核心用例与长尾用例分开维护；
3. **冻结窗口**：发版前 2~3 天进入需求冻结，之后仅接受 P0 变更并走「砍一个旧需求换一个新需求」的置换规则；
4. **测试资产按需求 ID 关联**：变更时一键列出受影响用例与脚本，评估从「靠回忆」变成「查表」；
5. **记录变更频次**：把每版本的需求变更次数当指标公示，这本身就能减少随意变更。

核心思路：**不是拒绝变更，而是让变更带上价格标签**。

## 二、知识点精选

### 接口与数据

**批量接口的部分成功语义**

先问清原子性：一条失败是全回滚还是部分成功。要求返回逐条明细（id + 状态），否则前端无法提示哪几条失败。边界覆盖空数组、单条、正好上限、超上限、重复 id、不存在 id、无权限 id。必测一条：**部分成功后重试同一请求是否幂等**。

**防重放三要素测试方法**

- timestamp：窗口内通过、窗口外拒绝、客户端时钟漂移；
- nonce：同一值重复使用必须拒绝（防重放核心），确认存储与过期策略；
- sign：篡改任一参与签名的参数即失效。

组合攻击必测：改 body 不改 sign、把旧请求原样重放、timestamp 改成未来时间。拒绝时应返回明确业务错误码而非 500。

**数据迁移一致性校验**

校验口径四件套：行数、关键字段校验和、金额汇总、枚举分布。必须**冻结迁移前基线快照**，否则无法归因差异。增量数据（迁移窗口内的新写入）最易遗漏。字段级比对重点：编码转换乱码、时间时区与精度、NULL 与空串、自增 ID 与序列错位。验收结论永远是「差异清单 + 逐条解释」。

### 自动化与 CI

**CI 执行时长优化五招**

1. 回归集分级（冒烟随提交、核心随合并、全量放夜间）——通常砍掉 70% 等待；
2. 并行（pytest-xdist、CI matrix，前提是无共享状态）；
3. 砍固定 sleep、用接口造前置数据；
4. 依赖与镜像缓存、复用登录态而非逐条登录；
5. 只重跑失败用例（`--lf`）。

**优化前先量各 stage 耗时占比**，别凭感觉优化。

**失败自动归因三分类**

- **环境类**：连接拒绝、DNS 失败、5xx、抓包无请求、同一时间多条同时失败、健康探针不通过；
- **脚本类**：定位器失效、契约字段变动、前置数据缺失；
- **疑似缺陷**：返回合法业务错误码但值不符，且手工可复现。

三类分流到不同责任人，避免一律记到研发头上。关键一步：**环境问题必须先做健康探针**再跑用例。

### 发布与容灾

**制品唯一性与版本指纹**

根本解法是「**构建一次、逐级晋级**」：同一制品只构建一次，从测试到生产复用，绝不各环境重新 build。镜像用 digest 而非 tag 引用；commit SHA 与构建号注入版本接口；测试报告记录被测版本号；上线前用版本接口核对。预发必须与生产同镜像、同配置结构，否则它给的信心是假的。

**混沌工程小团队四步落地**

1. 建立稳态假设（成功率、P95、业务量基线）——没有基线无法判断是否造成伤害；
2. 最小爆炸半径起步，先在预发、后在生产单实例小比例；
3. 先做「只观察不注入」，很多团队第一次发现的是「监控没告警」而非「系统扛不住」；
4. 设自动终止条件（错误率超阈值立即停）并安排观察者与值班兜底。

混沌工程的目标是**发现弱点，不是证明系统很强**。

## 三、技能精选

### 制品与版本治理

**价值判断**：只要每个环境各自 build 一次，就有出现「测 A 上 B」的必然性——这是结构性风险，靠人工核对无法消除。

**核心动作**：构建一次、测试/预发/生产复用同一制品 → 镜像用 `@sha256` digest 引用 → 上线前用版本接口对一遍 commit SHA。

**常用工具**：Docker、Harbor、Jenkins、Helm。

### 回滚演练

**价值判断**：回滚最大的坑不是代码，是**回滚后老代码读到新结构的数据**。

**核心动作**：DDL 向后兼容（先加不删、枚举只增不改语义）→ 数据修复脚本与代码回滚一起演练并计时 → 标准是 10 分钟内恢复且数据不自相矛盾。

**常用工具**：K8s、特性开关、数据库备份/回滚脚本。

### 主从与分片一致性测试

**价值判断**：分片后的 bug 不在「数据对不对」，而在「**跨片语义对不对**」。

**核心动作**：注入从库延迟把偶发变必现 → 影子库对照法（同一批数据分别灌单库与分片库，同一组查询打两边比对结果集）→ 明确哪些读必须走主库。

**常用工具**：MySQL、ShardingSphere、sysbench。

## 四、坑点精选

| 坑点 | 表现 | 破解方法 |
|---|---|---|
| **批量接口只测「全部成功」** | 传 10 条全合法验证 200 就结束，线上传超限或无权限的那条时行为完全没验证过 | 用例重心放在异常组合：部分失败、超上限、重复 id、无权限 id，以及部分成功后重试是否幂等 |
| **数据迁移只对总条数** | `select count(*)` 一致就签字，结果金额汇总差几万、编码乱码、时间整体差 8 小时 | 比对落到字段级：金额汇总、唯一键、枚举分布、编码、时区精度、NULL 与空串；并冻结迁移前基线 |
| **主从延迟靠「等几秒」硬扛** | 用例里写操作后加 `sleep(3)`，测试环境过了，线上从库延迟十几秒时业务直接展示旧数据 | 不用 sleep 掩盖，主动放大延迟把问题逼出来，再与研发确认哪些读必须强制走主库 |
| **测的包和上线的包不是同一个** | 测试环境是上午的构建，上线重新打包了同一分支的新提交，差了几个 commit | 构建一次逐级晋级，同一 digest 从测试走到生产；版本接口暴露 commit SHA，上线前核对 |
| **回滚只回代码不管数据** | 新版本加了字段、改了枚举，回滚老版本后老代码读到新数据直接报错 | DDL 向后兼容，回滚预案必须含数据修复脚本，并与代码回滚一起演练、一起计时 |
