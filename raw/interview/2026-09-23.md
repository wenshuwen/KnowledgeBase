## 一、面试题精选

### 测试理论 · 用例设计方法按「输入 / 规则 / 时序」三形态选型

**Q：面试官问你「会哪些用例设计方法」，只答等价类、边界值、判定表，为什么显得停留在教科书？**

因为方法不是越多越好，**关键是按输入空间的形态与业务的时序特征选型** —— 选错的代价是漏测或白写。可以分三类讲：

1. **输入维度可控 → 等价类 + 边界值**。这是底座。先划分有效与无效等价类，再补边界、边界外、刚好越界三种点。
2. **多条件组合 → 判定表 + 正交（pairwise）**。判定表用于条件 ≤ 4 个时穷尽规则与互斥项；条件再多则用正交表抽样，并**明确说出放弃了哪些组合、为什么可以放弃**（比如覆盖到 pairwise 即可）。
3. **有时序与状态 → 状态迁移 + 场景法**。先画状态图（状态 + 事件 + 守卫条件 + 动作），标出合法迁移、非法迁移与守卫条件。**非法迁移往往才是线上事故源头**（例如「已关闭订单被支付」）。场景法负责串主干、分支与异常回滚。

补一类加分项：**错误推测（基于历史缺陷模式）与探索式测试（基于启发式清单）** 用于「发现我没想到的」。前三类证明「该测的测了」，后两类负责补盲区。

### 性能测试 · 五类场景的划分与「稳定性测试看趋势不看峰值」

**Q：你们做性能测试一般跑几轮？跑的是哪一种压测？**

性能测试不是一种，而是**五种回答不同问题的场景**：

| 场景 | 回答的问题 | 准入标准 |
|---|---|---|
| 基准 Benchmark | 基线数字是多少 | 环境与配置冻结并记录 |
| 负载 Load | 正常业务规模扛不扛得住 | TPS / RT / 错误率三项同时达标，目标并发由流量模型反推 |
| 压力 Stress | 余量还有多少 | 给出 TPS 走平点、RT 非线性点、错误率上升点 |
| 稳定性 / 疲劳 | 会不会慢慢变坏 | 内存、连接数、FD、GC 频率、磁盘水位全程无单调上涨 |
| 尖峰 Spike | 崩不崩 | 允许 RT 变长、允许被限流拒绝，但不雪崩、不丢数据 |

**执行纪律**：先小并发验证脚本与监控 → 阶梯加压；同档位连跑 3 轮取稳定段；**轮间差异 > 20% 必须先解释原因，不得取平均或挑最优轮**。

最值得强调的一点：**稳定性测试的判据是「有没有单调上涨趋势」，不是「TPS/RT 有没有劣化」**。TPS 与 RT 全程稳定但内存持续上涨，仍应判为存在泄漏风险 —— 短时压测永远压不出这类问题，线上跑几天才会暴露。

### 安全测试 · SSRF 白名单绕过的成套变形与「请求是否发出」判据

**Q：开发说「我们已经限制只能请求白名单域名」，你怎么验证？**

先**列全入口**（图片 / 附件 URL 上传、网页抓取预览、Webhook 回调地址、PDF 生成、三方接口代理、远程数据源导入），再按四层攻击面验证：

1. **内网探测**：`127.0.0.1` / `localhost` / `169.254.169.254`（云元数据，可直接拿临时凭据，最高危）/ 内网网段。测试用可控探针，不要真扫内网。
2. **白名单绕过变形（核心得分点）**：进制写法（八进制、十进制整数、十六进制）；域名变体（大小写、结尾点）；**DNS 重绑定**（一次解析合法、二次解析到内网，纯 host 校验最易被打穿）；**URL 解析歧义**（用 `@` 把真实目标藏在后面）；**302 跳转绕过**（用一个允许域名跳到内网）。
3. **协议扩展**：`file://` 读文件、`gopher://` 打内网服务、`dict://` 探端口。**只校验 host 而不限制 scheme 即失守。**
4. **防护有效性判据**：**不要只断言「返回了错误」，要断言「请求根本没发出去」**。做法是用我方控制的接收端地址作为允许目标，构造各类变体请求，**观察接收端日志有无请求** —— 这是唯一的硬证据。

补充：结论必须注明是在哪套网络策略下验证的。测试环境与生产的安全组不同，结论不可平移。

## 二、知识点精选

### 数据库 · 事务隔离级别验证矩阵与 MySQL 的「快照读 / 当前读」之分

验证隔离级别的**前提是两会话 + 显式控制执行顺序**（谁先执行、在哪暂停、谁后执行）。手工点两个客户端窗口无法对齐时序，现象会时有时无，结论没有价值。用两个连接 + 事务控制点（或信号同步）复现。

| 现象 | 复现方式 | RU | RC | RR | SERIALIZABLE |
|---|---|---|---|---|---|
| 脏读 | A 写未提交，B 读 | 出现 | 不出现 | 不出现 | 不出现 |
| 不可重复读 | B 事务内两次读，中间 A 提交修改 | 出现 | 出现 | 不出现 | 不出现 |
| 幻读 | B 事务内两次同条件查，中间 A 插入提交 | 出现 | 出现 | 见下 | 不出现 |

**MySQL 的特殊之处（关键得分点）**：InnoDB 默认 REPEATABLE READ，靠 **MVCC 快照读**避免不可重复读；幻读是否出现取决于读的类型 ——

- **快照读**（普通 `SELECT`）：读事务开始时建立的一致性读视图，**看不到事务期间其他会话提交的新插入行**；
- **当前读**（`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE`）：会加**间隙锁（Next-Key Lock）**，此时新插入被阻塞，因此也避免幻读。

**丢失更新不是隔离级别能解决的**，必须靠乐观锁（版本号 / `WHERE value = 旧值`）或悲观锁。库存扣减应写成原子更新 `UPDATE ... SET num = num - 1 WHERE num >= 1`。

**三个实操提醒**：① 用 `SHOW ENGINE INNODB STATUS` 或 `performance_schema.data_locks` 核对真实加锁情况，避免归错因；② 连接池或中间件可能改变了会话隔离级别，测试前先 `SELECT @@tx_isolation` 确认真实级别；③ 结论要落到对开发的具体编码要求，而不是只报「有这个现象」。

### AI 测试 · 超长上下文：位置探针法与长度-准确率曲线

**核心认知：模型声明支持 ≠ 真的用得上。**「支持 128K」和「128K 下还准」是两件事。

1. **截断行为（功能底线）**：测刚好在限额内 / 刚好超过 / 远超三种输入，确认是明确报错、**静默截断**还是拒绝处理 —— 静默截断最危险，用户以为全文进去了。同时**确认按 token 还是按字符计算**：中文一个字符常占 1~2 token，按字数估会严重低估，要用分词器算真实 token 数。
2. **位置探针法**：把同一关键信息分别放在长文档的**开头 / 中间 / 结尾**，其余内容不变，提问该信息并对比三次准确率。经验上普遍存在 **lost in the middle** 现象（首尾记得住、中间易忽略）→ 结论应转化为工程建议：**关键约束放开头、检索依据放结尾**。
3. **长度-准确率曲线**：同一文档按阶梯长度加长，记录各长度准确率，**找出质量明显下降的拐点**。这个拐点才是该场景真正可用的长度上限，比厂商标称值有用得多。
4. **注意力稀释导致的串扰**：构造多份结构相似但关键值不同的文档（如多份合同），逐份提问，**检查是否把 A 的值答到 B 上**。合同审查、财务分析类场景必测。
5. **成本与延迟**：测出「长度 → token 消耗 → 响应时间」的对应关系，供产品取舍。

**结论取向**：测出长上下文不准时，正确应对往往不是换更大的模型，而是**改架构 —— 先检索再生成，塞 5K 高相关内容优于塞 100K 全文**。

### AI Agent · 记忆机制的四个测试维度（多用户隔离是红线）

被测对象不是「记住没有」，而是记忆的**写入、检索、遗忘、负面干扰**四件事。

1. **写入**：短期记忆（同会话内第 3 轮信息在第 8 轮能否引用）、长期记忆（跨会话 / 换设备）、显式记忆。**关键不是「记住了没有」，而是「记的内容是否被结构化」** —— 验证方式是过几轮后问「提炼型问题」，看能否从记忆中提炼答案，而不是原文回显。
2. **检索与准确性**：三类冲突场景 —— **信息更新**（先说 A 公司后改口 B 公司，问「我在哪家」必须答 B，不能两个都提）；**同类混淆**（多条同类型记录下取回是否正确）；**多用户隔离**（**安全红线**：A 的记忆绝不能出现在 B 的会话里，需用双账号交叉提问 + 同设备切号 + 并发会话专门验证）。
3. **遗忘与过期**：用户要求删除后是「打标记」还是「真的不可检索」—— **标记删除但检索仍命中等于没删，属合规问题**；时效性信息是否自动失效；容量上限时的淘汰策略必须有明确规则。
4. **负面干扰**：做对照组实验 —— 同一任务「带记忆」与「清空记忆」各跑一轮对比成功率。**带记忆反而更差说明检索阈值或写入策略有问题**，这个结论比「记忆能用」有价值得多。

**前置要求**：推动产品提供「当前记住了什么」的可查看入口，否则测试只能黑盒猜测，效率极低。

## 三、技能精选

### 测试方法论选型能力

拿到需求能判断其形态并据此选用例设计方法，且能说清覆盖了哪些风险、放弃了哪些组合。**这项能力决定用例集的上限**：方法选错，后面写得再工整也补不回漏测。

- **先判形态再选方法**：输入类 / 规则类 / 时序类各用不同套路；
- **状态图必须标出非法迁移**，这类用例最容易被漏；
- **组合抽样要写清放弃理由**，不写等于没论证；
- 用错误推测从历史缺陷库反推，补方法论的盲区。

常用工具：等价类 / 边界值、判定表与因果图、正交实验与 pairwise、状态迁移图、错误推测清单、探索式测试 Charter。

### SSRF 与注入类漏洞验证

能系统性梳理「服务端代为访问」的功能入口，用白名单绕过变形（进制、DNS 重绑定、URL 歧义、302 跳转）验证防护是否真的有效，并**以「请求是否发出」而非「是否报错」作为判据**。

- 先列全入口再动手，漏掉入口等于漏掉整个风险面；
- 白名单要按「scheme + host + 跳转」三维验证，只查 host 必失守；
- 判据是接收端有没有收到请求，不是接口有没有报错；
- 结论注明验证时的网络策略，测试环境与生产结论不可平移。

常用工具：Burp Suite、OWASP ZAP、自建接收端探针、DNS 重绑定服务、Python requests 重放脚本。

### Agent 记忆与多智能体测试

能把记忆拆成写入 / 检索 / 遗忘 / 负面干扰四维验证，并针对多 Agent 的协作协议（任务分解、消息传递、冲突仲裁、失败传播）设计用例。**核心产出是「该忘的忘没忘」与「用户隔离有没有被穿透」这类高价值结论。**

- 记忆写入要看「结构化程度」，用提炼型提问验证；
- 多用户隔离必须专门测（双账号交叉 + 同时并发会话），单列为红线用例；
- 删除后要验证「真的不可检索」，标记删除等于没删；
- 多 Agent 必须先有轨迹可观测，否则错误结果无从归因。

常用工具：轨迹（Trajectory）日志分析、记忆内容查看入口、token 计量与成本监控、并发会话脚本。

## 四、坑点精选

### 拿语句覆盖率当测试充分性的证明

**坑**：覆盖率只说明「这些代码被执行过」，说明不了「断言有没有辨别力」。一个把返回值打印出来不做断言的用例，也能贡献覆盖率。用覆盖率向上汇报，一旦线上出事会连自己都解释不清。

**破解**：核心模块改用**变异测试**抽检杀死率；同时补需求追溯矩阵与风险分级覆盖要求。汇报时说「分支覆盖 X% + 变异得分 Y% + 裸需求 0 条」这一组数字，比单个百分比有说服力得多。

### Agent 记忆只测「记住了没有」

**坑**：测完「用户说喜欢咖啡、后面问它答咖啡」就认为记忆功能通过。没有测信息更新（改口后是否还答旧值）、没有测删除（标记删除但检索仍命中）、更没有测多用户隔离 —— 而记忆串用户属于严重的数据泄露，事后极难补救。

**破解**：记忆测试必须四维覆盖：写入、检索（含更新与隔离）、遗忘与过期、负面干扰。删除后要验证「不可检索」而不只是「状态变了」；隔离用双账号交叉 + 并发会话专门验证，**单列为不可接受的缺陷级别**。

### 把 AI 生成的报告直接发出去

**坑**：模型编出的通过率、缺陷数、失败原因读起来都很合理，格式也漂亮，于是不做校验就对外。一旦有人拿着错的数字做上线决策，后果比「没有报告」严重得多，而且很难解释。

**破解**：**数字由脚本产出、模型只负责组织语言**；对输出做数字回溯校验，**出现源数据之外的数字即判不合格**。同时强制报告写明「未覆盖范围」，避免只跑了冒烟却看起来像全量回归。
