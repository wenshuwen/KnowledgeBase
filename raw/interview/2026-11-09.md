## 一、并发一致性与契约边界（api）

### 1. 题：超卖要断言三个数，而不是一次响应

**Q：库存 10 件、50 个并发请求，最后卖出 17 件。怎么复现与定位？**

核心认知：**串行调 50 次永远复现不出来**，请求之间没有窗口重叠，读写间隙不会被踩到。

复现做法：用线程池加 barrier 让 50 个请求同时到达，然后断言三个数。

| 断言项 | 判据 |
|---|---|
| 成功下单数 | ≤ 可用库存（10） |
| 库存扣减总量 | = 成功订单数 |
| 最终库存 | = 初始库存 − 成功订单数 |

三项任一不符即判并发一致性缺陷。定位顺序按嫌疑排：

1. 扣减是否「先查再改」（read-modify-write）——两次 SQL 之间有天然窗口；
2. 扣减条件是否写进 `where`（如 `where stock >= 1`），影响行数为 0 必须判失败；
3. 是否有版本号 CAS 或行锁兜底；
4. 数据库层是否有唯一约束 / check 作为最后防线。

> 补充判据：跑 10 轮看是否稳定复现。只偶发一次的超卖，往往是缓存扣减与库未对齐，而不是锁的问题。

### 2. 题：批量接口的部分成功必须显式写进契约

**Q：批量导入 100 条有 3 条非法，接口返回 200 且 errors 为空，问题严重吗？**

**比返回 500 更严重，因为它是静默丢数据。** 三种合法契约必须选一种并写进文档：

| 契约 | 语义 | 适用 |
|---|---|---|
| 全成功才提交 | 事务内一错全回滚 | 强一致（财务、库存） |
| 逐条独立 | 部分成功 + 逐条明细 | 批量导入 |
| 两段式 | 先预检再提交 | 数据量大、需人工确认 |

四组必测断言：

1. 响应结构为「成功 97 + 失败 3」，失败项带原始下标与原因；
2. **失败条目零副作用**——直接查库确认没写进去；
3. 整批重试不产生重复（业务唯一键或幂等键）；
4. HTTP 语义明确（207 或 200 + 明确 body），但**不能 200 + 空 errors 假装全成功**。

最坑的场景是「事务回滚了一半」：主表进了 97 条，关联明细没进，数据看着有、业务跑不通。

### 3. 题：Agent 自主重试是风险的放大器

**Q：Agent 调接口失败后自己改参数重试，把数据改坏了。怎么测与防？**

按错误类型定策略，而不是一律重试：

| 错误类型 | 正确策略 |
|---|---|
| 400 参数错 | 不重试，上报（重试也不会对） |
| 409 冲突 | 先查当前状态再决定 |
| 超时 | 归「不确定」，先查询副作用是否已发生 |
| 5xx | 有限重试（≤2 次，指数退避） |

三道防线：工具层限制次数与退避、接口层做幂等键、业务层用状态机阻止非法二次变更。

> 最危险的实现不是「重试太多次」，而是**Agent 自行改参数**：把金额四舍五入、把失败的商品 ID 换成相近的另一个 ID，表面重试成功、实际数据错了。验收必须加一条——自主重试的每次参数变更都要留下可读记录，否则不可审计。

## 二、知识要点

### 4. HTTP 缓存的三类验证器（api）

- **ETag / If-None-Match**：强验证器，取值必须覆盖所有影响响应体的因素（资源 ID、租户、用户、字段版本）。
- **Last-Modified / If-Modified-Since**：弱验证器，秒级精度，同秒内的两次修改分不出来。
- **Vary**：不是验证器但决定缓存键；没写 Vary，不同用户会互相命中（串号）。

配套三条：验证器变化时必须返回 200 + 新体；写操作后必须失效；带个人信息与金额的响应用 `private` 或 `no-store`，不进共享缓存。

### 5. 部分成功语义的三种契约（api）

全成功才提交 / 逐条独立 / 两段式，三者共同的硬约束是：**失败条目零副作用，且重试不产生重复**。判断一个批量接口有没有设计，先看它有没有明确选了哪一种，而不是看它返回什么状态码。

### 6. JSON 字段的索引与查询下推（db）

JSON 列上的表达式查询默认**不走普通索引**，只能全表扫。两条可用路径：生成列（STORED）加索引、多值索引（支持数组元素查询）。

验证方法：EXPLAIN 看 `type` 与 `rows`，再用 10 万行数据对比加索引前后的耗时。**用几百行数据测会得出反向结论**——小数据量下全表扫反而更快。设计层面，高频按元素查的字段应拆关联表，JSON 只留展示快照。

## 三、技能与方法

### 7. 接口缓存语义的验证（api）

把 ETag、Vary、Cache-Control 当被测逻辑而不是部署配置。三条可执行场景：

| 场景 | 操作 → 判据 |
|---|---|
| 验证器取值 | 改字段后用旧 If-None-Match 请求，断言 200 + 新值；返回 304 即判定取值规则缺字段 |
| Vary 缺失 | 两个不同 Authorization 请求同一 URL，断言 body 不同且含 `Vary: Authorization` |
| 写后失效 | 200 次写后读断言 100% 拿到新值，出现 1 次旧值即说明失效链路有缺口 |

判据的共同点是「重复请求」——**缓存缺陷在单次请求里永远正确**，因此必须靠用例覆盖，点点点发现不了。

### 8. 接口断言的三个层次（auto）

| 层 | 断言对象 | 失败含义 |
|---|---|---|
| 结构层 | 字段名、类型、必填、可空性（schema） | 契约变了 |
| 业务层 | 关键字段的具体值、集合条数与顺序 | 逻辑错了 |
| 安全层 | 敏感字段**不存在**、越权被拒 | 有泄露风险 |

三层分开写，失败信息才能直接指向问题类型。全量 JSON 比对的问题不是不够严，而是失败时只给一大坨 diff，最后大家都去点「更新快照」。

### 9. 水平越权的系统化验证（sec）

**越权的特征是不报错**：返回 200、结构完全正常，只是内容属于别人。因此必须把一个机械动作重复到底——两个同角色账号，把 A 的每个资源 ID 放进 B 的请求重放，断言全部 403 或 404。

三个常漏的入口：批量接口（常绕过列表的权限过滤）、导出接口（天然返回大量数据，可横向拖库）、筛选参数里的组织/租户 ID。

## 四、坑点与破解

### 10. 只断言状态码 200

业务字段改成 null、金额单位从元改成分，用例依然全绿——这种断言只验证了「服务还活着」。

**破解**：每个接口至少三条断言——状态码、关键业务字段的值、不该出现的敏感字段不存在。断言要绑定业务语义，不是绑定 HTTP。

### 11. 越权测试只测「没登录」

只验证不登录会被拒，就认为权限没问题。真正的高危是登录后的水平越权，接口返回 200 且看不出异常。

**破解**：双账号 ID 替换重放，脚本化覆盖所有带资源 ID 的接口；导出与批量接口单独加一轮范围越权验证。

### 12. 让 AI 生成用例但不校验

生成 200 条直接导进平台，重复的、映射不到断言的、测同一分支的全混在一起，通过率好看但拦截能力接近零。

**破解**：去重（向量相似度 0.9 + 语义指纹）、映射（每条必须指向接口与断言点）、评审三道闸都要过；对外只报**进回归数**，不报生成数。
