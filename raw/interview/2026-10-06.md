## 一、安全测试

### Q：接口越权是重灾区，你怎么系统化地测，而不是碰运气试两个 ID？

**结论**：越权不能靠随机试，要用「主体 × 客体 × 动作」的矩阵法，产出应该是一张权限矩阵，而不是一条 bug。

1. **建账号矩阵**：至少准备三到四类主体 —— 普通用户 A、普通用户 B（同角色、不同数据归属）、下级角色、管理员。只在单账号上试，测不出水平越权。
2. **明确客体归属**：把带归属关系的数据列出来（订单、合同、工单、消息、报表），每类造两条分属 A 和 B，记下各自 ID。
3. **交叉发请求**：用 A 的凭证访问 B 的客体 ID，覆盖查、改、删、导出、下载附件、批量操作六种动作。只测「查」是最常见的漏测，改和删往往更危险；批量接口尤其要试，常出现「单条校验了权限、批量接口忘了」。
4. **纵向越权单独一轮**：用低权限账号调管理端接口，包括前端隐藏但接口还在的情况 —— 很多越权藏在「菜单隐藏了、API 没鉴权」。
5. **绕行路径都要试**：换请求方法（GET 改 POST）、换参数位置（query 挪到 body）、加多余字段、走导出/分享/回调这类旁路接口，它们经常漏掉鉴权。
6. **判定口径**：只要返回了本人无权访问的数据或完成了本人无权执行的动作就是越权，与「是否看不到入口」无关。

### Q：离上线只剩三天，业务方要求必须出一份安全测试结论，你会怎么排优先级？

**结论**：先保「能被打穿」的面，再谈广度；结论必须写成风险清单，并明确告知覆盖范围不是全量。

1. **先盘资产与入口**：列出本次改动涉及的所有对外入口（Web 页面、开放接口、回调地址、上传入口、后台管理页），标出哪些「不需要登录就能碰」，这是最高优先级。
2. **按可利用性排序，不按漏洞数量排序**：优先验证越权、注入、认证绕过、文件上传、敏感信息泄露；「缺少安全响应头」「Cookie 没加 Secure」这类加固项记台账，不占关键时间。
3. **动态扫描要先扫再复核**：把高危项挑出来人工复验，不复验就不算结论 —— 扫描器的误报会让开发不信任你的报告。
4. **人工做业务逻辑验证**：扫描器永远覆盖不了的部分，如「换个 ID 能不能看别人订单」「优惠券能不能叠加刷」「审批能不能自己批自己」。
5. **结论写成风险清单**：每条含「入口 + 复现步骤 + 影响 + 建议修法 + 是否阻断上线」，而不是一句「存在中危漏洞若干」。
6. **明确边界**：三天覆盖的是「高风险面 + 本次改动」，不是全量；剩余范围记成待办并约好复盘时间。

### 知识点：安全测试的四个层次 —— SAST / DAST / IAST / SCA 分别管什么

| 层次 | 看不看运行 | 擅长 | 盲区 | 典型工具 | 适合的节奏 |
|---|---|---|---|---|---|
| SAST 静态 | 不运行 | 提前到编码阶段、能定位到代码行 | 误报高、看不懂运行期才成立的漏洞 | Semgrep、SonarQube、CodeQL | 提交/合并门禁 |
| DAST 动态 | 运行中探测 | 不挑语言、能发现真实可利用问题 | 爬不到的接口、依赖复杂业务状态的漏洞 | OWASP ZAP、Burp Suite | 测试环境定期跑 |
| IAST 交互 | 运行中插桩 | 误报低、覆盖面广（能看到实际执行的代码） | 需部署 agent、对性能有少量影响 | OpenRASP、商用 IAST | 测试环境常态化 |
| SCA 成分分析 | 不运行 | 第三方依赖的已知 CVE，性价比极高 | 只管依赖、不管自研代码 | Trivy、Dependency-Check、Dependabot | 提交门禁 |

**实践口径**：这四层都是「发现手段」，能不能闭环取决于是否有人复核与修复。串成流程：SCA 与 SAST 进提交门禁（只拦高危且已确认的），DAST 与 IAST 定期全量跑，结果统一进漏洞台账并跟踪到关闭。业务逻辑漏洞（越权、参数篡改、业务流程绕过）任何工具都测不出来，必须靠人工设计用例。

### 知识点：越权的两大类与最容易被漏的三种入口

- **水平越权**：同角色、不同数据归属 —— 用 A 的凭证访问 B 的资源 ID，「是否成功」即判据。
- **垂直越权**：低权限用户执行高权限操作 —— 用普通账号调管理端接口，前端隐藏入口不算防护。
- **最容易被漏的三种入口**：
  1. **批量与导出接口**：单条校验了权限，批量与导出常直接按 ID 列表取数，漏掉归属校验；导出一次泄漏一整个数据集。
  2. **旁路接口**：分享链接、预览链接、回调地址、文件下载地址、二维码 —— 为「免登录也能用」往往只校验一个可猜测的 token。
  3. **写操作与状态流转**：查询做了校验，但修改、删除、审批、状态推进没做。
- **落地做法**：产出权限矩阵（主体 × 客体 × 动作），矩阵能直观看出哪些组合没被覆盖，也便于回归。

### 技能：安全测试体系与漏洞闭环

- **定位**：重点不在「会用扫描器」，而在「知道扫描器测不到什么」—— 越权、参数篡改、业务流程绕过只能靠人工，也恰恰危害最大。
- **常用工具**：OWASP ZAP、Burp Suite、Semgrep、Trivy、sqlmap、SonarQube。
- **要点**：按资产与入口排优先级，优先「不需要登录就能碰到」的面；四类手段组合使用并理解各自盲区；越权产出权限矩阵；扫描结果必须人工复验；结论落成风险清单（入口 + 复现 + 影响 + 修法 + 是否阻断上线）。

### 坑点：把安全测试做成上线前的一次性动作

- **表现**：安全需求不做安全设计、编码阶段不扫依赖也不做静态检查，全堆到上线前集中测三天。最常见的问题反复出现，且每次都在「时间最紧、改动最多」的时刻暴露，最后只能以「已知问题、下期修」收尾。
- **破解**：把安全测试拆进流程，每层做自己最擅长的事 —— 依赖漏洞扫描与静态检查进提交门禁（成本极低、能拦住大部分老依赖带来的 CVE）；动态扫描与人工业务逻辑验证按版本节奏定期做；新功能上线前做针对性评估（只看本次改动涉及的入口）。一次性安全测试只能证明「那天没问题」，不能证明「一直是安全的」。

### 坑点：越权用例只用一个普通账号跑一遍就下结论

- **表现**：用一个账号登录，试试改 URL 里的 ID 能不能看别人的数据，没成功就写「越权测试通过」。水平越权需要两个同角色、不同数据归属的账号才能验证；垂直越权需要低权限账号去调管理端接口；查询之外的改、删、导出、批量和分享链接全没覆盖。
- **破解**：矩阵化 —— 三到四类主体 × 各类客体数据 × 六种动作，逐格验证并记录哪些格子未覆盖。产出物应是权限矩阵，零散记录看不出覆盖漏洞。

## 二、接口测试

### 坑点：接口用例只断言 HTTP 200，把「没报错」当成「没问题」

- **表现**：只要返回 200、JSON 能解析就判通过。于是「返回了错误码字段但 HTTP 是 200」「金额没变但接口说成功」「库没写进去但响应正常」「返回了不该返回的用户手机号」全部漏过 —— 表面前端可能正常，业务数据已经错了。
- **破解**：断言至少分四层 —— **协议层**（状态码、Content-Type、耗时阈值）、**结构层**（JSON Schema、字段类型与格式）、**业务层**（业务字段是否符合逻辑）、**副作用层**（数据库、缓存、消息是否与响应一致）。最关键的是第四层：只看响应会被「接口说成功但实际没落库」骗过，关键写接口必须查库验证。

## 三、自动化测试

### 技能：自动化测试稳定性治理

- **定位**：自动化最大的成本不是编写，是维护。核心动作是把通过率拆成四类失败（环境问题 / flaky / 真实缺陷 / 维护性变更）分别统计，混在一起看就无法改进。
- **常用工具**：Playwright、Selenium、Appium、pytest-xdist、Allure、Jenkins。
- **要点**：flaky 按类归因（等待 / 数据竞争 / 顺序依赖 / 断言过严 / 环境抖动）；定位优先用测试专用属性（如 data-testid），不依赖文案与 DOM 层级；重试必须打标记录并进 flaky 榜单，让重试有账可查；连续 flaky 的用例移入隔离区，保持主干干净。

## 四、测试理论

### 知识点：缺陷漏测率的定义与口径陷阱

- **两种常见定义**：① 漏测率 = 上线后发现缺陷 ÷（上线前发现 + 上线后发现），衡量「测试阶段拦下了多少」；② 上线后发现缺陷 ÷ 本次发布用例数或需求点数，衡量逃逸密度。
- **三个必须写清的边界**：统计窗口（上线后多久内算本次）；缺陷来源与分级（用户反馈 / 客服工单 / 监控告警 / 内部自查，是否只算 P1/P2）；是否属于本次需求范围（既存问题、未改动模块、已知情登记的不算）。
- **口径陷阱**：只看漏测率不看绝对量会混淆两种走向 —— 「测试更严格 → 上线前发现更多 → 分母变大 → 漏测率下降」与「测试更松懈 → 上线前发现变少 → 漏测率上升」，前者说明改进见效，后者说明质量下降。**漏测率必须与缺陷发现曲线、上线后缺陷绝对数一起看。**
- **正确用法**：不做横向评比（团队间不可比），做纵向趋势与归因 —— 找出「漏掉的那几条」漏在哪个环节（需求歧义、用例缺失、环境限制、时间不足），针对性补。指标用来找改进点，不是用来定责。

### 技能：测试策略与准出标准设计

- **定位**：策略能力是高级测试工程师与执行者的分水岭。价值一半在说明「测什么」，另一半在明确「不测什么、为什么」—— 后者才是资源有限时的真实决策。
- **常用工具**：风险矩阵、正交实验表、状态机建模、TestRail、Xray。
- **要点**：先定质量目标（最怕什么）再决定测什么、投多少人力；按「输入→处理→存储→输出→依赖」五段画功能地图；有状态机的功能先画状态图，重点测非法流转与并发流转；用「影响面 × 发生概率 × 可发现性」排优先级；每类风险都能说清用什么手段验证（日志 / 数据库 / 抓包 / 埋点）。

## 五、场景题

### Q：线上出现「偶发下单失败」，用户投诉已经在传，你怎么一步步定位？

**结论**：先止血、再归因、最后闭环，顺序不能反 —— 用户还在受影响时去深挖根因是不负责的。

1. **先量化与止血**：确认影响面（所有用户还是特定用户/渠道/商品/时段）、失败率、是否在扩大。影响面大且有明确开关（降级、限流、切流量、回滚），先执行再找原因。
2. **拉证据链**：拿一条具体失败单号，沿链路追 —— 网关日志 → 应用日志（traceId）→ 下游服务 → 数据库/缓存 → 第三方。重点看失败发生在哪一跳、报什么错、谁先超时。
3. **用监控收敛范围**：失败率随时间的变化曲线，与发布记录、配置变更、定时任务、流量高峰做时间轴对比 —— 「变化的时间点对齐了什么」通常一步就能锁定方向。
4. **列假设并用数据验证**：常见方向有发布引入的变更、缓存击穿、并发抢空导致业务失败、第三方不稳定、连接池耗尽、单分片/单机异常。每个假设都用数据证实或排除，不靠讨论。
5. **做可复现的最小场景**：找到触发条件后在测试环境复现（同参数、同并发、同数据状态），能复现才说明根因找准了。
6. **闭环**：修复 → 把这次场景固化成自动化用例 → 补监控告警 → 复盘记录改进项。没有「补用例」和「补监控」的修复是不完整的。
