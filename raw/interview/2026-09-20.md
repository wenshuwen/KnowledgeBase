## 一、面试题精选

### 测试环境 · 环境漂移的三类可观测抓手

**Q：怎么证明测试环境没有漂移？你会用哪些可观测抓手？**

判断先行：**漂移防不住，只能被测量**。三类抓手，且都要做成跑业务用例之前的门禁。

1. **版本指纹（最有效）**：应用构建号 + 配置版本 + 数据库变更脚本版本三者合成一个指纹，由应用暴露在健康检查接口里。用例启动第一条就断言指纹，不一致直接判「环境不合格」，而不是让后面几十条用例产生一堆假失败。这一步的价值是把「环境问题」从主观判断变成可断言的布尔值。
2. **依赖清单**：中间件版本、运行时版本（JDK / Python / Node）、字符集与时区、各依赖实际指向的地址。定时采集存基线并做结构化 diff —— 只有 diff 出来，「昨天还好今天怎么就坏了」才有答案。
3. **行为基线**：核心接口 P95、错误码分布、慢 SQL 条数。它不是用来卡性能的，而是发现环境悄悄变了：整体 RT 上浮 30% 通常不是被测系统退化，而是节点被换了规格或落到了更远的机器。

配套判断：环境自检若只探端口通不通，等于只验了第一层；服务起来了但版本是昨天的、库里没有基础数据、配置指向了另一个环境 —— 端口全绿而用例成片失败，正是最常见的场景。

### 场景题 · 线上偶发问题的观察窗口与样本量

**Q：线上某接口偶发 500，频率低但每天都有，你怎么设观察窗口并给出结论？**

最大的风险是**用主观的「很少发生」给它结案**。步骤：

1. **先量化样本**：总调用量、发生次数与时间段分布、是否有固定时间点（定时任务、整点对账）、相关请求特征（特定用户 / 参数 / 来源 IP）。「每天都有」往往就是每天某个时刻的批处理在触发。
2. **按频率反推观察窗口**：日均约 1 次至少要观察 3~7 天才有统计意义，且窗口内样本量要足够（万级调用以上），否则「这三天没出现」不能证明修好了。观察前先把成功判据写下来（次数为 0，或错误率低于阈值且无新增堆栈特征）。
3. **主动补证据而不是等**：把异常堆栈、上下游耗时、关键参数哈希打进日志（注意脱敏），让下一次复现自带现场；窗口内仍未复现，就用放大压力、注入故障或流量回放主动构造触发条件。
4. **结论要带风险等级**：低频、非核心链路、有兜底的可带监控继续观察；核心链路或数据一致性问题，即使一天一次也按 P1 处理。

**「偶发」是现象，不是分类，更不能当结论。**

### 性能测试 · 接口异步化改造后的关注点转移

**Q：接口做了异步化改造（同步改异步 + 回调），性能测试的关注点怎么变？**

核心判断：**「接口响应快」不再是性能结论**，它只证明「受理快」，真正的耗时被挪到了后台。观测口径从「一次请求的 RT」转为「端到端时延 + 队列健康度」。

1. **端到端时延拆三段**：受理耗时（接口返回）、排队耗时（消息在队列等待）、处理耗时（消费者执行 + 回调）。用户感知是三者之和，只看第一段会得出严重乐观的结论。这三段埋点必须在设计阶段提出，事后补埋点往往要等下一版。
2. **队列健康度是新的崩溃形态**：异步系统出问题的表现不是 RT 变慢而是**积压** —— 生产速率长期高于消费速率，队列长度上涨、端到端时延持续膨胀。要测积压到多少开始影响业务、有无背压或降级、消费者扩容后积压能否收敛、恢复需要多久。
3. **顺带守住正确性**：异步化最常见的隐患是丢消息与重复消费，压测中要断言「发出请求数 = 成功处理数 + 明确失败数」，并把幂等验证纳入。
4. **容量口径改写**：容量不再是「接口 QPS 上限」，而是「**可接受的端到端时延下能持续处理多少 TPS**」，并与业务 SLO 对齐。

## 二、知识点精选

### 测试环境 · 环境配方的版本化与回滚

把「一套环境」当作产物：**编排文件 + 镜像 tag 清单 + 初始化脚本 + 配置快照**共同构成环境配方，配方进 Git 并打版本号。任何一次环境调整都改配方并提交，而不是登机器手改。

价值有三：**可重建**（新同学或新分支随时拉起一致环境）、**可 diff**（今天比昨天多了什么，一问就有答案）、**可回滚**（环境出事的应对不是慢慢查，而是回滚到上一个配方版本重新拉起）。这是环境从「手工维护的资产」变成「可复现产物」的关键一步，也是「随时敢删环境」的前提 —— 只有能重建，环境才敢重置。

### 数据库 · 数据库指标联读与连接泄漏

**联读定性**：连接数先涨而 QPS 不涨 → 慢 SQL 或锁等待占住连接；QPS 先涨带动连接数 → 容量问题；连接数贴上限且 QPS 下跌 → 连接池耗尽（Sleep 居多＝应用不还连接，活动居多＝数据库侧慢）；慢查询涨而 QPS 平 → 数据量或执行计划变化。诊断结论必须附验证方式，否则只是猜测。

**连接泄漏只能靠趋势发现**：让应用暴露连接池活跃 / 空闲 / 等待数并接监控；写一条不变量断言「每次请求结束后活跃连接回到基线」，用恒定并发跑 10~30 分钟采样 —— 健康曲线呈锯齿状（有借有还），泄漏曲线呈**台阶式单调上升**直到打满上限。覆盖率上必须包含异常分支（出错未走 close / finally）、异步任务与批处理；定位时临时打开连接池的泄漏检测阈值，超时未归还即刻打印申请堆栈。

### AI 测试 · AI 功能降级的三个验收维度

降级逻辑平时永远走不到，必须用故障注入主动触发，覆盖超时、限流 / 配额耗尽、异常返回（空值、非法 JSON、截断）三类故障。

1. **触发正确性**：降级被触发且只触发一次，重试与降级不叠加 —— 常见缺陷是一个请求既重试三次又走兜底，用户等了两倍时间还拿到低质量答案，要断言总耗时在可接受范围内。
2. **兜底输出质量与安全**：规则兜底用模板或检索结果拼装，要验它不说误导性内容、不含未脱敏原文；尤其要测「模型输出 + 兜底内容拼接」的自相矛盾情形。
3. **可观测与可恢复**：降级必须打点（降级率、触发原因、耗时），否则线上一片降级你可能完全不知道；同时验模型恢复后自动切回、切换过程不抖动。

补充维度：**降级是否对用户显式告知**。让用户误信一个降级答案的代价，可能高于直接报错。

## 三、技能精选

### 测试环境 · 环境编排与一键重建

把整套环境写成可执行的编排文件，任何人任何时间都能拉起与配方一致的环境。核心不是「搭得快」，而是**「随时敢删」**——只有能重建，环境才敢重置。

**落地要点**：所有依赖版本集中在一个清单文件里，禁止散落；写**就绪探针而不是 sleep 等待**（容器起来 ≠ 服务可用，这是随机失败的头号来源）；提供 `make up / make reset / make destroy` 三条标准命令，把「重置环境」变成零心理负担的操作；把「重建耗时」当指标持续优化 —— 它直接决定出问题时你多久能拿到一个干净环境重新验证。

### 安全测试 · 接口鉴权矩阵测试

用「**角色 × 资源 × 操作 × 数据域**」四维矩阵穷举越权路径，核心目标是验证**服务端是否独立鉴权**，而不是依赖前端隐藏或网关拦截。

- 资源维度要覆盖列表 / 详情 / 导出 / 附件 / 报表，以及主键传参与业务编码传参两种方式；列表最容易只按角色过滤而漏掉数据域条件。
- **同角色不同数据域必须单独成维度**：多租户场景里两个普通用户权限模型完全相同，差别只在数据归属，这是最易失守也最难发现的边界；导出与批量接口常单独实现，是重灾区。
- 链式越权比单点越权隐蔽：通过订单 ID 拿到用户 ID，再用它去查对方信息。
- 必须补一条**网关旁路验证**：直连后端服务是否无需鉴权即可访问、内部认证头能否被伪造。若成立，则网关上的全部安全策略等同于未做。

矩阵要沉淀成脚本 + 数据构造（自动建两个租户各造数据），每次发版自动跑 —— 权限逻辑改一次就可能回归，人工回归不可持续。

### AI 测试工具 · AI 辅助日志归因

用 LLM 对失败日志做初步归因（环境 / 脚本 / 缺陷），采用**「AI 给建议 + 人工复核」**的协作模式，落点是缩短排查时间，而不是取代人。

**评测口径**：先建人工标注样本并核对一致率（低于 80% 说明分类标准本身不清，要先统一标准）；看**混淆矩阵而非准确率**（准确率会被大量正常样本稀释），最关键指标是「真实缺陷」类被误判为环境问题的漏检率；「无法判断」要单独成一类，不强行二分。

**工程约束**：不进硬门禁（误报阻塞发布的代价高于收益）；复核结果反哺为新样本形成迭代闭环；错误类型会随时间漂移，指标要按月重算，不能拿上线首月成绩一直说事。

## 四、坑点精选

### 场景题 · 用「偶发」给问题结案，不给频率与样本量

**表现**：「生产上偶尔会有」听起来像结论，其实什么都没说 —— 不知道频率、影响面，也不知道观察了多久。后果是问题被无限期悬着，直到某天放大成事故。

**破解**：把描述换成数字（出现次数 / 总调用量 / 时间段分布 / 影响用户量），并写下观察窗口与成功判据。窗口内未复现不等于修好，要么主动构造触发条件，要么给出「带监控继续观察」的结论并标注风险等级。

### 合规 · 把生产脱敏数据直接喂给外部模型

**表现**：「已经打过码了」是最常见也最危险的判断。掩码后的记录仍可能通过时间、地点、金额等准标识符组合重识别到个人，一旦外发就是数据泄露事件，且往往无法撤回。

**破解**：按数据分级决定去向 —— 合成数据与无个人属性参数可直接外发；含准标识符的数据必须泛化、加噪或聚合后再用；原始生产数据与凭据一律禁止外发。把判断做进架构（默认走私有部署模型）并在出口侧加敏感检测与审计日志。若业务确实需要真实分布，正确做法是**用合成数据复现分布特征**（类型、长度、基数、关联规则），而不是把真数据洗一洗就外发。

### CI/CD · Feature Flag 上线后长期不清理

**表现**：开关全量后无人认领，半年后台账里堆满没人说得清用途的 flag，代码里遍地开关分支。对测试的伤害很具体：开关是关着的 —— 用例跑了、绿了，其实什么都没验到；以及「旧功能与新功能同时打开」这类从未被测过的组合状态。

**破解**：flag 必须登记 owner 与预期清理时间，全量后自动开清理任务单并设到期时间，无主的定期强制清理；测试侧两条硬要求 —— **开工前落一份当前生效 flag 快照随用例结果留档**（便于解释「同一个用例为什么昨天过今天挂」），**关键用例对开关状态参数化**（开 / 关各跑一遍），不依赖环境当前值。
