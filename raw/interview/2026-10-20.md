## 一、AI 测试工具

### 知识点：合成数据的代表性看三个对照

判断「合成数据够不够用」，不看造了多少行，看三组对照：

| 对照 | 比什么 | 不一致的后果 |
|---|---|---|
| 基数 | 行数、枚举值数量、空值率 | 索引选择与排序行为失真 |
| 分布 | 关键字段直方图，尤其长尾（最大值与 P99 的倍数） | 溢出、精度、深分页问题测不出来 |
| 效率 | 同一批 SQL 在合成库与生产结构库上的执行计划 | 执行计划不同，则性能结论不可信 |

**实践要点**

- 合成数据能替代「数量」，替代不了「分布」；性能类结论尤其不能建立在均匀分布上。
- 必须专造一批「脏样本」：超长字符串、emoji、跨时区时间戳、重复值、负数、null。真实系统的故障集中在这些位置，而合成数据往往太干净。
- 造数量级不能省：几千条数据测不出索引失效与深分页，该按量级造就得造，哪怕跑一小时。

### 技能：AI 生成用例的评审闸门设计

AI 的产出量远大于人工评审的吞吐量，直接导致两种结局：全信（等于没评审）或全不信（等于白生成）。解法是把「信不信」拆成机器能过的关：

| 闸门 | 判什么 | 处理方式 |
|---|---|---|
| 结构闸 | 字段齐全、类型正确、id 唯一 | 全自动拦截 |
| 判据闸 | 期望结果是否含可观测对象与阈值 | 出现「正常/合理/符合预期」即打回 |
| 去重闸 | 标题与步骤的相似度 | 超阈值标「疑似重复」 |
| 覆盖闸 | 与需求条目的映射 | 只报告零覆盖，不拦截 |
| 人工闸 | 语义合理性与业务前置 | 只抽查，不逐条读 |

**实践要点**

- AI 生成用例有三个稳定偏向：偏正常路径、偏描述性判据、偏重复。三者都要靠闸门拦，不能靠提示词解决。
- 「疑似」与「确定」必须分开报：确定的直接拦，疑似的给人看，否则误杀会把整批堵住。
- 校验器要一次收集全部问题再统一输出，遇错即停会让你来回跑十几遍。

## 二、Agent

### 知识点：Agent 记忆的三类失效

| 失效类型 | 表现 | 危害 |
|---|---|---|
| 该记的没记住 | 指代断裂、约束丢失（说了要便宜的，后续仍推贵的） | 体验差，用户会重述 |
| 该忘的没忘 | 偏好已更新，旧记忆仍在生效 | 更危险：用户不知道 Agent 在按过期信息行动 |
| 不该记的记了 | 临时信息、敏感信息写入长期记忆，甚至跨用户泄漏 | 安全问题，可能违规 |

**判据**：不看它有没有「提到」，而看**行为有没有变**。用户说过对某成分过敏，推荐结果里是否真的排除了相关项——这才是记忆生效的证据。

### 问题：Agent 工具参数错误，怎么区分是模型问题还是工具描述问题

**Q：Agent 调工具时参数传错了，你怎么判断问题出在哪？**

先做两个交叉：换一个模型还错不错、换一种描述还错不错，四象限定位。

| 现象 | 归因 | 处理 |
|---|---|---|
| 换模型仍错，换描述就对了 | 工具 schema 表达问题 | 改描述，成本最低 |
| 换模型就对了 | 模型能力问题 | 换模型或精简上下文 |
| 都错，且换描述也错 | 上下文里没这个信息 | 补前置步骤或补数据源 |
| 都错，且描述怎么改都错 | 工具本身设计有问题 | 改参数语义、减少必填项 |

schema 的典型写法缺陷：参数名无语义（只写「订单号」，不说是用户侧还是内部 ID）、枚举用内部代号（`status: 3`）、参数间依赖未声明、多个相似工具（查订单 / 查物流）描述未区分。

**实践要点**

- 这类问题里七成以上是工具描述的问题。优化顺序应是：先改描述，再改上下文，最后才换模型。
- 把每次失败的工具参数、模型给的推理依据、上下文片段一起留存，形成「参数错误样本集」。同类错误反复出现＝schema 缺陷，零散出现＝模型波动。
- 顺手记住：正向用例测「它能不能做到」，反向用例测「它会不会做过火」，后者更易被漏。

## 三、大模型评测

### 问题：RAG 的「答对了」要分三层

**Q：上线一个 RAG 问答，你怎么定义一个答案算答对了？**

不用「像不像标准答案」，拆三层各自判定：

| 层 | 问什么 | 判定方式 |
|---|---|---|
| 检索层 | 依赖的片段召回了吗、排第几 | 完全客观：召回率、首位命中率 |
| 生成层 | 每个事实点有依据吗 | 逐句引用对齐，标不出支撑片段即无依据陈述 |
| 任务层 | 用户能据此解决吗 | 按评分细则人工或模型评分 |

三层是漏斗：检索不对不必看生成，生成不忠实不必看可用性。**分层的目的不是打分，是归因**——效果掉了能立刻分清是知识库、模型还是问题类型的问题。

**实践要点**

- 「答对了」必须绑定问题类型：事实型看准确率，流程型看步骤完整性，比较型看是否两方都覆盖。一个总分衡量所有类型，结论一定没用。
- 评测口径变了，任何跨版本对比都不可比，先对齐口径再谈效果。

### 坑点：用一条「标准答案」判断大模型答对没答对

**表现**：标准答案写「3 到 7 个工作日」，模型答「一般一周左右」被判错。算下来准确率很低，但实际体验并不差，团队因此不再信任评测结果。

**破解**：判据写成「必须包含的事实槽位」而不是整段文本——金额、时效范围、适用条件、极性。槽位齐了就算对，表述自由。这样评出来的数才和用户感受对得上。

## 四、工程纵深

### 知识点：AI 检查进流水线的「建议 / 阻断」双通道

| 通道 | 放什么 | 是否阻塞 |
|---|---|---|
| 建议 | AI 评审意见、用例建议、风险提示 | 不阻塞 |
| 阻断 | 密钥泄露、无 where 的 update/delete、高危依赖、覆盖率硬阈值 | 阻塞 |

**为什么 AI 判断不能当门禁**：模型有误报，误报一旦阻断合并，团队的第一反应是找绕道，不是修问题；绕道一旦成为习惯，整条门禁就废了。阻断只应留给确定性、可复现、误报极低的规则。

**实践要点**

- 豁免必须填原因、定负责人、带时效，过期自动失效；无时效的豁免等于永久关闭。
- 耗时压住：只查改动文件、异步执行，超过五分钟一定会被绕过。
- 用数据证明价值：统计拦下多少真问题、多少误报；误报率超三成的检查应降级为建议。

### 坑点：造数脚本只写 insert，不写清理

**表现**：每天造一批数据，从不删。三个月后环境里有上千万条垃圾数据，慢查询全冒出来，谁也说不清哪些能删，最后只能说「重建环境吧」。

**破解**：造数与清理成对设计——数据带批次标记，清理按批次删，挂进 fixture 的 teardown 保证一定执行。留一个「一键清理今天造的数据」的命令。

### 坑点：把 AI 检查设成硬门禁，误报一堆把流水线堵死

**表现**：上线两周报了三百条问题，其中两百多条误报。开发开始习惯性点「忽略」，后来真问题也没人看了。

**破解**：先用一个月做「影子模式」，只报不拦，统计真问题率；误报超三成就降级为建议。门禁留给确定性检查，这是唯一能长期坚持的分工。

### 技能：Prompt 版本管理与回归基线

提示词是行为逻辑，不是配置项。它在后台被随手改一句，整个应用的行为就变了——「模型忽然变笨」的事故，追下去多半是某次未经评审的提示词改动。

| 做法 | 具体要求 |
|---|---|
| 版本化 | 提示词进 Git，改动走 MR，禁止后台直接编辑生效 |
| 变更说明 | 每次改动附「期望改变什么、不应改变什么」 |
| 回归 | 固定评测集与基线对比，通过后才允许发布 |
| 可回滚 | 保留旧版本，回滚时间按分钟计 |
| 扰动样本 | 纳入基线，防止改动让某类表达静默失效 |

## 五、场景与性能

### 问题：线上偶发白屏，怎么定界

**Q：用户投诉偶发白屏但复现不了，你怎么定界？**

复现不了通常不是问题神秘，而是现场没留下。按五步走：

1. **量化分布**：用户数、时段、机型、浏览器版本、网络、页面。分布本身能排除一半可能——集中机型是兼容性，集中时段是发布或定时任务，集中弱网是超时。
2. **补齐观测**：确认 JS 错误上报（含 sourcemap 还原）、资源加载失败上报、接口失败上报是否齐全。白屏最怕「前端啥也没报」，缺埋点就先补埋点，别继续猜。
3. **按层切分**：资源层（CDN 异常、旧 HTML 引用已删除的 JS）、渲染层（字段为 null 导致渲染中断）、数据层（接口慢且无错误态兜底）、兼容层（新语法旧内核不支持）、环境层（代理或拦截插件）。
4. **主动构造而非等复现**：限速、禁缓存、旧版本浏览器、构造超大或为空的响应、模拟资源 404。多数「偶发」在条件构造出来后是必现的。
5. **验证闭环**：除了修，还要回答「为什么监控没报」和「同类写法还有多少处」。

**经验**：占比最高的成因是**新旧版本混布**——旧 HTML 去请求已被替换的 JS 文件。判据很明确：比对 HTML 版本与 JS 的 hash 是否匹配，所以第一步就查这个，往往最快。

### 技能：压测报告的结论化表达

报告没人看，是因为它回答「我测了什么」，而不是「你该改什么」。四段固定结构：

| 段落 | 内容 | 关键要求 |
|---|---|---|
| 结论 | 承载多少、瓶颈在哪层、余量多少 | 数字必须带场景与配置 |
| 证据 | 具体位置 | 连接池活跃数打满、等待从 5ms 涨到 400ms、SQL 走全表扫描 |
| 建议 | 改什么、预期收益、成本、风险 | 按性价比排序，无成本估算无法排期 |
| 局限 | 环境差异、数据量级、是否 Mock、流量模型 | 报告的可信度来源 |

**写作三原则**：用对比不用绝对值（和上一版、和基线比）；给曲线不只给点（能看出拐点）；余量不足要直接写「不建议上线」，不要用「建议关注」这种软话。

**跟进**：发出去不算完，一周后要问「哪几条采纳了、哪几条没采纳、为什么」。没有跟进，报告就是文档垃圾。
