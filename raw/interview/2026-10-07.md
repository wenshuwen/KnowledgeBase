## 一、AI 测试

### Q：同一个问题问三遍得到三份不同答案，这种非确定性怎么设计断言？

**结论**：放弃对字面输出的断言，改为对「约束」与「语义」的断言，分四层从便宜到贵。

1. **硬约束断言**：长度范围、可否解析、字段是否齐全、枚举值是否在允许集合内、有无敏感词。这些是确定性的，直接断言。
2. **结构化断言**：要求输出 JSON 时用 schema 校验，不合规即判失败，必要时触发自动重试。
3. **语义断言**：用向量相似度或另一路模型做裁判，判「是否覆盖要点」而非「字面是否一致」。
4. **多次采样 + 比例判定**：参数固定、跑 N 次，以「达标率 ≥ 阈值」作为通过条件，同时把每次输出留档，便于对比版本漂移。

**关键补充**：评测模型自身也会漂移，必须锁版本、锁 prompt，并定期用人工标注的小样本校准判准——否则等于用一把会伸缩的尺子去量另一个不稳定的对象。

### Q：RAG 系统上线前重点测哪几层？线上答错时怎么判断是检索还是生成的问题？

**结论**：拆四层测，各层指标不同；线上定位靠「把召回的片段和最终回答一起打出来」这一步。

1. **数据层（入库）**：文档解析是否正确（表格、扫描件、多栏排版是重灾区）、切分是否切断完整语义、元数据（来源 / 版本 / 权限）是否带全。
2. **检索层**：用「标准问题 → 应召回文档」的标注集算 Recall@K / Precision@K，看多路召回融合后的排序。
3. **生成层**：答案是否忠于召回内容（是否幻觉）、引用是否指向正确片段、格式是否合规。
4. **端到端**：任务完成率 + 人工抽检。

**定位判据**：召回里本来有正确答案、生成却答错 → 生成层问题（prompt 或模型）；召回里根本没有正确答案 → 检索或数据层问题（切分粒度、embedding、权限过滤把正确内容滤掉了）。

**最易漏的一层**：不同角色的用户问同一个问题，召回范围必须不同。权限过滤必须单独造用例，这类问题一次泄漏就是事故。

### Q：Agent 会调用工具去查订单、发短信、退款，这类有副作用的调用怎么测才安全？

**结论**：绝不让测试直接打到真实副作用上；断言重点从「有没有真的执行」转为「有没有以正确参数、在正确时机发起调用」。

1. **环境隔离**：测试环境下游全部指向沙箱或 mock；做不到时至少让下游能识别测试标记并走干跑分支。
2. **工具层打桩 + 断言调用意图**：桩记录「被调用的工具与参数」，测试断言参数正确性与调用时机，而不是真实副作用。
3. **幂等与并发验证**：Agent 有重试机制，最易出的事故是重复执行。必须验证「重试、超时、并发下会不会重复发短信、重复退款」，判据是幂等键与落库流水，不是工具返回成功。

**两类必须单独测的越界**：**金额越界**（100 算成 1000、部分退款执行成全款）与**权限越界**（Agent 以服务身份调用，天然高权限，一次提示词注入就可能变成任意工具调用）。建议给高风险动作配「动作确认网关」（资金、外发消息、删除数据），并专门验证网关拦得住。

## 二、AI 测试知识框架

### 知识点：LLM 输出非确定性的三个来源与对应断言策略

| 来源 | 表现 | 断言策略 |
|---|---|---|
| 采样随机性（temperature / top_p） | 输入完全相同，输出仍不同 | 固定参数 + 多次采样 + 比例判定（N 次中达标 ≥ M 次） |
| 上下文变化 | 历史消息、召回片段、系统时间、工具返回值都会变 | 把上下文当输入的一部分固化——用例存完整消息数组，而非一句话 |
| 上游模型升级 | 供应商静默更新或主动切版本，输出分布整体漂移 | 固定模型版本号 + 建立回归基线，每次切版本跑全量评测集对比涨跌 |

**实践口径**：把「结构合法性」与「内容正确性」分开断言。结构（JSON 可解析、字段齐全）是确定性的，可以硬断言，能让用例尽早失败，省下后面昂贵的语义判定成本。

### 知识点：幻觉的三种成因与分层的抑制、验证手段

| 成因 | 抑制手段 | 验证手段 |
|---|---|---|
| 知识缺失型（模型本来没有这块知识） | 接检索（RAG）+ 系统提示限制「只依据给定资料回答」 | 忠实度评测：把答案拆成原子陈述，逐条判断是否被召回内容支持，算支持率 |
| 上下文冲突型（召回资料互相矛盾或已过期） | 数据治理：资料带版本号与生效时间，检索时先过滤 | 构造含新旧版本冲突的用例，断言模型采用现行版本 |
| 指令泛化型（为回答完整而自行补全细节） | 输出约束：要求逐句引用来源，无依据时明确输出「不知道」 | 拒答评测：造一批知识库无答案的问题，看是否老实说不知道 |

**拒答率的双向含义**：拒答率过高说明业务可用性差，过低说明幻觉风险大——**两个方向都是问题**，必须一起看。

**长期观测**：线上把「未命中知识库但仍给出确定性回答」的请求单独打标并人工抽检。幻觉不可能被消灭，只能被圈定并持续监控。

### 知识点：Agent 测试的五个观测面

1. **任务完成度**：最终有没有达成目标。唯一的硬结果，但颗粒度太粗，不能只有这一层。
2. **轨迹合理性**：调用了哪些工具、顺序对不对、有没有绕路或死循环。可断言「必须先调 A 才能得到 B」「禁止调用超权限的工具 C」。
3. **工具调用正确性**：参数拼得对不对（金额、时间、ID）、失败后是否按策略重试或降级、超时如何处理。
4. **成本与步数上限**：一次任务的 token 消耗与步数必须有上限。没有这个约束，一个 bug 就能循环几百次，成本直接失控。
5. **时延**：首字时延与端到端时延，多步任务的累积时延尤其要盯。

**工程关键**：先把工具层 mock 掉做离线、可重复的逻辑评测，再用少量真实端到端用例验证集成；必须把完整轨迹（每步的思考、工具、参数、返回）落盘，否则出问题连复现都做不到。

## 三、技能与工具

### 技能：大模型效果评测与指标设计

**定位**：传统测试靠断言，大模型测试靠指标加评测集；这项能力的核心是给定业务场景能设计出可衡量、可复现、能指导决策的评测方案。

**五个要点**：
1. 先定指标再选工具：意图分类看准确率/召回，问答看要点命中率，生成看格式合法率。
2. 评测集覆盖四类样本：正常问法、边界问法、对抗问法、应拒答场景。
3. 固定模型版本与采样参数，把「版本」当成回归变量。
4. 用人工标注的小样本定期校准自动评测的判准，防止尺子本身漂移。
5. 评测报告要能回答三件事：涨了多少、降了多少、哪些用例回归了。

**常用工具**：Promptfoo、RAGAS、DeepEval、LangSmith、OpenAI Evals。

### 技能：Agent 行为轨迹的评测与可观测性建设

**定位**：Agent 的不确定性在「过程」里，不会观测轨迹就只能测个大概。

**五个要点**：
1. 每次执行落完整轨迹：每步的输入、思考、工具名、参数、返回、耗时、token。
2. 断言分两层：最终任务完成度 + 中间轨迹约束（必调某工具、禁调某工具、步数上限）。
3. 把工具层 mock 掉，让 Agent 逻辑能离线、可重复地评测。
4. 给成本与步数设硬上限，超限即判失败并告警。
5. 用少量真实端到端用例验证集成，其余用离线评测跑量。

**常用工具**：LangSmith / LangFuse、OpenTelemetry、自定义 trace 落盘、pytest 加工具层 mock。

### 技能：AI 辅助生成用例的适用边界与人工把关点

**定位**：把 AI 用在「发散和重复劳动」上价值最大，用在「判定业务正确性」上最危险。

**适用边界**：
- **适合交给 AI**：扩展测试思路（补边界与异常组合）、把需求文档转成用例草稿、生成重复度高的数据与桩、把自然语言描述转成脚本骨架。优势是发散和批量。
- **不适合交给 AI**：判定业务正确性、决定测试优先级、确认接口字段与业务规则的事实性——因为 AI 会一本正经地编造字段名、接口路径和业务规则。

**三个把关点**：入库前的事实性核对（接口、字段、枚举值都要与真实文档对齐）；覆盖率比对（AI 倾向写正常流程，异常与边界要人工补）；最终判准由人拍板。

**价值判据**：用「人工修改率」衡量——如果一半以上的产出要被重写，省下的时间可能还不如自己写，PoC 就该叫停。

## 四、面试坑点

### 坑点：把大模型的「不稳定」当成 bug 去修

- **表现**：看到同一问题两次答案不同就提缺陷，开发回复「这是模型特性」，来回扯皮，缺陷被挂起，评测进度也停了。
- **破解**：先区分「非确定性」与「错误」——非确定性是采样带来的合理差异，错误是不满足业务约束。把断言建立在约束与指标上（格式合法率、要点命中率、拒答正确率），对多次采样做比例判定，而不是逐字比对。评测阈值要和产品一起确认，白纸黑字写进验收标准。

### 坑点：只断言 Agent 的最终输出，不看中间轨迹

- **表现**：用例只检查「最后有没有答对」，结果 Agent 绕了十步、调了错误的工具、甚至调用了越权接口，只要最后蒙对就算通过，问题被完全掩盖。
- **破解**：把轨迹也纳入断言——必须调用哪些工具、禁止调用哪些工具、总步数上限、每次工具调用的参数正确性。同时把完整轨迹落盘，失败时能直接看出是哪一步跑偏，而不是只看到一个错误结果。

### 坑点：给 Agent 的失败重试不设上限，一次故障就让成本失控

- **表现**：某个工具偶发超时，Agent 陷入重试循环，一个请求跑了几百步、烧掉大量 token，账单出来才发现。
- **破解**：在 Agent 层设三重硬限制——最大步数、单次任务 token 上限、总耗时上限，任一超限立即终止并记为失败。同时给工具重试加指数退避与次数上限，并把「重试次数超阈值」接入监控告警。成本与步数必须是被断言的指标，不能只当观察项。

## 五、待图谱化的候选关联（供每周编译时判断，勿在此处建链）

- 非确定性断言 ↔ 传统用例有效性三问（「它能失败吗」在 LLM 场景下的变体：它会不会因为噪声而红）
- 忠实度评测 ↔ RAG 检索层指标（Recall@K 决定忠实度的上限）
- Agent 轨迹断言 ↔ 接口契约测试（两者的共同点：把「过程」变成可比对的结构）
- Agent 动作确认网关 ↔ 测试环境危险操作防护（生产禁写 / 沙箱隔离）
- AI 辅助生成用例 ↔ 用例有效性自检（AI 产出必须过同样三问）
- 内容安全评测集 ↔ 回归评测集（安全用例应是硬门禁，与功能评测分库管理）
- 提示词版本管理 ↔ 环境即代码（同属「把可变因素纳入版本控制」的思路）
