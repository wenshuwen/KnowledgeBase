## 一、性能测试

### 1. 队列积压的两个判据：消费 TPS 与积压斜率

**Q：生产端稳定 3000 QPS、消费者只跑到 2400，积压从 2 万涨到 40 万，是消费端慢还是流量本来就超了？**

判断积压性质，只需要两个数：

- **消费 TPS**：把生产端停掉，让消费者单独追积压，得到的才是消费能力的真实上限。追到 5000 说明是生产猛；只有 2400 且越追越慢，说明单条处理退化（下游超时、重复重试、锁竞争）。
- **积压斜率**：生产 TPS 减消费 TPS。若稳定为正且等于这个差值（约 600 条每分钟），是**纯容量缺口**；若斜率随时间变大，说明越追越慢，属于**消费劣化**。

补一条交叉判据：**积压增长时消费 TPS 是否同步下滑**——下滑即劣化，不下滑即产能不足。

容易被忽略的第三种情况：**毒消息**。消费失败重投会让同一批消息反复出现，表面看是积压，本质是消费失败率在放大，此时要看死信队列与重试次数，而不是加消费者。

> 迁移到通用场景：任何「生产者 - 队列 - 消费者」结构（消息队列、日志管道、异步任务），判据相同——先量化稳态消费能力，再看斜率，最后看积压增长时的消费 TPS 走势。

### 2. 安全水位的三个决定因素

安全水位不是拍一个百分比，而是三个约束的交集：

| 因素 | 含义 | 对水位的影响 |
|---|---|---|
| 拐点位置 | 延迟开始非线性上升的负载点 | 水位必须明显低于拐点 |
| 突发余量 | 线上流量突发系数，常见 1.3~1.5 | 保证突发时不越拐点 |
| 故障冗余 | N+1 冗余下少一台时剩余节点能否承接 | 有效容量再降一档 |

同一套系统在不同冗余策略下水位不同：单机无冗余可能只敢定 50%，多副本可到 70%。所以结论要按「当前冗余策略下建议水位 X%，依据拐点 Y、突发系数 Z」来写，**裸百分比没有信息量**。

### 3. 容量规划与水位核定的三件交付

容量规划的产出不是「一份压测报告」，而是三件东西：

1. **容量曲线**：阶梯加压（从 500 并发起每 5 分钟加 500）直到 P99 破阈值或错误率破 1%，记录该点作为拐点；
2. **安全水位**：以拐点吞吐的 70% 反推并发数与机器台数，注明依据来自哪一轮压测；
3. **扩容建议**：4 台与 8 台各压同一场景，比对**单机有效 QPS**，衰减超 15% 即判定存在共享瓶颈，并列出候选（数据库连接、缓存单分片、队列分区、网关转发）。

> 判据要点：扩容之后必须复测单机有效 QPS。把「加机器等于翻倍」写进容量规划，是大促事故最经典的起点。

## 二、安全测试

### 4. 全链路压测的流量染色三要素

**Q：压测流量要引到接近生产的链路，怎么保证不污染真实数据？**

染色不是加一个请求头就完事，要保证三件事同时成立：

- **透传**：标记在网关注入，经 RPC、消息队列、异步任务全程不丢。任何一跳丢了标记，就会写进真实库。
- **路由**：按标记切换影子表、影子 topic、缓存前缀，读写都走影子。
- **兜底**：识别不到标记的写入**默认拒绝**，只放行白名单。默认拒绝远比默认写入安全。

验证方式要两头看：压测后**真实表行数增量为 0**，同时**影子表确实有数据**。只查一头都可能漏——真实表没变也可能是流量根本没打进来。

### 5. 压测流量的安全边界与凭据管理

| 边界项 | 做法 | 验收判据 |
|---|---|---|
| 流量放行 | 来源白名单，限定时间窗，结束自动失效 | 报告记录防护状态（全开/白名单/关闭） |
| 凭据 | 环境变量或密钥服务读取，仓库不留明文 | 密钥扫描命中即阻断提交 |
| 账号 | 单独开、权限只覆盖压测数据、设有效期 | 用完即停 |
| 写入 | 影子表 / 影子 topic / 缓存前缀 | 真实表零增量 |

两条容易被忽略的推论：

1. **误杀本身就是结论**。防护因高频同源误判正常业务，说明真实高并发下它也会误杀，要报给安全团队评估阈值，而不是忽略。
2. **限流阈值低于系统容量时，应用层扩容等于白做**。用户会先被网关拦住，还没到应用。

## 三、数据库

### 6. 主从延迟的观测与容错口径

**Q：读写分离架构，压测时主从延迟被放大，用例怎么写？**

延迟的测试重点不是「复制有多快」，而是「读到旧数据时业务能不能接受」。

- **观测**：复制延迟与位点差距都要采，取 P99 与最大值。平均值没有意义——平均 200ms 但峰值 5 秒，用户照样看到空列表。
- **分级**：余额、库存、订单状态属强一致，必须走主库；列表、统计属最终一致，可接受秒级延迟但要给上限。
- **用例**：两条最容易暴露问题的是「写后立刻读」与「写后立刻列表查询」。这正是线上「下单成功但列表里没有」的根因。
- **兜底**：延迟超阈值时要能降级走主库，且降级不能反过来把主库打挂。

### 7. 慢查询在压测里的四种伪装

低 QPS 高慢查询，通常落在这四类：

| 类型 | 表现 | 排查抓手 |
|---|---|---|
| 索引失效 | 字段被函数包裹、隐式类型转换、前缀模糊匹配 | 执行计划看 type 与 rows |
| 深分页 | 越翻越慢，几万页时单条查询吃满 IO | 对比不同页码的执行计划 |
| 大表 JOIN / 统计 | 报表类查询挤占联机事务资源 | 压测时段 Top SQL 排行 |
| 造数失真 | 随机数据命中率极低，线上快的查询在压测里全表扫 | 按真实分布造数后复测 |

处理顺序固定：**先出 Top SQL 与执行计划，再判断是代码问题还是造数问题**。只写「慢查询多」的报告，开发改不动。

## 四、AI 与 Agent 测试

### 8. AI 读压测报告的能见度边界

| 能力 | 能做 | 不能做 |
|---|---|---|
| 指标筛查 | 从数百指标中挑出偏离基线最大的几项 | 判定偏离的业务影响 |
| 形态归纳 | 把耗时曲线分类为台阶型、锯齿型、线性上升 | 判定尖刺成因（需日志时间戳与线程栈） |
| 文本产出 | 生成报告叙述初稿 | 替代证据链 |

核心风险是**把相关当因果**。可操作的做法：让 AI 出候选清单，人工逐条用监控、日志、火焰图证伪；报告里标注「AI 初筛、人工核验」。验证工具本身可信度的方法，是拿 3~5 个**已知根因**的历史案例做回放对照，方向判对少于 2 条就降低它在流程中的权重。

### 9. Agent 压测的双层指标

Agent 服务不能只看 QPS 与延迟，必须两层一起看：

- **任务层**：成功率、任务 P95 时长、平均步数、重试次数。
- **步骤层**：模型调用耗时、工具调用耗时、编排自身耗时、单步失败率。

关键结论：**并发升高时若平均步数上涨，说明系统在反复试错**。此时成功率可能还有 95%，看着达标，但成本与耗时已经翻倍——这是隐性容量消耗，也是账单爆炸的前兆。达标线应写成三条绑定：成功率达标、P95 达标、平均步数不显著上涨。

### 10. Agent 容量与隔离验证

三组最有效的场景：

1. **并发下步数漂移**：10 并发与 100 并发各跑 200 个任务，比较平均步数，上涨超 20% 即判定存在重试放大；
2. **分段耗时拆解**：把任务拆成推理、工具调用、编排三段打点，定位占比最高的一段再定向优化；
3. **上下文串台**：多用户并发跑各自任务，抽查输出是否混入他人会话内容，出现 1 例即判隔离失败。

> 对外部工具的压测原则：**默认全部用替身**，只有拿到明确许可的才打真实第三方，且要限速。容量测试测的是自身编排能力，把对方打挂要背的是一起线上故障。

## 五、常见坑点（性能方向）

### 11. 性能报告只写 QPS 和平均耗时，不写错误率与队列积压

报告上吞吐 8000 看着漂亮，实际里面 12% 是报错，队列还积压 30 万条。上线后用户看到的是报错和延迟，报告却显示「性能达标」。

**破解**：报告至少四条线——**有效吞吐、错误率、P95 与 P99、资源与队列水位**。有效吞吐要扣除断言失败的请求，队列积压单独给趋势图。

### 12. 全链路压测不染色，压测订单写进真实业务表

为「更真实」把压测流量打到真实链路，压测结束真实业务表多出几万条脏数据，当天对账全乱，还要停机清洗。

**破解**：染色（请求头全程透传）加影子表与影子 topic，再加**未识别标记默认拒绝**；压测后核对真实表行数增量为零。

### 13. Agent 压测只看任务成功率，不看平均步数

100 并发下成功率还有 95%，看着达标。实际 Agent 因为工具调用失败在反复重试，平均步数从 6 步涨到 14 步，成本翻了倍。

**破解**：成功率、P95 时长、平均步数、重试次数四条一起看。步数随并发上涨就是重试放大。

## 待图谱化的候选关联

以下为后续做单源精读时可展开的方向，本文不建立交叉引用：

- 积压斜率 → 容量缺口的判定口径、生产者与消费者的配额对齐
- 安全水位 → 拐点定义、突发系数、故障冗余的容量折算
- 流量染色 → 影子库设计、测试数据治理、生产数据脱敏
- 高水位下的限流 → 网关限流与系统容量的关系、降级预案的有效性
- 主从延迟 → 读写分离的一致性分级、强一致路径的界定
- 慢查询四类伪装 → 执行计划解读、造数分布的真实性
- AI 归因边界 → 相关与因果的区别、证据链的最低要求
- Agent 双层指标 → 重试放大的成本模型、多用户上下文隔离
- 平均值的失效 → 分位数口径、长尾对体验的影响权重
