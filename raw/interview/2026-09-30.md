## 一、测试理论（theory）

### 题 1：面试官问「测试的价值怎么证明」，怎么用量化模型回答？

**Q：** 面试官问「测试的价值怎么证明？老板觉得测试就是成本中心」。你会怎么用量化模型来回答？

**A：** 别讲「我发现了多少缺陷」——那是工作量不是价值。用 **质量成本（Cost of Quality, CoQ）** 把「测试投入」和「没有测试的代价」放在同一张账上算。

**四象限：**
1. **预防成本**——需求可测性评审、用例评审、自动化框架与环境治理。花在缺陷产生之前，最便宜。
2. **评估成本**——执行测试、回归、性能与安全验证。
3. **内部失败成本**——提测返工、缺陷修复、环境重搭。
4. **外部失败成本**——漏到线上的缺陷：客诉、退款、紧急发布、品牌损失。**通常比前三项加起来高一个量级。**

**落到数据上：** 用「缺陷逃逸率」（线上缺陷 ÷ 总缺陷）、「缺陷发现阶段分布」（越靠左越省）、「返工工时」三个指标画趋势；线上逃逸缺陷按影响用户数 × 平均损失折算金额。

**加分点：** 主动指出 CoQ 的边界——不能为了压外部失败成本而无限抬预防成本，判断标准是**边际投入是否还能换回边际损失下降**。这正是高级测试要做取舍的地方，也解释了为什么不是「测越多越好」。

### 知识点 1：质量成本（CoQ）四象限

**要点：** 质量成本是把「质量」翻译成钱的一套模型，也是回答「测试值不值」最有力的框架。

- **① 预防成本**：需求可测性评审、用例评审、自动化框架与环境治理、编码规范与静态检查。四象限里最便宜的一环。
- **② 评估成本**：执行测试、回归、性能与安全验证、评测集维护。
- **③ 内部失败成本**：提测被打回、返工、缺陷修复、环境重建、阻塞等待。
- **④ 外部失败成本**：客诉、退款赔付、紧急发布、品牌损失——比前三项加起来高一个量级，是论证测试价值的主战场。
- **落地指标**：缺陷逃逸率、缺陷发现阶段分布、返工工时占比；逃逸缺陷按「影响用户数 × 单次损失」估金额。
- **关键取舍**：不是「投入越多越好」。一旦某环节投入已换不回损失下降，应主动提出缩减——**只会证明「该加投入」的测试，说服力反而弱**。

### 技能 1：质量成本核算与测试投入决策

- **能力定义**：用 CoQ 四象限把测试投入与漏测代价放在同一张账上算，据此决定「哪些环节该加投入、哪些已边际失效」，把测试价值从「工作量」升级成「财务语言」。
- **常用工具**：缺陷系统导出的阶段分布与逃逸统计、线上事故与客诉台账、工时与返工率报表、Pandas / BI 看板做趋势与边际分析。
- **五个关键动作**：① 口径与财务/业务对齐；② 核心指标只选三个（逃逸率、发现阶段分布、返工占比）；③ 外部失败成本区分直接与间接损失；④ 每次结论附估算方法与不确定性；⑤ 同时指出「哪块投入不值得再加」。
- **为什么值钱**：只会报「发现 120 个缺陷」的测试，在资源收缩时最先被砍；能说清「把逃逸率从 8% 压到 2% 相当于每年省下多少」的测试，才有资格参与投入决策。

## 二、接口测试（api）

### 题 2：接口里的金额、税率这类小数，怎么测精度与舍入？

**Q：** 接口里有金额、税率、折扣率这类小数。你会怎么测它们的精度与舍入问题？

**A：** 核心动作是**先搞清楚服务端用什么类型存、用什么规则舍入**，再构造用例。

**第一步 确认类型。** 金额用 `DECIMAL(18,2)` 还是 `double`？用二进制浮点存金额本身就是隐患——`0.1 + 0.2 != 0.3` 的误差会累积。看到 `double`/`float` 就应单独提风险项，而不是当用例问题处理。

**第二步 确认舍入规则。** 银行家舍入还是四舍五入？在前端算还是后端算？**多环节各自舍入**是金额对不上的头号原因——前端按「单件价 × 数量 × 折扣」、后端按「单件价 × 折扣 × 数量」，舍入点不同就差一分钱。

**第三步 构造用例：**
- **除不尽**：总价 100 按 3 份分摊，余下 0.01 归谁？必须有明确规则。
- **反向验算**：所有分项**加总必须等于总金额**——这条断言能抓出大部分分摊缺陷。
- **边界值**：0、0.005、超大金额、负数（退款）、科学计数法输入。
- **格式一致性**：返回 number 时前端解析可能丢精度（超过 2^53 直接失真），属接口设计缺陷。
- **多币种**：不同币种小数位不同，汇率换算后怎么舍入。

**加分点：** 写一条「Σ分项 == 总额」的通用校验复用所有金额类接口，比逐条写期望值可靠得多。

## 三、安全测试（sec）

### 知识点 2：CORS 配置错误的三类测试入口与判高危标准

**要点：** 先纠正高频误解——**CORS 是浏览器实施的策略，服务端只是声明，它不保护接口本身**（curl/脚本不受影响）。它的真实风险是「恶意网页在用户已登录的浏览器里读取接口数据」。

- **入口 ①** `Access-Control-Allow-Origin`：是否 `*`；是否与 `Allow-Credentials: true` 同时出现（浏览器会拒绝该组合，但「回显 Origin」的实现等价且更危险）。
- **入口 ② 反射式白名单**：把请求头里的 Origin 原样回写 = 对所有域名开放。验证：把 Origin 改成 `https://evil.example.com`，看响应头是否原样返回。
- **入口 ③ 前缀/后缀匹配绕过**：白名单用 startswith/endswith 判断时，`https://trusted.com.evil.com`、`https://eviltrusted.com` 可能被误放行。
- **判高危需三条同时成立**：允许携带凭证（Cookie）+ Origin 可被任意域名控制 + 有敏感数据可读。三条齐了必须修；只有第一条且不涉及敏感数据可降为低危建议项。
- **易漏点**：预检请求 OPTIONS 常被网关直接放行不做鉴权，导致「鉴权只在 GET 生效、OPTIONS 裸奔」，需单独验证其返回与实际鉴权逻辑一致。

### 坑点 1：把 CORS 当鉴权用

- **坑在哪**：开发认为「加了 CORS 白名单，别的网站就调不了我们的接口了」。实际上 CORS 由浏览器执行，curl、Postman、任何脚本完全不受影响；若服务端采用「回显 Origin」的实现，等于对所有域名开放。
- **怎么破**：先纠正认知——**CORS 不是鉴权，绝不能替代服务端校验**。然后按三个入口测：① Origin 改成恶意域名看是否原样回写；② 用同前缀/同后缀的恶意域名试前缀匹配绕过；③ 单独验证 OPTIONS 预检是否绕过鉴权。**判高危要三条齐**：允许携带凭证 + Origin 可控 + 有敏感数据可读。

## 四、AI 测试（ai）

### 题 3：模型供应商要换一家，怎么做迁移验证并给出「能换/不能换」的结论？

**Q：** 模型供应商要换一家（或者大版本升级）。你怎么做迁移验证，最后给出结论？

**A：** 换模型不是「跑一遍冒烟看回答还像不像」，而是一次**有明确验收标准的迁移验证项目**，分五步。

**① 先明确「为什么要换」。** 降本 / 提效 / 合规（私有化）/ 原供应商下线——动机决定验收标准的侧重。

**② 建评测集（地基）。** 从线上采样 200~500 条，覆盖高频意图、长尾、边界异常、对抗输入、多轮；每条有标准答案或评分细则；**版本化，迁移前后必须用完全相同的评测集**。

**③ 双跑对比（A/B 同输入）。** 三种方式交叉：**确定性指标**（结构化输出解析成功率、必填字段完整率）最可靠；**LLM-as-a-Judge**（必须先人工标 50~100 条算一致率，不达标不能用它的结论）；**人工盲评**（隐藏模型名、随机顺序，避免先入为主）。

**④ 非功能维度（最易翻车）。** 上下文窗口与长输入质量衰减、**Function Calling / 结构化输出支持度（经常是迁移真正的卡点）**、TTFT 与端到端 P95、RPM/TPM 配额、按真实 token 重算成本、一周错误率、合规条款。

**⑤ 结论要带「条件」和「兜底」。** 「X/Y/Z 三类场景不劣于旧模型；A 场景长文档摘要下降 12%，建议该场景保留旧模型路由或补提示词复测；灰度 5%→20%→100%，监控首 token 时间与解析失败率，回滚为配置级切换、5 分钟生效。」——只说「能换」是不合格的结论。

**加分点：** 保留双模型可切换的抽象层，让迁移从一次性大工程变成「随时可灰度、随时可回滚」的日常操作；测试侧对应能力就是把评测集做成可在 CI 里对任意模型跑的回归套件。

## 五、大模型工程（llm）

### 知识点 3：流式输出的五个必测维度与体感指标分离

**要点：** 流式输出的价值在**用户体感**，所以「最终文本正确」必要但不充分。等输出完再断言，会漏掉全部体感问题。

- **① 首 token 时间（TTFT）**——体感第一决定因素。总耗时 5 秒但首 token 0.3 秒，用户觉得快；首 token 2 秒、总 3 秒，用户觉得卡。统计 **P50/P95** 而非平均；RAG 场景检索耗时会直接推迟 TTFT。
- **② 块间节奏（token/s）**——是否稳定吐字，还是停顿数秒再猛吐一片。**停顿的体感伤害比慢更大**。
- **③ 增量拼接正确性**——所有 chunk 拼起来是否等于非流式结果。坑位：多字节字符跨 chunk 被切断、JSON 必须用增量解析器（不能拼字符串再 parse）、Markdown 表格与代码块中途渲染错乱。
- **④ 中断与恢复**——用户点停止时服务端是否及时停（**继续生成会白烧 token**）；重连是重发还是续传。
- **⑤ 流内错误表达**——HTTP 状态码在流开始前已发出（通常 200），中途错误只能靠流内协议（如 SSE 的 error 事件）。要测「中途模型超限 / 内容被拦截 / 后端异常」时前端能否正确提示，而非无限转圈或显示半截乱码。
- **手段**：慢速消费（测背压）、中途断 TCP（测是否停止生成与释放资源）、直接消费 SSE/WebSocket 报文断言事件序列（start → delta → done）。
- **纪律**：体感指标（TTFT、token/s、中断率、异常流占比）进性能监控，内容质量进评测体系，两条线分开管理。

## 六、AI Agent 测试（agent）

### 技能 2：Agent 轨迹回放与危险动作护栏验证

- **能力定义**：把线上真实轨迹（含工具参数与返回原文）录制下来，用「录制-回放」模式让 LLM 与工具双桩固定，形成确定性用例；并对写操作类工具验证四道护栏。
- **前提**：轨迹必须完整落库——输入与系统提示词版本、模型与参数、每步 LLM 输出、工具名与**参数原文**、**工具返回原文**、耗时与 token、环境快照。**缺了「工具返回原文」就无法回放**，这也是最常被漏的一项。
- **回放四步**：① 冻结输入；② 把不确定性外置成桩（LLM 响应按序回放、工具返回 Mock 带下标）；③ **写行为断言而非文本断言**——步骤级、前置校验级、终止级、副作用级（写操作必须拦截成**影子调用**，只记录不执行）；④ 定位是模型问题（信息齐全仍选错）还是架构防护缺失（工具对但系统没做二次校验就执行，后者更严重）。
- **四道护栏**：Schema 强校验（`additionalProperties: false`、enum 白名单）、参数来源校验（关键业务参数只允许来自可信来源）、失败处理与重试上限、危险工具额外闸门（前置确认 + 额度限制 + 可撤销 + 审计日志）。
- **升级为资产**：把每次线上坑 case 攒成场景回归集（尤其「危险动作」类），改提示词 / 换模型 / 改工具定义时全量跑一遍——相当于给 Agent 建了一套「特征测试」。轨迹含真实用户数据，入库前必须脱敏。

## 七、测试环境搭建（env）

### 技能 3：测试环境就绪校验与资源配额治理

- **能力定义**：把「环境就绪」写成可执行的**五层检查脚本**，并用 ResourceQuota 与监控把「环境偶尔变慢、Pod 反复重启」变成可解释、可预警的现象。
- **五层检查（顺序不可乱）**：
  1. **基础层**——服务 Running **且已 Ready**（不是启动中），健康检查端点正常**且返回体内含版本号**。
  2. **依赖层**——DB/缓存/MQ/配置中心/注册中心/对象存储连通；**外部依赖必须确认指向 Mock 或沙箱而非真实第三方**（真发短信真扣款的根因就在这）。最佳做法：让被测服务暴露「依赖自检」接口，把每个依赖的连通性与目标地址打出来。
  3. **配置层**——关键配置与目标环境一致；**输出配置内容 hash 作为指纹**，让「被谁改过」一目了然；检查上次联调遗留的临时配置。
  4. **数据层**——字典与主数据存在且状态合法；数据量级满足测试需要；关键账号未被上一轮污染。
  5. **版本层**——每个服务返回的版本号 = 提测单声明的版本，制品指纹（镜像 digest / commit sha）一致。专治「测错包」。
- **资源侧治理**：给每个测试环境设 ResourceQuota 与 LimitRange，requests 按实测稳态用量设（避免超卖）；给非生产环境设优先级与抢占策略；把节点水位、驱逐事件、Pod 重启次数纳入监控告警。
- **落地纪律**：脚本必须**只读且幂等**；不通过则不允许提测（闸门而不是公告）；同时定清「失败谁修、多久修好」的责任矩阵，否则脚本跑红也没人管。

### 坑点 2：测试环境只检查「Pod 是 Running」，不检查就绪与依赖连通

- **坑在哪**：环境预检停留在「进程起来了」。常见后果：容器还在 Readiness 探针重试阶段就开始测、某个依赖指向了生产第三方、版本部署错了没人发现。故障发生在测试阶段，却要花几倍时间分辨是环境问题还是应用缺陷。
- **怎么破**：按五层做成脚本闸门，其中**依赖层检查必须显式打印目标地址**，而不是只判断「通不通」——专治误连真实第三方。

## 八、AI 测试工具（aitools）

### 坑点 3：评测集定稿后长期不动，分数越来越高却没人怀疑它已失效

- **坑在哪**：评测集被用来调参（过拟合）、题目可能进了训练语料（污染）、业务已变但题没变（腐化）。表现是**离线分数稳定上升**，团队据此认为「效果在变好」，直到线上客诉增加才发现评测早就不具备区分力。最糟的是有人为了通过评测去改标准答案。
- **怎么破**：四条防腐纪律——① **版本化 + 冻结**，要改就出新版本并记录原因，**绝不允许改答案让它通过**；② **切分调优集与验证集**，验证集只在发布评审跑且不出示明细（防过拟合唯一有效手段）；③ 保留 **holdout 留出样本**，只在换模型/架构变更时启用；④ **定期与线上真实意图分布对齐**（建议按季度采样轮换、淘汰业务已下线的旧题）。
- **判失效最硬的信号**：**「离线涨、线上不涨」**。另可做**污染检测**——对题目做同义改写与噪声注入，分数暴跌说明模型记住了形式而非能力。
- **补充**：防线应是三层而不是一个数字——离线评测集（相对变差没有）+ 灰度与线上指标（真实但有噪声）+ 人工抽检（校准评测机制本身是否可靠）。

## 待图谱化的候选关联

- 质量成本（CoQ）四象限 ↔ 缺陷逃逸分析 ↔ 缺陷发现阶段分布 ↔ 测试价值度量三指标
- 质量成本的边际效益判断 ↔ 测试范围裁剪与风险决策 ↔ 自动化 ROI
- 需求追溯矩阵（RTM） ↔ 需求评审的测试视角清单 ↔ 用例有效性评估 ↔ 僵尸用例下线
- 金额精度与舍入 ↔ 接口三层断言体系 ↔ 幂等性与「Σ分项 == 总额」反向验算
