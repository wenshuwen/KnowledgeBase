## 一、Agent 测试

### Q：AI Agent 和普通问答机器人在测试上最大的差别是什么？怎么给 Agent 设计测试策略？

**结论**：差别在于 Agent **有「过程」**——它是「输入 → 规划 → 调工具 → 观察结果 → 再规划 …… → 输出」。因此测试必须分层，不能只有一个断言点。

1. **单步能力层**：工具调用是否正确（选对工具、参数合法、必填齐全）。可以像测接口一样断言，是最确定的一层。
2. **规划层**：给一个目标，看拆出的步骤是否合理、顺序对不对、有没有漏掉必要前置（如先查订单再退款）。这一层没有唯一正解，只能用「必需步骤出现 + 禁止步骤出现」来判。
3. **编排与状态层**：多轮对话中记忆是否保持、上下文是否串（问 A 用户的事却引用了 B 的数据）、循环与重试有没有上限。
4. **端到端任务层**：按任务完成率、平均步数、平均耗时、工具调用成功率评估。

**Agent 特有的两个必测项**：一是**终止性**——必须验证它在任何情况下都能停下来，不许死循环烧钱；二是**权限边界**——可调用的工具集合必须最小化，写操作（下单、发消息、删数据）必须有确认或幂等保护。这两项不通过就不能上线。

### Q：Agent 调工具失败时怎么测？重试、降级、兜底这几条路径怎么设计用例？

**结论**：先把工具失败分成四类，每类期望行为不同，用例分开写，最后形成一张**故障矩阵**（行＝故障类型，列＝是否重试 / 重试上限 / 是否降级 / 是否告知用户 / 是否回滚），每格至少一条用例。

1. **瞬时故障**（超时、连接被重置、503）：期望有限重试。断言三件事——重试次数不超上限、退避间隔递增（不是死循环猛打）、重试成功后任务继续。
2. **永久故障**（400 参数错误、404 不存在、403 权限）：期望不重试或只纠正一次，把错误转成可读说明或改用备选路径。最常见的坑是**把 4xx 也当成可重试**，对同一个错误请求连打十次。
3. **语义失败**（200 但结果不对，例如查到的订单不属于当前用户）：期望 Agent 能识别异常并自我纠正，或明确报告「没查到」而不是编一个。要专门造「返回空结果」「返回脏数据」的桩。
4. **部分失败**（多工具串联时第 3 步失败）：期望不留下半成品状态，必须验证前置扣款是否回滚或进入待人工处理队列。

**必测的成本护栏**：让工具持续失败，看 Agent 会不会无限重试把 token 与调用额度烧光。步数、重试、单任务成本三类上限都要可配置。

### Q：越权测试怎么做？横向越权和纵向越权的用例怎么设计？

**结论**：越权的本质是**服务端用客户端传来的 ID 或字段做校验，而没有用当前登录身份验证资源归属**。用例设计很机械但很有效。

1. **横向越权（同级别用户之间）**：准备两个同角色账号 A、B，各造一份业务数据，用 A 的 Token 请求 B 的资源 ID。**参数位置要全部覆盖**：路径里的资源 ID、查询串参数、请求体里的用户 ID 字段、以及 header。很多系统只在路径做了校验，请求体里的字段直接落库。
2. **纵向越权（权限提升）**：普通用户访问管理端接口、前端隐藏但后端没校验的接口（重灾区，**前端隐藏按钮不等于后端做了鉴权**）、越权访问批量导出与统计类接口。

**四种具体方法**：ID 遍历（改相邻值或别人的值，断言 403/404 而不是 200）；角色替换（同一请求换不同角色 Token 比对差异）；参数污染（额外传角色、租户 ID 这类字段，看服务端是否盲信）；专测批量与导出接口（常因性能优化绕过单条校验）。

**判据**：返回 404 可以接受，**返回 200 且带别人的数据绝对不行**；同时检查日志是否记录了这次越权尝试。这类用例成本极低，必须做成参数化自动化回归，每次发布都跑。

## 二、测试知识框架

### 知识点：评测集的三道防线——双人标注、留出集、定期换血

评测集的质量几乎决定了评测结论的质量，噪声会直接变成结论偏差。

1. **第一道防线：双人独立标注 + 分歧仲裁**。有标准答案的题由两人各自标注，不一致的拉齐口径再入库，否则评测集本身带噪声。
2. **第二道防线：留出集（holdout）**。把评测集切成「调优集」与「留出集」——调 prompt 只看调优集，上线判定看留出集，**留出集不参与任何调优**。如果所有题都被用来调 prompt，那就是在训练集上考试，分数必然虚高，也就失去了判定价值。
3. **第三道防线：定期换血**。留出集用过一段时间后会被间接污染（团队会记住它的分布），按季度补充新样本、淘汰过时题。

**配套要求**：评测集要做版本管理，记录每次题目增删。否则两次评测的分数不可比——分数涨了可能只是因为删掉了几道难题。

### 知识点：慢查询定位——「索引明明建了还是慢」的六个原因

排查路径是**从现象往根因走，每步都用数据说话**：先用慢查询日志 / 监控拿到「哪条 SQL + 频次 + 平均与 P99 耗时」（高频的小慢比偶发的大慢更伤整体），再用 `EXPLAIN` 看 `type` / `key` / `rows` / `Extra`，并用实际执行看**真实行数**（优化器的预估经常错）。

「索引建了还是慢」的六个常见原因：

1. **索引失效**：字段上做了函数或运算、隐式类型转换（字符串列传了数字，或反之）、前导模糊匹配、`OR` 连接了未索引字段。
2. **不满足最左前缀**：联合索引 `(a,b,c)` 却只按 `b` 查。
3. **回表太多**：二级索引命中的行数很大又要回主键取数据，随机 I/O 比全表顺序扫还慢——应改为**覆盖索引**。
4. **索引选择性太低**：如只在取值极少的列上建索引，优化器会主动放弃使用。
5. **统计信息过期**：行数估算错误导致选错计划。
6. **锁等待或资源争抢**：SQL 本身很快但被别的事务锁住——这时看执行计划没用，要看锁等待与活动会话。

### 知识点：灰度 / 蓝绿发布的五个验证点

发布方式本身会引入新的失效模式——问题往往不在功能，在**流量与状态**。

1. **流量切分是否真的生效**：按用户标识、header、比例三种维度验证路由。最常见的问题是比例不生效或缓存导致串流。
2. **会话与状态连续性**：同一用户在切换过程中连发请求，不能一半走新一半走老，否则表现成「莫名退出登录」或数据错乱。
3. **共享资源是否隔离或兼容**：数据库、缓存、消息队列的双版本兼容；**缓存 key 必须做版本隔离**，否则互相污染。
4. **回滚路径**：最常被跳过的一步。要实际演练——回滚后新版本写入的数据老版本能否正确读取、新版本发的消息老版本能否消费。**不能回滚的发布等于单向门。**
5. **观测是否分版本**：错误率、延迟、业务指标、日志里的版本标识必须能分开看，否则出问题无法判断归属。

## 三、技能与工具

### 技能：Agent 轨迹评测与可观测性建设

**核心**：把 Agent 的每一步变成**可记录、可断言、可回放的数据**，让「时好时坏」变成可定位的工程问题。

- **落盘内容**：每步的输入、思考、工具名、参数、返回、耗时与 token。
- **断言分两层**：最终任务完成度 + 中间轨迹约束（必调某工具、禁调某工具、步数上限）。
- **离线化**：把工具层 mock 掉，让 Agent 逻辑可离线、可重复评测；少量真实端到端用例验证集成。
- **成本护栏**：给步数与成本设硬上限，超限即判失败并告警。
- 常用工具：LangSmith / LangFuse、OpenTelemetry、自定义 trace 落盘、pytest + 工具层 mock。

### 技能：业务逻辑漏洞挖掘（越权、并发、支付）

**核心**：扫描器覆盖不到的地方恰恰是业务逻辑层的高危缺陷——业务规则被绕过。

- 每个接口问三个问题：**谁的资源、什么角色、状态是否允许**。
- 参数位置全覆盖：路径、查询串、请求体、header 各测一遍。
- 带价格、数量、状态、审批流的参数一律尝试篡改。
- 对「限制次数」「限制额度」的功能做并发测试，断言不超发。
- 常用工具：Burp Suite / mitmproxy（改包重放）、两个角色账号 + 参数化脚本、并发工具、越权自动化回归集。

### 技能：质量推动与冲突沟通

**核心原则**：把「是不是 bug」的争论转成「事实与影响」的讨论，并接受「决策可以是不修，但必须留痕」。

- 缺陷报告先备齐**事实**：最小复现步骤 + 预期与实际 + 判定依据（需求文档 / 验收标准 / 接口契约）。
- **依据模糊时，它其实是需求缺口**，这正是测试最有价值的产出。用一个具体问题让决策者回答：「线上出现这种情况，用户会看到什么、我们怎么解释、要不要人工兜底」——把「不重要」逼成「明确接受或明确修」。
- 优先级分歧时提供**决策依据**而非情绪：影响面、严重度（数据错 / 资金错 / 体验差）、触发概率、有无绕过办法、修复成本量级。
- 接受不修，但要求**登记为已知问题**（带触发条件与临时方案）+ 加监控或日志 + 纳入后续清单。
- **红线（资金、数据安全、合规）不让步**，其余靠数据与影响面说话。

## 四、坑点与破解

### 坑点：只测「用户主动输入恶意指令」，不测间接注入

- **表现**：用例全在输入框里写「忽略以上指令」，但真实攻击面是 Agent 读取的外部内容——网页、邮件、文档、数据库字段。用户什么都没做，Agent 读了一份被投毒的文档就把数据发出去了。
- **破解**：把恶意指令**埋进 Agent 会读取的数据源里**（网页正文、附件、接口返回字段）来做用例，重点验证三件事：是否发起了对外网络请求、是否泄露了系统提示或其他用户数据、是否调用了白名单外的工具。同时在实现层区分「数据」与「指令」，工具调用前做白名单校验。

### 坑点：压测报告只写 TPS，不写缓存命中率

- **表现**：用预热好的缓存跑出一份漂亮数据就交差。真实环境命中率低得多，未命中要回源查库，实际性能可能只有报告里的几分之一；热点 key 集体过期时会直接打穿数据库。
- **破解**：报告必须显式写清命中率，并用**多档命中率分别跑出曲线**；单独压一遍回源路径；专门造「热点 key 过期」「批量失效」「缓存重启」三类场景。**判据看数据库 QPS 峰值会不会被打穿**，而不只看接口响应时间。

### 坑点：功能在单版本环境测得很全，就认为灰度发布没有风险

- **表现**：功能用例都在单一版本、固定环境下跑过。灰度引入了**双版本共存、数据共享、流量动态变化**三个新变量，缓存串流、字段不兼容、会话丢失这类缺陷在单版本环境里根本不会出现。
- **破解**：灰度期把重点从「功能可用」转到「共存是否安全、回滚是否可行」——验证按比例与按用户的路由真的生效、切换瞬间会话保持连续、缓存 key 做了版本隔离，并**实际演练一次回滚**，确认新版本写入的数据能被老版本正确读取。

## 五、待图谱化的候选关联（供每周编译时判断，勿在此处建链）

- Agent 四层测试模型 ↔ 传统测试金字塔（同为「分层断言、越下层越确定」的思路，但 Agent 的「层」是按执行阶段而非按集成粒度划分）
- Agent 轨迹断言 ↔ 接口契约测试（共同点：把「过程」变成可比对的结构）
- 间接提示词注入 ↔ 存储型跨站脚本（同为「不可信数据被当指令执行」，防护思路同源）
- Agent 工具权限最小化 ↔ 越权测试（一个在授权侧、一个在验证侧，互为闭环）
- 评测集留出集 ↔ 回归测试集管理（共同点：不参与调优的那份数据才有判定权）
- 评测集版本管理 ↔ 环境即代码（同属「把可变因素纳入版本控制」）
- 灰度回滚演练 ↔ 数据库迁移的回滚验证（同一个问题：新写入的数据老版本能不能读）
- 慢查询定位的对照实验法 ↔ 性能压测的基线对照（共同点：改前测基线，改后再测，靠数据而非感觉）
- 缓存命中率与压测结论 ↔ 测试数据量与环境差异（同属「压测口径必须写清、否则结论无效」）
- 需求可测性评审 ↔ 缺陷争议处理（依据越明确，争议越少；两者都指向「判定依据必须前置」）
- 事务死锁的加锁顺序统一 ↔ 分布式场景的幂等设计（不同层解决同一个「重复 / 互锁」问题）
