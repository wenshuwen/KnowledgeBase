## 一、面试题精选

### 数据库 · 联合索引最左前缀与「怎么验证它真的生效」

**Q：联合索引的最左前缀原则，你会怎么用一个例子给开发讲清楚？又怎么验证索引真的生效了？**

核心一句：**联合索引 (a,b,c) 能命中 a、ab、abc 三种从左往右的连续前缀，单独查 b 或 bc 用不上** —— B+ 树先按 a 排、a 相同再按 b 排，跳过 a 就没法二分定位，只能全表扫描。比喻就是电话簿：只报名不报姓，整本书只能从头翻。

三个容易被忽略的延伸点：

1. **范围查询会截断其后的列**：`where a=1 and b>5 and c=3` 实际只能用到 a、b，c 拿不到索引的过滤与排序能力。
2. **顺序无关、对齐有关**：`where b=2 and a=1` 优化器会自动调整，仍命中；但列不能跳。
3. **失效四件套**：列上套函数、隐式类型转换（字符串列用数字查）、前置 `%` 的 like、or 连接非索引列。

验证方法：**EXPLAIN 看 key / key_len / rows / Extra**。判断要点是 **key_len 才能反推用了几列** —— 只看 type 会误判（range 也可能是只用了第一列）。Extra 里出现 Using filesort / Using temporary 说明排序或聚合没吃到索引。

结论表达上有个细节值得记住：**优化前后各跑 1000 次取 P95 对比，不要各跑一次看谁快** —— 单次耗时的差异大部分来自缓冲池冷热，不来自索引。

### 安全测试 · 如何证明「鉴权是在服务端做的」

**Q：你怎么验证权限校验是在服务端做的，而不是仅仅在前端把按钮藏起来了？**

立场先行：**前端隐藏按钮只是体验优化，不是安全控制**。验证只有一个原则 —— 绕过界面，直接打接口。

1. **抓包改字段重放**：用普通账号正常操作一次，把请求里的用户 id / 订单 id / 租户 id / 角色 code 改成别人的重放，看服务端是否拒绝。最基础也最有效。
2. **低权限 token 直调高权限接口**：很多系统前端做了路由守卫，后端完全没校验，这是高频漏洞。
3. **删掉前端限制**：把 disabled 按钮改成可点、用直接 URL 打开被隐藏的菜单，验证是否存在「UI 不可见但接口可达」的路径。
4. **看响应体是否泄露**：即使返回 403，若错误信息带出他人数据片段或本应隐藏的敏感字段，也是缺陷。
5. **批量接口单独测**：传 10 个 id，9 个是自己的、1 个是别人的，**看服务端是整体拒绝还是部分执行**。
6. **无鉴权路径排查**：拉出接口清单（Swagger / 网关路由）逐条试「不带 token」访问，重点看内部接口、健康检查、调试接口、未下线的旧版本接口。

落地组织方式：做成 **「角色 × 资源归属 × 操作」矩阵**（自己的 / 同租户他人 / 跨租户 × 查改删导出），每个格子一条断言，期望结果明确写成「403 或 404，且不返回任何业务数据」。矩阵化才能保证覆盖完整、后续版本可回归。

两个高频盲区：**多租户（同角色不同数据域）与批量接口的部分执行**。

### AI Agent · 任务成功率的分层口径

**Q：Agent 的任务成功率怎么定义和统计？中间步骤做对了但最终结果不对，算成功吗？**

我的答案：**必须分层统计，只报一个「成功率」的数字没有信息量**。立场是 —— **中间步骤再漂亮，最终目标没达成就是失败**。

四层口径，从产品视角到工程视角逐层收窄：

1. **任务级成功率**：用户目标是否达成。唯一对外汇报的口径。
2. **过程级正确性**：工具选择是否正确、参数抽取是否准确、步骤是否多余或缺失。**这一层用来定位失败的环节**，不用于判定成败。
3. **失败归因分类**：规划错误 / 工具错误 / 参数错误 / 知识缺失 / 幻觉 / 超限（步数、token、超时）。没有归因的成功率只是一条曲线，有归因的才能指导优化。
4. **效率与成本口径**：平均步数、工具调用次数、token、端到端 P95。「成功但用了 40 步、花了 8 毛钱」在很多场景等于不可用。

要单独统计的一类：**「编造的成功」比「诚实的失败」危害大得多**，必须从成功率里挑出来单列。

统计纪律：评测集要带标准答案与标准步骤；Agent 有随机性，**同一任务跑多次、报告「N 次里的成功次数」，而不是挑最好一次**；每次运行的步骤序列、工具入参出参、耗时、token 必须落库，否则无法归因也无法复现。

## 二、知识点精选

### 数据库 · InnoDB 死锁：成因、现场与预防

- **成因**：两个以上事务以**相反顺序**持有并等待对方的锁；唯一约束冲突并发插入；长事务放大窗口。
- **现场**：`SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 段含双方完整 SQL、持有的锁与等待的锁；生产用 pt-deadlock-logger 持续采集。
- **预防**：统一加锁 / 更新顺序；事务内不包远程调用与大批量循环；尽量用主键或唯一索引定位（等值命中可退化为行锁甚至不加锁）。
- **兜底**：捕获 1213 后**带随机退避重试**并打点告警。
- **验收标准**：不是「永不发生死锁」，而是「**自动重试后最终成功 + 有可观测告警**」。

### 性能测试 · 内存泄漏的定位手段

- **趋势判据**：看运行时堆内存的**最低点（GC 后残留）是否逐次抬升**；绝对值无意义。容器还要看是否被 OOMKilled。
- **只能长稳暴露**：持续 2~8 小时、混合场景、节奏稳定；跑十分钟的压测测不出泄漏。
- **定位链（JVM）**：jstat -gcutil 看回收效果 → jmap -histo:live 看实例数增长 → 抓堆快照用 MAT 做**两份快照的支配树 diff** → 回溯 GC Root 引用链；生产优先 async-profiler alloc 模式（低开销持续采样）。
- **Python / Node**：tracemalloc / objgraph / memray、--inspect + heap snapshot diff，方法同为「两时点 diff + 引用链回溯」。
- **典型根因**：本地缓存或静态集合只增不减、监听器与连接未注销、ThreadLocal 未清理、日志与指标收集器持有引用。
- **报告口径**：换算成「**以该速率 N 天后耗尽 X GB**」的可决策时间窗口，而不是只写「存在内存泄漏」。

### 测试理论 · 假阴性（漏测）的六大来源

1. **断言太弱**：只断状态码或仅断关键字段。
2. **数据太干净**：单用户单线程、无脏数据、无数据量。
3. **环境与生产结构性差异**：单机测多节点、测试库无数据量、未开限流。
4. **只覆盖主流程**：异常、重试、超时、部分成功缺失。
5. **Mock 与真实依赖不一致**：理想响应掩盖了延迟、限流与额外字段。
6. **为了跑过不断放宽断言**，最终等于没断。

治理主线是 **缺陷复盘倒查（线上逃逸率）**：每条线上缺陷追问「哪条用例本该拦住它、为什么没拦住」，结论回写用例；并用变异测试定期体检用例集 —— **注入了 bug 却仍然全绿的用例块，就是摆设**。

## 三、技能精选

### CI·CD · 流水线测试分片与并行执行

价值在于把回归从「两小时排队」压到「二十分钟跑完」，直接决定团队愿不愿意跑测试。

- 切分单位用**文件 / 类 / 目录**而非单条用例，保住 setup/teardown 配对与内部顺序。
- 优先按**业务域**切（失败归属清晰），而非纯按数量均分（互相踩数据）。
- 均衡看**执行耗时**而非条数：上一轮上报耗时，本轮做贪心装箱，通常提升 20%~40%。
- 分片参数走环境变量（SHARD_INDEX / SHARD_TOTAL），本地默认单片全量。
- 分片数的上限受「**最短分片 ≥ 5 分钟**」约束 —— 再多分，镜像拉取与结果聚合的固定开销会吃掉并行收益。

### 测试框架 · pytest hook 扩展开发

判断一位测试工程师是「写用例」还是「搭框架」，看他会不 会用 hook 解决问题。

- **pytest_runtest_makereport**：失败自动截图 / 存日志 / 立刻上报，截图路径塞进 report.extras，配合 pytest-html 直接展示。
- **pytest_collection_modifyitems**：按目录或文件名自动打标签、按变更范围筛选用例、调整执行顺序。
- **pytest_addoption / pytest_configure**：注册命令行参数（如 --env）与全局初始化。
- **pytest_sessionfinish**：会话结束汇总指标推送、沉淀失败列表供下轮排序。
- 纪律：**hook 里所有外部调用一律 try/except，绝不向外抛异常** —— 在 hook 里抛异常会把整轮结果吞掉甚至直接崩。
- 设计原则：**可观测性交给 hook，用例保持干净只表达业务**。

### AI 测试工具 · 选型与价值验证

第一问永远是：**「它替代了哪一步人工动作，这一步占我们多少时间？」** —— 答不上来的工具，无论多火都不引入。

五个维度：**可验证性**（产出能否被自动校验，最关键）→ **集成成本**（能否进 CI、结果能否落到现有报告）→ **确定性**（能否固定 seed / 锁定版本）→ **成本口径**（按调用量计费的要算年度量级）→ **数据与合规**（一票否决项，不是打分项）。

两个经验性结论：

- **先引入「辅助人」的工具，再考虑「辅助流水线」的工具** —— 辅助人的工具出错时人在环上还能兜住，直接进流水线的工具一旦不可靠会污染回归信号。顺序错了，好工具也会因一次事故被彻底否掉。
- PoC 必须带量化目标（如「用例设计时间从 4 小时降到 2.5 小时、经评审可用率 ≥ 60%」），**没有量化目标的 PoC 一定得不出结论**。

## 四、坑点精选

### 安全测试只跑扫描器，拿工具报告当测试结论

扫一遍扫描器、导出一份报告就算做过安全测试，结果报告里全是低危误报，真正的越权与业务逻辑漏洞（改价、薅羊毛、批量接口绕过）一个没发现。

破解：**扫描器只覆盖「技术形态已知」的问题，业务逻辑与越权必须手工验证** —— 按角色 × 资源 × 操作做矩阵，重点测批量与导出接口的权限校验和部分成功语义。工具报告只是起点，结论必须是自己验证过的。

### Agent 测试只看最终输出，不看工具调用过程

最终答案看起来对就判通过，实际上它调用了错误的工具、传了错误的参数，或干脆没调工具而是凭记忆回答。这种「侥幸成功」换个输入必然失败，却被计入了成功率。

破解：把 **trace 落库并按过程判定**（工具选择、参数抽取、步骤顺序是否与标准步骤一致），并把过程判定结果纳入归因分类，让「侥幸成功」被识别出来而不是算作成功。

### 测试环境里的定时任务与消息消费者没人管，互相抢数据

后台有个每 5 分钟跑一次的任务在改数据、MQ 消费也在改数据，但没人把它当成「环境的一部分」；用例频繁偶发失败，团队大量时间花在排查「是不是代码问题」上。

破解：梳理出环境的**自治执行体清单**（定时任务、消费者、补偿任务、缓存刷新），默认关闭、按需触发、按标识前缀隔离，并在变更巡检里比对处理量。退一步至少让用例使用独立命名空间，断言只看自己的数据。**做环境梳理时先列这张清单，往往能立刻解释很多「偶发失败」。**
