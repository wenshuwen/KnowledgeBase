## 一、自动化测试

### Q：自动化用例总是「时好时坏」（flaky），你会怎么系统性治理？

**结论**：先量化、再归因、后治理，重试是最后一步且必须有上限与留痕。

1. **先量化**：统计每条用例最近 N 次的执行结果，单独算出「失败但重试能过」的 flaky 率。有数字才知道该修哪几条，而不是全量重写。
2. **归因分类**：等待不当（固定 sleep）、数据竞争、环境抖动、顺序依赖、断言过严（断言了时间戳/traceId 等动态字段）。
3. **按类治理**：等待改显式条件；数据竞争改用例自造自清；环境抖动用 mock/契约顶掉；顺序依赖找共享状态；断言过严改断稳定业务字段。
4. **兜底**：确属外部不可控的，允许有限次重试（1 次）但必须打标记录进 flaky 榜单，每周复盘清零。

**判据**：flaky 治理的本质是把不确定性收敛到「可解释、可归因、有上限」，而不是让它消失。

### Q：接口自动化里测试数据互相污染，怎么设计数据管理？

**结论**：数据污染的本质是「多条用例共享同一份可变数据」，解法是隔离 + 自造 + 清理。

1. **隔离**：每个执行者（本地 / CI 并行分片）用独立命名空间，所有测试数据带统一批次前缀。
2. **自造**：用例不依赖「库里预先存在的数据」，前置步骤里自己通过接口创建并拿回 ID。
3. **清理**：后置里删掉自己造的数据；清理失败用 try/finally 兜住、单独打日志，不影响主断言。
4. **无法删除的场景**（流水类）：按批次号查询、只断言本批次数据，而不是断言总数。

**红线**：不要用生产数据做自动化断言的基准，数据一变用例全红，属伪稳定性。

### 知识点：自动化测试金字塔的现代修正 —— 从「数量分布」到「成本分布」

| 经典说法 | 现代修正 |
|---|---|
| 单元多、接口中、UI 少 | 不看数量比例，看**反馈速度**：能否在几分钟内给出可信反馈 |
| 只有三层 | 微服务下补上**契约层**，在不启动全链路的情况下挡住集成问题 |
| 倒金字塔（冰淇淋筒）是反模式 | 症状：回归越来越慢、失败越来越多、没人敢改代码 |

### 技能：自动化测试框架设计与维护

- **分层**：驱动层 / 对象层 / 业务层 / 用例层，改动影响面可控；测试数据构造与断言工具独立成模块。
- **常用工具**：Playwright、Selenium、Appium、pytest、Allure、Jenkins / GitLab CI。
- **要点**：数据自造自清；显式等待替代 sleep；建 flaky 榜单与稳定性指标；把框架当产品维护（版本、文档、示例用例、向后兼容）。

## 二、测试理论

### 知识点：探索式测试的记录方法 —— SBTM 会话式测试管理

1. **会话（Session）**：固定时长（60~120 分钟）、有明确目标、不被打断的探索时段；每个会话配一份「章程」说明测什么、怎么测、找什么。
2. **时间分配统计**：按「测试设计/执行」「调查问题」「记录缺陷」「搭建环境」四类统计占比。调查问题占比高 → 系统可测性差。
3. **会话记录单 + 缺陷与疑点**：逐条记下做了什么、观察到什么；未确认的疑点也要留痕。

**价值**：把「靠个人灵感」的探索变成可度量、可交接、可复现的过程，用「会话覆盖率」回答「某模块被探索了多少」。

## 三、接口测试

### Q：接口返回是嵌套很深的 JSON，断言怎么写才既稳定又有区分度？

**结论**：避免两个极端 —— 全字段比对（脆弱）与只断 status=200（无区分度），改为分层断言。

1. **契约层**：必填字段存在、类型正确、枚举值合法。
2. **业务层**：只断与本次用例意图相关的字段，而不是全字段。
3. **关系层**：字段间逻辑一致（如 total = list 长度、金额 = 单价 × 数量），最易抓到真 bug。
4. **忽略层**：时间戳、traceId、自增 ID 显式列进忽略清单。
5. **反向断言**：对「不该出现的字段」也要断言（内部字段、敏感字段不得下发）。

**实现**：JSON Schema 校验结构 + JSONPath / JMESPath 做局部断言，而非全量 diff。

## 四、性能测试

### 知识点：性能测试中「稳态」怎么判定

| 信号 | 判据 |
|---|---|
| 吞吐 | 连续 2~3 分钟 TPS 波动小于 5%~10% |
| 响应时间 | 平均 RT 与 P95 无趋势性升降，围绕水平线波动 |
| 资源 | CPU / 连接池不再持续爬升；**内存持续爬升通常意味着泄漏** |

- 一次压测的时间结构：**预热期 → 稳态期（正式采样）→ 结束观察期**，只取稳态期数据。
- 短时间稳态看着好，长稳测试才暴露内存与连接泄漏，关键场景必须做长稳。

### 技能：性能压测方案设计与瓶颈定位

- **要点**：按真实业务比例建混合场景；容量规划加思考时间、极限探测加集合点，两者不混用；阶梯加压找拐点（TPS 不涨 / RT 非线性抬升 / 资源贴顶）；压测机自身也要监控；关键场景做长稳。
- **常用工具**：JMeter、k6、Locust、Gatling、Prometheus、Grafana、Arthas。

## 五、AI 测试

### Q：AI 应用的「非确定性输出」怎么设计断言？

**结论**：把「精确匹配」降维成多维度可判定约束，从五个层次做断言。

1. **结构约束（完全确定）**：是否合法 JSON、字段齐全、类型正确、长度限制。
2. **内容约束（规则判定）**：必须包含的关键信息、必须不包含的措辞（禁止承诺、他人隐私）。
3. **语义约束（模型/向量判定）**：与参考答案做语义相似度或裁判模型打分，设通过阈值；**裁判模型本身要抽样校验**。
4. **行为约束（多次采样）**：同一输入重复 N 次，统计满足前三条的比率。
5. **安全约束（红队用例）**：注入载荷不得奏效、不得输出违规内容。

**准出标准改写**：关键约束 100% 通过 + 质量指标达标；断言从「布尔值」变成「指标分布」。

### 知识点：AI 应用测试的「三层断言模型」

| 层 | 内容 | 准出要求 |
|---|---|---|
| 确定性层 | 结构、格式、长度、字段完整性、敏感词 | 必须 100% 通过，任何一次不通过都是真缺陷 |
| 统计层 | 准确性、相关性、忠实度 | 不低于基线且达标，需给出置信区间 |
| 安全层 | 越权、注入生效、违规内容、数据外泄 | **零容忍**，任何一次触犯都是阻塞级 |

**补充**：三层之外仍需人工抽样复核，防止「规则写得对但规则本身错」（如把「拒答」误判成「回答正确」）。

### 技能：大模型应用质量保障

- **要点**：三层断言；同一输入重复采样用分布判定；准备带标准答案与依据标注的评测集；规则能判的与需模型判的分开；评测集覆盖边界、对抗、兜底、历史回归四类。
- **常用工具**：pytest、promptfoo、DeepEval、Ragas、LangSmith。

## 六、AI Agent 测试

### Q：AI Agent 的测试，跟普通对话应用有什么本质不同？

**结论**：对话应用的输出是「一段文本」，Agent 的输出是「一连串带副作用的动作」，由此多出四个测试维度。

1. **过程而非结果**：要断言动作序列（调用哪个工具、参数为何、顺序如何），因为「绕远路碰巧答对」会被误判通过。
2. **工具调用的参数正确性**：工具选对但参数传错（金额负数、日期格式错）会造成真实副作用，最隐蔽也最危险。
3. **停止条件与循环**：必须测「达不到目标会不会无限循环」「重试有没有次数上限」，否则一次故障就能烧掉大量成本并反复执行写操作。
4. **副作用与可回滚**：不可逆操作是否需要二次确认、是否有干跑模式、失败是否可回滚。

**工程手法**：把模型调用做成可录制/可回放，让「工具编排逻辑」变得确定，把不确定性收敛到「模型决策」一个点上，用例才稳定可回归。

### 知识点：Agent 的「动作序列」断言设计

- **工具集合**：该调的调了、**不该调的没调**（后者常被忽略，但多调一次往往意味着理解偏差）。
- **关键参数**：对金额、ID、日期、数量做值域校验；重点检查引用的 ID 是否来自上一步真实返回，而非模型编造。
- **顺序约束**：先查后改、先校验后提交等业务先后要求。
- **收敛性**：总步数与重试次数有上限；同一工具同一参数重复调用超阈值要告警（既是质量也是成本问题）。

### 技能：AI Agent 行为与编排测试

- **要点**：将 LLM 调用层 mock 化，让编排逻辑测试完全确定；断言工具集合、参数、顺序、收敛性；设置步数与重试上限并把成本当 SLI 监控；评测集覆盖能力、边界、对抗、兜底、回归五类。
- **常用工具**：LangSmith、Langfuse、OpenTelemetry、轨迹回放框架。

## 七、大模型工程

### 知识点：大模型评测的指标体系与「裁判」选择

| 类别 | 指标 | 适用 |
|---|---|---|
| 任务正确率 | 准确率、字段级 F1、数值精确匹配 | 有标准答案的任务，最客观，优先 |
| 生成质量 | 语义相似度、忠实度、完整性 | 开放式生成 |
| 行为指标 | 指令遵循率、格式合规率、拒答正确率、幻觉率、平均步数/成本 | Agent 与对话系统 |
| 体验指标 | 人工评分、人工偏好对比 | 最贵但最接近真实感受 |

**裁判选择**（各有取舍）：规则打分（便宜稳定、只覆盖可判定部分）→ 模型打分（覆盖开放内容，但存在偏好偏差，需人工标定一致率）→ 人工打分（最可信、成本最高）。
**实践建议**：规则能判的绝不用模型判；模型打分须先用人工标注集校准，一致率不达标不能作为准出依据。

## 八、测试环境搭建

### 知识点：测试数据的来源与治理策略

| 来源 | 优点 | 代价 |
|---|---|---|
| 生产数据脱敏导入 | 最贴近真实分布 | 脱敏不彻底有合规风险，量大导入慢 |
| 接口/脚本造数 | 清爽可控可复现，自动化首选 | 造复杂关联数据成本高 |
| 基线数据集快照 | 起点一致，适合回归 | 需要维护快照与恢复机制 |
| 程序化生成（随机+约束） | 可造大量边界数据 | 需设计约束，易生成无效数据 |

**三条铁律**：数据由测试负责生也负责清；测试数据带批次标识、只断本批次；禁止依赖「库里预先存在的那条数据」。
**补充**：数据的生命周期（谁造、用多久、何时清、清理失败怎么办）也要有约定。

### 技能：测试环境即代码与一键重建

- **要点**：基础设施用 IaC 描述、应用用容器镜像固化版本、配置从外部注入、准备基线数据集、外部依赖（短信/支付）统一 mock 或接 sandbox；每个分支/流水线独立环境实例，用完即销毁。
- **常用工具**：Docker、Docker Compose、Kubernetes、Terraform、Ansible、Testcontainers。
- **边界**：环境即代码不能替代数据治理 —— 机器能重建，但数据从哪来、会不会脏仍需单独设计。

## 九、CI/CD

### 知识点：流水线门禁的「分层」设计

| 层 | 内容 | 目标耗时 |
|---|---|---|
| 提交前 | 格式、静态检查、极快单元测试 | 10 秒级 |
| 合并请求门禁 | 完整单元 + 接口测试、构建、代码扫描 | 10 分钟以内 |
| 合并后/夜间 | 全量回归、UI 自动化、性能基线、兼容性矩阵 | 上班前出结论 |
| 发布前 | 核心主链路冒烟、数据库变更校验、配置一致性 | 最快且能拦发布 |

**两个原则**：门禁必须可信（频繁误报会让团队习惯性忽略红灯，flaky 优先修理而非加自动重试）；门禁失败必须给明确原因（哪条、为什么），否则会增加排查成本、动摇门禁价值。

## 十、数据库与 Linux

### 知识点：慢查询的定位路径 —— 从现象到根因

1. **先确认慢在哪一段**：数据库执行慢，还是应用层慢（连接池等待、序列化、网络）。用应用侧与数据库侧的耗时差值判断。
2. **拿到真实执行计划**：看访问方式、连接顺序，以及**每步预估行数 vs 实际行数**（差一个数量级 → 统计信息或数据分布问题）。
3. **看锁等待**：计划很好却慢，先查是否在等锁。
4. **看返回数据量**：SQL 快但结果集极大，网络传输与解析也会成瓶颈，改分页或只取必要字段。
5. **最后才看索引**：补索引前先确认选择性，选择性差的列加索引反而更慢。

**补充**：区分「单次慢」与「高频次慢」—— 一条 50ms 的 SQL 每秒调 1000 次，比一条 2s 的 SQL 更值得优先优化。

## 十一、场景题

### 知识点：线上问题的排查框架 —— 止损—定位—复现—归因—类问题

1. **止损**：先评估影响（用户量、金额、是否持续），能止血先止血（回滚、开关、限流、摘流量）。根因可以慢慢查，损失不能慢慢止。
2. **定位（缩小范围）**：三条线索交叉 —— 时间线（与什么变更对齐）、数据特征（异常数据的共同点）、分布（全部用户还是特定机型/地域/版本）。
3. **复现**：能复现才有根因；不能复现就先补埋点，用可观测性换下一次的定位速度。
4. **归因**：区分直接原因（空指针）与根本原因（为什么没有校验、为什么没人发现）。只修直接原因，同类问题必复发。
5. **类问题排查 + 沉淀**：同根因影响的其它链路一并排查；把问题转成回归用例、监控告警、流程改进。

**实用技巧**：处理时同步记录时间线（几点发现、几点做了什么、几点恢复），复盘效率显著提升。
