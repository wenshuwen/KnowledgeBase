## 一、测试环境：声明式建成不等于可用

### 1. 题：apply 成功就能跑用例了吗

**Q：环境是用声明式工具建出来的，apply 成功就能直接跑用例了吗？验收环境看哪几项？**

不能。**apply 成功只证明「资源被创建」，不证明「服务可用」**。资源创建与服务可用之间隔着配置、数据、证书、依赖四道坎。

五项自检（应脚本化，apply 后自动跑）：

| 项 | 查什么 | 失败表现 |
|---|---|---|
| 解析与连通 | 域名解析到预期地址、端口 TCP 可通、应用层探活 | 用 ICMP 判通会漏掉「网络通但应用挂」 |
| 版本台账 | 镜像 digest、中间件版本、配置版本 | 版本错配后所有用例结论都要打折 |
| 数据基线 | 种子数据、脏数据清理、时钟同源 | 缺数据导致大面积失败，报错很像业务 bug |
| 资产有效期 | 证书、令牌、密钥、license 剩余天数 | 不足 7 天预警，否则会在某日凌晨集体红 |
| 核心冒烟 | 5~10 条关键链路 | 前四项都过但链路上不通，只有冒烟能发现 |

判据要落在输出物上：生成一份**环境就绪报告**，任一项不过即标记「环境未就绪」，不把测试流量切过来。这一步的真正价值不是省时间，而是**在源头把「环境问题」和「代码问题」分开**。

### 2. 题：临时环境怎么回收，怎么验证回收干净

**Q：每个分支一套临时环境，环境越堆越多，怎么回收？回收了怎么验证干净？**

按需环境失控的根因是**没有生命周期管理**，靠人自觉一定会漏。

三段式回收（比一刀切删除安全）：

1. **到期前 2 小时通知可续期**——直接删会让「忘了续期」变成事故。
2. **到期先停机、保留数据 3 天**——留出反悔窗口。
3. **3 天后彻底销毁**。

回收是否干净的判据是**四处核对**，不是看控制台列表：

| 位置 | 残留后果 |
|---|---|
| 云资源（按 tag 查） | 计费持续、配额被占 |
| DNS 记录 | 下次申请同名域名冲突，最难排查 |
| 容器命名空间 | 镜像与 PVC 残留 |
| 环境注册表条目 | 自动化以为环境还在，调度到已删环境 |

两个配套约定：一是**创建时强制打标**（owner、用途、expire_at，缺一不建）；二是**保护名单**（预发、生产、protected 标记）不进自动回收。无 owner 的孤儿资源只出报告、不自动删——这类往往占成本大头，但谁也不敢贸然删。

上线节奏建议先跑一个月「只报告不删除」的观察模式，确认误判率可接受再开真删。

### 3. 技能要点：声明式环境的验收

- 看镜像 **digest** 而不是 tag，tag 会被覆盖。
- 五项自检要写成脚本，人工检查一定会漏。
- 资产有效期必须进就绪检查，否则就是一颗定时炸弹。
- 回收结果按四处清单核对，控制台「看不到了」不算证据。

## 二、性能与容量：先证明扩了，再找串行点

### 4. 题：扩容一倍机器，TPS 只涨 8%

**Q：线上扩容了一倍机器，TPS 只涨了 8%，怎么定位卡在哪？**

分三步，顺序不能反：

1. **先判断是不是真扩容**。机器翻倍但连接池总数、Worker 进程数、线程数是否跟着变？配置没变等于并发能力没变。这类原因占比很高，却最容易被跳过。
2. **找「不随并发变化」的那一层**。压测时同时采集入口 QPS 与每层 QPS、利用率，看哪一层在入口翻倍后完全没有涨。三个典型串行点：**单一主库写入**、**全局计数器或发号器的单个 key**、**第三方依赖的固定 QPS 上限**。
3. **看利用率拐点**。某层利用率到 80%~90% 就不动，说明它已饱和，继续加应用机器只是让它更早饱和。

证明结论的方式：把那一层单独扩容或加缓存再压一次，TPS 有明显跃升则结论成立。

报告写法：**「当前瓶颈在 X 层，入口扩容收益上限约 Y」**，而不是「扩容效果不佳」。

### 5. 坑点：延迟降了就认为性能变好

并发翻倍后 P99 从 80ms 降到 60ms，就报优化成功——但没看成功率。实际情况往往触发了限流降级，**大量请求被快速失败，耗时极短，把分位数拉低了**。

四种可能，逐一排除：

| 解释 | 验证方式 |
|---|---|
| 测量条件不同 | 固定预热轮次与采样窗口，看缓存命中率是否变了 |
| 触发限流降级 | 看成功率，跌了就是假数据 |
| 排队掩盖 | 看端到端耗时，服务端降但端到端没降即此因 |
| 统计口径 | 样本量、分位算法（插值法、直方图桶宽）是否一致 |

做法是把 QPS、成功率、端到端延迟、服务端延迟**四条时间序列叠在一张图上**，任一背离先解释它。

## 三、接口与兼容：把「兼容」做成可比对的东西

### 6. 技能要点：接口版本的兼容回归

多版本并行期的风险不在新接口，而在**老接口被静默改坏**：两版共用同一个数据结构，改一处影响两版，而且往往不报错、只是行为变了。

- **契约冻结**：老版本只允许加字段，不允许删字段、改类型、改语义。
- **响应快照比对**：把每个接口的响应结构存成快照，发版自动比对，出现类型变化或字段消失即失败。这是唯一能兜住「静默变更」的自动化手段。
- **分层回归**：老版本只跑「快照比对 + 核心链路」，新版本跑全量，成本才可控。
- **弃用要有两个阈值**：调用方数量与调用量都降到阈值以下，再启动下线公告与弃用响应头。

### 7. 题：开压缩后 TPS 涨了但客户端偶发解析失败

**Q：接口开了 gzip 压缩，TPS 上涨，但客户端偶发 JSON 解析失败，从哪几个方向查？**

判断：TPS 上涨说明带宽确实省了，解析失败说明**内容在链路上被改变了**，两件事不矛盾，问题在中间某一层。

四个方向：

1. **内容被截断**——比对 Content-Length 与实际字节数、分块传输的 chunk 边界。
2. **重复压缩**——网关压一次、应用又压一次，只解一层得到的是仍压缩的字节流。查响应头是否出现两次编码，或解压后看首字节是否仍是压缩魔数。
3. **缓存没按编码区分**——缺 Vary 头时，缓存会把压缩版本返给不支持压缩的客户端，特征是「换台机器就好了」。
4. **空响应带编码头**——204/304 带 Content-Encoding 会让客户端解空体报错。

验证修的判据不是「不报错了」，而是**「内容没变」**：开关压缩各抓同一批，解压后做字节级 diff 必须完全一致；再补一条不带压缩头的客户端用例验证回退路径。

## 四、数据库：数据对了，体验可能还是错的

### 8. 题：唯一索引并发插入的竞态

**Q：唯一索引 + 并发插入报 1062，业务要求「已存在就返回已有记录」，怎么测？**

竞态窗口是**先查后插**：两个并发同时通过「不存在」判断，第二个插入撞唯一索引。

测试方式：同一业务键用 20 个并发同时提交，断言三件事——

1. 库里只有 1 条记录；
2. 20 个请求里没有一个返回 500 或数据库异常；
3. 其余 19 个返回「已存在」的正常业务响应，且记录 id 与第一条一致。

**只断言第一条是最常见的漏测**：数据确实只有一条，但 19 个用户看到报错，体验上等于失败。

三种实现语义的差别：

| 语义 | 实现 | 问题 |
|---|---|---|
| 失败返回 | 直接抛异常 | 用户看到 500 |
| 返回已存在 | 冲突后重查一次返回 | 正确做法 |
| 静默忽略 | 忽略冲突继续 | 调用方拿不到已有记录 id，易误用 |

边界还要补一条：**软删除 + 唯一索引**，删除后再插同键仍会冲突。

## 五、大模型与 Agent

### 9. 知识点：temperature 归零的残余随机源

四个来源，配置无法消除：

- **浮点归约顺序**——GPU 上累加顺序不固定，末位误差经 softmax 放大成不同的 token 选择。
- **批处理拼接**——同一请求与不同请求拼在一个 batch 里，数值互相影响；表现为低峰期与高峰期结果可能不同。
- **并行 kernel 与副本差异**——不同卡型、驱动版本。
- **模型或路由版本不一致**——多副本落到不同版本，差异最大也最易被忽略。

对测试的三个直接结论：

1. 不能写字符串相等断言；
2. 断言分层：结构断言（字段齐全、类型正确）→ 关键实体断言（数字、结论方向）→ 语义等价判定；
3. 指标写**采样次数与一致率**（如 10 次采样 9 次一致），不写「已验证通过」。

严格复现只在调试场景用：固定 seed、单请求 batch、固定版本与副本。

### 10. 题：Agent 中间步拿到错误结果还继续走了

**Q：Agent 第 3 步的工具结果是错的，它继续往下走，最后输出还挺合理，这种错误传播怎么测？**

这是 Agent 测试里最危险的一类：**错误被平滑吸收，答案通顺但没有依据**。

前置条件：每步的工具名、入参、返回、以及它对返回的解读都要有 trace。没有 trace 就无从测起，这一条要作为需求提给研发。

测法：mock 工具返回四类异常——空列表、过期数据、字段缺失、明显矛盾的数值。

断言它必须**「暴露」而不是「吸收」**：

| 正确行为 | 危险行为 |
|---|---|
| 空结果时重试或换参数 | 静默补全，自己编一个合理值 |
| 发现矛盾时停下提问 | 把空结果当作 0 |
| 无法确认时在答案里声明不确定 | 两个矛盾数据挑一个用 |

两类高危模式要专门盯：**合理但无据**（答案通顺却追溯不到任何工具返回）、**部分成功当成功**（10 个文件处理成 3 个就汇报完成）。

判据可以简化成一句：**最终答案里每个事实性结论，都应该能追溯到某一步的工具返回**。

### 11. 技能要点：AI 根因结论的校验

语言模型最擅长的就是把相关性讲成因果，而且讲得非常自信——它的错误形态不是「说不出来」，而是**说得特别像真的**。

- 判据一：**有没有证据链**。结论必须指到具体日志行、指标名、时间点。
- 校准方式：拿已知根因的历史故障做盲测，统计「命中率」与「自信但错」的比例。后者偏高时，只能用于生成假设。
- 三类典型失效：把时间相近当因果、把数据缺失当正常、编造不存在的错误码或字段。
- 正确用法：让它输出「假设 + 待验证的检查项」，检查项要可执行，由人执行验证。
- 边界：涉及资金、合规、对外定责的结论必须人工复核并留痕。

## 六、理论：覆盖够不够，看维度不看条数

### 12. 知识点：覆盖维度的六向枚举

两个测试对同一需求给出的用例数差 3 倍，**数量不是指标，维度才是**。

| 维度 | 要覆盖什么 |
|---|---|
| 输入域 | 等价类、边界、特殊字符、超长、空值 |
| 状态 | 状态机每条合法迁移 + 非法迁移 |
| 时序 | 并发、重试、超时、乱序到达 |
| 权限 | 角色 × 数据归属 × 字段级 |
| 环境 | 版本、配置、网络条件、依赖可用性 |
| 异常 | 依赖失败、部分成功、降级路径 |

判据：每格至少一条，关键格（资金、权限、不可逆操作）要求多条；空白格靠历史逃逸缺陷回填。

3 倍差距多数是这种情形：一个人写了 300 条，其中 250 条是同一格的变体，有效覆盖格数反而不如另一个人 100 条。所以先**去重归并再比格数**，否则比的是勤奋不是覆盖。

## 七、其他坑点三则

### 13. 坑点：是 JSON 接口就不做 CSRF 防护

认为跨站发不了 JSON 就免测。实际上用 text/plain 或表单编码仍可提交，服务端不校验 Content-Type 时一样能改数据。

判据不是「是不是 JSON」，而是**服务端是否严格校验 Content-Type，且校验来源或带 CSRF token**。验证方式是用本地跨站页面实际构造一次提交，看数据是否被改掉。

### 14. 坑点：AI 生成的用例不去重就入库

一次生成几百条全收下，其中大部分是同一场景换个说法，维护成本暴涨但覆盖维度没增加。

衡量指标应是**去重后的有效覆盖格数与新增覆盖格数**，不是条数。生成后要按场景标签归类、语义去重、与覆盖矩阵比对，再人工抽检断言是否有意义（最常见的隐性问题是断言写成「响应不为空」）。

### 15. 坑点：兼容性只在自己用的浏览器上过一遍

开发用主浏览器测完就宣布兼容，其他浏览器与低版本内核上一片红。

做法：兼容性收敛到高风险五类用例跑矩阵（渲染布局、键盘焦点、上传下载、弹窗新窗口、表单校验提示），其余只跑主浏览器；批量红先归因同根因（常见是隐式等待不生效），再合并成一个缺陷。

## 待图谱化的候选关联

以下为后续每周精读时可考虑与既有页面建立关联的方向（本文件不写双向链接，避免在原料层留死链）：

- 环境就绪五项自检 ↔ 测试环境搭建与验收：可作为「环境可用性」判据清单
- 临时环境 TTL 与回收核对 ↔ 环境成本与资源治理：与「环境数量成本模型」互补
- 扩容串行点定位 ↔ 性能瓶颈分析：与「压测结论可信度」同源
- 延迟与成功率联合判读 ↔ 性能指标解读：补「好看数据」的识别方法
- 契约快照比对 ↔ 接口兼容性测试：可作为回归裁剪的实例
- 唯一冲突的三种语义 ↔ 数据库约束与并发：与「软删除撞唯一索引」配对
- temperature 残余随机 ↔ 大模型输出断言：与「非确定性断言设计」衔接
- Agent 中间步错误传播 ↔ Agent 可观测性与护栏：与「破坏性动作护栏」互补
- 覆盖六向枚举 ↔ 测试设计方法论：可作为「覆盖是否充分」的判定框架
