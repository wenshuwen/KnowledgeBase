## 一、性能测试

**Q：压测目标（TPS）是怎么推导出来的？**

目标不能拍脑袋，从三个来源推：

- **业务量推算**：日均业务量 × 集中系数 ÷ 时间窗 ≈ 峰值 TPS，再乘 2~3 倍冗余。例：日均 100 万单、80% 集中在 4 小时 → 1000000×80%÷4÷3600 ≈ 55 TPS，目标取 110~165。
- **历史容量基线**：上一版压测或上线的容量数据 + 扩容比例，用来评估容量是否线性增长、瓶颈在哪一层。
- **业务 SLA 倒推**：产品约定「下单 3 秒内返回」，据此反推系统至少要扛住的并发量。

定完目标必须同时定**验收口径**：TPS 达标线、P99 响应时间上限、错误率上限（一般 < 0.1%）、资源水位红线。没有验收口径的压测，结论只能靠感觉表述。

**知识点：性能指标体系（四类必须同看）**

| 类别 | 代表指标 | 作用 |
|---|---|---|
| 吞吐量 | TPS / QPS | 容量能力的直接体现 |
| 响应时间 | P50 / P95 / P99（**不看平均值**） | P50 看典型体验，P99 看长尾 |
| 正确性 | 错误率 | 高吞吐下容错会被放大 |
| 资源水位 | CPU / 内存 / GC 停顿 / IO / 连接池占用 | 找瓶颈、评估余量 |

理由：TPS 高但 P99 爆掉说明存在排队；错误率低但资源打满说明没有余量。缺任何一类，结论都不可靠。

**技能：压测目标推导与容量模型建立**

要点：业务量 → 峰值 TPS 的换算公式；冗余系数按业务重要性与扩容速度定；用单机容量外推集群容量并验证线性假设；把目标写进压测报告首页以免事后争论。常用工具：JMeter、k6、Locust、Grafana、Prometheus。

**坑点：压测只压被测服务，完全不考虑上下游依赖**

压测环境的数据库是空表、缓存冷启动、下游是 mock，压出来的漂亮数据一上生产就崩。真实瓶颈常在下游（数据库连接数、第三方限流、消息堆积）。
破解：确认「数据量与真实同量级、缓存状态贴近真实、下游可承受」；下游不能压时，在报告里显式标注「本次未覆盖下游，结论仅适用于服务本身」。

## 二、AI 与大模型测试

**Q：怎么评测一个 RAG 问答系统？**

必须**分段归因**，否则不知道是检索的锅还是生成的锅。

| 层 | 关键指标 |
|---|---|
| 检索层 | Recall@k、MRR（正确文档是否召回、排得靠不靠前） |
| 生成层 | 忠实度（可溯源、无幻觉）、答案相关性、格式合规率 |
| 端到端 | 人工/模型评分、业务信号（追问率、点踩率、任务完成率） |

还要单独测三类非功能项：**拒答正确性**（知识库没有的内容应拒答而非编造）、**引用准确性**（引用段落是否真的支持结论）、**上下文溢出时的降级表现**。
关键动作：**先建评测集再调优**，否则每次改动只能凭感觉判断「好像好了点」。

**知识点：Agent 测试的四个维度**

1. **结果**：任务是否完成、输出是否合规（必要但不充分）。
2. **轨迹**：工具选择是否正确、参数是否准确、调用顺序是否合理、有无重复调用、失败后能否重试或换策略、是否陷入循环直到步数上限。
3. **安全（副作用）**：Agent 会真的发信、写库、下单、删文件。要验证高危操作的确认机制、权限边界、是否在沙箱执行、敏感信息是否会外泄。
4. **成本**：平均步数、token 消耗、单任务耗时与费用。能完成任务但成本高到不可用，同样不合格。

**坑点：把「工具调用返回成功」当成「这一步业务成功」**

Agent 调用下单接口拿到 HTTP 200 就认为下单成功继续往下走，实际业务返回的是「库存不足」，最后报告任务完成、实际什么都没做。这是 Agent 测试最高频的缺陷。
破解：工具层做**双层判断**——先看网络层是否成功，再看响应体业务码/业务字段是否成功；用例专门构造「调用成功但业务失败」的场景，验证 Agent 是否识别并补救（重试、换方案、如实上报），而不是继续往下走。

## 三、安全测试

**技能：越权漏洞的系统化排查（四类入口 + 双维验证）**

- **四类入口**：① URL 路径参数（`/order/{id}` 换成他人 ID）；② 请求体字段（`userId`/`tenantId`/`orgId` 可篡改）；③ 查询参数（`?userId=`/`?role=`）；④ Header 透传（`X-User-Id` 等网关透传身份头可伪造）。
- **双维验证**：水平越权（同级用户互访）、垂直越权（低权限调高权限接口）。

落地方法：维护「接口 × 参数位置 × 角色」矩阵，脚本批量替换身份重放，结论沉淀成回归用例。
关键认知：**防御必须在服务端逐次校验资源归属**，前端隐藏入口与网关鉴权都不足以防御越权。

## 四、数据库

**知识点：索引失效的常见写法清单**

1. **对索引列做函数或运算**：`where date(create_time) = '...'`、`where id + 1 = 100`。
2. **隐式类型转换**：字符串字段传数字、数字字段传字符串。
3. **前导模糊匹配**：`like '%abc'`（`like 'abc%'` 可以走索引）。
4. **联合索引不满足最左前缀**：索引 (a,b,c)，查询只用 b 或 c。
5. **`or` 连接非索引列**，整体退化为全表扫描。
6. **范围查询后续列失效**：索引 (a,b)，`where a>1 and b=2` 中 b 用不上索引排序。
7. **优化器主动放弃**：区分度太低（如性别字段）或统计信息过期导致预估行数严重偏离。

排查手段：`EXPLAIN` 看 type / key / rows / Extra，重点盯 `ALL`（全表扫描）与 `Using filesort` / `Using temporary`。

## 五、测试环境治理

**技能：环境变更留痕与准入控制**

环境问题的根源往往不是「被改了」，而是「改了没人知道」。做法：禁止登录机器直接改配置，变更统一走配置中心或流水线并带审批与记录；高危变更（连接串、功能开关、限流阈值）单独二次确认；变更后自动健康检查、异常立即回滚；定期审计变更记录，识别绕开受控通道的隐性改动。
常用工具：Nacos/Apollo、Ansible、GitOps/ArgoCD、堡垒机、审计日志。

## 六、场景题 · 线上排查

**Q：线上出现「用户下单成功了但订单查不到」，怎么排查？**

数据不一致类问题，核心方法：**沿链路找「哪一步成功了、哪一步没成功」**。

1. **先确认现象**：拿具体用户与时间，直接查库 —— 是「没写入」还是「写了但对不上」。
2. **分段核对**：网关日志 → 订单服务是否生成订单 ID → 库存是否扣减 → 缓存与库是否一致。库存扣了但订单没落库，是典型的事务/分布式事务问题。
3. **怀疑主从延迟**：查询走从库时，主库已写、从库未同步会出现短暂查不到；确认延迟时长与是否有强制走主库的开关。
4. **判断影响范围**：个案还是批量、是否集中在某次发布之后。
5. **修复与兜底**：存量数据修复脚本 + 复核、补查询入口或监控告警。
6. **沉淀**：把场景写成回归用例（主从延迟、消息丢失、并发扣减），这些正是常规测试最容易漏的地方。

## 七、协作与决策

**坑点：故障排查结束就收工，不把场景沉淀成用例**

定位出问题、修完就散，下一版重构时同一问题原样复现，又要重新排查一遍。
破解：把「故障 → 用例」定为固定动作——每次复盘至少产出**一条可自动化的回归用例**或**一个监控告警项**。来自真实故障的用例，价值远高于凭空设计的用例。

**坑点：把用例数量当成测试充分性的证明**

汇报「本次设计 500 条用例」但没有回答「覆盖了哪些风险、哪些没覆盖」。数量多但集中在主干顺利路径，异常分支、并发、边界全漏。
破解：用**需求覆盖率 + 风险覆盖**替代用例条数；梳理需求点清单逐条映射；单独列出「本次未覆盖的风险及原因」。汇报时先说高风险场景覆盖情况，再说总量。

## 待图谱化的候选关联（暂不写 `[[]]`，由每周编译任务决定合并去向）

- 压测目标推导 ↔ 容量上限的阶梯加压拐点（同一主题的「目标侧」与「极限侧」）
- 性能四类指标同看 ↔ 压测结果对比的控制变量清单（度量与实验设计的一体两面）
- P99 与长尾成因 ↔ 慢查询按总耗时而非单次耗时排序（「平均值/单点」误导性的两处体现）
- Agent 轨迹与副作用 ↔ 多轮会话的状态与上下文（Agent 测试的两个正交难点）
- RAG 分段归因 ↔ 大模型非确定性输出的规则化断言（概率系统的「分层」思路复用）
- 越权四类入口矩阵 ↔ 接口断言四层模型（均为「参数位置/校验层次」的系统化清单）
- 环境变更留痕 ↔ 环境指纹与差异清单（同一问题的「事前控制」与「事后检测」）
- 主从延迟导致查不到 ↔ 事务隔离级别对测试结论的影响（数据可见性问题的两处落点）
- 故障转回归用例 ↔ 用例充分性的风险覆盖判据（沉淀与度量的闭环）
- 索引失效写法清单 ↔ 慢查询定位的分层排查（同一主题的「清单」与「流程」两种承载形式）
