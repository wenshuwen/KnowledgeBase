## 一、安全测试

### 1. 一次水平越权的完整发现过程

**Q：你实际发现过什么安全问题？讲一次完整的过程。**

**发现**：某订单详情接口形如 `/api/order/detail?orderId=xxx`，orderId 为自增整数。抓包时注意到该接口未在查询条件中约束归属。

**验证**：账号 A 下单取得 orderId，改用账号 B 的会话请求同一 orderId —— 返回 200，且响应体包含 A 的收货人、手机号、地址。将 orderId 递减可遍历其他用户订单。

**影响判定**：水平越权，可按 ID 遍历全站订单，涉及个人信息泄露，定级为高危、阻塞发布。

**修复**：查询条件补归属约束（订单号 + 当前用户双条件），并把归属校验抽为公共方法。

**回归**：按权限矩阵补一组用例 —— A 查 B、B 查 A、匿名查、非法 ID、已删除订单，纳入接口自动化，权限相关改动自动重跑。

**可复用的结论**：判断越权不能以「接口有没有报错」为准，而要以「返回的数据是否属于当前用户」为准。返回 200 且带他人数据即高危。

### 2. 越权测试的三类入口

| 类型 | 做法 | 易漏点 |
|---|---|---|
| 水平越权 | 同角色用户之间横向串资源 ID | 只测详情接口，漏测**列表接口**（不按当前用户过滤会一次泄露全量） |
| 垂直越权 | 低权限会话重放高权限接口请求 | 只验证「被拦住了」，未区分拦在网关还是拦在业务层 |
| 变体 | 改请求体 userId / 路径 tenantId / JWT 的 role 字段 / 换 HTTP 方法绕过拦截器 | 只在某一 HTTP 方法上配了拦截器 |

**判定口径**：返回 200 但业务码为「无权限」算通过；返回 200 且带他人数据必须报高危。

### 3. SSRF 的三处高危入口与三层防御

**入口**：① 远程图片/文件转存（传 URL 让服务端下载）；② webhook、回调、消息推送的接收地址配置；③ URL 预览、网页抓取、在线转码这类「给链接我帮你处理」的功能。

**攻击目标**：云主机元数据地址 `169.254.169.254`（取临时凭据）、内网管理端口、内网服务发现接口。
**绕过手法**：十进制/八进制 IP、`0.0.0.0`、DNS 重绑定、302 跳转、`@` 分隔的 URL 混淆。

**三层防御**：协议白名单（仅 http/https，禁 gopher/file/dict）→ 解析后校验真实 IP 不在内网/回环/链路本地段（**只解析一次，防重绑定**）→ 统一出网代理 + 域名白名单。

**测试要点**：「拒绝」与「超时」必须区分 —— 超时可能意味着请求已发出只是无回显，需结合服务端出网日志确认。

### 4. JWT 的五个实现缺陷

1. **alg 混淆**：header 的 alg 改为 `none`，或 RS256 换 HS256 用公钥当密钥自签。服务端必须固定期望算法，不信任客户端声明。
2. **密钥弱**：HS256 短密钥可离线爆破，爆破后即可伪造任意身份。
3. **无法主动失效**：JWT 自包含，签发后到期前一直有效；改密码、封号、退出登录后旧 token 仍可用。
4. **payload 明文**：仅 base64 编码而非加密，不能放手机号、身份证、内部角色标识。
5. **过期与签发者校验缺失**：不校验 exp/nbf/iss/aud，token 可跨系统串用。

**工程解法**：短 access token（15~30 分钟）+ 可吊销的 refresh token（服务端存储），或维护 jti 黑名单。
**必测**：篡改 payload 后签名是否失效、alg 改 none 是否被拒、退出登录后旧 token 是否立即不可用。

### 5. 敏感数据的四个链路落点

数据泄露很少是「数据库被拖库」，更多是在旁路被顺手带走：

- **响应体**：返回了页面用不到的字段（完整手机号、身份证、内部成本价）
- **日志**：请求参数、响应体、异常堆栈整体打日志；异常栈常带 SQL 与完整入参，而日志平台权限往往比数据库更宽
- **缓存与临时文件**：Redis 存明文证件号、导出文件落临时目录未清理、CDN 缓存了带用户信息的响应（缺 `Cache-Control: private`）
- **导出与下游**：批量导出、报表、消息推送、第三方同步，常绕过主链路的脱敏逻辑

**验证方法**：用带唯一标记的手机号走完整流程，再全局搜日志与缓存，看它出现在哪些不该出现的地方。

## 二、接口测试

### 6. 接口断言的四个层次

| 层次 | 断言内容 | 常见漏测 |
|---|---|---|
| 协议层 | 状态码、响应头（Content-Type、缓存控制） | 只断 200 |
| 业务层 | 业务码、message 语义是否与场景匹配 | 不同失败原因返回同一模糊文案 |
| 数据层 | 字段类型、金额精度、必填为空是 null 还是不返回、时间格式与时区 | 全漏 |
| 副作用层 | 数据库、缓存、消息、下游调用是否发生且只发生一次 | 全漏 |

**典型反例**：下单接口返回 200 且 code=0，但库存扣减是异步的，前端立刻查订单查不到。只断言响应体的用例全绿，用户却下不了单 —— 需补「返回后轮询查最终状态」断言。

### 7. 幂等的两种语义与测法

**两种语义**：① 重复请求不产生重复副作用；② 重复请求返回一致结果。很多系统只做到前者。

**测法**：固定业务唯一键（订单号或客户端生成的 requestId）→ **并发**发 5~20 次（串行测不出竞态，因为首次已完成落库与幂等键写入）→ 核对副作用（订单一条、库存扣一次、券核销一次、消息一条）→ 核对返回（返回首次结果或明确「已处理」，而非 500 或新建一单）。

**边界必测**：幂等键过期后重试；幂等键相同但参数不同（应拒绝，不能拿旧结果糊弄）；首次请求超时但实际成功。
**支付额外必测**：回调重复投递 —— 第三方回调天然重发，处理不幂等即重复发货或重复加余额。

## 三、性能测试

### 8. TPS 上不去的五层排查顺序

| 层 | 看什么 | 关键判据 |
|---|---|---|
| 1 压测机 | CPU、带宽、端口耗尽（TIME_WAIT）、连接上限 | 压测机与 TPS 同步饱和 → 结论作废 |
| 2 入口 | SLB/Nginx 连接数与带宽、SSL 握手、keep-alive | — |
| 3 应用 | 线程池/连接池打满、GC 停顿、锁竞争 | **CPU 高而 TPS 不涨 = 忙等或锁竞争；CPU 低而 TPS 不涨 = 在等 IO** |
| 4 依赖 | 慢查询、连接池耗尽、Redis 大 key/热 key、下游 RT | 全链路追踪看耗时落在哪个 span |
| 5 数据量 | 上量后执行计划变化、索引失效 | 小数据量结论不可外推 |

**方法**：先单接口基准压测拿单机容量，再做混合场景；否则多接口叠加无法归因。

## 四、数据库 · Linux

### 9. 慢查询的四步排查与 EXPLAIN 五项

**四步**：① 确认是语句慢还是等锁（状态 `waiting for lock` 时优化 SQL 无效）；② 看执行计划；③ 找没走索引的原因；④ 核对数据量与统计信息。

**EXPLAIN 五项**：`type`（`ALL` 全表扫、`index` 全索引扫，目标 `ref`/`range`）、`key`（实际使用索引，NULL 即未走）、`rows`（预估扫描行数）、`filtered`（过滤后剩余比例）、`Extra`（`Using filesort`/`Using temporary` 需警惕，`Using index` 是覆盖索引）。

**索引失效六因**：列上做函数或运算、隐式类型转换、前导模糊 `like '%x'`、违反最左前缀、`OR` 连接非索引列、统计信息过期。

### 10. 联合索引最左前缀的三个实践结论

- **等值条件顺序无所谓**，优化器会重排 —— 「顺序必须与索引一致」是常见误解
- **范围条件之后的列无法再用索引**（`(user_id, status, create_time)` 上 `where user_id=? and create_time>?` 跳过 status，create_time 用不上）
- **区分度高者优先**是通用建议，但若业务固定按某列查，该列必须放首位，哪怕区分度不高

**验证**：改完看 `EXPLAIN` 的 key 与 rows，并用真实数据量对比耗时。

## 五、AI 与 Agent 测试

### 11. 大模型评测的四层指标

| 层 | 判据 | 手段 |
|---|---|---|
| 事实层 | 能否找到出处，重点核对数字/日期/人名/条款编号/链接 | 关键实体断言 |
| 约束层 | 格式、长度、语言、禁用词、不得给越界建议 | 规则断言，命中即失败 |
| 行为层 | 该拒的拒了、不该拒的没误拒、信息不足是否追问 | 对抗样本 + **无答案题** |
| 质量层 | 相关性、完整性、可读性 | rubric + 模型裁判，**必须人工抽样校准** |

**三条硬要求**：评测集版本冻结（换题不可比）；保留「历史失败集」做回归；同条件跑三次看稳定性。**总分涨而合规率跌 = 变差。**

### 12. Agent 的四层测试框架

1. **意图理解层**：模糊表达下选对工具与参数（时间范围解析、指代消解、多意图拆分）
2. **工具调用层**：参数合法性（必填缺失/类型错/越界）、失败是否重试、**重试上限**、是否调用权限外工具
3. **轨迹层（Agent 特有）**：**不能只看最终答案** —— 看步数（绕 8 步 = 规划有问题）、看是否重复调同一工具（死循环）、看是否跳过必要校验
4. **结果与副作用层**：业务状态是否正确，**任务重放两次是否产生重复副作用**

**三个必测项**：工具报错时的降级（坦白失败 vs 编造成功）、循环与超时上限、提示注入（尤其间接注入）。

**关键数字**：单步成功率 95%，10 步任务的端到端成功率约 `0.95^10 ≈ 60%` —— **用户感受的是 60%，不是 95%**。

### 13. 提示注入的四类样本与间接注入

- **直接注入**：输入里写「忽略以上所有指令…」
- **间接注入（最危险）**：恶意指令藏在 Agent 会读取的数据里 —— 网页、PDF、邮件正文、代码注释、工具返回的 JSON 字段。用户只让它「总结这个网页」，完全没做错任何事
- **越权诱导**：诱导它调用未授权工具，或用当前身份不该有的权限操作
- **数据外带**：诱导它把系统提示、内部资料、他人数据拼进回复或 URL 参数带出

**风险升级的本质**：普通聊天被注入是「说错话」；Agent 被注入是「做错事」，因为它有工具权限。
**防御三层**：外部内容标记为数据而非指令（结构化分隔，不直接拼进提示）→ 工具层参数白名单 + 危险操作二次确认 + 最小权限 → 输出层出网与敏感字段外发审计。
**测试关键**：把恶意内容放进「数据」位置而非「用户输入」位置，很多团队只测了直接注入。

### 14. RAG 的三段评测与常见误判

| 段 | 指标 | 说明 |
|---|---|---|
| 检索 | Recall@K、MRR | 纯离线可算，不需模型，**最该先做** |
| 上下文组装 | 截断、chunk 切分、多来源冲突排序 | **最隐蔽的问题来源** |
| 生成 | 忠实度、完整性、有无夹带 | — |

**最常见误判**：一出问题就调提示词、换模型，其实资料压根没被召回。**排查第一步永远是打印模型实际拿到的上下文。**
**必测项**：知识库里没有答案的问题应明确说不知道，而非拿相邻资料硬凑（RAG 里特别常见，因为总有内容可参考）。

**长上下文不等于替代 RAG**：中间信息利用率低、token 成本与首字延迟线性增长、检索层承担按用户权限过滤、引用可追溯 —— 四点仍成立。

## 六、场景题 · 线上故障

### 15. 「支付成功但订单未生成」的定界与定位

**定界（先做）**：起始时间、影响用户量、是否集中在某渠道/地区/版本。**时间点最关键** —— 与发布、配置变更、下游故障时间线对得上，方向基本就定。

**找断点**：沿 `支付回调 → 消息队列 → 订单服务 → 落库` 逐段确认。**看消息堆积量是最快的一招**，堆积即消费端卡住。

**用指标判性质**：错误率没涨但 QPS 掉 → 在等锁或等下游；错误率涨 → 直接看异常栈。

**常见根因**：回调幂等键冲突导致重复回调被吞、消费线程池打满、订单号生成器时钟回拨导致主键冲突、数据库连接池耗尽。

**处置顺序**：先止损（扩容消费者消化积压 / 摘流 / 回滚 / 关开关），再定位根因；同时兜住用户侧（补单、退款、公告）。

**事后**：补「支付成功数 vs 订单生成数」对账监控。**凡是「用户先发现、我们后知道」的故障，都说明可观测性有缺口，这比修 bug 更重要。**

## 七、软技能 · 协作机制

### 16. 测试基线不稳（提测后代码仍在变）的三步解法

**代价**：测的是 A 版本、开发同时合了 5 个提交 —— 报的缺陷可能已修，也可能引入未覆盖的新问题，最终「测了一周说不清测的哪个版本」，出问题无法回溯。

1. **把提测版本变成不可变标识**：构建号或提交 SHA，部署该制品而非「主干最新」。测试报告写清版本号，**不带版本号的缺陷单不收**。
2. **约定变更窗口**：测试期内的主干改动要么走「补丁 + 通知 + 影响面说明」，要么攒到下一轮。**关键不是禁止改，而是让改动可感知** —— 不知道改了就等于没测。
3. **明确重测范围判定规则**：改了哪个模块、影响哪些接口由开发在提交时说明，据此决定全模块回归还是只跑冒烟。不做无差别全量回归，也不做「改完不管」。

**沟通话术**：不说「你们别老改代码」，而说「我需要一个稳定的版本号，否则没法给你可信结论，也没法在出问题时回溯」。
