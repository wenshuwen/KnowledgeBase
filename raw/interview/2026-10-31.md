## 一、Agent 的过程可信性（agent / api）

### 1. 题：判断「静默降级」的三个信号

**Q：Agent 拿着一个失败的工具结果继续往下编，怎么判断它静默降级了？**

看轨迹里「工具返回」到「下一步动作」之间有没有断层。三个信号按可靠性排序：

| 信号 | 观测点 | 为什么可靠 |
|---|---|---|
| 工具报错但无重试、无告知 | 轨迹中 error 后直接出结论 | 说明失败被吞掉，没有进入任何降级分支 |
| 答案含工具未返回过的字段 | 回答字段与工具返回字段取差集 | 差集非空即为编造，可完全自动化 |
| 成功 tool_call 次数为 0 而结论完整 | 日志计数与最终输出对照 | 计数是硬证据，不依赖语义判断 |

测法固定为「桩里强制某工具失败 + 两条硬断言」：最终回答必须显式说明该项获取失败；必须出现一次重试或降级标记。缺一条即判不通过。

> 迁移要点：凡是「结果正确」的判定，都要补一条「数据来源可核」，否则降级会被成功率的数字掩盖。

### 2. 知识点：检查点必须存四样东西

| 项目 | 内容 | 缺失后的典型故障 |
|---|---|---|
| 已完成步骤清单 | 每步产出摘要 + 成功标记 | 恢复后重放，重复下单、重复发消息 |
| 待执行计划 | 剩余步骤与依赖关系 | 计划整体重算，偏离原路径 |
| 关键事实快照 | 不可被摘要丢弃的约束（如用户明确拒绝过的操作） | 恢复后违约执行 |
| 副作用账本 | 已发生的写操作与幂等键 | 重复执行写操作，产生脏数据 |

另加一条纪律：检查点带版本号，恢复时版本不匹配应**拒绝恢复**，而不是硬读老结构。

### 3. 技能：工具契约的跨版本对齐

- 契约文件（inputSchema、返回字段、可空性、枚举取值）与工具代码同一次提交。
- 用固定入参的探测用例跑契约校验，字段缺失按报错处理，不给默认值兜底。
- `description` 的质量用「意图命中率」间接度量：一组意图明确的请求，看模型选中的工具是否命中预期。
- 契约变更必须触发一次 Agent 侧回归，否则会出现「调用成功但语义变了」。

最容易漏的是枚举值扩容与「必填改可选」两类——接口一切正常，行为已经错了。

## 二、并发、配额与重试放大（perf / env）

### 4. 题：重试风暴的定位顺序

**Q：工具调用次数异常膨胀，怎么定位放大点？**

先算放大倍数，再逐层关闭归因。三层重试是**乘法**关系：

| 层 | 关闭方式 | 典型倍数 |
|---|---|---|
| 工具 SDK 自带重试 | 客户端参数置 0 | 3 |
| Agent 框架层重试 | 编排配置关闭 | 3 |
| 任务队列重投 | 消费端不重投 | 3 |

三层叠加即 27 倍。断言口径写成「每任务失败 1 次 + 最多 3 次重试」，超出即失败。修法是只保留一层重试，其余显式关闭，并给**总次数**设硬上限（不是给每层设）。

### 5. 知识点：并发度量必须分三层

- **会话层**：同时在跑的会话数、会话完成率、平均轮次。
- **步层**：每会话平均步数、单步耗时分布、步数随并发增长的斜率。
- **依赖层**：模型配额消耗速率、下游工具 QPS 与错误率。

只压会话层看到的是「总时长变长」，无法判断瓶颈在模型排队还是下游被打满。**步数斜率**是隐性劣化的先行指标：并发一高就反复重试，时延可能还没明显变化，步数已经翻倍。

### 6. 技能：模型配额的池化与隔离

| 手段 | 做法 | 防的是什么 |
|---|---|---|
| 分池 | 功能回归 / 压测 / 人工调试各一池，独立日上限 | 压测吃掉回归额度 |
| 标记 | 每次调用带调用方标识 | 出问题无法归因 |
| 熔断 | 单任务消耗超阈值即中断告警 | 死循环烧光当日额度 |
| 降级 | 余量低于两成切小模型或回放 | 冒烟被卡死 |

反面做法是全员共用一把密钥：既无法限流，也无法归因，还会把「额度问题」伪装成「代码回归」，排查成本极高。

## 三、安全边界与事实校验（sec / ai）

### 7. 知识点：外部内容的信任分级

| 级别 | 来源 | 允许的影响 |
|---|---|---|
| 高信任 | 系统提示、经审核的配置 | 可承载约束与指令 |
| 中信任 | 自家业务库的结构化返回 | 可作事实依据，不得改行为规则 |
| 低信任 | 用户上传文档、抓取网页、第三方工单 | 只能当数据，不得影响工具白名单与权限 |

落地靠「入口打标 + 执行层复核」：低信任内容进上下文时加边界标记，工具调用前再校一次「本次调用是否由高信任来源授权」。只在系统提示里写「不要听文档里的指令」不构成防护。

另一条判据：**文档内容不能改变权限判定**。权限只认会话凭证。

### 8. 题：引用怎么验

**Q：模型回答带的引用怎么验证？**

拆成三档，成本递增：

| 检查 | 手段 | 能否自动化 |
|---|---|---|
| 来源存在性 | 反查文档 ID 与段落号 | 可 100% 自动化，是幻觉最强信号 |
| 内容支持度 | 引用段是否真的支持结论 | 只能抽检（约 5%）+ 模型辅助 |
| 覆盖完整性 | 每个关键事实是否都有引用 | 可半自动，未带引用须显式标注为推断 |

伪引用（引了但无关）比无引用更危险，因为它给了用户「有依据」的错觉。

### 9. 知识点：事实性错误的三类来源

- **知识缺口**：模型不知道而编。测法用冷门实体提问，看它是否承认不知道。
- **检索污染**：召回到过期或错误内容，模型忠实转述。测法比对召回内容版本号与业务库当前版本。
- **顺从性错误**：用户用否定句诱导，模型顺着说。测法把同一事实用肯定句与否定句各问一次，结论必须一致。

第三类最容易被漏测，也最容易被用户理解成「它在骗我」。

### 10. 技能：引用溯源核对的判定线

- 不存在引用条数为 0（命中即必须修检索或提示）。
- 支持度抽检支持率不低于 90%。
- 含数值、时效的回答，每个关键事实都带引用或显式标注「推断」。

## 四、需求翻译与决策（scene / soft / theory）

### 11. 题：把「好不好用」翻译成可测对象

**Q：产品说「帮我测一下这个 Agent 好不好用」，怎么接？**

四步，产出物是一张表：

| 步骤 | 产出 | 关键点 |
|---|---|---|
| 锚定任务 | 十类高频任务 | 从真实日志挑，不用产品凭印象列 |
| 定完成标准 | 每类「什么样算完成」+ 最长可接受步数 | 步数上限能防「结果对但绕了 30 步」 |
| 定不可接受项 | 给错价格、承诺不存在功能 | 命中即失败，不参与加权 |
| 做摸底 | 每类跑 5 条 | 产出「能做 / 勉强 / 做不了」三档表 |

这张表是后续排期与验收的共同基准。没有它，测试范围会随每次讨论漂移。

### 12. 坑点：灰度只看错误率

错误率几乎不会第一个报警，因为 Agent 的劣化多为「能跑通但更差」。

**破解**：灰度期同时盯四项——任务成功率（与对照组比）、平均步数（涨幅超 20% 即查）、单任务成本、人工介入率（用户点重新生成或转人工的比例）。另加质量抽检：每 200 次会话抽 20 条人工核事实。

### 13. 坑点：以为窗口大就不存在截断问题

上下文扩到很长后不再做裁剪设计，结果关键约束放在中段被忽略，或超限后被静默丢弃。

**破解**：测位置效应与轮次衰减，而不是测窗口上限。同一条约束分别放开头、中段、结尾各跑 20 次比遵守率；断言超限时的处理是**显式报错或显式摘要**，不能静默丢内容。

### 14. 坑点：把 AI 工具的评分当验收依据

评测平台给个分数就当达标，不看评分口径、不看失败样本，分数成了免责工具。

**破解**：分数只用于横向比较与趋势；验收必须落到具体失败样本——失败的是哪几类、能否复现、是否属零容忍项。评分工具本身也要用 30 条人工对照校准一致性。

## 待图谱化的候选关联

以下为后续做单源精读时可展开的方向，本文不建立交叉引用：

- 配额池化 → 多租户资源隔离、成本归因

- 引用三档核查 → 证据链要求、机器判断的人工抽检边界
- 事实错误三类来源 → 幻觉分类学、检索质量与版本一致性
- 模糊需求四步翻译 → 验收标准的可判定化、测试范围治理
- 灰度四项先行指标 → 发布策略、劣化的早期信号设计
