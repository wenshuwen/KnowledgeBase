## Python 基础

### 1. 浅拷贝是「用例之间串数据」的隐性根因

**Q：测试代码里用 `dict(base)` 复制请求体模板，为什么跑完所有用例的参数都变了？**

- 浅拷贝只复制容器本身，**嵌套的 list / dict 仍指向同一对象**。改里层等于改原对象，于是前一条用例改的字段会带到后一条。
- 三类典型症状：**单跑对、连跑错**；批量造数「看着 200 条实际只有 1 个样本」；快照类断言永远通过（期望值与实际值是同一对象）。
- 收敛写法：**模板只读 + 每条用例进来先 `copy.deepcopy()`**，并在 fixture 里断言模板未被修改。

| 结构形态 | 浅拷贝是否够用 | 判断依据 |
| --- | --- | --- |
| 扁平字典（值全是 str / int / bool） | 够用 | 无可变嵌套 |
| 含 list / dict / 自定义对象嵌套 | 必须深拷贝 | 里层共享引用 |
| dataclass 含 list 字段 | 必须深拷贝，且默认值用 `default_factory` | 默认参数与浅拷贝是同一类陷阱 |

**判定口径**：凡是要被修改的容器，进函数前先复制；默认参数一律写 `None` 再在函数体内初始化。

### 2. 装饰器在测试里的三个固定用途

- **重试**：只对可重试异常生效；**断言失败必须直接失败**，重试会把真 bug 藏起来。
- **耗时统计**：逐用例打点，跑完倒序排，用于定位回归时长的长尾（实测常见「30% 用例占 70% 时长」）。
- **前置条件声明**：缺登录态 / 缺前置数据时自动准备或显式 skip，把「环境没准备好」与「代码有 bug」分开。
- 硬约束：必须 `functools.wraps`，否则报告里用例名全变成 `wrapper`；**层数控制在 2 层以内**，再往上堆栈被埋、排查成本反升。

## 接口测试

### 3. 分页接口的三类边界

| 边界 | 测什么 | 判据 |
| --- | --- | --- |
| 参数 | `page=0/-1`、`pageSize=0/超大/非数字` | 必须有上限保护，否则是可拖库入口 |
| 越界页 | 超出最后一页 | 返回**空数组**而非 4xx/5xx |
| 数据变动 | 翻页期间插入新数据或排序字段变更 | 不得出现相邻页重复或记录丢失 → 加稳定第二排序键（id） |

- **深分页代价**：`limit 100000,10` 需扫描并丢弃前 10 万行，延迟随页码线性上升；判据是翻到第 500 页时 RT 是否明显劣化，优化走游标分页或延迟关联。
- 附带必查：`total` 与实际可翻条数是否一致（count 与 list 条件不一致的高频缺陷）。

### 4. 幂等性测试的四种重复方式

- **串行重复**：连发两次 → 库里只有一条记录、余额只扣一次。
- **并发重复**：10 线程同幂等键 → 串行能过、并发会双写，是最容易漏的一类。
- **跨时间重复**：隔数分钟再发 → 验证幂等记录的有效期。
- **反向验证**：换幂等键、业务参数相同 → 应能正常创建；被拦说明去重键选错，误杀了正常业务。
- 落库断言优先看**记录数与金额**，接口返 200 很容易，重复扣款才是真事故。

## 性能测试

### 5. 长连接与短连接会把结论带偏

- **短连接**把三次握手（及 TLS）计入每条请求，压轻量接口时握手可能比业务更贵，**测出来是建连能力**；还会快速堆积 TIME_WAIT，端口耗尽后压测机先崩。
- **长连接**更接近 App / 网关真实行为，**但会掩盖连接数相关的问题**，秒杀类场景的真实压力恰在「同时建立大量连接」那一瞬间。
- 结论写法：**两套都压并分别标注场景**——长连接出容量基线，短连接出建连上限。只报一个数极易被误用。
- 暗坑：脚本未显式设置连接池大小时吃默认值（常见 8），20 并发下 RT 恒定不降，**默认值就是暗瓶颈**。

### 6. 排除压测客户端是压测的第一步

服务端 CPU 仅 18% 而 TPS 见顶时，按序排除：① 压测机 CPU / 内存 / fd / 端口；② 连接池与线程池等待队列；③ 下游 RT 与锁等待；④ 是否被全局锁串行化；⑤ 带宽与内核参数。

**判据**：每一层都要有指标证明「不是它」，而不是靠猜；报告里必须写明瓶颈位置。

## 安全测试

### 7. 测试账号权限决定了越权能不能被测出来

- 用管理员账号跑全部用例，所有接口都成功，**越权漏洞被完全掩盖**。
- 做法：至少准备三种角色（普通用户 A、普通用户 B、管理员），权限类用例**用最小权限账号跑**。
- 判据：**A 用自己的凭证访问 B 的数据被拒绝**；「未登录被拦截」只覆盖了未认证，没覆盖越权。
- 配套：JWT 场景下重点看 `alg` 是否白名单校验、`exp` 是否存在、登出与改密后旧 token 是否立即失效。

### 8. 账号枚举与暴力破解的判据不同

| 问题 | 判据 | 常见漏点 |
| --- | --- | --- |
| 账号枚举 | 存在 / 不存在账号的**状态码、文案、响应时间、响应长度**是否可区分 | 文案统一了但响应时间差 200ms 仍可枚举 |
| 暴力破解 | 连续失败后是否出现验证码 / 锁定 / IP 限流 / 递增延迟 | 改 `X-Forwarded-For` 绕过限流；大小写与空格绕过计数；App 端接口限流缺失 |

## 数据库

### 9. 事务隔离级别对应的四个现象

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 复现要点 |
| --- | --- | --- | --- | --- |
| 读未提交 | 可能 | 可能 | 可能 | A 改值不提交，B 能读到 |
| 读已提交 | 否 | 可能 | 可能 | A 两次读之间 B 提交更新 |
| 可重复读 | 否 | 否 | 可能 | 范围查询期间 B 插入并提交 |
| 串行化 | 否 | 否 | 否 | 并发度骤降、易锁超时 |

**测试关注点**：测试环境与生产的隔离级别是否一致——不一致会让并发问题在测试环境完全测不出来。

### 10. 一条 SQL 突然变慢的定位顺序

1. 确认是否真慢：并发高时慢常是**锁等待或连接池排队**，不是 SQL 本身。
2. 看执行计划四列：`type`（ALL 即全表扫）、`key`、`rows`、`Extra`（Using filesort / temporary）。
3. **对比历史执行计划**——变化才是根因。
4. 找变化点：数据量增长、统计信息过期（`ANALYZE TABLE`）、索引失效（函数包裹、隐式类型转换、前缀模糊）、表结构变更。
5. 最后才谈加索引，并验证 `rows` 是否真的下降。

**提醒**：在小数据量库里测慢查询没有意义——扫 5000 行比走索引还快，优化器会直接全表扫。

## CI/CD

### 11. 流水线分层与可承受反馈时长

- 排序原则：**越便宜、越早能失效的放越前面**——静态检查 → 单测 → 接口/契约 → 关键路径 E2E（5~10 条）→ 全量回归与性能基线。
- **提交阶段反馈控制在 10 分钟内**：超过阈值开发就会绕过门禁，**门禁被绕过的根本原因是太慢，不是纪律**。
- fail fast：第一层挂了立刻终止，不跑完五层再报。
- 灰度期验证四件事：实际流量比例（按版本统计请求数，1000 次落在 10%±1%）、切分维度稳定性（同一用户多次请求稳定命中）、数据兼容（新旧版本同时在线）、回滚可用。

## AI / Agent / 大模型

### 12. Agent 参数幻觉的三类表现与检测

| 类型 | 表现 | 检测方式 |
| --- | --- | --- |
| 编造实体值 | 订单号 / 用户 ID 看着合理但库里没有 | 该值能否在上游工具返回中找到出处 |
| 结构错位 | 参数名、层级、类型不符 | schema 强校验；注意宽松校验会静默接受并写脏数据 |
| 复述替代引用 | 不直接用上一步返回的 ID，自己复述一遍 | **入参与上游返回值做值级比对**，一位之差即失败 |

**工程解法**：不靠模型自觉——参数强校验 + 明确错误信息回灌（告知「该 ID 不存在，请先调用 search」）+ 把查 ID 收敛成专用工具。**能靠工具保证的，不要靠提示词保证。**

### 13. RAG 分流：先判断是检索还是生成

- 唯一核心判据：**把标准答案所在文档直接塞给模型，它能不能答对**。
- 能答对 → 检索问题（没召回 / 召回但排名靠后 / 切分不当）。
- 还答错 → 生成问题（未约束「只用给定材料」/ 材料冲突选错 / 材料无答案时编造）。
- 量化两指标：**召回率**（标准文档是否在 topK）、**忠实度**（答案每句能否在材料中找到依据）。
- 中间态：召回对、答案对，但用的是**旧版文档**——属于知识库更新链路问题，既非检索也非生成。

### 14. 长文档切分的三个失败模式

1. **切断语义单元**：固定字数切分把表格或结论劈开 → 召回半条信息，答案缺条件。
2. **块太大稀释语义**：一块混三个主题，embedding 变成平均值 → 哪个主题都匹配不准，「召回了但答偏」。
3. **缺上下文致指代失效**：块里出现「该政策」「上述条款」却无前文 → 解法是给每块加文档标题与章节路径前缀。

## 场景题

### 15. 「偶尔失败 + 日志无异常」的排查顺序

1. **把「偶尔」量化**：频率、时间点、用户、商品、支付方式，最好拿到订单号。没有具体实例无法排查。
2. **看另一种日志**：网关 access log（状态码、耗时）、风控拦截记录、库存流水、下游返回码。**很多「失败」是业务成功但前端判断错，或被风控静默拦截。**
3. **横向比失败实例**：同一商品 / 时段 / 渠道 / 版本 / 仓——共同点即嫌疑点。
4. **重点怀疑四类无声失败**：超时被上层吞掉、幂等键冲突导致请求被丢弃、库存或券并发竞争的错误码被忽略、前端把业务失败当成功处理。
5. **资产化**：补用例、补监控、补日志。**「失败路径没留下可判定痕迹」本身就是缺陷。**

### 16. 用户描述与系统事实之间的三种偏差

- **归因偏差**：用户说「付了钱没到账」，实际下单未支付成功 → 先拉订单状态与支付流水，不按用户的因果链走。
- **时间偏差**：说「刚才」实为三天前 → 用用户 ID 反查最近行为，而非按时间窗定位。
- **现象偏差**：说「页面卡住」，实为接口慢或被拦截 → 看网络请求与响应码，不看页面表现。

**原则**：用户描述是线索不是事实；第一步永远先拿「用户 + 时间 + 对象 ID」。
