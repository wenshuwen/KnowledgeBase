## 一、面试题精选

### 接口测试 · 超时与重试

**Q：接口的「超时 + 重试」策略怎么测？重试风暴怎么验证？**

先拆成两件独立的事：超时看「谁先超时」，重试看「重试叠加后的流量」，单看都没问题，叠起来才会出事。

1. **超时链路由内向外逐层放宽**：把客户端 / 网关 / 服务 / 下游的超时值列成表，检查是否单调放宽。若外层比内层短（客户端 3s 而服务 10s），客户端早已放弃而服务仍在执行 —— 用户看到失败但后端实际成功，这是「假失败」，重试一来就变成重复操作。差值太小（外层仅多 100ms）在抖动下同样会让外层先死。
2. **重试必须四件套**：确认幂等前提（天然幂等或带幂等键）、限制最大次数、指数退避 + 随机抖动、约束重试总时长。最危险的组合是「同步重试 3 次且无退避」，多层重试的放大倍数呈乘法关系（3 层各 3 次即 27 倍），一抖动就把连接池占满。
3. **量化放大系数**：统计「实际请求数 ÷ 业务请求数」。用故障注入工具把下游 RT 从 100ms 拉到 2s，看是否出现阶梯式放大；再持续注入错误，观察熔断阈值是否生效、是否出现雪崩。

配套细节：连接超时与读超时要分开设置；超时错误码必须与业务失败错误码区分，否则重试策略无法按类型生效。

### 测试理论 · 测试策略随产品生命周期变化

**Q：产品从 0 到 1 和成熟期，测试策略应该有什么不同？**

判断依据一句话：**风险在哪，策略就在哪**。0 到 1 的风险在「做错方向」，成熟期的风险在「改坏存量」。

- **0 到 1 阶段**：核心链路优先于边界与异常；刻意压低保用例数量，把精力放在探索式测试与灰度验证；先把监控告警补上（可观测性没建起来，灰度等于盲飞）。此阶段追求高覆盖率是典型的资源错配。
- **成熟期**：重点是变更影响面控制与回归效率 —— 回归集按风险分级、自动化覆盖率顶上来，并开始度量过程指标（逃逸缺陷率、线上故障数、缺陷收敛速度）。
- **高速增长期（最易被忽略的拐点）**：需求与并发同时上涨，必须提前建性能基线、提前做回归自动化，否则会陷入「人加得比需求慢」的泥潭。

### 安全测试 · 业务逻辑漏洞的三个组合维度

**Q：业务逻辑漏洞（薅羊毛、越权改价）怎么设计测试？**

这类漏洞不违反任何技术规范，扫描器几乎全盲，但价值最高 —— 直接对应资金损失。方法论是把业务当成状态机与参数集合来拆：

1. **状态维度**：画出业务状态机，找不可能的状态转移与跳过中间状态（已取消还能发货、已用券还能再用、退款成功还能再退）。支付场景额外测「部分支付 + 重复回调」。
2. **参数维度**：聚焦服务端不该信任的客户端字段 —— 价格、折扣率、金额、积分、用户 ID、角色标识。抓包把价格改成 0.01 重放，看服务端是否以自身计算结果为准；再测负值（数量为负等于反向刷钱）与精度（浮点舍入能否套利）。
3. **身份维度**：垂直越权与水平越权都要覆盖，且必须用不同角色的真实 token 交叉验证 —— 有些系统前端做了隐藏但后端没校验。

另两类高频形态：**并发竞态**（并发核销同一券、并发下单同一库存）与**流程绕过**（跳过风控、绕过实名或绑卡校验）。落地方式是把这三类整理成团队 Checklist，在需求评审阶段就问「有没有可被组合利用的路径」。

## 二、知识点精选

### 接口测试 · HTTP 缓存的三种作用域与四条用例

**作用域**：客户端本地缓存、CDN/网关共享缓存、服务端自身缓存（对 HTTP 头不敏感，需单独测失效策略）。

**两类机制**：强缓存（Cache-Control / Expires，命中不发请求）与协商缓存（ETag / Last-Modified，发条件请求，命中返回 **304 且无 body**）。

**四条必测用例**：不该缓存的敏感接口是否 private / no-store（否则 CDN 缓存 = 数据串号）；内容变更后 ETag 是否同步变化；max-age 刚过期是否回源；Vary 是否覆盖影响内容的维度（Accept-Language、Authorization 等，配错会中英文串页）。

**验证靠证据**：缓存是否生效要看「请求有没有打到源站」—— 响应头 Age / X-Cache（HIT/MISS）配合源站访问日志命中计数。只看到 200 不能作为证据。

### 性能测试 · GC 日志三看法

- **看频率**：Young GC 每秒多次 → 新生代过小或分配速率过高；Full GC 频繁 → 老年代不足、内存泄漏或元空间问题。
- **看停顿**：单次停顿直接决定尾延迟能否达标。若 P99 目标 200ms 而某次 Full GC 停了 1.5s，P99 偏高就是必然结果而非「偶发噪声」，必须调堆或换收集器。
- **看回收效果（最关键）**：健康的 Full GC 后老年代占用应显著下降；若前后几乎不变，基本可判定泄漏，需导 heap dump 分析支配树。

实践：压测时单独收集 GC 日志并可视化；必须做 8~24 小时稳定性测试观察老年代是否呈锯齿状缓慢抬升（短时压测发现不了泄漏）；把 Full GC 次数写入性能报告作为容量结论依据。

### 自动化测试 · 自动化债务的四个量化指标

- **Flaky 率** = 重跑才通过的用例 / 总用例。超过 5% 即说明用例集不可信。
- **失败归因分布** = 脚本问题 / 环境问题 / 真实缺陷的占比。脚本 + 环境超过七成，说明债务主要在自己这边。
- **单条用例修改频次**（近 30 天 git 改动次数）。高频改动往往指向定位不稳或断言过细。
- **执行时长集中度** = 最慢 10% 用例占总时长比例，定位少数吃时间的用例。

**优先级矩阵**：高频失效 × 高业务价值 → 优先改造（拆断言、换稳定定位、加数据自愈）；低频失效 × 高价值 → 先补齐失败留证让它可诊断；长期无人关注 × 低价值 → 直接退役。**删除低价值用例往往是收益最高的偿还方式**，很多团队不敢删，结果用例集越来越重。推进节奏上要设「每周偿还额度」，比一次性大重构更容易落地。

## 三、技能精选

### CI/CD · 制品晋级与构建指纹

**核心原则**：一次构建、多次晋级。流水线只打包一次，产出带版本号与 digest 的不可变制品，各环境拉同一 digest 仅注入配置。各环境分别打包时，依赖解析、基础镜像、时间戳都可能不同，两次构建在逻辑上不构成同一被测对象，「测试通过」不成立。

**构建指纹** = git commit + 制品 digest + 构建时间 + 依赖锁文件哈希。测试报告与上线单都带该指纹，上线前比对即可证明一致性，不依赖流程自觉。

**三项配套**：制品库禁止同版本覆盖（防悄悄换包）；配置不打进制品（否则又变成多份包）；回滚靠部署旧版本制品而非重新打包。

### 测试环境 · 第三方依赖隔离的四层策略

按推荐度排序：① 官方**沙箱地址**（改动最小，首选）；② **域名劫持到自建 mock**（按真实契约实现，可构造超时、失败、乱序回调等分支）；③ **代码开关**（最不推荐，必须限定非生产可开，并加启动期互斥校验：生产配置下开关为真则直接启动失败）；④ **捕获式 mock**（短信、邮件捕获后可断言「发给谁、内容是什么」，比只看接口返回强）。

**两个必测场景**：第三方**异步回调**（重试、重复投递、乱序送达）与依赖不可用时的**降级路径** —— 后者最常被忽略但价值最高。

### 数据库 · Linux 性能排障四件套

- **top / htop**：定位进程；重点看 load average 与核数比值，以及 %us / %sy / %wa 的构成。
- **vmstat 1**：看全局趋势；wa 高说明在等 IO，cs（上下文切换）异常高常见于锁竞争，r 队列长期大于核数说明 CPU 排队。
- **iostat -x 1**：%util 持续接近 100% 是设备饱和，await 从毫秒跳到几十毫秒说明开始拖后腿，aqu-sz 堆积说明处理不过来。
- **pidstat**：-u 看 CPU、-d 看 IO、-w 看上下文切换，把「哪个进程」精确到「哪个线程」。

判据先定好再排查：设备 %util 触顶 → 存储问题；cs 异常高 → 锁竞争；两者都不异常才回头怀疑应用逻辑。抓栈工具按语言分工（Java 用 jstack、Go/C 用 perf、Python 用 py-spy）；容器场景必须交叉看宿主视角与 cgroup throttling 计数。

## 四、坑点精选

### 性能测试 · 省掉疲劳测试，只跑十分钟就断言没有内存泄漏

**表现**：短时压测看到堆内存用完就回收，便认为内存管理正常。实际上泄漏的表现是「每次 Full GC 后老年代基线缓慢抬升」，需要数小时甚至数天才能显现。

**破解**：把 8~24 小时稳定性测试列为容量结论的必选项；重点看老年代占用、活跃连接数、文件句柄数三条曲线的长期趋势；一旦发现单调上升立即导 heap dump 定位，不要等到上线后靠定时重启续命。

### 数据库/环境 · 时间不同步导致签名失败，被误判成代码 bug

**表现**：容器与宿主机时钟偏移几十秒，带 timestamp 的签名校验被判「请求过期」，排查时一头扎进签名算法与代码逻辑，浪费大量时间还改错方向。

**破解**：环境构建统一配置 NTP，并把时钟偏移纳入环境巡检；用例显式构造时间偏移，断言服务端返回明确的「时间偏差」错误码而非含糊的 401（同时验证容忍窗口合理且超窗必拒）；容器显式设置 TZ，业务侧避免用本地时间做跨节点判断。

### 安全测试 · 文件上传只验后缀就认为过关

**表现**：传一个可执行脚本被拦下就判定防护有效，没有验证内容与类型是否一致、文件是否可直接访问、响应头是否可执行 —— 而 SVG 内联展示导致的存储型 XSS、上传目录可直读导致的脚本执行，都从这些缺口进来。

**破解**：覆盖四条路径 —— 后缀与 MIME 绕过（含双后缀、大小写、截断、少见可执行后缀，并确认后端独立校验）；内容与类型不一致（改名上传、SVG/EXIF 载荷）；存储与访问（应存对象存储或非 Web 目录，经签名下载接口访问，响应头强制 attachment 与 nosniff）；资源耗尽与路径穿越。验证要看实测证据，而不是代码里「调了一个校验函数」。
