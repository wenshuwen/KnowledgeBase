## 一、面试题精选（3 条）

**Q：接口功能测试全过、上线后却被业务方投诉数据不对，你会从哪查？**

这类问题九成不在接口本身，而在「接口正确但业务不正确」。按四层往下查：其一，参数语义层——字段名与类型都对，但我对语义的理解错了，比如某状态字段传 1 以为是启用、实际 1 是停用，或金额单位是分不是元。其二，组合与状态层——单接口全对，连续操作后状态错，典型是并发下单、重复提交、优惠券叠加，单条用例跑不出来，必须做时序组合加幂等测试。其三，数据流层——接口返回对，但落库、缓存与消息不一致，要直连数据库和缓存核对，确认写入真的成功、异步消费没丢消息。其四，上下游口径层——接口对，但下游或前端展示口径不同，比如金额精度、时区、分页排序。定位手法只有一条：拿业务方的原始数据，从入口一路追到落库和下游展示，把断点找出来，再回头补用例。

**Q：接口的权限测试你会怎么设计？只测「登录 / 未登录」够吗？**

远远不够，只测登录态漏掉的恰恰是最严重的那类问题——越权。按四个维度设计：认证维度（无 token、空 token、过期、签名被篡改、其他应用的 token，且要看错误码是否明确而非笼统 500）；垂直越权（用低权限账号直接调用高权限接口，必须被拦）；水平越权（最容易被漏也最严重——用 A 用户的合法 token 去访问 B 用户的资源，把请求里的用户标识、订单标识换成别人的）；批量与枚举维度（把 ID 换成顺序号遍历，看能否批量拿到他人数据，很多系统单条拦得住、批量就漏）。做法上最关键的是身份矩阵：准备多个不同权限与归属的账号，同一接口用每个身份各跑一遍，把「谁应该能、谁应该不能」写成矩阵逐格断言。只有把「不该成功的」也断言为失败，才算真的测了权限。

**Q：线上接口大面积报错，你作为测试怎么响应？**

测试的定位是：先帮确认范围，再做复现与验证，最后负责回归与类问题排查。第一，不单独行动，先对齐指挥，然后快速给出「用户视角的现象谱」——是所有接口还是某个接口、所有用户还是特定群体、有没有可用的降级路径；这类信息开发从日志里看不出来，但测试几分钟就能从外部摸清。第二，用外部视角帮忙定界：从不同网络、不同账号、不同客户端各打一遍，把「哪些通了、哪些没通」的矩阵交出去，常能一句话缩小范围。第三，止血优先，同时准备一个可复现的最小请求，让开发直接拿去验证。第四，恢复后立刻做完整验证：不是等开发说「好了」就结束，要按核心业务链路从入口到落库完整跑一遍，并确认数据有没有被写坏（重复扣款、重复发货、状态错乱）。第五，复盘时交付两样东西——一套能覆盖这次故障的回归用例，以及这类故障的预防性检查项。

## 二、核心知识点（3 条）

**1. 接口断言的四层模型**

| 层次 | 断言对象 | 能抓到的缺陷 | 常见做法 |
|---|---|---|---|
| 通信层 | HTTP 状态码、连接、超时 | 服务不可用 | 只证明「服务活着」 |
| 协议层 | 字段齐全、类型、必填 | 字段改名、结构变更 | JSON Schema / OpenAPI 校验 |
| 业务层 | 关键字段实际值、状态流转 | 算错、状态未推进 | 前置快照 → 调用 → 后置快照比对 |
| 副作用层 | 落库、缓存、消息、日志 | 数据不一致、消息丢重 | 直连库与缓存核对、Mock 记调用次数 |

关键认知：只断言通信层的用例是自动化里的假绿——它永远会通过，也永远发现不了问题。工程上把「调用前查快照 → 调用 → 调用后查快照 → 比对差值」固化成断言模板，是提升有效覆盖率最省力的做法。

**2. 「写入后查不到」的五类原因与判定顺序**

按排查成本从低到高排列。其一，查得太快，接口返回时事务还没提交完，加一次重试或短暂轮询即可判定。其二，读写分离的主从延迟，写主库读从库，直连主库查一次即可区分。其三，事务被回滚，接口内部后续步骤失败导致前序写入回滚而接口仍返回成功——这是真缺陷，要查事务边界与异常处理。其四，查错了地方，分库分表路由到别的分片、写进影子表、被软删除标记或状态与时间条件筛掉，改用唯一业务标识直查、不加任何过滤条件即可排除。其五，缓存遮蔽，数据库写成功而读走缓存拿到旧值，绕过缓存直查库即可确认。工程建议：断言「写入生效」优先用唯一标识直查，不要用列表类接口——分页、排序、状态过滤与缓存都会成为干扰项。

**3. 不确定输出的断言方式：从「值相等」到「约束满足」**

大模型接口输出天然不确定，用期望值相等的断言必然失败，可行的替代是把断言从具体值上移到约束。格式约束：可解析（JSON 能被反序列化）、字段齐全、类型正确、长度在范围内，这一层可完全自动化并能抓到大量低级问题。内容要素约束：必须包含某些关键信息、不能包含某些内容（违禁词、未在上下文中出现的编造信息、他人数据），这是防幻觉的主力。引用一致性：事实性内容必须能在检索片段里找到出处，可通过要求输出引用标记或对关键实体做回溯来实现。统计式判定：同一输入跑 N 次看通过率与方差，结论应为「该场景下约束满足率 96%（20 次）」而不是「跑了一次是对的」。一句话原则：确定性系统断言「等于什么」，概率性系统断言「满足什么条件、以多大概率满足」。

## 三、高级测试技能（3 条）

**1. 接口契约驱动的用例矩阵设计**

以接口契约为唯一依据铺开用例矩阵：参数维度固定四类（合法、边界、非法、缺省），场景维度覆盖正向、异常、权限、并发与幂等，并让每一次契约变更都能被 diff 检出。关键动作有三个：先冻结契约再推导用例（把 OpenAPI 或字段定义作为唯一依据，而不是照着已有实现反推）；把错误码与错误信息当作契约的一部分断言；把契约入库，接口变更时用 diff 拦住破坏性变更（删除字段、改类型、改语义）。这样做的价值是用例集与实现解耦——代码重构不会让用例集体崩，而契约一旦被偷偷改动会立刻红灯。

**2. Agent 轨迹断言与容错测试**

Agent 的价值在过程，只看最终输出等于没测。断言要推进到轨迹层：调用序列（该调的调了没有、顺序对不对、有没有多调——多调常意味着重复扣款或重复发送这类真实损失）；关键参数（用正确的业务标识调正确的工具，调用成功不等于参数正确）；副作用核对（Agent 声称完成的动作，系统里是否真有记录）；调用次数（用 Mock 记录，验证重试有上限）。再配一层故障注入：让工具返回 500、超时、空结果，专项检测最危险的那条路径——工具失败了但 Agent 装作成功并编造结果。测编排时压低随机性（温度、种子、Mock 返回固定），评效果时才放开跑多次，两者的测试目标不同，不能混。

**3. CI/CD 质量门禁的分层与失败分类**

流水线门禁最常见的错误设计是每次提交触发全量回归，结果是开发等不起、失败越积越多、门禁最终被整体绕过。正确做法是分层加分级时效：提交级只跑改动影响范围内的核心冒烟并控制在几分钟内；合并后跑全量接口回归；夜间跑全量与性能基线；发布前跑端到端与安全扫描。两个必不可少的配套：一是失败分类，区分「本次变更引入的失败」与「历史遗留失败」，后者不阻塞发布但要有归属人与修复期限；二是范围裁剪，用代码变更反查受影响接口，只跑相关用例。衡量门禁是否有效，看的不是拦住了多少，而是开发愿不愿意看它。

## 四、面试坑点（3 条）

**1. 只断言接口返回状态码与业务码，把「不报错」当成「业务正确」**

接口返回正常、业务码为 0，用例就判通过。结果字段值算错、状态没流转、数据没落库，测试依然全绿，问题留到线上才暴露。破解：把断言分成四层并强制覆盖后三层——协议层校验字段结构与类型、业务层校验关键字段的实际值与状态流转、副作用层查数据库、缓存与消息。做法上别只看响应体，用「调用前查快照 → 调用 → 调用后查快照 → 比对差值」。用例评审时加一条硬规矩：断言里只出现状态码的用例一律打回。

**2. 权限测试只验证「未登录被拦截」，不验证「A 用户能否看到 B 用户的数据」**

用例覆盖了无 token、过期 token 被拒绝，就认为权限测过了，而真正的越权——水平越权——发生在「用户是合法登录状态，但访问了不属于自己的资源」。破解：补一个身份矩阵，多角色 × 同接口逐格断言，重点构造水平越权（把请求里的资源标识换成别人的值），再补批量枚举场景（ID 换成顺序号遍历）。只有把「不该成功的」也断言为失败，才算真的测了权限。

**3. 只断言 Agent 的最终输出，不看它的工具调用轨迹**

Agent 给出了看起来正确的答案就判通过，实际上它可能调了错误的工具、传了错误的参数，或者根本没调工具、直接编了一个答案。破解：把断言推进到轨迹层——调用序列、关键参数、副作用核对、调用次数四条都要断言；再配故障注入专项检测「工具失败但 Agent 装作成功」这条最危险的路径。没有轨迹就无法归因，也就无法测试。

- 契约驱动的用例矩阵 ↔ 接口版本演进与兼容性（契约作为「唯一依据」的两处落点）
- Agent 轨迹断言 ↔ Agent 三类失败（没做完 / 做错了 / 装作做完了）（失败分类与检测手段的对应）
- 质量门禁分层与失败分类 ↔ 自动化维护成本来自定位器与数据（门禁有效性与框架健康度的同一判据：开发愿不愿意用）

- 水平越权身份矩阵 ↔ 批量枚举越权（单点与规模化的同源缺陷）
- 线上故障外部现象谱 ↔ 灰度期新老双跑比对（「从外部对比发现差异」的两种场景）
- 恢复后的数据核对与异常数据处理 ↔ 缺陷分级中的可探测性维度（后果不可见时风险应上调）
