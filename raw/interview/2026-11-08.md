## 一、Agent 的工具结果必须归一化（agent）

### 1. 题：HTTP 200 不代表调用成功

**Q：Agent 调工具拿回 200，但响应体里业务码是失败。怎么防止它当作成功继续往下走？**

问题出在「只要 2xx 就算成功」这个判断上。分三层落：

| 层 | 做法 | 断言对象 |
|---|---|---|
| 归一化 | 把工具结果压成成功 / 业务失败 / 不确定三态，附原因 | 归一化后的状态与原因字段 |
| 动作 | 业务失败时应停下、换参重试或上报 | **下一步动作**，而非「它是否知道」 |
| 契约 | 工具返回结构固化成断言，字段改名即破坏性变更 | 响应 schema |

> 关键认知：**最容易漏的是动作层**。模型嘴上说「调用失败了」，手上还是拿空结果继续编排，日志里看不出任何异常。

补充判据：超时归「不确定」而不是「失败」，因为它意味着副作用未知，后续应先查询再决定是否重试。

### 2. 题：声明与事实脱钩

**Q：Agent 回「已为你创建工单」，后台其实没有这条记录。怎么测？**

这是 Agent 产品最危险的一类缺陷——对用户来说看起来完全成功，缺陷要等投诉才暴露。

三个动作，按有效性排序：

1. **断言落在副作用上**：每条写操作用例都配一条对账断言，调用后直接查目标系统，核对记录数、关键字段、有无重复；
2. **制造失败再听话术**：把创建接口改成返回 500，看它是说「创建失败」还是照样宣布成功。这一条几乎每次都能抓到问题；
3. **测部分成功**：创建成功但通知失败，断言报告的是「已创建、通知失败」，而不是笼统的成功或失败。

工程建议：**回复里带可核验凭据**（单据号、时间戳、影响行数）。有凭据，测试和用户都能自己核，比任何措辞约束都可靠。

### 3. 题：多步任务中断恢复后重做

**Q：任务跑到一半断网，恢复后前面几步又做了一遍，怎么根治？**

根因是**没有幂等键，也没有检查点**，恢复时不知道哪些步骤已落地，只能从头再来。

断言三件事：已完成步骤不重复执行、外部副作用次数与预期一致、最终状态正确。第二条最关键——很多实现「看起来没重做」，实际又发了一次消息或又扣了一次款。

还要单独测**断在写操作中间**（请求已发、响应未知）：正确行为是先查询确认，而不是直接重试。

修复三条：有副作用的步骤带业务幂等键；每步完成落检查点（步骤号、入参摘要、结果摘要）；恢复时从最近检查点续跑。**这三条必须在代码层，写在提示词里的「不要重复执行」不可靠。**

## 二、性能：CPU 低不等于没瓶颈（perf）

### 4. 题：三秒延迟与 40% 的 CPU

**Q：压测时 CPU 只有 40%，P99 已经三秒，凭什么说瓶颈不在应用本身？**

CPU 不高说明请求**没在算，而是在等**。等的对象无非三类：连接池、下游、锁。

把单请求耗时拆成四段——取连接、应用逻辑、SQL 执行、下游 HTTP，在链路追踪里取 P99 那条样本逐段看。若取连接占一半，CPU 当然低，因为线程都在排队。

判据表：

| 现象 | 指向 |
|---|---|
| 取连接耗时占比高 | 池上限不足或连接不归还 |
| SQL 执行耗时占比高而库 CPU 低 | 等锁或等 IO |
| 下游调用耗时占比高 | 串行依赖，考虑并行或降级 |
| 各段都短但总耗时长 | 排队在更外层（网关、线程池） |

确认方式只认一种：**把怀疑的那段单独放大**。池上限从 20 加到 50 再压一次，P99 掉下来才算证明。

### 5. 知识点：开放模型与闭环模型

固定并发（闭环）与固定到达率（开放）压出来的结论**不可互换**。闭环在系统变慢时压力会自动缩小，于是容易得出「还扛得住」；开放不管多慢都照发，排队会被放大。

选法只问一句：用户会不会因为慢就不来了？不会（定时任务、上游调用）就用开放模型。

### 6. 坑点：压测跑完不核对业务正确性

只盯吞吐和延迟，不验压测期间下的单有没有都落库、金额对不对。数据库被打爆写丢几百条，报告上仍写着指标达标。

对策：压测必须配**业务对账**——跑前记订单数与库存，跑后比对增量与总金额；链路里有异步消费的，等消费位点追平再核，别拿半截数据出结论。

## 三、连接池：一个报错，四种病因（db）

### 7. 知识点：池等待的四段拆分

「池超时」只是表象，背后有四种完全不同的原因：

| 病因 | 现象特征 | 修法 |
|---|---|---|
| 取连接排队 | 活跃连接数高、语句耗时低 | 加池或减少占用时间 |
| 慢 SQL 占池 | 活跃连接数高、语句耗时高 | 治 SQL，而非加池 |
| 事务未提交不归还 | 活跃连接长期占满、语句早已结束 | 查事务边界与异常分支 |
| 连接泄漏 | 连接数阶梯上升不回落 | 查归还路径，短压测看不出来 |

所以监控必须分段打点：取连接耗时、语句执行耗时、事务持有时长、池内空闲连接数。四个曲线在手，判断只需两眼。

一条硬约束：**池上限必须小于数据库连接上限并留余量**，否则调大池只是把排队从应用挪到数据库。

### 8. 题：池超时但库 CPU 只有两成

**Q：压测报连接池等待超时，数据库 CPU 才 20%，怎么定位？**

按上表的四条线索查，顺序建议：先看库内活跃会话在跑什么、跑多久（排除慢 SQL 与长事务），再看池上限与库上限的比例，再看连接数曲线是否回落（泄漏），最后才怀疑池容量。

反面做法是把上限从 50 改成 500——压测数字会好看，上线后打满数据库，连带拖垮同库的其他服务。

## 四、AI 评测：两个统计陷阱（ai）

### 9. 题：拒答率涨了，准确率没降

**Q：拒答率从 3% 涨到 11%，准确率没降，算回归吗？**

算，但不能用「准确率没降」来反驳自己。**拒答样本通常被排除在准确率分母之外**，拒答变多时准确率反而容易好看。

三步判：

1. **看拒答落在哪些题**——集中在某几个意图是有针对性退化，均匀打散更像提示词或温度变化导致的保守化；
2. **区分该拒与不该拒**——安全类拒答是好事，业务类拒答是坏事，混算总数会得出相反结论；
3. **把拒答题补进评测集**——这次能发现是因为抽了样本，下次未必。

对外统一口径用**有效回答率**（非拒答且正确 ÷ 全部），它同时惩罚答错和不答。

### 10. 知识点：4 分差距先问是不是噪声

非确定性系统里同版本跑两次差几分是常态。做法是先测噪声带：同版本连跑 5 次算标准差；再锁定评测集版本号。只有差异超出一到两个标准差、且评测集未变，才可以谈提升。

### 11. 坑点：回退只验证「有返回」

主模型超时切小模型，只验证了切过去，没验证输出下游能不能吃。故障恢复后解析全线报错，故障时间反而更长。

对策：回退后跑同一套 schema 校验（必填、类型、枚举），不通过就再降一级或走兜底文案；同时记录**实际服务模型**，否则事后无法归因是哪一档在答。

## 五、AI 工具链：投喂与批量的两个可核对项（aitools / sec）

### 12. 技能：上下文投喂的完整性

AI 生成用例漏字段，八成不是模型不认真，而是**投喂的文档被静默截断**——超出窗口的部分直接丢弃，而字段定义常在文档后半段。

三个可核对动作：

| 动作 | 判据 |
|---|---|
| 投前算体积 | 文档 token ÷ 模型窗口 > 1 即必然截断 |
| 抽尾部字段反查 | 从末尾抽 3 个字段名，生成结果里都不出现即判定没读到 |
| 生成后核覆盖 | 用脚本解析文档得到必填字段清单，逐条断言至少被一条用例覆盖 |

改法：按接口切块投喂（每块控制在数千 token），或先抽成「字段名 / 类型 / 必填 / 枚举」的小表再投。

### 13. 技能：请求走私的测法

同一段字节，入口按 Content-Length 切、后端按 Transfer-Encoding 切，两个身体就错位，多出来的部分被当成新请求。三个必要条件同时成立才可利用：解析规则不同、连接被复用、攻击者能控头部。

三个用例：**双头冲突**（两个头都带且长度不一致，应直接 400）、**重复长度头**（两个不同 Content-Length，应直接 400）、**分块边界夹带**（合法 chunked 尾部藏一段请求，断言不会绕过鉴权命中后台接口）。

判断标准只有一条：**能否用前一个请求的身份影响后一个请求**。修复只在入口做规范化有效，在后端做校验无效——后端看到的已经是切好的请求。

### 14. 坑点：把平均响应时间当验收标准

验收单上写「平均 RT < 200ms」，长尾却能到两秒八。平均值把长尾抹平，而用户流失几乎都由长尾决定。

一律报分位数：P50 看典型体验、P95 看多数人上限、P99 看最差那批。再补一条超时率，说明有多少请求根本没等到结果。
