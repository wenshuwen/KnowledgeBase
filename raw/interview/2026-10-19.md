## 一、AI Agent 测试

### 知识点：轨迹是 Agent 测试的最小观测单元

一次 Agent 运行至少要留五项，缺任何一项，失败都无法归因：

| 记录项 | 用途 |
|---|---|
| 每轮输入摘要 | 判断上下文是否丢失、约束是否还在 |
| 模型输出 | 判断决策意图与工具选择动机 |
| 工具名与参数 | 判断执行层是否越权、参数是否符合语义 |
| 工具返回 | 判断失败是「模型判断错」还是「上游返错」 |
| 耗时与 token | 判断收敛性、定位成本膨胀点 |

没有轨迹时，只能得到「结果不对」这一句话；有轨迹才能拆成「理解错 / 选错工具 / 参数错 / 上游返错 / 不会终止」五类。

**实践要点**

- 每次运行分配 trace id，同一 case 多次运行可横向对比分布。
- 只看最终输出的评测，会把「绕八圈蒙对」误判为稳定能力。
- 轨迹长度不是能力指标，过长本身就是收敛性问题。

### 技能：Agent 任务完成度的多维判定

不用「答得像不像」判断好坏，把完成度拆成三个可量化维度，各有独立判据：

| 维度 | 衡量内容 | 典型指标 |
|---|---|---|
| 结果 | 任务是否达成 | 关键实体齐全、格式可解析、数值在区间 |
| 过程 | 路径是否合理 | 工具选择正确率、轮次数、无效重试次数 |
| 成本 | 是否可持续 | 单任务 token、工具调用次数、端到端时延 |

关键设计：**任一维度跌破阈值即判不通过，不做加权平均**。加权会把「成本翻倍换 2 个点成功率」这种结构性恶化平均掉，最后得出「整体提升」的错误结论。

## 二、接口与工具调用

### 面试题：Agent 的工具调用该怎么测

**核心答案：分三层，加一组异常输入。**

| 层次 | 测什么 | 判定方式 |
|---|---|---|
| 协议层 | 工具名、参数结构、必填项、类型 | 用工具 schema 做契约校验，可全自动 |
| 语义层 | 参数值在业务上是否说得通 | 构造「格式合法但业务上不该出现」的值 |
| 副作用层 | 外部系统变了没有、变了几次 | 对账 + 幂等键校验 |

第四组是**异常输入**：工具超时、返回 500、返回空、返回脏数据。分别观察 Agent 是重试、降级，还是**把错误当成功继续往下走**——最后一种最危险，因为它会输出一本正经的错误结论，从用户视角完全看不出异常。

### 坑点：只测「应该做什么」，不测「不该做什么」

正常路径的用例总能写一大堆，越权、误删、乱发消息这类反向场景往往一条没有。而 Agent 的风险恰恰集中在反向。

**破解方法**：每条正向用例配一条反向用例——

- 不该调的工具是否被拒
- 不该传的字段是否被拦
- 不该说的话是否被护栏挡住

判据看**实际发生的工具调用**，不看它嘴上怎么答。

## 三、安全测试

### 面试题：提示注入怎么测

**按「载体」分类造用例，比按攻击手法分类更好维护，也更容易查漏。**

| 载体 | 典型场景 |
|---|---|
| 用户直接输入 | 明确要求忽略前置指令 |
| 工具返回内容 | 网页、检索结果、API 响应里夹带指令 |
| 上传文档 | 文档隐藏层、白字、注释里写指令 |
| 历史上下文 | 前面几轮埋下、延后触发 |

每类配三个目标：**越权调工具 / 泄露系统提示词 / 绕过内容策略**。四乘三构成十二格矩阵，每格至少一条用例，并随工具清单变更自动扩充。

**判据**：落在系统侧——工具调用日志、下游请求记录、返回体是否出现敏感字段。模型回一句「抱歉，我不能这么做」**不构成通过证据**，因为工具可能已经被调用、数据已经被读出，只是最后一步被拦。

## 四、性能测试

### 面试题：压测结果与线上表现差很远，问题在哪

**先确认压的是不是同一条链路。** 五个常见来源：

1. **压测机先到瓶颈**——CPU 打满、端口耗尽、带宽不够，压不上去却以为服务扛住了
2. **数据量差异**——压测库小，同一条 SQL 在线上大表上直接超时
3. **缓存状态不同**——压测是冷缓存或全热缓存，与线上稳态不一致
4. **依赖被 mock**——压测绕过了真实第三方耗时
5. **流量模型不同**——压测是均匀流量，线上是尖峰加长尾

排查顺序：**压测机自身指标 → 服务端 → 依赖**。经验上前两项占一大半，很多「服务扛不住」其实是压测端先跪了。

### 坑点：压测只压服务，不压压测机

压测机 CPU 打满时 TPS 上不去，看起来像服务到瓶颈。于是扩容服务、优化代码，折腾一圈才发现瓶颈在压测端，之前结论全部作废。

**破解方法**：全程监控压测机的 CPU、内存、网络、连接数、TIME_WAIT；分布式压测逐台看。判据：压测机 CPU 超过 80% 时，先怀疑压测能力而不是服务能力。

## 五、数据库

### 知识点：并发写入的四类典型问题

| 问题 | 成因 | 判据 |
|---|---|---|
| 丢失更新 | 都读旧值再写回，后写覆盖前写 | 最终值与预期不符 |
| 超卖 | 扣减非原子，读与写之间存在竞争窗口 | 实际扣减量大于库存 |
| 死锁 | 交叉更新多行，互相等锁 | 事务被回滚，出现死锁日志 |
| 唯一键冲突 | 并发插入同一业务键 | 出现重复键异常或重复数据 |

**统一判据看最终数据与影响行数，接口返回不可信。**

### 坑点：并发测试不开 barrier，实际跑成了串行

起了 20 个线程不等于并发。线程启动存在时间差，第一个请求可能已经写完，第二十个才开始读，冲突窗口根本没重叠——测试全绿，线上照样超卖。这种「假并发」比不测更危险，因为它提供了错误的安全感。

**破解方法**：用 `threading.Barrier` 或 `CountDownLatch` 让请求同时放行；在服务端日志里核对请求到达时间是否真的重叠。判据不是「跑了多少线程」，而是「时间窗口有没有交叠」。

## 六、AI 评测与 CI/CD

### 知识点：评测集的四类样本与一个 holdout

| 类型 | 作用 |
|---|---|
| 核心能力集 | 业务底线，必须全过 |
| 长尾集 | 历史 badcase，防回退 |
| 对抗集 | 边界、异常、诱导输入 |
| 回归集 | 防改坏其他场景 |

此外必须留一份**不公开的 holdout 集**做最终判定，防止评测集泄露进训练数据导致分数虚高。盲测分数显著低于常规评测，就是泄露的强信号。

### 坑点：评测集和训练数据混在一起，分数越跑越好看

模型等于提前看过答案，所有指标都是绿的，上线后用户一用就发现完全不是那么回事。这种自欺欺人最难发现。

**破解方法**：holdout 集不参与任何调优；定期用全新采样的线上样本做盲测；评测集更新与训练数据更新走两条独立流程。

### 技能：提示词变更的回归影响面分析

把 prompt 当代码管：**版本化 + 回归集 + 分层对比**。

| 步骤 | 动作 |
|---|---|
| 改前 | 标出该 prompt 服务的所有意图与调用方，列出受影响场景 |
| 改后 | 按意图分层统计通过率，不只看总体 |
| 对照 | 锁定高频真实输入作为锚点，禁止被优化掉 |
| 判定 | 新旧版本同批 A/B 对比，避免把模型漂移算到 prompt 头上 |

**最容易犯的错**：只看总体通过率。总数持平很可能是「修好了 A 类、弄坏了 B 类」，两个一平均正好看不出来。

### 技能：制品晋级与可追溯发布

核心一句：**一次构建、多次晋级**，绝不重新打包。

- 构建产出带版本号与 commit sha 的**不可变制品**
- 测试、预发、生产复用同一制品，仅配置不同
- 部署后**拉运行时版本与 sha 跟制品库比对**，不一致直接拦下

要防的三个坑：流水线某步偷偷重新 build；配置绕开制品管理直接改服务器；hotfix 手工替换产物导致制品与代码对不上。这一步校验很便宜，但能挡住最贵的一类事故。
