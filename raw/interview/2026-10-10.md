## 1. 面试题精选（3 条）

### Q1：测试环境总是和线上表现不一致，怎么系统性排查？

关键是把「不一致」拆成**可验证的四类具体差异**，而不是笼统地说「环境不一样」：

1. **拓扑差异**：机器规格、副本数、中间件版本、网络链路。测试环境一台机器、线上八台，并发行为完全不是一回事。
2. **配置差异**：超时时间、线程池大小、缓存开关、限流阈值、功能开关。这类参数在测试环境经常被调成「方便调试」的值——超时设成 60 秒而线上是 3 秒，那么线上必然出现的超时问题在测试环境**永远复现不了**。这是最隐蔽也最常见的一类。
3. **数据差异**：线上千万级、测试环境一万条，索引走不走、深分页慢不慢、慢查询出不出现，全都不同。
4. **依赖差异**：第三方被换成 mock，而 mock 往往比真实服务「善良」——不超时、不报错、不返回脏数据。

排查完输出一张差异对照表，逐项标注「会影响哪一类缺陷」，再决定哪些必须对齐、哪些可以用补测覆盖。

### Q2：多套环境（开发、测试、预发、生产）怎么规划隔离与数据流向？

先按用途给每套环境定清职责，再谈隔离：

- **开发环境**：开发自用，可随时重建、数据随便造，测试不在这套环境出结论。
- **测试环境**：功能回归与集成测试，配置与线上一致（除规模），数据可清理可重建。
- **预发环境**：与生产同构，用于发布前验收与性能基线，不接生产流量。
- **生产**：只做灰度验证与线上巡检。

数据流向坚持**单向**：生产脱敏数据可以向预发与测试同步，测试数据**绝不回写生产**。隔离维度守三件事：**凭据隔离**（各环境独立密钥与第三方账号）、**数据隔离**（独立库，不共用）、**流量隔离**（域名与网关分组区分，压测流量严禁打到预发或生产）。

常见事故都源于隔离没做严：测试配置误填生产地址、压测脚本指向线上库、调试时用生产账号发了真实短信。这类问题应在环境初始化时用配置校验兜住。

### Q3：线上出了故障，测试应该做什么？

按**止损 → 分析 → 补防线**三阶段，测试的角色不同：

1. **止损阶段**——测试第一件事是**提供信息，而不是找责任**：影响范围（多少用户、哪些功能、什么条件触发）、有无临时规避手段、最近有没有变更（发布、配置、数据、依赖方）。**多数故障的根因就在最近的变更里**，这个信息价值极高。
2. **分析阶段**——测试不可替代的价值是**复现与缩小范围**：通过固定变量把触发条件缩到最小，输出「什么条件下必现」；同时核验数据侧影响——有多少数据被写坏、能不能修、修完业务是否自洽。
3. **补防线阶段**——推动三件事落地：一条能复现该故障的**回归用例**、一个能提前发现的**监控告警**（这次为什么没告警）、一个**流程卡点**（为什么这个变更没被拦住）。

原则：**复盘的对象是防线，不是人**。只讨论「谁犯的错」的复盘，下次还会出同样的问题。

## 2. 知识点精选（3 条）

### K1：环境漂移的四类差异源

| 差异源 | 具体内容 | 主要影响的缺陷类型 |
|---|---|---|
| 拓扑 | 机器规格、副本数、中间件版本、网络链路 | 并发、容错、集群行为类 |
| 配置 | 超时、线程池、缓存开关、限流阈值、功能开关 | 超时、降级、限流类（最隐蔽） |
| 数据 | 规模与分布 | 索引命中、深分页、慢查询类 |
| 依赖 | 第三方被替换为 mock | 超时、错误码、脏数据类 |

查完输出对照表，逐项标注「影响哪类缺陷」，再定哪些必须对齐、哪些用补测覆盖。

### K2：慢查询定位的四个方向

看执行计划后按四个方向归因：**索引未命中**（字段做函数运算、隐式类型转换、前导通配匹配）、**索引选择错误**（统计信息过期）、**回表过多**（返回字段未被索引覆盖）、**深分页**（大偏移量写法在数据量小的时候毫秒级，上量之后是灾难）。

关键提醒：**测试环境数据量低时优化器可能直接选择全表扫描**，结论不可信。必须在接近线上规模的数据上复现，或用生产只读库跑一次 EXPLAIN 只取计划不执行。

### K3：Agent 可靠性的三个维度

- **结果可靠性**：同一任务重复 10～20 次的成功率与结果差异。跑一次通过不算通过。
- **过程可靠性**：成功率相同但路径可能完全不同——有的靠正确的工具调用链完成，有的靠反复试错撞对。后者在真实环境一抖就废，必须对调用轨迹做断言（工具选择、调用顺序、无效调用次数）。
- **故障表现**：工具超时、报错、空数据、格式非法时的行为。最危险的是**编造一个看起来成功的结果**，只有人工核对才会发现。

配套要求：外部工具全部换成可控桩；给 Agent 设成本与步数上限，超限即判失败——不设上限的 Agent 在故障时会失控烧钱。

## 3. 技能精选（3 条）

### S1：测试环境一致性与漂移治理

能系统性比对测试环境与线上的拓扑、配置、数据、依赖四类差异，输出差异对照表并推动关键项对齐，让测试结论可外推。**核心动作不是下结论，而是产出对照表。**

- 先查配置差异，超时与线程池这类「方便调试」的取值是最高频的隐形差异源。
- 数据规模差一个数量级，索引与慢查询的行为就完全不同。
- 常用工具：配置中心、容器编排、基础设施即代码工具、配置 diff 脚本。

### S2：CI 质量门禁与灰度验证设计

门禁按成本从低到高排：静态检查 → 单元测试与**增量**覆盖率 → 接口自动化回归 → 安全扫描 → 部署后冒烟。

- **增量覆盖率比全量覆盖率更难刷、更有约束力**；全量覆盖率可以用在低风险模块堆无关测试的方式抬高。
- 门禁挂了必须有人处理，给绕过加记录并统计绕过率；长期零拦截的规则要么收紧要么删掉——留着只会让人习惯性忽略。
- 灰度必须专门验证**新旧版本交叉读写同一份数据的一致性**，这是最容易被漏掉、风险最高的一项。

### S3：质量分歧的量化沟通

质量推动的难点不是技术判断，而是让别人认同这个判断重要。把争论从「是不是 bug」转到「这个行为的代价是什么」：

1. **先对齐事实**：确认复现条件一致，很多分歧源于环境或路径不同。
2. **再对齐标准**：开发按代码实现判断、测试按用户预期判断、产品按投诉风险判断，把问题拉回需求文档或行业惯例找共同判据。
3. **然后量化代价**：触发条件、概率、用户会遇到什么、有无规避方式。「订单超过 100 条时字段错位，影响全部多单用户」比「这个字段有 bug」有说服力得多。
4. **最后分级处理**：低风险可降级，但必须写入已知问题清单并附规避方案；涉及数据错误、安全与合规则坚持并升级。**所有结论落在书面上**，口头说过的「先不管」三个月后就是糊涂账。

## 4. 坑点精选（3 条）

### P1：把测试环境的超时和线程池调大，让用例能跑通

**现象**：为了把不稳定用例弄绿，把超时从 3 秒改成 60 秒、线程池调大几倍。用例确实不红了，但线上真实暴露的超时问题在测试环境被永久掩盖，测试结论完全失去外推价值。

**破解**：超时、重试次数、线程池这类参数必须与线上保持一致，并在配置中心里显式管理。确需放宽的场景，在用例上标注「宽松配置」并单列一份对照结果。

### P2：灰度阶段只重跑功能回归，不验证新旧版本的数据兼容性

**现象**：把老版本的回归用例在新版本上重跑一遍，全绿就宣布没问题。完全没验证新老版本同时读写同一份数据时会不会互相看不懂——字段含义变了、格式变了、枚举值改了，都会造成数据错乱。

**破解**：灰度验证清单里必须包含交叉兼容项——新版本写入的数据老版本能否正常读取、老版本写入的能否被新版正确处理；涉及存储结构变更时，还要验证回滚后旧代码读新数据的表现。

### P3：Agent 工具调用没有次数与成本上限，故障时无限重试

**现象**：工具调用失败后 Agent 会自己重试，没有次数上限也没有成本控制。一次外部服务抖动就让 Agent 连续重试几百次，既烧钱又把故障放大到对端，事后才发现账单异常。

**破解**：为每次任务设置工具调用总次数上限与成本上限，超限立即中断并明确报错；重试采用退避策略，并区分可重试与不可重试的错误类型。
