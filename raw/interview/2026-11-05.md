## 一、流水线为什么要按「关键路径」优化（devops）

### 1. 题：50 分钟压到 20 分钟的动作顺序

**Q：流水线跑一次 50 分钟，两周内怎么压到 20 分钟？**

顺序比努力重要，错误顺序是直接分片——分完往往发现固定成本翻倍，总时长没降。

| 步骤 | 动作 | 目的 |
|---|---|---|
| 1 | 逐 stage 量耗时并画串行依赖图 | 找出真正压在关键路径上的那 3~5 段 |
| 2 | 按层次拆流水线（提交级 / 合并级 / 发布级） | 把重活从每次提交里挪走 |
| 3 | 砍等待：预拉环境、依赖缓存、分层镜像 | 等待常占三成以上，且不动测试范围 |
| 4 | 只对最长的一段做分片 | 并行收益最高、固定成本最低 |

一个可核对的实例：50 分钟里有 18 分钟在串行等环境就绪，把环境预拉与依赖下载并行后落到 21 分钟。

> 关键认知：**「排队」和「准备」通常占三到五成，却几乎没人优化**。只盯「执行测试」那一段，可压缩空间很小。

### 2. 题：同一 commit 出了两份互相矛盾的结果

**Q：同一 SHA 触发两次构建，后完成的覆盖了先完成的报告，怎么根治？**

这是**触发幂等**没做，三个层面同时锁：

1. **触发键**用 commit SHA，不用分支名（分支会被复用，历史会被覆盖）；
2. **并发组**按 SHA 归并，新构建自动取消同组旧构建；
3. **产物路径**带构建号或 SHA，禁止写固定路径。

结果归属上的一条硬规则：**同一 SHA 只允许一个「有效结果」，其余标 superseded 保留可查，而不是删除**。删掉之后质量数据出现双份矛盾，门禁读哪条全看运气。

### 3. 题：分片后总时长反而变长

**Q：分成十片为什么比不分还慢？**

三个成因，按命中率排序：

| 成因 | 现象 | 判据 |
|---|---|---|
| 分片不均 | 九片跑完等一片 | 最长片与最短片耗时比超过 1.5 倍即失衡 |
| 固定成本摊不平 | 片越多，环境准备付得越多 | 单用例 200ms 而准备 40s 时，分片几乎无收益 |
| 共享资源互抢 | 越多并行越慢 | 测试库锁等待、连接池打满 |

经验拐点：40 分钟的套件分 6 片到 9 分钟，再往上反而回到 11 分钟。**分片数有拐点，先测 4/6/8/12 四个点再定。**

## 二、异步链路的断言怎么写才算验了（api）

### 4. 题：回调接口「没东西可断」

**Q：下单返回「受理成功」，结果靠回调返回，怎么断言？**

结果不在响应里，要**换观察点**：先建接收端（可控 mock 或测试专用消费端）把回调落库，再驱动业务，最后按业务单号做**带超时的轮询**（如 30 秒）。

四个断言维度，少一个就有一类线上事故测不出来：

| 维度 | 缺了会漏掉什么 |
|---|---|
| 到没到 | 消息丢失、链路中断 |
| 到了几次 | 重复投递导致重复入账（资损） |
| 内容对不对 | 字段错、金额错 |
| 顺序对不对 | 旧消息覆盖新状态（状态回退） |

> 反模式：`sleep 5` 之后查一次。既有随机失败，又掩盖了「超过 5 秒才到」的性能问题。

### 5. 题：至少一次投递下的幂等断言

**Q：同一条消息投两次就重复扣款，说明缺什么？**

前提先摆正：**至少一次投递是默认语义，重复是正常的，不是异常**。所以断言不是「别重复」，而是「重复了也不出错」：

- 同一条消息投两次 → 业务只产生一条记录、一次扣款；
- 后到的旧消息（低版本号）被丢弃，不回退状态；
- 乱序到达时，要么等待、要么拒绝重试，不能把状态改错。

测试手法：在队列前挂一个可控代理，按 case 注入重复与乱序，比改代码造数据可靠。

## 三、知识点：三条可直接复用的判据（devops / api / theory）

### 6. 触发幂等的三个维度

触发键（SHA）→ 并发组（按 SHA 归并、新取消旧）→ 产物路径（带构建号）。三者任一缺失都会产生「同一份代码、多个结论」。

### 7. 异步契约的三个必测点

**到达**（时限写进用例，超时即失败）、**次数**（幂等键加唯一约束兜住）、**顺序与版本**（旧消息被丢弃）。只验「收到」的用例，等于把失败路径全留给线上。

### 8. 测试预言的五类来源

断言凭什么判对错，强度递增：

1. 人工判断（最弱，不可回归）
2. 需求规格
3. 历史行为（回归基线）
4. 参考实现（旧版本或另一套算法对算）
5. **不变量**（总额等于明细之和、状态机禁用的迁移）

判据：**一条用例若说不出预言来自哪一类，它大概率只是「跑通了」**。变异测试是检验断言强度的硬手段——杀死率低于六成，覆盖率再高也不说明问题。

## 四、技能：三项值得长期练的（devops / env / agent）

### 9. 流水线关键路径与耗时预算

把流水线拆成四段：**排队、准备、执行、收尾**，逐段定预算（如提交级 8 分钟）。只有「超预算且处在关键路径上」的段才值得投人。配套动作：每段设硬超时、同分支新提交自动取消旧构建。

### 10. 依赖锁定与构建可复现

三层锁定，缺一层就不成立：

| 层 | 锁什么 | 常见漏法 |
|---|---|---|
| 依赖 | 全量锁（含间接依赖）+ 哈希 | 只锁直接依赖，间接依赖每次解析出不同版本 |
| 运行时 | 语言版本、glibc、libssl 随镜像一起锁 | 只锁包不锁基础镜像 |
| 验证 | 装完再 freeze 与锁文件 diff | 锁了但不校验，实际仍会漂移 |

> 漂移最大的危害不是出错，是**出错时无法归因**：今天红明天绿，没人说得清是哪次装包变的。

### 11. Agent 执行结果的证据核验

原则：**不采信自述，只验证外部事实**。「已完成」是一个文本声明，与是否执行没有强关联。

每类任务配可核对的事实：文件存在且内容 diff 符合预期、接口调用日志有本次请求 id、库里有对应记录、测试报告时间戳属于本次构建。要求 Agent 返回**证据指针**（路径 / 请求 id / 日志行号），拿不出指针的交付按未完成处理。

还要防一种更隐蔽的情况：**做了但做错了范围**——要求改 A，它顺手重构了 B 和 C，测试全绿但改动面扩大数倍。所以证据里必须包含改动范围。

## 五、坑点：三条反复踩的（devops / sec / agent）

### 12. 用重跑掩盖不稳定

构建红了点重跑，绿了就当过。这既训练团队忽略红灯，也把真实缺陷埋进概率。

**破解**：重跑记录次数与原因；同一用例 7 天内重跑 3 次自动进隔离区并建单；把 flaky 率做成看板上的数字。**重跑到绿，等于用运气替代判定。**

### 13. 脱敏只处理主表字段

结构化字段脱了，备注、工单描述、聊天记录、导出附件里的手机号与证件号原样保留。更隐蔽的是**只做无盐散列**——手机号空间只有 11 位数字，彩虹表几分钟可反查，「看起来脱了其实没脱」。

**破解**：字段级敏感分类清单 + 正则全扫（含对象存储与备份）+ 每次回灌后自动扫描、命中即阻断环境开放。

### 14. 把模型自述当执行证据

Agent 说「已完成并测试通过」，实际文件没写、测试没跑。采信自述是 Agent 类工具最典型的过度信任。

**破解**：一律要求证据指针，拿到外部系统核对；核对不到就判未完成。高危操作（转账、删除、发信）另加二次确认兜底。
