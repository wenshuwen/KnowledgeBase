## 一、安全测试（sec）

### 题 1：越权测试怎么设计？最常见的漏点在哪？

**Q：** 越权测试你怎么设计？最常见的漏点在哪？

**A：** 越权是业务系统里**最高发、最高危、也最容易被漏测**的一类漏洞——它属于权限模型与业务语义问题，扫描器基本无能为力，只能靠人设计。

**两类先分清：**
- **水平越权（横向）**：同级别用户之间，A 能操作 B 的数据。
- **垂直越权（纵向）**：低权限用户执行高权限操作。

**核心手法一句话：「拿自己的合法身份，去操作不属于自己的资源」——只改标识、不改身份。**

**四步设计：**

1. **先建权限矩阵**：行 = 角色（游客/普通用户/商家/客服/管理员/超管），列 = 所有接口与资源操作。
   - **默认填「拒绝」，只有明确标注允许的格子才算允许**——避免「没写就等于放开」。
   - 矩阵里每个「未明确标注允许」的格子都是待验证的越权点，测试范围从「凭感觉」变成「有清单」。

2. **水平越权必测的五类入口（只测「查详情」远远不够）：**
   | 入口类型 | 为什么是漏点 | 测试手法 |
   |---|---|---|
   | 写操作（改、删） | 危害最大 | 优先级最高，先测 |
   | 批量接口 | 入参是数组/逗号分隔 ID，往往只校验第一个 | 传 `[自己的ID, 别人的ID]`，看是否两条都成功 |
   | 导出接口 | 直接按查询条件出数据，绕过列表页权限过滤 | 最经典的重灾区 |
   | 旁路入口 | 分享链接、附件下载 URL、消息跳转、图片直链、打印页、二维码 | **经常压根不做鉴权，只靠「URL 猜不到」当安全** |
   | 二次入口 | 列表页过滤了、详情页没过滤；详情页过滤了、编辑页没过滤 | 顺着资源 ID 遍历所有能访问它的接口 |

3. **垂直越权用「降级重放」**：用管理员抓到的请求**换成普通用户 token 重放**，预期 403。
   - 典型假防护：**前端隐藏了菜单但后端接口没关**。
   - 绕过维度：HTTP 方法切换（GET 被拦但 DELETE 没拦）、URI 大小写/双斜杠/路径变形、`X-Forwarded-For` 与 `X-Original-URL` 之类头部试探。

4. **参数污染与 ID 遍历**：同参数传两次（`id=1&id=2`）、传数组、加空格与编码变形。
   - 成因：**校验逻辑只作用于第一个参数，而业务逻辑取了最后一个值**（解析不一致）。
   - 同时做小范围 ID 遍历（连续扫 100 个），判断是偶发还是批量泄露。

**工具：** Burp Suite（Repeater 手工验证、Intruder 批量遍历）；**Autorize 插件可自动重放全部请求并替换为低权限身份，越权测试效率提升一个量级。**

**根因层面的整改建议（写进报告）：** 越权反复出现几乎都是因为**「鉴权写在控制层、数据归属校验写在业务层，两层没对齐」**。正确做法是**所有带资源 ID 的接口在数据访问层强制附加「当前用户 ID」条件（行级权限）**，而不是依赖业务代码记得判断。

### 题 2：限流与防刷怎么测？只测「超过阈值返回 429」够不够？

**Q：** 限流与防刷怎么测？只测「超过阈值返回 429」够不够？

**A：** 不够，这是典型的「测了表面、没测机制」。**核心不是验证它能不能拦，而是验证「拦得准不准、兜得住兜不住、以及被绕过时损失有多大」。**

**五个层次：**

1. **阈值准确性**：打到第 100 次、101 次看是否被拦。要测三件事：
   - **计数窗口边界**（固定窗口会在切换瞬间放过 2 倍请求，滑动窗口不会——重要验证点）
   - **计数维度**（按用户 / 按 IP / 按接口 / 按用户+接口组合，四者都要验）
   - **限流粒度优先级**（单接口限流与全局限流同时命中时哪条先生效）

2. **绕过尝试（最有安全价值）**——攻击者一定不会老老实实从一个 IP 一个账号发请求：
   - 换 IP：只按 IP 限流 + 代理池即可绕过 → 高危发现
   - 换用户标识 / 不带登录态（**未登录路径的限流最常被漏**）
   - 伪造 `X-Forwarded-For` / `X-Real-IP` / `User-Agent`：**系统若信任客户端传的 X-Forwarded-For，攻击者可随便伪造 IP 绕过——非常经典的高危缺陷，必测**
   - **换入口**：同一业务能力有 H5 / APP / 小程序 / 开放接口 / 内部接口多个入口，往往只在主入口做了限流

3. **降级与体验**：正确返回 **429 + Retry-After 头 + 明确文案**，不是 500 或静默失败。
   - 必须验：**正常用户会不会被误伤**——按 IP 限流时，同一出口 IP 下的公司/学校用户会互相拖累，这是上线后投诉的主要来源。

4. **高并发下的准确性（真正难点）**：用 200 并发同时打，实际通过数是否接近阈值？
   - 若远超阈值 → 计数器有竞态（如 Redis get-then-set 非原子）——**隐蔽但很常见**。
   - 还要验**限流器自己不能成为瓶颈或单点**，它挂了应降级为放行而非阻断。

5. **防刷的业务侧兜底（必测）**：
   - **短信/验证码接口**（被刷直接资损）：有效期、一次性使用、同号/同 IP 频率、图形验证码触发策略
   - **登录接口**：失败次数锁定、锁定后能否通过改大小写或加空格绕过、**锁定机制本身能否被用来恶意锁定他人账号（拒绝服务）**
   - **下单/领券**：并发下超卖或超领（并发+限流交叉场景，必须单独测）
   - **接口枚举**：遍历 ID 能否批量获取数据，有没有返回总量提示

**工具：** JMeter / k6 / Locust 做精确计数与并发验证（**k6 的 constant-arrival-rate 执行器最适合「严格每秒 N 次」的限流测试**）；Burp Intruder 做绕过试探。

**验收标准：「拦住攻击者的同时不误伤正常用户，并且在被绕过时有第二道防线」。**

### 知识点 1：OWASP Top 10（2021 版）速查与测试动作映射

**价值不在清单本身，而在于它是「共同语言」**——让风险等级与整改优先级有公认依据，避免测试与开发在严重性上扯皮。

| 编号 | 风险 | 典型表现 | 测试动作 |
|---|---|---|---|
| A01 | **失效的访问控制**（长期第一） | 越权（水平/垂直）、未授权访问、目录遍历、CORS 过宽 | **换身份重放、替换资源 ID、批量接口夹带他人 ID、遍历旁路入口（导出/分享/附件直链）**；扫描器测不出，必须手工设计 |
| A02 | 加密机制失效 | 明文/弱哈希存密码、HTTP 可用、弱 TLS | 查库看密码字段形态、`curl -I http://` 验强制跳转、testssl.sh 扫协议套件、检查 Cache-Control |
| A03 | 注入 | SQL / NoSQL / 命令 / LDAP 注入、XSS | 单引号+布尔差异初判、时间盲注验证无回显、**重点测动态排序字段与原生 SQL**、报错是否外泄 |
| A04 | 不安全设计 | 业务逻辑缺陷、缺频率限制、状态机可跳过 | **只有懂业务的人能测——这是测试工程师相对扫描器的最大优势领域** |
| A05 | 安全配置错误 | 默认口令、错误页暴露堆栈、目录列表、云存储桶公开、Debug 上线 | 探默认路径与账号、构造异常看错误页、检查对象存储匿名访问 |
| A06 | 脆弱与过时的组件 | 依赖库已知 CVE | Trivy / Dependency-Check / Snyk，**并纳入 CI 门禁** |
| A07 | 身份识别与认证失败 | 弱口令、无失败锁定、会话固定、Token 不过期、验证码可复用 | 暴力破解测试、会话劫持与固定测试、Token 失效与续期、**用户枚举（登录错误提示是否区分账号存在）** |
| A08 | 软件与数据完整性失效 | 不校验签名与来源、不安全反序列化、制品被篡改 | 篡改制品与更新包看是否被拒、测反序列化接口 |
| A09 | 安全日志与监控失效 | 关键操作无审计、日志可篡改、告警不生效 | **执行敏感操作后断言审计日志含操作人/时间/对象/结果；故意触发异常断言告警真的到人** |
| A10 | SSRF | 服务端按用户输入去请求 URL（图片抓取、Webhook、文件导入） | **把 URL 换成内网地址（127.0.0.1、云元数据地址）、内网域名、DNS 重绑定绕过校验** |

**使用建议：** 做成评审 checklist，每个新需求上线前过一遍相关条目；报告里用 A01~A10 编号标注缺陷，便于统计与跟踪趋势。**但别当穷举清单——它覆盖「常见」而非「全部」，业务逻辑漏洞永远是最大盲区。**

### 知识点 2：安全测试的分层策略：SAST / DAST / IAST / SCA 各管什么

很多团队做安全测试就是「发布前跑一次扫描」，效果很差——**不同层次能发现的问题类型完全不同，正确做法是按阶段组合使用。**

| 手段 | 原理 | 擅长发现 | 优点 | 缺点 / 工具 |
|---|---|---|---|---|
| **SAST** 静态 | 不运行代码，分析源码找危险模式 | 硬编码密钥、字符串拼接 SQL、命令注入、不安全反序列化、日志打印敏感字段、弱加密算法 | **能在提交阶段发现，修复成本最低**，可做 pre-commit / CI 门禁 | 误报率高需人工过滤；看不到运行时与配置问题；动态语言分析深度有限。Semgrep、SonarQube、CodeQL、Bandit |
| **DAST** 动态 | 像攻击者一样从外部发请求观察响应 | 注入、XSS、SSRF、目录遍历、错误配置、认证缺陷、部分越权 | **不依赖源码，能发现真实可利用的漏洞** | 覆盖依赖爬虫质量（**认证后的深层页面常爬不到**）、**测不出业务逻辑漏洞**、可能污染数据（**绝不能在数据敏感环境盲目跑主动扫描**）。OWASP ZAP、Burp、Nuclei |
| **IAST** 交互式 | 运行时插桩，边跑测试边观测数据流 | 定位精确（给出到代码行的调用链）、误报极低 | **误报率显著低于 SAST/DAST，最适合集成进自动化测试**——跑一遍接口自动化顺带完成扫描 | 需部署 Agent（生产通常不允许）、影响性能、语言支持有限、依赖已有自动化覆盖。Contrast、Seeker、洞态 IAST |
| **SCA** 成分分析 | 识别依赖库版本，比对漏洞库 | **已披露的组件漏洞**（Log4Shell、Fastjson 这类） | **性价比极高且必须自动化**——现代应用 90% 代码来自三方库，手工管不过来 | Trivy、Dependency-Check、Snyk、Grype |

**我的组合策略：**

- **提交阶段**：SAST（只跑增量 + 高危规则）+ 密钥扫描（gitleaks）
- **CI 阶段**：SCA 依赖扫描（阻断高危）+ 单元测试内联 IAST
- **测试环境部署后**：DAST 被动扫描（随功能回归一起跑，不额外加压）+ 认证态的主动扫描
- **版本发布前**：**手工安全测试，聚焦业务逻辑漏洞**（越权、并发、支付绕过、状态机、限流绕过）

**一句话：工具负责覆盖面与效率，人负责业务逻辑与攻击链组合。用工具打底、用人工补深，才是完整策略。**

### 技能 1：安全测试设计

**能力描述：** 能把「做一次安全测试」这类模糊需求，拆成有范围、有标准、有分级、有交付物的可执行方案。核心能力不在工具使用，而在业务逻辑漏洞的手工设计（越权、并发、支付绕过、状态机跳过、限流绕过）。

**常用工具：** Burp Suite（含 Autorize 越权自动化）、OWASP ZAP、Nuclei、Semgrep、Trivy / Dependency-Check、testssl.sh

**关键要点：**
- 先定范围与分级标准（**引用 OWASP Top 10 建立共同语言**），再动手测
- **越权是最高发最高危项**：换身份重放 + 替换资源 ID + 遍历旁路入口（导出/分享/附件直链）
- 错误信息泄露（堆栈、SQL、内网信息）、用户枚举、硬编码密钥都是高危必测项
- 任何安全测试都要有**残留风险声明**：说明哪些没测、风险多大

## 二、Agent 测试（agent）

### 题 3：Agent 调用外部工具出错、或被诱导调用了危险工具，怎么测？

**Q：** Agent 调用外部工具出错，或者被诱导调用了危险工具，你怎么测？怎么保证不会造成不可逆后果？

**A：** 这是 Agent 测试里我最看重的一块，因为**传统软件的 bug 最多是「功能不对」，Agent 的 bug 可能是「真的把钱付了、把数据删了、把邮件发出去了」——不可逆。** 原则是：**先在隔离环境建立「副作用可断言」的能力，再谈功能正确性。** 顺序反了就会天天在生产事故里学测试。

**第一步（前置条件）：把副作用变成可观测、可回滚的**
- **所有外部工具在测试环境一律走 Mock / 沙箱**：支付走沙箱、短信走测试通道、邮件进本地邮件池（MailHog / Mailpit）、文件操作走临时目录、外网请求走本地代理。
- **Mock 层要记录三样：被调用次数、调用参数、调用时序**——这三样是 Agent 断言的核心数据源。
- **在测试环境设置蜜罐标记**：只有越权操作才会访问到的 URL、只有危险写操作才会改到的标记位。**用副作用做断言比看输出文本可靠一个数量级。**

**第二步：工具故障的注入矩阵（六类，每类都要验证 Agent 行为）**

1. **超时/无响应**：等待、重试还是放弃？重试有次数上限与退避吗？
2. **报错（业务错误码）**：能否正确理解含义（「余额不足」应停止而非重试）？会不会把错误码当成功？
3. **返回脏数据**：空值、类型不对、超长、乱码、**含 prompt injection 的文本**——重点验证会不会照着脏数据里的指令去行动（间接注入）。
4. **返回部分成功**：批量操作一部分成功一部分失败，**最容易出现「报告全部成功但其实一半失败」的谎报**。
5. **工具被篡改/降级**：模拟返回错误业务数据（如查询订单返回了别人的订单），验证是否有合理性检查。
6. **长时间无进展**：连续多步不推进时能否识别并终止。**死循环与无限重试会烧掉大量 Token，也是隐性成本事故。**

**第三步：危险动作的三道防线**

| 防线 | 做法 | 必测的绕过路径 |
|---|---|---|
| **一：权限最小化** | 工具调用身份必须是当前用户，**不得使用高权限服务账号** | 让 A 用户的会话触发工具读写 B 用户数据，断言**由系统拒绝，而不是靠模型「懂事」拒绝** |
| **二：高危动作确认** | 支付、退款、删除、外发消息、改权限、执行代码由**系统层强制**二次确认 | ① 用户说「不用确认直接执行」② 模型自称「用户已确认」③ 多步任务中插入危险步骤④ 用编码/间接表述伪装成无害操作 |
| **三：白名单与限额** | 工具目标受白名单约束 | 验证能否拦 SSRF；单会话调用次数/金额/数据量上限是否生效（**防提示注入诱导出「导出全部用户数据」**） |

**正确实现应该是「确认动作由系统层强制执行，不依赖模型判断」。**

**第四步：可逆性演练**
- **幂等验证**：重复发同一指令、或工具调用成功后 Agent 重试，断言**不会执行两次**（重复下单、重复退款是过去最典型的事故形态）。
- **回滚/补偿验证**：多步任务执行到一半失败，已执行的前几步能否回滚？**不能回滚的步骤必须在设计上要求前置确认或改为可逆操作。**
- **事故演练**：故意执行一个「错误但有代表性」的危险动作，走一遍发现→定位→止损→恢复，验证 trace 是否足以定位、止损开关是否可用。

**工具：** Mock 工具层（自研，含调用记录与故障注入）、WireMock / MockServer、MailHog / Mailpit、ChaosBlade / Toxiproxy、LangSmith / Langfuse（trace 断言）、Vault（确保测试环境没有真实凭据）。

**排优先级的底线：功能测试可以容忍「做得不对」，安全测试不能容忍「做了不该做的」。所以一定是「防住坏事」优先于「做成好事」。**

### 知识点 3：Agent 测试的核心——断言「过程与副作用」而非「最终文本」

**Agent 与普通 AI 功能的根本区别是它有过程（多步推理）和副作用（工具调用）。** 最终答案对了但中间调了不该调的工具、或者重复执行了三次——**只看输出的测试会完全漏掉。**

**断言的三根支柱：**

1. **工具调用序列**：调了哪些工具、顺序、次数、参数。需从 trace（LangSmith / Langfuse）或 Mock 工具层的调用记录里取。
2. **最终状态**：数据库/外部系统里的真实业务状态是否正确。
3. **副作用（含「无副作用」）**：有没有发消息、写库、访问外网。**「不该做的时候没做」必须显式断言**——典型缺陷：用户只问「这个订单能退吗」，Agent 直接执行了退款。

**五个测试层次：**

| 层次 | 内容 | 关键点 |
|---|---|---|
| ① 单步能力 | 意图理解、工具选择、参数构造、结果解析、是否追问 | **自然语言到结构化参数，时间与时区最容易错**；**缺参数时瞎猜是高危** |
| ② 工具调用正确性与安全性 | 不该调时不调、无重复、无死循环、依赖顺序、权限绑定当前用户、高危动作确认 | **Agent 用高权限服务账号是重大缺陷** |
| ③ 多步推理与终止性 | 任务完成度、无解/矛盾任务、步数与预算上限、中间失败恢复 | **无解任务能否明确说做不到（而不是无限重试或编造）——最易漏测的失败模式** |
| ④ 输入鲁棒性与对抗 | 工具返回脏数据（含注入内容）、超长/多意图输入、长会话记忆、**重复指令幂等** | **幂等是 Agent 造成资损的主要方式** |
| ⑤ 可观测性与成本 | trace 完整性、多步任务 Token 与延迟分布、超限保护 | **没有 trace 的 Agent 不可测也不可运维，应作为准入要求** |

**基础设施（与普通 AI 测试最大的工程差异）：Mock 工具层**——把工具替换成可断言、可注入故障（超时/报错/脏数据/部分成功）、可记录调用次数与参数的模拟实现。**这是让「断言工具调用序列」成为可能的前提。**

**记忆口诀：** Agent 测试问的不是「答得对不对」，而是**「做了什么、做了几次、失败会不会停、有没有做不该做的」**。

## 三、数据库与 CI/CD（db / devops）

### 技能 2：数据库测试与变更把关

**能力描述：** 能验证复杂数据场景（分库分表跨片、事务一致性、索引效率）并参与数据库变更的风险把关。**核心产出是「影响行数 + 回滚方案 + 兼容性矩阵 + 数据对账结果」四件套。**

**常用工具：** ShardingSphere / MyCat（路由日志验证）、Flyway / Liquibase、gh-ost / pt-online-schema-change、binlog2sql / my2sql、Archery / Yearning、EXPLAIN + 慢查询日志

**关键要点：**
- **分片后「单库能跑通」没有信息量**，缺陷全在**跨片分页、跨片事务、全局唯一约束失效**三处
- **唯一索引在分片后不再全局有效**，必须专门测并发重复提交
- 任何数据订正前先估算影响行数并要求备份，**禁止无 where 的全表更新**
- **回滚方案必须在预发实际演练；代码能回滚不代表数据能回滚**

**数据库变更的把关四问：** 这次变更影响多少行？怎么回滚？新旧版本共存时会不会出问题？变了之后数据还对不对？——**四个问题都能给出明确答案才允许上线。**

---

### 技能 3：CI/CD 质量门禁设计

**能力描述：** 能设计分级、可执行、能防退化的流水线质量门禁：把测试活动按「反馈速度」分布到提交前、集成、发布、生产四个阶段，并为每道红线配置 owner、豁免机制与度量指标。

**常用工具：** Jenkins / GitLab CI / GitHub Actions、Docker + Harbor、ArgoCD / Flux、SonarQube、Trivy、Argo Rollouts / Flagger

**四级门禁（按阶段与严格度）：**

| 级别 | 时机与时长 | 跑什么 | 严格度 |
|---|---|---|---|
| **L1 提交级** | 秒级，本地 | 静态检查、格式、**密钥泄露扫描**、增量单测 | **绝对阻断**（修复成本几乎为零） |
| **L2 集成级** | 分钟级，CI | 全量单测 + 覆盖率门禁 + **接口冒烟集（100~200 条，5 分钟出结果）** + 契约测试 + **SCA 依赖扫描** | **核心用例失败绝对阻断** |
| **L3 发布级** | 十几分钟，CD 前置 | 完整接口回归 + 集成测试 + UI 端到端 + **性能基准对比（退化超阈值告警）** + DB 变更验证 + 回滚演练 | **允许有条件阻断** |
| **L4 生产级** | 持续 | 生产冒烟探针 + 核心 UI 用例定时回归（兼作可用性监控）+ 关键业务指标自动比对 | 偏离阈值触发自动回滚或告警 |

**防退化的三个机制（比设计本身更重要）：**

1. **分级，不一刀切**：致命项（编译失败、安全高危、核心用例失败）阻断；一般项（覆盖率小幅下降、非核心用例失败、代码异味）只告警。**「全阻断」的门禁活不过两周。**
2. **正式豁免机制**：允许临时豁免，但必须记录原因、期限、责任人，且自动到期失效。**禁止口头绕过——门禁最常见的死法就是被绕过一次后再也没人遵守。**
3. **每条红线有 owner 与时限**，门禁结果与提交作者关联。定期统计**门禁拦截率与误报率**：拦截率高说明有效，误报率高要优化规则而不是关掉。

**核心判断：流水线里的测试不是一个阶段，而是一组分布在不同触发点上的质量门禁。设计时优先考虑「反馈速度」——开发不会等 4 小时后的结果，他们只会在 5 分钟内用到的门禁面前停下脚步。**

## 四、面试坑点（pitfalls）

### 坑点 1：把安全测试等同于「跑一次扫描器」

**现象：** 上线前用 ZAP 或 AWVS 扫一遍，出一份满屏中低危的报告，然后当作业已完成。结果是真正的**越权、并发、支付绕过、验证码复用**这些高危逻辑漏洞一个都没被发现——而它们恰恰是最容易被真实攻击者利用的。

**破解方法：** 先定范围与分级标准（引用 OWASP Top 10 建立共同语言），再组合手段：**SAST 管代码反模式与密钥泄露、SCA 管组件 CVE、DAST 管技术层漏洞，而手工测试专攻业务逻辑。**

手工部分必做清单：
- **水平/垂直越权**（含批量接口夹带他人 ID、导出与分享等旁路入口）
- **并发下的超卖与重复提交**
- **状态机跳过**
- **支付金额与优惠券篡改**
- **限流绕过**（伪造 X-Forwarded-For、换入口、换匿名维度）
- **验证码与短信接口防刷**

最后必须有**残留风险声明**。

---

### 坑点 2：只测登录接口的「未登录返回 401」，就认为权限没问题

**现象：** 认证检查通过就下结论，忽略了两件更危险的事：**前端隐藏了菜单但后端接口没鉴权**（直接调接口就能越权），以及**已登录的低权限用户能调到高权限接口**。这类「假防护」上线后往往直接导致数据泄露。

**破解方法：** 权限测试必须做三件事：
1. **降级重放**：用管理员抓到的请求换成普通用户 token 重放，预期 403
2. **数据归属校验**：用 A 的 token 把资源 ID 换成 B 的，覆盖查/改/删/导出全部动作，并遍历所有能访问该资源的接口（列表、详情、编辑、打印、附件直链）
3. **参数污染与路径变形**：同参数传两次、传数组、URL 编码、大小写变形、加 `X-Original-URL` 头

**正确做法是要求「数据行级权限」在数据访问层强制生效，而不是依赖业务代码记得判断。**

---

### 坑点 3：对「危险操作」的防护依赖模型的判断力

**现象：** 指望模型「懂事」，靠系统提示词里写「不要执行危险操作」来防住越权和误操作。实际上一句提示注入、一个编码绕过、或者多轮对话里的渐进诱导就能让它照做。而这类操作的后果往往**不可逆**——真的付了款、真的删了数据、真的把用户信息发到了外部地址。

**破解方法：** 安全必须由**系统层强制**，而不是模型的自觉。三道防线：

1. **权限最小化**——Agent 工具调用必须绑定当前用户身份，绝不能使用高权限服务账号。**实测「A 用户的会话去读写 B 用户数据」应被系统拒绝（而不是靠模型拒绝）。**
2. **高危动作系统层强制二次确认**——涉及支付、退款、删除、外发消息、改权限、执行代码的，确认由系统强制执行；并要测绕过路径（用户说「不用确认」、模型自称「用户已确认」、多步任务中插入危险步骤、用编码伪装成无害操作）。
3. **白名单与限额**——工具目标受白名单约束（防 SSRF 与批量导出）、单会话调用次数/金额/数据量上限。

**另：所有工具在测试环境必须走 Mock 或沙箱**（支付沙箱、邮件本地池、外网本地代理），**绝不允许任何测试路径打到真实生产工具**。
