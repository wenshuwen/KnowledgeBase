## 一、面试题精选

### 安全测试 · 越权的两条线：横向测「改删」，纵向测「独立鉴权」

**Q：越权测试你会怎么做？只测「把 ID 换成别人的能不能查到」够吗？**

不够，那只是最表层的一条。越权在 OWASP 里叫 **Broken Access Control**，长期排在前列，因为它是**业务逻辑缺陷而非技术漏洞** —— 扫描器基本扫不出来，只能靠人设计用例。

**横向越权（同级别用户之间）**

- 用 A 的凭证访问 B 的资源：换 ID、遍历 ID、改参数里的 userId；
- **不只测「查」，更要测「改」和「删」** —— 很多系统查做了校验，写操作忘了；
- 关注**间接引用**：订单号、工单号、文件名、导出任务、消息 ID、附件下载链接，这些容易只做前端隐藏；
- 边界场景：B 的资源已删除 / 未激活 / 属于其他租户时，错误信息是否泄露了资源存在性。

**纵向越权（低权限访问高权限功能）**

- 普通用户直接调管理员接口：重点不是页面入口藏没藏，而是**后端有没有独立鉴权**；
- 改请求里的角色字段（如 role=admin），看服务端是否信任了客户端传入的角色；
- 检查**功能点级鉴权与数据级鉴权是否分离** —— 有权限进这个页面，不等于有权限看这个页面的全部数据。

**三个容易被漏的面**

1. **多租户隔离**：A 租户的 token 是否可能读到 B 租户的数据，重点测分享链接、导出、搜索、统计报表这些「旁路」接口；
2. **接口新旧版本**：新接口加了鉴权，旧版本接口（/v1/ 之类）还开着；
3. **非 HTTP 入口**：MQ 消息、定时任务、内部 RPC 接口绕过了网关鉴权。

工具上用 Burp Suite 的 Repeater 手工重放 + Intruder 做 ID 遍历，再用 Autorize 这类插件自动对比不同身份的响应差异。**但用例设计必须人工做**，工具只负责省掉重复点击。

### CI/CD · 回滚可靠性的四条判据：从「能回」到「敢回」

**Q：你们怎么保证回滚是可靠的？有回滚脚本就算可靠吗？**

有脚本只能算「能回」。我判断回滚可靠的标准是四条：**有预案、演练过、可度量、有决策人**。

**1. 预案要覆盖三个维度，不只是代码**

- **应用层**：回滚到上一个镜像 tag / 制品版本；
- **数据层**：最容易翻车 —— **代码能回，数据往往回不去**。新增字段可以留着，但改列类型、删列、数据订正脚本都必须单独设计回滚。我会把「本次发布是否涉及不可逆数据变更」当成一个必答项；
- **配置层**：开关、限流阈值、路由规则是否要一起回。

**2. 必须在预发演练过，而不是写在文档里**

做法是：**每次发布后的预发验证里包含一次回滚演练** —— 验证回滚耗时多久（这个数字决定故障恢复时间）、回滚后核心业务是否立即可用（有没有残留的新版本数据格式导致旧代码报错）、过程中是否产生数据丢失。**没演练过的回滚脚本，第一次执行一定是在事故现场。**

**3. 回滚能力要可度量**

记录两个指标：**回滚触发到恢复的时间**与**回滚成功率**。如果发现故障要 5 分钟、回滚要 20 分钟，那实际影响时长就是 25 分钟 —— 这个账要提前算进灰度策略与告警灵敏度的设计里。

**4. 要有明确的决策人**

回滚决策不能等开会。建议把决策权下放给值班的研发或测试负责人，并设定**客观触发条件**：错误率超过 X%、P99 超过 Y ms、核心业务成功率低于 Z%。**有客观触发条件的回滚，比「大家觉得不太对」的回滚快得多。**

还有一个经验：**能靠开关降级就不要靠回滚**。回滚是重操作（影响全量用户），开关只影响一个功能点，粒度更细、速度更快。所以新功能默认走开关控制，让降级成为第一选择，回滚作为兜底。

### AI 测试 · RAG 的分段定位：答错要能分清「检索错」还是「生成错」

**Q：RAG 系统的测试你会怎么设计？从哪几个环节验证检索质量？**

RAG 的测试难点在于：**最终回答错了，可能是检索错了，也可能是模型总结错了**。所以要把链路拆开分段定位，绝不只看最终答案对不对。

链路：文档解析 → 切片（chunking）→ 向量化 → 检索（召回 + 重排）→ 拼 Prompt → 生成 → 后处理。

**1. 知识入库环节（最容易忽略，但错在这里的最多）**

- **解析完整性**：PDF 表格、扫描件、多级标题是否被正确解析？重点看表格和列表有没有被打散；
- **切片质量**：一段完整语义是否被切断？**测试方式是拿一个「答案跨越两个切片」的问题看能否召回**；
- **元数据**：来源、版本、生效时间、权限标签是否带上 —— 这决定了后面能不能过滤。

**2. 检索环节（可以量化，最容易做出说服力）**

- **Recall@K**：标注「问题 → 正确文档」样本，看正确文档是否出现在 Top-K 里；
- **MRR / NDCG**：正确文档排第 1 还是第 8，直接影响模型会不会被干扰；
- **拒答能力**：知识库里根本没有的问题，系统应明确说「查不到」而不是编 —— **幻觉重灾区，必须单独测**；
- **权限过滤**：A 用户的提问绝不能召回 B 用户的私有文档，这是硬性安全边界。

**3. 生成环节**

- **忠实度**：回答是否完全基于召回内容，有没有超出上下文编造；
- **引用准确性**：给出的出处是否真的支持该结论 —— **引用了不相关的文档比不引用更糟**；
- **完整性**：多跳问题（需要综合两段内容）能否答全。

**4. 端到端与工程指标**：任务级准确率、首 token 时间与总时长、Token 消耗、检索耗时占比、同一问题多次提问的一致性。

落地建议：**检索指标做成自动化，每次构建都回归；端到端质量用评测集 + 定期人工抽检**。

## 二、知识点精选

### AI Agent · 工具调用的五类失败模式

工具调用是 Agent 从「会说话」变成「能做事」的关键环节，也是最容易造成真实破坏的地方 —— **选错工具往往带来不可逆的副作用**。

1. **选错工具**：有专用工具却用通用工具，或相似工具混淆。测法是给每个工具写「该用 / 不该用」判定样本集，重点覆盖**同时满足两个工具条件的边界意图**。
2. **参数构造错误**：漏参、类型错、值幻觉。**时间（相对转绝对）、金额、ID 三类最危险**，必须断言入参语义而不只是格式合法。
3. **调用时机错误**：信息不足却不澄清就执行（**最危险的失败模式**）、该查不查直接编、用户只是咨询却发起了写操作。要专门设计「信息不足」和「只是咨询」两类用例，断言期望行为是**追问或说明**。
4. **循环失控**：反复调用同一工具、调用次数爆炸、并发调用互相干扰。需给工具加调用计数、设硬上限，并断言超限时能正确退出。
5. **错误处理**：工具返回失败后是否有限重试、是否换方案、是否如实告知；用 mock 注入超时、500、空结果、格式异常看兜底行为。

**断言的核心三件套是「调用了什么、传了什么、然后做了什么」**，而不是只看最终回答像不像对的。

### 数据库 · 大表在线变更（DDL）的测试与回滚

**核心风险不是「能不能加上」，而是加的过程会不会锁表、会不会拖垮主库、失败能不能回退。**

- **先确认锁行为**：MySQL 5.6+ 的 Online DDL 加索引通常 INPLACE 不阻塞 DML，但**改列类型 / 长度基本会锁表重建**；加字段用 nullable 且不带默认值，以免全表重建；
- 大表必须用 **gh-ost** 或 **pt-online-schema-change**（建影子表 + 增量同步 + 原子改名），代价是需要额外磁盘空间和主库负载；
- **测试要点**：变更期间并发跑核心业务观察超时与锁等待；**变更前后比对行数与关键字段的校验和**（cut-over 瞬间是高风险点）；触发器 / 外键 / 唯一约束是否被正确带上；主从延迟是否飙升；老代码读新表、新代码读老表两个方向的兼容性；
- **保护措施**：gh-ost 设置 --max-load 与 --critical-load 超过阈值自动暂停、低峰期窗口、**--postpone-cut-over 先只做数据同步、人工确认后再切换**；
- **回滚**：加索引的回滚是删索引，相对安全；**删字段等于丢数据**。必须提前说清「这次变更的回滚代价是什么、什么时候必须放弃回滚改走修复」。

一条体现经验的建议：**改结构能用「新加列 + 双写 + 迁移 + 下线旧列」四步走，就不要直接改列类型。**

### Python · pytest fixture 与参数化的六个组合陷阱

1. **执行次数放大**：参数化 30 组会让 function 级 fixture 也跑 30 次，执行时间爆炸 —— 作用域应取「满足用例独立性的最大范围」。
2. **ScopeMismatch**：function 级 fixture 不能依赖 session 级；反向可以。想在模块级 fixture 用「某条用例创建的 ID」在设计上就是禁止的。
3. **ID 不可读**：默认 0/1/2，失败时只知道「第 17 组挂」—— 用 `ids=` 显式命名（如「缺少手机号」），**低成本高收益的必做项**。
4. **收集期求值**：parametrize 的参数在**收集阶段**求值，里面调接口会导致「还没跑用例就卡住」，且报错很难读；耗时的准备要放进 fixture（执行期）。
5. **名字冲突**：参数名与 fixture 同名会直接用参数值而**不调用该 fixture**，加 indirect=True 才会走 fixture —— 行为不直观，容易写出「以为在走 fixture 其实没有」的用例。
6. **清理风险**：fixture 在 yield 之前抛异常时，清理代码不会执行；用 `request.addfinalizer` 或外层 fixture 兜底。

职责边界一句话：**fixture 管「环境与依赖」，parametrize 管「同一逻辑的不同输入」**，两者不要互相承担对方的职责。

## 三、技能精选

### 测试环境搭建与治理

能从零规划测试环境体系（**稳定 / 联调 / 预发三层**）：稳定层给自动化流水线用，要求随时可用、**一键重置到基线快照**；联调层按需多套并存，靠命名空间或容器隔离；预发层与生产同构，用于发布前验证与回滚演练。

常用工具：Docker / Docker Compose、Kubernetes、Terraform、Ansible、Testcontainers、Nginx。

**关键点**

- 先保证一套环境「永远可用、随时可重置」，再谈多套。很多团队失败在于环境数量上去了，但没有一套可以信任；
- **配置即代码**，两套环境的差异应该是 `git diff`，而不是靠人回忆；
- 自动化差异比对的**重点是「不可接受差异白名单」之外的任何差异都告警**，而不是只盯几项；
- 环境要有状态页，否则坏了所有人都在群里问；
- 最常见的三类坑：**时区差异、开关状态差异、中间件版本差异** —— 优先纳入自检脚本。

### 安全测试基础能力

掌握 OWASP 常见风险的测试方法，能独立完成越权、认证鉴权、敏感信息泄露、敏感数据存储等测试，并能对缺陷合理定级、给出可落地的修复建议。

常用工具：Burp Suite、OWASP ZAP、sqlmap、jwt_tool、nmap、SonarQube / SCA 扫描。

**关键点**

- 越权重点测「改」和「删」，不只测「查」；
- 定级看**是否可被批量遍历** —— 单条信息泄露为中低危，可批量拉取身份证/银行卡为高危；
- 敏感字段的定级要能回答「能拼接出什么」；
- 修复建议分短期（出口统一加脱敏拦截器）与长期（DTO 白名单输出）；只改一个接口是最容易复发的方式。

### 复杂场景分析与问题定位

面对偶发问题、数据不一致、链路超时这类模糊现象，能通过**量化范围 → 圈定时间 → 还原链路 → 验证假设**的路径把问题收敛到具体环节，并给出可复现手段。这是高级测试最核心的能力之一：**从「有人反馈不好用」到「这是哪个环节的什么问题」。**

常用工具：ELK / Loki、链路追踪（Jaeger / SkyWalking）、Arthas、Kibana、binlog 分析。

**关键点**

- 先把现象**量化**：规模、分布、方向。不同方向指向不同根因 —— 漏写多为事务边界问题，孤儿数据多为删除逻辑或外键缺失，金额不等多为并发或精度问题；分布集中指向某次变更，随机分布指向并发或幂等；
- 用 binlog + update_time 圈定**首次出现时间**，再去比对该时间窗内的变更记录（发布、配置变更、DDL、跑批）—— 这一步能把「偶发 bug」变成「某次变更的后果」；
- 用一条具体数据的**完整生命周期**拼出轨迹，往往一次就暴露根因；
- 结论必须可复现、可验证，不靠猜测。

## 四、坑点精选

### 越权只测了「换成别人的 ID」，没测「换成别人的角色」

横向越权测得很全，但普通用户直接调管理员接口、或者请求里带上 role=admin 这类纵向越权完全没覆盖，而线上真实的重大事故多半出在纵向越权上。

破解：先拿到一份**角色 × 接口的权限矩阵**，按矩阵逐格验证服务端的独立鉴权；同时确认后端不信任客户端传入的角色字段。多租户系统必须单独测跨租户的旁路接口。

### 回滚脚本从没在预发演练过，就直接写进应急预案

预案文档写得很完整，但真出事时第一次执行，才发现回滚后旧代码读不懂新版本写入的数据格式，或者 DDL 变更的数据根本回不去，恢复时间远超预期。

破解：把**回滚演练放进每次发布的预发验证清单**，实测回滚耗时与回滚后核心业务可用性，并记录为指标。凡涉及不可逆数据变更，必须单独设计数据回滚方案。

### 灰度期只看监控大盘变绿就放量

错误率和延迟都正常，但灰度用户里已经有一批订单状态卡住、金额为空。**技术指标绿不代表业务正确**，这类问题往往要等用户投诉才暴露。

破解：灰度必须做业务校验 —— 用 SQL 抽查灰度用户的业务数据确认无异常值，用可定向命中的灰度账号主动跑核心用户旅程，并把放量判据（观察时长、样本量、硬阈值）提前写成表。**没有假设的灰度只是慢速发布。**

## 待图谱化的候选关联

以下为本日沉淀中值得在单源精读时建立关联的候选（此层为原料，不使用双方括号链接语法，避免在原料层留下未解析链接）：

- 横向越权与纵向越权 ↔ 角色 × 资源 × 操作矩阵 ↔ 多租户数据域隔离
- 批量接口部分成功语义 ↔ 越权定级的批量可遍历判据 ↔ 接口遍历测试手法
- 回滚可靠性四条 ↔ 数据层不可逆变更 ↔ 预发回滚演练
- 降级优先于回滚 ↔ Feature Flag 生命周期 ↔ 灰度放量判据
- 回滚耗时指标 ↔ 故障恢复时间（MTTR）↔ 告警灵敏度设计
- RAG 分段定位 ↔ 检索指标（Recall@K / MRR）↔ 拒答能力与幻觉检测
- 忠实度与引用准确性 ↔ 输出侧溯源校验 ↔ 评测集与标注规范
- Agent 工具调用五类失败模式 ↔ Agent Trace 字段清单 ↔ 工具故障注入
- 第一个偏离点定位法 ↔ 长链路失败的单步重放 ↔ 带轨迹的回归用例集
- 大表在线变更 ↔ gh-ost 限速与 cut-over 切换 ↔ 数据校验和比对
- DDL 变更的兼容性 ↔ 新加列双写迁移四步走 ↔ 回滚代价分级
- fixture 作用域与参数化 ↔ ids 可读性 ↔ 收集期与执行期职责划分
- 测试环境三层设计 ↔ 配置即代码与差异白名单 ↔ 环境自治执行体清单
- 复杂场景定位四步 ↔ binlog 时间窗圈定 ↔ 单条数据的生命周期还原
