## 一、面试题精选

### 接口测试

**Q：接口返回 200 就代表测试通过吗？**

不代表。HTTP 200 只说明网关与应用层把请求接住了，业务上可能是失败的。
完整断言必须覆盖四层：

1. **状态码加业务码** —— 很多系统在 200 的响应体里包着业务失败码；
2. **响应体结构** —— 字段是否齐全、类型是否正确；
3. **数据落库** —— 查询库或调详情接口做二次确认，**最容易被漏掉的一层**；
4. **副作用** —— 是否重复发通知、重复扣款、消息是否只投递一次。

**Q：接口契约测试是什么，解决什么问题？**

一句话：把「服务之间字段的口头约定」变成可自动校验的契约。
消费方把自己的期望（请求与响应结构）写成契约文件提交到契约仓库，提供方在 CI 里跑一遍，不一致就让构建失败。
价值在于**不依赖真实联调环境**，比全链路回归快得多，能把问题从集成阶段左移到单元阶段。
常用工具：Pact、Spring Cloud Contract、Dredd（基于 OpenAPI）。

### 性能测试

**Q：压测的 TPS 上不去，怎么排查？**

按「从外到内、从下到上」逐层排除：

| 层次 | 排查点 |
|---|---|
| 压测端（**最易忽略**） | 并发线程数、连接池、压测机 CPU、日志同步写盘 |
| 网络与网关 | 带宽、反向代理连接数与 upstream 配置、全局限流 |
| 应用层 | 线程池、DB 与 Redis 连接池、GC 停顿、慢 SQL、同步锁串行化 |
| 中间件 | 消息队列积压、Redis 热 key、DB 锁等待与主从延迟 |

一个实用的判读经验：**响应时间抖动**基本指向 GC 或锁竞争；**响应时间稳定但吞吐上不去**，多是资源池太小。

### AI Agent 测试

**Q：AI Agent 测试和普通 AI 功能测试有什么本质区别？**

重心从「输出对不对」变成「过程和动作对不对」。三个本质差别：

1. **非确定性放大** —— 95% 正确率的步骤连做 10 步，整体成功率只剩约 60%，所以指标必须按**任务级成功率**统计，而非单步准确率；
2. **要测副作用** —— Agent 会真的调工具、写库、发消息，必须验证动作是否只发生一次、参数是否正确、是否越权调用（与接口测试的幂等、越权测试同源）；
3. **要测过程合规** —— 看轨迹：走了哪些工具、有没有多余调用、有没有陷入死循环、超时后是否正确终止。

工程做法：工具层打桩隔离副作用 → 固定随机种子与模型版本 → 构造任务集批量评测并重复采样 → 引入**轨迹断言**。

## 二、知识点精选

### 接口测试：四层断言模型

传输层（状态码、耗时、响应头）→ 业务层（业务码、字段完整性与取值域）→ 数据层（落库、缓存、消息）→ 副作用层（是否重复下单、重复通知）。
写用例前在脑中过一遍这四层，覆盖率会明显提升。

### 安全测试：OWASP Top 10 里最该测的四类

1. **失效的访问控制（越权）** —— 业务系统中频率最高，也最难被扫描器发现；
2. **注入类** —— 验证重点是是否真的用了参数化，而非关键字过滤；
3. **身份认证与鉴权缺陷** —— 弱口令、token 永不过期、验证码可复用、短信接口可被刷；
4. **敏感数据泄露** —— 响应体冗余返回、日志明文打印凭据、接口未脱敏。

这四类必须靠设计用例手工验证，扫描器只能兜底。

### 检索增强（RAG）：评测的两层指标

必须把检索与生成**拆开测**，否则无法定位问题：

- **检索层**：召回率（正确文档是否被取到）、排序质量（MRR / NDCG）、切分质量（文本块粒度）；
- **生成层**：忠实度（是否完全来自检索上下文，**直接对应幻觉**）、答案相关性、引用准确性；
- **端到端**：无答案时是否明说找不到。

一条能省大量无效调优的工程经验：**先修检索，再调生成**。

## 三、技能精选

### 接口测试用例设计能力

把接口当契约来测，覆盖功能、数据、异常、并发四维，并逐层断言到数据落库。
工具链：Postman / Bruno（调试协作）、pytest + requests（自动化）、OpenAPI（契约来源）、抓包工具（最小复现）。
关键动作：异常用例必须覆盖必填缺失、类型不符、越权、重复提交、下游超时；把高频缺陷场景**反向补进用例集**，形成团队资产。

### 安全测试与漏洞验证

核心竞争力是「**业务逻辑漏洞**」——扫描器只能发现通用问题，越权、并发状态错乱、参数覆盖这类缺陷必须靠理解业务来设计用例。
工具链：Burp Suite（含 Autorize 插件做越权批量比对）、OWASP ZAP、Semgrep / SonarQube（静态）、Trivy（依赖）。
红线：所有测试限于授权范围；造数据一律用符合校验规则但无效的假数据；可能污染数据的操作要在隔离环境做并准备回滚方案。

### AI Agent 测试与轨迹断言

会用轨迹断言、能把工具层打桩隔离出来，才谈得上定位「为什么这一步走错了」——只断言最终输出，永远只能知道它错了，不知道错在哪。
工具链：LangSmith / LangFuse（轨迹记录）、OpenTelemetry GenAI（统一埋点语义）、Stub 工具层。
要点：按任务级成功率分层统计；固定任务集做回归并多次采样；权限层做硬约束（工具白名单 + 高危操作二次确认），测试环境禁用高危工具。

## 四、坑点精选

### 坑点一：接口测试只断言 HTTP 200

**表现**：很多系统会在 200 的响应体里返回业务失败码，只断言状态码会让失败用例变绿。
**破解**：断言至少三层——HTTP 状态码、业务 code、关键业务字段；涉及写操作再补一次查库或调详情接口做数据校验。

### 坑点二：靠关键字过滤判定注入已修复

**表现**：用黑名单过滤单引号、union 等关键字，很容易被编码、大小写、注释穿插绕过，本质是不安全的；只要 payload 被拦就认为防住了，给的是虚假安全感。
**破解**：验证修复要看代码是否用了**参数化查询或预编译**，而不是看 payload 有没有被拦；测试时补上编码绕过与二阶注入场景。

### 坑点三：只断言 Agent 的最终输出文本

**表现**：Agent 的失败往往体现在过程里——调错工具、多调了高危工具、陷入循环。只看最终输出会漏掉这些，甚至会把「结果对了但过程危险」判为通过。
**破解**：记录并断言轨迹——期望调用的工具是否调用、不该调的有没有调、调用次数是否在预期范围、步数是否异常。
