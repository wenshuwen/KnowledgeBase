## 一、面试题精选

### 接口测试 · 异步消息链路

**Q：消息队列异步链路的接口怎么测？重复消费、乱序怎么仿真？**

异步链路要按「生产 → 传输 → 消费 → 补偿」四段验证，不能只验生产端返回成功：

1. **生产端**：校验消息体结构与必填字段、幂等键、发送失败时的重试与落库兜底；
2. **消费端**：用消息轨迹、埋点或消费偏移证明「确实被消费了」，而不是只看发送成功；
3. **重复消费**：手动重投同一条消息（同幂等键），断言业务只生效一次，第二次返回幂等提示而不是报错；
4. **乱序**：在状态流转场景刻意颠倒投递顺序，验证旧消息不会覆盖新状态；
5. **补偿**：让消费端抛异常达到最大重试次数，验证进死信队列、有告警、有可重放手段。

异步结果一律用「轮询 + 最长等待」代替固定 sleep，否则在 CI 上不是慢就是假失败。

## 二、知识点精选

### AI Agent 测试 · 上下文预算

**上下文预算管理**

上下文是最容易被忽视的容量瓶颈，要当资源来管：

- **输入侧**：历史对话做摘要或滚动窗口；RAG 只注入 Top-K 并控制片段长度；系统提示词精炼；
- **工具侧**：工具返回必须截断，并明确告知模型「这不是全部」；超大 payload 先摘要再注入，否则一次返回就能吃掉整个窗口；
- **输出侧**：限制单步输出长度与最大循环次数；
- **可观测**：监控每轮 input / output token 曲线、上下文占用率，以及对「接近上限」设告警。

典型失效表现：对话越聊越傻、忽略最近指令、关键约束被挤掉——这三类都要做成回归用例，而不是等用户反馈。

### 性能测试 · 长尾延迟

**长尾延迟的五个常见成因**

P99 远高于 P95 时按顺序排查：

- **GC**：整堆回收造成周期性尖刺，与 GC 日志时间线对齐即可确认；
- **池排队**：连接池 / 线程池被打满，少数请求排队，排队时间直接进 P99；
- **缓存未命中**：命中率 95% 意味着 5% 的请求穿透到数据库走慢路径；
- **锁与热点**：同一行或同一 key 串行化，定时任务、日志刷盘、慢查询抢占资源；
- **网络与中间件**：丢包重传、跨机房、带宽打满。

定位手法是把落在 P99 的请求单独捞出来（按接口、时间戳、trace 对齐）——慢请求时间戳集中出现，基本就能锁定上面某一条。

## 三、技能精选

### 自动化测试 · 断言分层设计能力

把断言按稳定性与业务重要性分级，是压误报最有效的手段：

- **硬断言**：业务核心结果、金额、状态流转、数据一致性——失败即失败；
- **软断言**：次要模块、文案、兜底字段——记录不中断，一次跑完看全部问题；
- **趋势 / 规则断言**：时间戳、排序、耗时、随机 ID——改规则校验（区间、单调性、正则），不做等值比较。

配套两条纪律：失败必须输出期望值与实际值；把「环境 / 数据导致的失败」单独归类统计误报率，而不是混进缺陷列表。常用工具栈：pytest、JSON Schema、pydantic、Playwright expect。

### 测试环境搭建 · 环境即代码（IaC）

把环境当代码是「一键拉起 / 一键销毁」的前提：

- **声明式定义**：docker-compose 或 Helm / K8s 清单描述应用、数据库、缓存、MQ、Mock 的完整拓扑，版本与被测版本绑定；
- **生命周期命令**：create / reset / destroy 三件套，拉起时自动初始化数据，销毁时清理存储卷，避免僵尸环境；
- **数据基线**：迁移脚本 + 造数脚本，让环境随时回到已知状态；
- **成本控制**：按需创建、闲置回收、小规格实例、共享中间件只留一套；
- **可视化**：每套环境有归属人与到期时间——成本失控多来自「没人记得还有这套环境」。

### CI/CD · 制品可追溯能力

保证「测的包就是上线的包」：

- **只构建一次**：产物打上唯一版本号（含 commit SHA），测试、预发、生产都拉同一制品；
- **制品不可变**：发布后不可覆盖，用校验和或签名验证「拿到的与构建产出的一致」；
- **缓存有边界**：依赖缓存带 key 并支持失效；镜像构建防层缓存把旧代码带进去；
- **可溯源**：制品能反查哪个 commit、哪条流水线、谁构建；
- **加一条断言**：部署后从服务里读出版本号与本次流水线版本号比对，不一致直接失败。

## 四、坑点精选

| 坑点 | 表现 | 破解方法 |
|---|---|---|
| **异步链路只测「消息发出去了」** | 断言生产端返回成功就认为功能通了，消费是否发生、是否重复、失败后有没有补偿都不看 | 拆成生产 / 传输 / 消费 / 补偿四段逐一验证，用消息轨迹或落库证据证明「确实消费了」，并强制覆盖重复消费与乱序 |
| **只看平均 RT，不看长尾** | 报告只给平均响应时间与 TPS，P95 / P99 一概没有，线上少数用户体感极差却没人发现 | 报告固定输出 P95 与 P99 并解释长尾成因；验收标准按分位线定，不要用平均值承诺用户体感 |
| **Agent 测试不管 token 成本** | 只验证功能对不对，回归一次烧掉大量额度，上线后没有熔断机制 | 把单任务 token 与调用次数上限、单租户配额、单次回归预算三档门禁一起纳入测试项，超限必须熔断并告警 |
