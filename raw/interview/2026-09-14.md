## Agent 工具调用测试（Function Calling）

怎么测试 Agent 的工具调用（Function Calling）？——拆成四层测：

一，工具选择准确性——构造需要不同工具的任务集，断言 Agent 选对了工具，选错率是核心指标；二，参数正确性——生成的参数过 JSON schema 校验，重点测缺字段、类型错、枚举值越界；三，异常处理——工具超时、返回错误码、返回空结果时，Agent 是重试、换工具还是诚实汇报失败，死循环防护必须设最大迭代次数；四，组合调用——多步任务里工具的调用顺序和上下文传递。

再提一个特别关注的点：参数注入——用户输入直接拼进工具参数的话可能被用来执行越权操作，这块要跟安全测试联动。

## Agent 死循环的三层防御（异常处理与兜底机制设计）

（大厂真实考题：Agent 调用三个工具后就死循环了，异常处理和兜底机制怎么设计？）考的是 Agent 工程化的三层防御：

① 工具层硬隔离：每个外部工具调用都包 try-catch，而且不能只捕获异常，要返回结构化错误给 LLM，比如 `{"status":"failed","error_type":"Timeout","retry_after":5}`，让模型知道失败了、该等多久、能不能重试；

② 推理层熔断：同一工具连续失败 3 次或检测到循环调用，强制中断——必须实现 Max Iteration 上限和 Loop Detection；

③ 规划层自我修正：更高级的做法是让 Agent 反思『刚才哪里做错了、要不要换个工具』，也就是 Reflection 模式。

测这块要专门构造『工具持续超时』『返回格式异常』的用例，验证熔断是否真的生效。

## Harness 工程（驾驭工程）

Harness 直译『驾驭装置』，一句话：**Agent = Model + Harness**。

模型负责『想』和『生成』，Harness 负责让它『能做事、做得对、出问题能被发现』——包括工具封装、上下文管理、权限控制、重试熔断、日志监控、回滚这一整套工程外壳。

和测试的关系特别直接：一个测试用例 Agent 越跑越不稳定，问题往往**不在模型，而在模型之外的 Harness**——比如上下文无限增长、工具权限没收敛、没有失败兜底。

所以测 Agent 不能只盯着 prompt 和回答质量，要把 Harness 当被测对象：工具调用链路、状态管理、失败恢复，都得有验证手段。

## Agent 多轮对话与记忆机制测试

多轮对话重点测上下文一致性：同一信息用户在第三轮说过，第七轮 Agent 还记不记得；用户中途改口——「刚才说错了，改成上海」——能不能正确覆盖旧信息；上下文超长时会不会把关键信息丢掉，可以故意灌长历史做压力测试。

记忆机制分短期和长期：短期记忆测窗口边界和滑动截断策略；长期记忆测写入时机（什么值得记）、检索准确性（能不能想起相关事实）、遗忘策略，还有记忆冲突——新旧记忆矛盾时以谁为准。

最后测记忆安全：记忆库被注入污染后，Agent 会不会被带偏。

## RAG 与 Fine-tuning 的选型（QA 场景）

选择标准就一条：知识变不变。QA 场景的规格文档每个迭代都在变，微调一次成本高、更新慢，所以默认 RAG——文档更新即刻生效。微调适合窄而稳定的任务，比如让缺陷报告统一成团队语风这种格式问题。

RAG 的测试重点：分块策略合不合理（表格被切一半就检索不到了）、检索相关性（召回的 top-k 对不对）、引用准确性、没有相关文档时诚不诚实拒答、以及延迟和 token 成本。

## 大模型回归测试与评测集管理

把大模型当成「一个持续演化的非确定性组件」来设计回归。评测集管理用三层：**核心集（Golden Set）** 50~100 条精选，触之即报警，跑得最快最严；**全量集** 200~500 条覆盖业务主链路，做版本升级 / prompt 大改时的全量回归；**线上回流集** 持续从用户反馈收集进评测池，每月 review 后升级为核心/全量集。

每次回归看三件事：**指标分布**（不是只看 mean，要看 P50/P90 分位和 worst-case）；**Bad Case 抽样**（最差的 10 条人工复盘，找系统性模式）；**前后对比**（同一份评测集，baseline vs 当前版本的 per-sample diff）。

版本管理：评测集 + 模型版本 + prompt 版本 + temperature 四个绑定进一个 experiment 记录，跑哪版、跑什么 prompt、打的什么分要能复现——这是和传统 CI 不一样的核心。
