## 一、测试工作量的估算与可追溯

排期与结论这两件事经常被当成「凭经验说」，其实都能拆成可核对的账。

### 1. 题：测试工作量怎么估，而不是乘个系数

**Q：迭代排期会上，主管让你给这个需求估测试工作量。你的数字是怎么算出来的？**

系数法（开发 5 天乘 0.4）之所以不可靠，是因为它把一个多因素问题压成一个数，事后无法解释偏差从哪来。改成三条锚分别估、再相加：

| 锚点 | 算式 | 易漏项 |
|---|---|---|
| 执行成本 | 用例条数 × 分档单条成本（简单 / 中等 / 复杂三档系数） | 造数据、铺前置状态、截图留证都算成本 |
| 缺陷往返 | 预估缺陷数 × 单个缺陷平均周转（提交→修复→回归） | 常占总执行量的 20%~30%，最易被整块漏掉 |
| 等待时间 | 等环境、等挡板、等发版窗口 | 它不是工作量，但占排期，应单列为阻塞风险 |

**判据**：三个数分开呈现，并主动指出最不确定的一项。估时的产出不是一个人天数，而是**把不确定性标出来**——若环境最不确定，先要环境而不是先要人。

### 2. 知识点：测试结论的可追溯三件套

一次执行必须能回答「你测的是哪个东西」，靠三个不可变标识钉住：

1. **被测版本**：构建产物的 commit 或镜像 digest。**分支名不行**，分支会往前走，两周后无法还原当时的提交。
2. **数据版本**：快照 id，或造数脚本版本 + 随机种子。缺这一条，第二次跑的差异分不清是代码变了还是数据变了。
3. **环境指纹**：中间件大版本 + 关键配置值 + 依赖服务版本，由初始化脚本自动算 hash，不靠手抄（抄错比不写更糟）。

三者同时出现在测试报告与缺陷单。**缺被测版本的「测试通过」是一个无法复查的断言。**

## 二、容量结论的成立边界

「压测全绿」这句话能不能兑现，取决于它在什么条件下取得的。

### 3. 题：全链路压测怎么保证不脏业务数据

**Q：做全链路压测，流量要打到生产集群，怎么保证不把真实用户的数据搞脏？**

拆四层，缺一层就不开压：

| 层 | 关键动作 | 最易失效点 |
|---|---|---|
| 流量标识 | 固定 header 标记并全链路透传 | **异步路径**：MQ 消息头、定时任务上下文、线程池换线程 |
| 数据落点 | 影子表 / 影子库，**读也要隔离** | 只隔写会导致读到真实数据并写脏缓存 |
| 外呼拦截 | 短信、支付、物流、推送走挡板或网关拦截 | 靠口头保证而非逐项打勾 |
| 兜底清理 | 影子数据带独立租户标识 + 误写排查脚本 | 只有清理脚本没有排查脚本 |

**验收动作**：先压 100 QPS 跑 3 分钟，再查真实表与缓存有无新增记录。这一步放在正式压测之前，而不是之后。

### 4. 知识点：数据量对性能是阶跃而非线性

测试库与生产库差几个数量级时，结论不可外推，因为性能在若干点上是**跳变**的：

- **内存边界**：索引能全放内存走内存树，放不下即读盘，P99 可翻十几倍；
- **排序与临时表**：超出内存阈值后落盘，耗时突增；
- **分页深度**：深 offset 扫描随数据量线性放大；
- **JOIN 规模**：驱动表变大后执行计划可能从索引嵌套循环翻转成全表扫。

造不出同量级时的退路：测两档数据量画「数据量 → P95」曲线外推，并标注为推算值；再用执行计划单独验证可能阶跃的点（索引是否命中、排序是否落盘、深分页是否走覆盖索引）。

## 三、权限与配置：看不见的那一半

界面上看不到的东西，往往才是决定安全与行为的部分。

### 5. 知识点：权限控制的三个落点

菜单隐藏只是体验层，不是安全边界。三个落点分别验：

| 落点 | 验法 | 期望 |
|---|---|---|
| 路由 | 直接输入 URL | 只影响体验，不构成防护 |
| 接口 | 低权限 token 直调高权限接口 | **403**；返回 401 会让前端误跳登录，掩盖真实问题 |
| 数据 | 同接口下核对返回条数 | 只返回有权限的 N 条，而非全部 |

补充动作：从前端打包产物与网关日志里捞「文档中不存在」的接口，常能发现调试遗留、完全无鉴权的端点。

### 6. 技能：环境差异清单与配置指纹

「配置看起来一样但行为不一样」，差异多藏在中间件与框架默认值里。五处高频来源：

1. **连接池与超时**：池满后故障形态从「慢」变成「报错」；
2. **线程池与队列**：测试环境队列几乎不满，拒绝策略从未被触发，上线首次触发即雪崩；
3. **缓存**：本地缓存开关、TTL、单机还是集群——测试常关缓存，一致性问题无法复现；
4. **日志级别**：DEBUG 与 INFO 的字符串拼接与落盘量可差 20% 以上吞吐，且部分逻辑写在 `isDebugEnabled()` 分支里；
5. **中间件参数**：MQ ack 模式与消费并发、数据库隔离级别、字符集、`sql_mode`（宽松模式静默截断 vs 严格模式直接报错）。

**落地方式**：两个环境各自导出配置指纹（键 + 值 + 来源）用脚本 diff，差异分成「有意为之」与「意外漂移」，前者入档、后者提工单。**靠记忆比对，一定会漏。**

## 四、数字对不上时怎么定位

「总数与明细不一致」是业务方最不信任测试的一类问题，因为它看着像测试没测出来。

### 7. 技能：数据一致性与分层对账

按三层分开证明，因为三层的处理人和修法完全不同：

| 层 | 做法 | 结论 |
|---|---|---|
| 库内 | 只读从库按同一条件跑 COUNT | 库内就少 → 上游写入问题；库内不少 → 接口口径问题 |
| 接口 | 逐页拉取并统计去重条数 | 合计少于库内 → 隐式上限（分页默认值、检索引擎的条数上限） |
| 跨系统 | 按业务号做左右差集 + 比对同步位点时间 | 差额集中在最近数分钟 → 延迟；长时间未追平 → 故障 |

**固化用例**：随机造 N 条数据，验证「总数 = 各页明细去重后条数之和」。等式成立才算口径统一，而不是靠人眼看两次。

### 8. 技能：Agent 规划质量评测

只评最终结果，会把「运气好蒙对」和「真的会规划」混在一起。三个可比对维度：

1. **步骤完整性**：对齐人工标准序列，算覆盖率；**要区分「合并成一步」与「真漏一步」**，前者是加分项。
2. **顺序正确性**：用偏序关系判定，不必完整相等；硬依赖倒置（先扣库存再校验余额）判 P1，软依赖倒置只记效率问题。
3. **冗余度**：重复执行与方案横跳。带副作用的工具上重复执行会造成真实损害，必须拦截。

补一条实践细节：**必须设步数上限**（如最多 12 步），否则 Agent 会用 40 步慢慢试出来，看着成功但成本与时间都不可接受。

## 五、三个反复出现的坑

### 9. 坑点：评测集被简单样本撑高

500 条评测集里 350 条是单句直答，准确率 92% 看着漂亮；上线后用户问的多条件、矛盾信息类问题全线崩。

**破解**：给评测集打 L1~L4 难度标签分层报数，按生产日志的意图分布重采样、每层保底 30 条；再统计失败类型分布——**总分只说行不行，失败分布才说该改什么**。

### 10. 坑点：分片上传只校验合并后的总 md5

缺片时部分实现会补零凑长度，重复分片被追加写入，只验总 md5 就可能完全查不出来。

**破解**：三个点都打——每片上传后核服务端记录的分片号、合并前核分片清单条数与发送数一致、合并后核整体 md5。缺片时要求接口明确报错，不允许「成功返回一个小文件」。

### 11. 坑点：PR 绿主干红就去重跑

同一个提交合入主干后红了，第一反应是重跑；碰巧绿了就当没事，实际是变量作用域、密钥可见性、缓存或共享环境的差异一直在。

**破解**：把两条流水线的变量表、镜像版本、依赖 lock hash 打出来逐项 diff。重点查 PR 级变量与主干变量的值差、fork PR 拿不到密钥导致的降级跳过、主干并发共享测试环境的相互干扰。

### 12. 场景判据：带缺陷上线的四问

发版前发现 P1，不给「能上/不能上」的二元答案，四问答完再给带条件的建议：

| 问 | 关键事实 | 对结论的影响 |
|---|---|---|
| 影响面 | 触发条件、用户比例、影响资金/数据/体验 | 「打开首页就中」不可上；「特定配置+时序」可量化 |
| 降级能力 | 能否用开关关掉、只对内部开放 | 有可控开关，风险从不可控变可控 |
| 回滚成本 | 几分钟能回滚、是否丢数据、有无不可回滚 DDL | 需 5 分钟内可回滚才有资格「先上再看」 |
| 不上的代价 | 错过窗口影响市场活动还是可顺延 | 区分「必须上」与「最好上」 |

结论写成条件式（「建议上，前提是开关默认关闭 + 18 点前完成全链路回归」），并书面记录决策人与前提。
