## 一、场景题（scene）

### 题 1：主观反馈「搜索结果明显不对」，但指标全正常，怎么变成可定位的问题？

**Q：** 客服反馈一批用户说搜索结果明显不对，但接口成功率、响应时间、错误率全都正常。怎么把这个主观反馈变成可定位的技术问题？

**A：** 核心不是「去查 bug」，而是**先把主观描述转成可采样的客观信号**，否则会一直停在「用户说不对、我们看指标正常」的循环里。四步：

**1. 把「不对」定义出来。** 拿 10~20 条具体会话（搜了什么、期望什么、实际拿到什么），目的不是复现而是拿到**可判定样本**；再和业务一起把「不对」写成判据（如「搜品牌词前 3 条出现竞品」）。有判据才能统计「不对率」。

**2. 定时间。** 把变更时间线拉出来：**索引重建、排序权重、召回策略、模型或规则版本、AB 实验开量、缓存刷新**。搜索类问题八成是变更引起的。

**3. 定人群。** 看是否只在某个分群上「不对」——端、地区、用户分层、实验桶。若只有少数用户反馈，很可能是**分群或灰度桶**问题，此时全量指标当然正常。

**4. 拆链路。** `query 理解 → 召回 → 粗排 → 精排 → 结果拼装 → 缓存`，拿几条坏样本逐段比对，看从哪一段开始偏离。

**收尾：把结论固化成用例**（「搜 A 词，前 3 条必须命中 B 品类」）挂进回归，让排序策略改动能被自动拦住。

### 知识点 1：主观反馈的可量化转换

**要点：** 用户/客服的反馈基本都是「不好用、不对、很慢」，这类描述**不可测、不可复现、无法验收**，测试的第一个动作永远是转译。

- **第一步 收集样本**：10~20 条真实会话，含时间、账号（脱敏）、操作路径、期望与实际。
- **第二步 定义判据**：与产品一起把「不对」写成可判定条件，要求**两个人能独立判出同一结论**。
- **第三步 量化成指标**：有了判据才能算比率（「100 条样本中 22 条不满足判据」），这个数字才能进报告与验收标准。
- **第四步 反向定验收线**：把指标变成可回归的门槛（如「品牌词竞品率 ≤ 1%」），挂进评测集定期跑。
- **两个常见错误**：直接去猜代码（浪费开发时间）；用「复现不了」结束问题（让问题永远悬着）。
- **适用范围**：搜索/推荐相关性投诉、AI 生成质量问题、偶发体验问题、任何「用户说不清哪里不对」的反馈。

### 技能 1：场景题拆解与漏斗定位

- **能力定义**：把「用户说不对 / 偶发 / 复现不了」模糊场景，拆成可采样样本、可对齐时间线、可分层人群、可逐段比对链路，输出可定位结论。
- **常用工具**：链路追踪（SkyWalking / Jaeger / OpenTelemetry）、请求 ID 串联的结构化日志、Grafana 类监控、流量录制回放（GoReplay）、分群分析（埋点平台 / SQL 分组）。
- **五个关键动作**：① 先转译再动手；② 时间线对齐（变更记录 vs 故障时刻）；③ 分群排查一次只切一个维度；④ 拆链路逐段比对；⑤ 结论必须固化成用例或监控。
- **高级与普通的分野**：不在于会不会查，而在于**能不能把「说不清的问题」变成「可判定、可统计、可回归的问题」**。

## 二、数据库（db）

### 题 2：同一条 SQL 在测试环境很快、生产很慢，差异从哪来？

**Q：** 一条查询在测试环境很快，生产上很慢。同样的 SQL、同样的数据量级，差异可能来自哪些地方？

**A：** 「SQL 一样、量级一样、结果差很多」最典型的根因是**执行计划不同**，而不是 SQL 本身有问题。

**先确认计划是否真不同**：两边跑 `EXPLAIN`（优先 `EXPLAIN ANALYZE`），对比 `type` / `key` / `rows`。只要索引选择或预估扫描行数不同，问题就在这。

**六个常见原因：**

1. **数据分布不同**——测试数据均匀、生产长尾。低区分度的索引在生产上会被优化器放弃。
2. **统计信息过期**——基数估算失真。验证：`ANALYZE TABLE` 后重跑看计划是否变化。
3. **参数化查询（参数嗅探）**——不同参数值得到不同计划。**用生产那个具体参数值**在测试环境执行来验证。
4. **索引结构差异**——发布脚本漏执行导致缺索引。对比两边 `SHOW CREATE TABLE`。
5. **版本与参数不同**——大版本升级改变优化器行为；`optimizer_switch`、`innodb_buffer_pool_size` 等会影响计划。
6. **缓冲池差异**——测试数据全量驻留内存，生产大量走磁盘 IO。同一计划、不同物理代价。

**别忽略非数据库原因**：并发压力、锁等待（长事务持锁）、连接池排队、应用侧 N+1。验证方式是把 SQL 在生产只读从库单独执行，若很快则不是 SQL 问题。

**输出物**：两边执行计划 diff + 敏感参数验证结果 + 数据分布对比，并建议测试环境用**脱敏后的生产数据分布**造数。

### 知识点 2：执行计划差异的六个成因 + 一个排查口径

**要点：** 排查起点固定为「对比 `EXPLAIN` 的 `type` / `key` / `rows`」，而不是先怀疑 SQL 写法。

| 成因 | 特征 | 验证手法 |
|---|---|---|
| 数据分布不同 | 生产长尾，同一索引区分度差 | 比对状态/枚举字段的取值分布 |
| 统计信息过期 | 表频繁变更但未 ANALYZE | `ANALYZE TABLE` 后重跑看计划是否变 |
| 参数嗅探 | 换参数值结果不同 | 用生产的具体参数值复现 |
| 索引结构差异 | 缺索引或多索引 | diff `SHOW CREATE TABLE` |
| 版本/参数差异 | 升级或参数不一致 | 对比版本号与优化器相关参数 |
| 缓冲池差异 | 计划相同但 IO 不同 | 看 `Handler_read` 与 IO 指标 |

**补充三类非 SQL 原因**：并发压力、锁等待、连接池排队、应用侧 N+1 —— 用「在只读从库单独执行该 SQL」来区分。

## 三、AI Agent 测试（agent）

### 题 3：Agent 多步任务被中断，恢复后应该继续还是重来？怎么测？

**Q：** Agent 的多步任务中途被打断（用户取消、服务重启、超时），恢复后应该继续还是重来？这种状态一致性问题怎么测？

**A：** 本质是**「Agent 的执行是一份分布式事务」**：执行被切成多步，每步都可能产生副作用，中断点可能落在任意步之间。**「重来」的风险是副作用重复，「继续」的风险是状态错乱。**

**1. 先分中断类型**（不同类别的正确行为不同）：用户主动取消（应立即停止并释放资源，已产生副作用要明确处理）、服务重启/崩溃（应从检查点恢复）、超时无响应（要有明确超时判定 + 区分「重试同一任务」与「生成新任务」）、依赖不可用（表现相似但需分开处理）。

**2. 测试设计：在「步骤边界」做矩阵，而不是随机中断。** 把任务拆成 N 步，**在每一步之前和之后各注入一次中断**（Mock 工具、杀进程、断网、抛异常），得到 `2N` 个中断点的可复现矩阵。

**3. 每个中断点断言四件事：**

- **副作用不重复**（最核心）——核对下游真实状态：订单几条、券几张、付费接口调了几次，用幂等键核对。**「最终结果对但中间重复扣款两次」是最危险的形态。**
- **状态机的状态合法**——不能出现「显示已完成但只跑了 3 步」；任何一个状态都要对应一组确定已完成的步骤。
- **恢复行为符合设计**——继续执行时上下文必须完整恢复（中间变量、已获取数据、已做判断），否则会得到错误结果。
- **对用户有明确反馈**——不能永远转圈，要有可操作项。

**4. 并发与竞态**（最易出问题）：取消恰好发生在最后一步执行时；两个实例同时恢复同一任务导致重复执行。测法是重复跑多次统计不一致比例。

**验收标准写法示例：** 「在 2N 个中断点上分别注入取消与进程重启，要求：① 任何情况下同一业务标识的副作用最多发生一次；② 恢复后状态为『已完成』且实际完成步骤数等于设计步骤数；③ 无法恢复的任务必须给出明确失败原因且无残留副作用。」

### 知识点 3：Agent 成本副作用的四道围栏

**要点：** 成本失控的特征是**不报错、不违规，只是持续烧钱**。四道围栏按优先级：

1. **预算上限（单任务 / 单用户 / 全局）**——最容易漏的测试场景是**「必然失败的任务」**：Agent 在「努力但徒劳」时最容易反复重试烧钱。要求超限时优雅终止并给出说明，而不是抛异常或静默死循环。
2. **人工确认（Human-in-the-loop）**——有成本且不可逆的操作（下单支付、按次计费接口、发短信、创建云资源）应有人工确认或明确授权边界。测试确认流程**能否被提示注入绕过**、确认一次是否等于无限授权。
3. **重试与循环的成本放大控制**——是否指数退避（而非立即重试）；是否出现「调用成功但 Agent 认为失败而重复调用」（幂等性问题）。注入依赖超时/失败，度量成本放大倍数并要求有明确上限。
4. **成本可观测性**——每次调用带「任务 ID / 用户 / 功能 / 工具名」标签，支持按任务维度统计成本。没有这件能力，前三道围栏的判据无法验证。

**实用技巧**：用「会记账的 Mock 工具」替换付费接口（按真实计费规则累计虚拟费用），即可安全压出极端情况下的成本上界。

## 四、安全测试（sec）

### 知识点 4：网关统一鉴权的四类绕过入口

**要点：** 网关统一鉴权把安全责任集中到一处，但安全性**完全建立在「所有流量必经网关」这一前提上**。四类入口：

1. **网络层绕过**——后端服务端口在集群内可达，直接请求 Service / Pod IP 即可跳过网关。**这是最严重的一类**：一旦成立，所有网关鉴权形同虚设。验证是在集群内起容器直接 curl 后端地址。
2. **路径匹配绕过**——网关匹配规则与下游框架解析规则不一致。典型变形：`/admin/`、`//admin`、`/./admin`、`%2e%2e`、`/API/Admin`、`/admin;.js`。**每一个白名单前缀都要跑一遍这套变形。**
3. **框架自带端点未纳管**——`/actuator/*`、`/health`、`/metrics`、`/env`、Swagger UI、监控页，常直接暴露环境变量与数据库连接串。要**按服务逐个扫**。
4. **身份头伪造与内部调用**——网关鉴权后把身份透传成内部头（`X-User-Id` / `X-Role`），若下游无条件信任，外部请求自带同名头即可冒充任意身份。要验证**网关是否剥离了外部传入的同名头**。

**关键提醒**：网关管「你是谁」，不代表管「这条数据是不是你的」。**网关统一鉴权后，越权测试一条都不能少。**

### 坑点 1：批量接口只测「能不能删自己的数据」

**现象：** 只用自己的一批 ID 测通了就认为权限没问题。而批量接口的实现往往是「循环处理、只校验第一个」或「一条 `IN` 语句全跳过校验」，测试通过完全说明不了安全性。

**破解：** 固定用例模板 —— **一批 ID 中混入 1 个他人 ID，并分别放在首位、末位、中间各测一次**（不同实现漏校验的位置不同）；再补「不存在的 ID」「已删除的 ID」「跨租户 ID」「超量提交（1000 个）」四类。同时验证返回语义应为**整批拒绝**而非「部分成功」。批量导出要单独试「参数注入绕过筛选条件、导出全量数据」。

## 五、大模型工程（llm）

### 知识点 5：Chunk 策略变更的回归验证清单

**要点：** chunking 参数看起来只是「一个数字」，改它不发版、不走评审，但它决定模型能看到什么内容，**等于改了模型的知识来源**；影响又是概率性的（不报错、只是部分答案悄悄变差）。属于典型的**「绕过质量流程的隐性变更」**。验证覆盖四层：

1. **结构层（先查硬问题）**——语义单元是否被切断（表格切两半、条款拦腰截断、代码被切开）；overlap 是否真生效；**元数据继承是否正确**（错了会召回废弃版本或越权内容）；边界内容是否丢失。验证手法：**把所有 chunk 拼回去与原文对照**。
2. **检索层（量化对比）**——用「问题 → 正确 chunk」标注集算 `Recall@k`（没召回就不可能答对，最关键）、MRR/NDCG。**必须分场景看**：事实型 / 跨段落型 / 表格清单型**对 chunk 大小的敏感方向相反**，只覆盖一类会「优化了一类、改坏另一类」。
3. **生成层（端到端）**——答案准确率 + **引用正确率** + 拒答率。重点看引用正确率：chunk 边界变化最易出现「答案对但引用错」（引用指向不含依据的相邻 chunk），传统指标看不出来。
4. **工程层（代价）**——chunk 变小 → 数量变多 → 检索延迟与存储上升；chunk 变大 → 单次 Token 变多 → 成本上升、可能触发截断。**要把代价一起报出来让业务决定值不值。**

**机制建议**：把 chunking 参数纳入版本管理，与提示词/模型版本走同一条「改动 → 跑评测 → 对比 → 发布」流程；记录「参数 + 指标」历史曲线，避免每次从零重试。

## 六、测试环境与发布（env / devops）

### 技能 2：环境故障演练与容量验证

- **能力定义**：组织生产与预发的容量演练和故障注入（混沌工程），从最小可控范围起步，用明确判据验证降级、切换与恢复能力，并配备中止开关。
- **常用工具**：Chaos Mesh / ChaosBlade（故障注入）、GoReplay / jvm-sandbox-repeater（流量回放）、Prometheus + Grafana（判据观测）、Argo Rollouts（实例级操作）。
- **推进节奏（关键）**：**测试环境单实例 → 测试环境依赖故障 → 生产低峰单实例 → 生产降级依赖 → 生产容量演练 → 生产多故障叠加**。每一步都必须「上一轮结论被验证有效」才能进。
- **硬性前置条件**：业务低峰且已同步各方；**中止开关（Kill Switch）能在 30 秒内停止注入并恢复**（没有就不做）；回滚预案已演练；**先确认告警能发出**——很多演练暴露出「故障发生了但没告警」，这本身就是高价值发现；写操作走影子表或标记演练数据。
- **测试承担的三角色**：设计判据与验证用例、观测异常行为（任何不符合预期的现象都记录）、复盘与固化（有效判据转成常态化自动校验）。

### 坑点 2：把「流水线绿了」等同于「发布成功」

**现象：** 部署任务返回成功就认为发完了，不确认新版本真的在跑、核心链路真的能用、业务指标没有恶化。半新半旧（部分实例还是旧版本）、配置未生效、数据库脚本未执行这类问题就此漏过。

**破解：** 把发布后验证做成**自动化的固定步骤**（不通过则自动回滚或暂停放量），清单至少五项 ——
① **版本确认**（抽查实例实际运行的镜像/提交号，而不是看部署日志说成功）；
② **核心链路冒烟**（登录 + 下单 + 支付等主干）；
③ **数据库变更校验**（字段/索引/数据订正是否真的生效）；
④ **关键业务指标比对**（与发布前基线对比错误率、成功率、转化）；
⑤ **错误日志扫描**（新出现的异常类型与堆栈）。

## 七、AI 测试与 Python 工程（ai / python）

### 坑点 3：AI 功能只做上线前的离线评测，不做线上质量监控

**现象：** 上线前评测过了就认为质量有保障。上线后再没人看质量，直到用户投诉或业务发现指标下滑才回头查，此时已积累大量差体验，且无法确定从哪次变更开始。

**破解：** 重点不是技术指标（成功率永远 100%），而是**质量代理指标**：重新生成率、负反馈率、追问次数、采纳率、会话异常中断率，并**按模型/提示词版本下钻**做新旧对比。再加最有效的一招 —— **固定探针问题每天跑一次做漂移检测**，输出分布明显变化即告警，能抓住上游模型被静默升级、向量库被重建这类「没人反馈但确实变了」的静默退化。告警阈值用**基线 + 变化率**，并用样本量下限避免小样本噪声导致告警疲劳。

### 技能 3：测试工具工程化（配置、日志与资源管理）

- **能力定义**：把测试脚本当工程产物来做 —— 分层配置与密钥外置、启动时校验、结构化日志、长跑场景下的资源自监控与断点续跑。
- **常用工具**：PyYAML / pydantic-settings、dataclass + typing、logging（脱敏）、`tracemalloc` / `gc` / `/proc/self`、systemd / supervisor。
- **配置四层**：默认 / 环境 / 本地（进 `.gitignore`）/ 密钥（**不进仓库**），**合并而非替换**（环境层只写差异项）。密钥用单独方法读取且**不参与日志打印**，提供脱敏的 `describe()` 用于排查加载问题。
- **启动时校验**：必需项、类型、密钥非空、环境可达性 —— **缺失即报错退出并说明「缺哪项、从哪来、怎么配」**，把运行期故障变成启动期提示。
- **长跑自监控三件套**：内存（RSS / 峰值）、**打开的文件句柄数**（单调上涨即泄漏，最容易被忽略）、单轮耗时趋势。
- **异常处理分层**：单任务失败记录原因并继续；框架级错误（配置错、连接串错）快速失败退出。**禁止用一个大 `except Exception` 包住整个循环** —— 会让脚本「继续跑但产出全是错的」。

## 待图谱化的候选关联

> 以下为条目间的潜在关联线索，供每周单源精读时判断是否合并/交叉链接（本层不写 `[[]]`，避免原料层出现死链）。

1. 「主观反馈可量化转换」↔「AI 功能评测集构建」——同一套「先定判据再量化」的方法论，只是对象不同（用户体验 vs 模型输出）。
2. 「时间线对齐定位法」↔「缺陷逃逸分析」——都需要把故障时刻与变更记录并排看。
3. 「执行计划差异六成因」↔「测试环境数据分布失真」——同一根因的两种表现（SQL 层 vs 环境层）。

7. 「网关统一鉴权绕过」↔「越权测试矩阵」——网关照做身份，业务照做数据权限，两层都要测。
