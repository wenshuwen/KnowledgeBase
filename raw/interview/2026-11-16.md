## 一、CI/CD：把确定性做成门禁

### 1. 题：同一提交构建两次，产物不一致怎么查

**Q：同一个 commit 在流水线里构建两次，产物 hash 不一样，你怎么查？**

这道题的答题结构感比细节更重要：**分四层往下剥，每层给出可核对的判据**。

| 层次 | 典型根因 | 判据 |
|---|---|---|
| 元数据 | 构建时间戳、构建号、git 描述写进产物 | 解包排除这些字段后重算 hash，看是否一致 |
| 依赖 | 版本写成范围符或 latest，两次拉到不同版本 | 比对锁文件与构建日志里实际下载的版本 |
| 缓存 | 缓存键算错，复用了过期中间产物 | 清缓存后双构建一致、带缓存不一致 → 键算错 |
| 顺序 | 并行打包、目录遍历顺序不固定 | 表现为偶发不一致，最难定位 |

真正常被追问的是第一层：**很多「不一致」只是元数据不同，内容其实相同**。先证明这一点，能省掉后面三层排查。

守卫手段：同一 commit 连构两次比对 hash，不一致即失败。这条守卫的性价比很高——它把「偶发」变成了「每次构建都验」。

### 2. 题：构建一次到处部署，成立的前提是什么

**Q：「构建一次、到处部署」和「每个环境各自构建」怎么选？**

倾向**只构建一次**，但要能说出它成立的三个前提，否则这条实践在落地时会变成坑：

1. **配置外置**——环境差异靠配置或环境变量注入。如果代码里仍有 `if env == prod` 这类分支，各环境跑的实际不是同一份逻辑，构建一次的收益就不存在了。
2. **制品可追溯**——用 digest 而不是 tag 标识制品（tag 会被覆盖，digest 不会），每次部署记录 deploy 的是哪个 digest。
3. **环境之间只有配置差异**——若预发与生产的中间件跨大版本，预发验证过的制品上生产仍有风险，需在发布单里显式声明差异。

**必须各自构建的例外**：编译期裁剪渠道包、按环境签名或混淆、老项目把环境写进产物。

落地形态：构建一次 + 部署时注入配置 + **每环境部署后跑冒烟**。最后一个动作不能省——配置注入错是这类流程最常见的故障，光靠制品一致防不住。

### 3. 题：变更冻结怎么才能真的拦住人

**Q：变更冻结期和发布窗口，你在流水线里怎么落地？**

群里喊「本周冻结」是无效的，要变成流水线能拒绝的规则。

- **冻结窗口用配置表达**，命中窗口时生产发布任务直接拒绝执行并给出原因与联系人，而不是弹确认让人点过去。
- **留一条受控的紧急通道**。完全堵死会逼着人绕过流程手工上线，那更危险。紧急通道要求填变更单号、指定审批人、自动通知值班群，且**强制发布后 30 分钟内跑完核心冒烟**，事后单独出清单复盘。
- **区分「冻结什么」**：冻结生产变更，不冻结代码合并。研发照常提交、照常跑 CI，只是不能发生产。
- **窗口看流量曲线**，取低谷且给回滚留足时间——窗口离高峰只剩 20 分钟时，一旦出问题根本来不及处置。

自检动作：在冻结期故意触发一次发布，确认流水线确实拒绝了。**配置写了但判断分支没生效**，是这类机制最常见的失效方式。

## 二、性能：先证明测的人没拖后腿

### 4. 题：TIME_WAIT 暴涨是不是服务端瓶颈

**Q：压测时客户端报端口耗尽、TIME_WAIT 暴涨，这是被测服务的瓶颈吗？**

大概率不是，是压测机自己的问题。看到 TIME_WAIT 就喊「服务端撑不住」是性能测试里最常见的误判。

机制：短连接下主动关闭方进入 TIME_WAIT 并保持约 60 秒，可用本地端口数量有限（受内核参数约束），高 QPS 下一分钟量级就能耗尽，之后 `connect` 直接失败。

**判据（三条）**：

1. 压测机上 TIME_WAIT 数万、本地端口接近上限；
2. 同时看服务端连接数与 CPU 都不高；
3. 把并发调低后错误消失、TPS 也一起降 → 说明是被压测端先投降。

治理顺序：开长连接复用（最有效）→ 分布式多机压测 → 调本地端口范围（只缓解）。

最值得记住的一条：**用空接口压一次，得到的就是本次压测的天花板**。业务接口的结论一旦超过这个数字，就必须标注为压测端受限。

### 5. 知识点：分位数为什么不能只看一轮

P99 由尾部 1% 样本决定，样本少时方差极大——请求数只有千级时，P99 由个位数请求决定，一次偶发停顿就能把它抬高数倍。

- **样本量**：要让 P99 有意义，尾部样本通常需上百，即总请求数上万。
- **多轮取中位数**：同配置跑 3 到 5 轮取中位数，并报出波动范围；异常轮单独排查而非平均掉。
- **区分噪声与真波动**：TPS 稳定而 P99 抖多为环境噪声；P99 与 TPS 同时劣化说明系统在某阈值附近不稳定，这才是真发现。

报告里写「P99 = 230ms」是假精确；写「5 轮中位数 230ms，波动 210~260ms，另 1 轮异常已排除（同机跑了构建任务）」才是可用结论。

### 6. 知识点：预热与冷启动是两件事

冷启动慢在四处：缓存未命中、连接池未建立、JIT 未编译、本地索引与字典未加载。若压测只跑 1 分钟，冷启动尖峰就会主导整份报告。

- **容量压测必须预热**：低并发预热 1~3 分钟后**重置统计**再计时。用正式并发预热等于提前打掉一轮能力。
- **冷启动要单独立项**：关心的不是峰值 TPS，而是「多久恢复到正常水位」「期间错误率与超时是否可接受」。

两件事混在一次执行里，两头都测不准。

## 三、安全：属性写了不等于生效

### 7. 题：Cookie 三个属性怎么验才算验过

**Q：Cookie 上的 HttpOnly、Secure、SameSite 三个属性，怎么验证真的生效？**

三个属性的作用点都在客户端，**只看响应头不够**，要验浏览器实际行为。

| 属性 | 验证动作 | 注意点 |
|---|---|---|
| HttpOnly | 控制台执行 `document.cookie`，目标 Cookie 不应出现 | 「读不到」才是生效，不是「被写了但隐藏」 |
| Secure | 用 HTTP 访问同一域名，抓包看请求是否带该 Cookie | localhost 属安全上下文，本地测不出差异 |
| SameSite | 从不同站点构造跨站请求并抓包 | Strict 完全不带；Lax 仅 GET 导航带；None 必须配 Secure，否则被浏览器丢弃 |

三个里最容易配错的是 SameSite：**必须跨站构造**（不同站点，不是不同端口）才测得出来。

另有一条常被漏的：**登出后拿旧 Cookie 值直接请求接口，服务端必须拒绝**。如果只在前端删了 Cookie，攻击者手里的旧值照样能用。

### 8. 知识点：频控绕过的五个方向

测频控不能只发几次看拦住没有，要测边界与绕过两条线。

1. **维度**：限的是手机号还是 IP？换 IP 不限说明单维度可被代理池刷。
2. **格式变体**：号码加前缀、加空格、大小写差异，服务端不做归一化就可绕。
3. **参数污染**：同参数传两次，看后端取第一个还是最后一个。
4. **并发**：同时发 10 个请求，若「先查次数再自增」缺少原子操作，会全部通过——**这是最常见的并发漏洞，且串行循环测不出来**。
5. **验证码本体**：是否重复下发、位数与字符集是否可枚举、错误次数是否受限。

比频控缺失更严重的还有一条：**验证码与业务动作未绑定**——A 场景拿到的码能用在 B 场景，或一个码能重置两个账号。

## 四、数据与环境：约束在边界上才见真章

### 9. 题：软删除与唯一索引的冲突

**Q：唯一索引加上软删除，会不会出问题？怎么测？**

会。逻辑删除只是标记，行还在，唯一索引继续占位，同一业务键再也插不进去。

**一条用例即可暴露**：注册 → 软删除 → 用同一手机号再注册，第二步应成功。

| 修法 | 需要注意的地方 |
|---|---|
| 联合唯一 (phone, deleted_at) | 删除时间精度：秒级时间戳下同一秒删两次仍冲突；多条已删记录的 NULL 是否参与唯一要按实际库确认 |
| 删除时业务键改名 | 简单有效，但污染数据、影响按业务键查询 |
| 删除标记用固定值参与联合唯一 | 实现稍复杂，行为最可控 |

**修完必须反测三件事**：删除后的数据查不出来、恢复功能可用、两条有效记录不能并存（防止为解决问题直接删掉唯一索引，那是更严重的错）。

### 10. 知识点：迁移验证的四层对账

迁移验证的核心是对账，不是「抽样看几条觉得没问题」。

1. **总量**：行数一致，差异要能解释；还要看按状态、按时间分区的分布——总数对但分区错位说明筛选条件写错。
2. **字段级**：精度（金额小数位截断）、编码（emoji 与生僻字变问号）、空值（空串与 NULL 互转影响查询条件）、时区（时间戳整体偏移，最常见的隐性错误）、默认值（新增字段未赋值）。
3. **业务语义**：状态码含义变了（老表 1 表示已支付、新表 2），直接搬等于全量错状态。验法是在新老表上各跑一次关键业务查询，**比对结果集**而不是只比字段。
4. **双写一致性**：两边同时写入是否一致、一边失败如何补偿。这层只在写入高峰才暴露，最容易漏。

工具建议：对账脚本**输出差异清单而非差异数量**（300 条差异要能一条条看出规律），脚本幂等可重复跑。最后必须有演练过的回滚方案——切换窗口内新写入的数据怎么办，没演练过等于没有。

### 11. 知识点：容器环境不一致的四类根因

本地能跑、CI 不能跑，按顺序排查：

| 顺序 | 根因 | 判据 |
|---|---|---|
| 1 | CPU 架构不同（arm64 / amd64） | 两边 `uname -m` 不一致，原生依赖编译失败或靠模拟奇慢 |
| 2 | 依赖走公网 | 本地有缓存、CI 每次拉公网，限流超时；改内网源后耗时骤降 |
| 3 | 大小写与时区 | 大小写敏感导致 import 失败；容器默认 UTC 导致日期断言差 8 小时 |
| 4 | 资源限制 | CI 内存 CPU 更小，堆参数写死会 OOM，随机被杀进程 |

根治：本地与 CI **共用同一镜像与同一份 compose**，差异只允许通过环境变量注入。

## 五、AI 与 Agent：概率系统的验证方式

### 12. 题：把「答得不好」拆成三段

**Q：RAG 系统答非所问，你怎么判断是检索的问题还是生成的问题？**

方法很直接：**不看最终答案，单看检索结果**。

1. 正确段落有没有进 top K？**没进 → 问题在检索层**，换模型、改提示词都白费。
2. 进了但排第 8、而只取前 5 → 问题在排序或截断。
3. 进了前 3 还是答错 → 才轮到生成层。此时只保留正确段落再问一次：答对说明是被相似错误段落干扰，答错说明上下文理解或提示词有问题。

三个指标一起看，责任就分清了：**召回率**（正确文档进 top K 的比例）、**命中位置**（排第几）、**忠实度**（答案的断言能否在上下文中找到依据）。

经验比例：**八成问题在检索**。切分粒度过大导致相似度稀释、embedding 与领域不匹配、查询未做改写，这三类最常见。

## 六、软技能与坑点：可复用的两条

### 13. 技能：AI 产出的有效性验证

AI 让「产出数量」变廉价，于是质量判断变贵。会看数字的人容易被覆盖率骗。

- **变异测试**是当前最便宜的尺子：往源码注入小改动，看测试会不会红。注入 20 个变异只抓住 4 个，说明这批测试基本是摆设。
- **三种垃圾断言**：只断言不抛异常；断言与实现同义（实现错断言也错）；只判非空或类型。三种都能刷高覆盖率，但零拦截力。
- **分工原则**：人给定预期结果、AI 写代码；或 AI 写测试、人审断言。**AI 擅长写样板，不擅长判断什么是对的**。

### 14. 坑点：定级可谈，是不是 bug 不让步

与开发对 bug 定级有分歧时，先分清分歧类型：

- **事实分歧**（是否复现、是否环境问题）用证据解决：最小复现路径 + 请求响应与日志 + 出现频率（10 次里几次）。
- **口径分歧**（等级高低）回到定级标准：影响多少用户、有无资损、有无绕过手段、有无替代方案。把**业务后果**讲清楚，等级自然就清楚了。
- 仍不一致则升级到决策人，双方理由都记录，不单方面标注。

长期解法是团队有一份**带例子的公开定级标准**，并用真实 bug 定期校准。原则：**定级可以谈，但「是不是 bug」不让步**——前者是判断，后者是事实。

### 15. 坑点：Agent 的凭证不能用管理员

给 Agent 配管理员级别密钥图省事，测试时表现完美，直到某次输入诱导它执行批量删除，损失不可逆。

四道防线叠起来才叫可控：**最小权限专用凭证**（删除类只给标记删除）→ **破坏性动作二次确认且不可绕过** → **工具层限制作用域与单次上限** → **软删除与快照兜底**。

安全假设必须是「模型随时会判断错」——这不是不信任模型，而是承认概率系统的本质。
