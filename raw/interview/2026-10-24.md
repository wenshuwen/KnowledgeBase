## 一、面试题精选

### Q1：接口在网关上都做了统一鉴权，为什么还要单独测服务内部？

**答**：网关只覆盖「从外面进来」的流量，服务自身往往没设防。真实风险有三条：

- **内网横向移动**：边缘机器被拿下后，攻击者直接打服务端口，完全绕过网关；
- **服务间调用被伪造**：内部接口信任调用方传的用户标识（如 header 里的 `X-User-Id`），改一下就冒充别人；
- **新入口漏配**：定时任务、MQ 消费者、运维脚本直连服务，走的都不是网关。

**验证方法**：把服务端口映射到本地，**不带 token 直接请求核心查询接口**；再把身份标识改成别人的重放一次。

**判据**：每个入口都能**独立**拒绝未授权请求，而不是依赖上游已经验过。

> 归入方向：接口测试 / 安全测试 —— 「鉴权不是一层，是一条链」

### Q2：密码重置链路怎么测？哪些地方最容易被忽略？

**答**：按「申请—发送—校验—重置」四段拆，每段都有独立的攻击面：

| 阶段 | 关键检查项 |
|---|---|
| 申请 | 账号存在与否的响应差异（文案、状态码、耗时）→ 用户枚举；申请频率无限制 → 短信轰炸 |
| 发送 | token 是否可预测（自增 ID、时间戳、手机号哈希）；是否绑定用户、是否过期、能否复用 |
| 校验 | 用 A 的 token 重置 B 的密码；篡改 token 内的用户标识 |
| 重置 | **旧会话是否失效**（最常漏） |

**最易忽略的两点**：响应差异、旧会话不失效。功能测试全绿，安全上一查就是洞。

> 归入方向：安全测试 —— 「重置类链路的四段攻击面」

### Q3：限流怎么绕？只验「超过阈值返回 429」够不够？

**答**：不够。429 只证明计数器在工作，不证明拦得住人。五条绕过路径：

1. **伪造来源标识** —— 轮换 `X-Forwarded-For` / `X-Real-IP`；
2. **路径变体** —— 重复斜杠、大小写、结尾加点、URL 编码；
3. **切换维度** —— 同 IP 换账号，或同账号换分布式 IP；
4. **参数位置** —— 账号放 body / query / header，只对其中一处计数；
5. **并发突破** —— 「先查计数再自增」，并发时全部放行。

**判据**：不是「有没有 429」，而是**绕过尝试下实际成功次数是否被压住**。

> 归入方向：接口测试 / 安全测试 —— 「限流验证的判据设计」

## 二、知识点精选

### K1：密钥泄露的四个落点

1. **代码与配置**：业务代码、单测、脚本、Dockerfile 里的硬编码；
2. **前端产物**：打包进 JS 的第三方 key，发布即公开；
3. **日志与异常**：完整 URL 带 token、连接串被打印、APM 全量采集；
4. **镜像层**：构建时 COPY 后 `rm`，历史层仍可提取。

**排查顺序按暴露面从大到小**：前端产物与公开仓库 → 日志系统 → 镜像层。

### K2：最小权限账号的验证矩阵

按「账号 × 操作」逐格验证：SELECT / INSERT / UPDATE / DELETE / DROP / GRANT + 跨库读写。

三个高频问题：多个服务共用一个账号（含只读服务拿到写权限）、测试环境一律 root、废弃账号未回收。

**判据**：删掉某个库，业务应只挂掉依赖它的模块；全站崩说明权限没有隔离。

### K3：RAG 检索越权的三个断点

1. **metadata 过滤缺失** —— 写入时未打 tenant / 部门 / 密级标签，或查询时未按身份 filter。典型错误：前端过滤了文档列表，向量检索没过滤；
2. **权限变更不生效** —— 调岗、降密后旧 chunk 仍在索引中可被召回；
3. **多轮上下文残留** —— 上一轮召回的内容留在历史消息里，权限回收后仍被引用。

**验证方法**：用 A 的账号问只有 B 才知道的细节，并在对话中途回收权限观察后续轮次。

## 三、技能精选

### S1：鉴权链路穿透测试

**要点**：按「入口」而不是按「系统」验证鉴权。三类典型场景（均带可核对数字）：

- 直连服务端口不带 token 请求，期望 401/403；
- 篡改 `X-User-Id` 从 1001 改成 1002 重放，期望按真实身份拒绝；
- 构造伪造 MQ 消息投递，期望消费端校验来源与业务归属。

**工具**：Burp Suite、curl、kubectl port-forward。

### S2：Agent 高危动作的确认与回滚设计

**要点**：把「能做什么」和「能做多大」分开控制。

- **工具分级**：读 / 写 / 高危（删除、退款、发消息、改配置、批量）三级，高危必须人工确认并展示参数；
- **参数约束**：白名单只约束工具名是不够的，还要限金额上限、收款方白名单、操作对象归属；
- **可回滚**：写操作前留快照，批量操作尤其要。

**测试重点**：构造越权指令、超范围参数、批量请求，看三层是否都拦住。**判定看 trace，不看最终回答**。

### S3：渗透报告的分级与修复推动

**要点**：不按厂商等级排，按「可利用性 × 影响面」重排。

1. **根因合并** —— 多个条目常源于同一处缺失（如数据归属校验），修一处消一片；
2. **利用门槛** —— 是否需登录、角色、内网、用户交互；
3. **影响面** —— 能读多少条、能否写、能否横向。

**产出**：问题、根因、门槛、影响、修复成本、建议顺序，与研发共同确认。每条都要有可执行的验收条件（如「B 角色请求 A 的订单返回 403 且响应体为空」）。

## 四、坑点精选

### P1：只在网关验越权，不从内网直连服务

网关鉴权让人误以为「鉴权已覆盖全站」，所有越权用例都从外部域名发，永远发现不了服务自身没做校验。

**破解**：每轮固定加一组「绕开网关」用例 —— 直连服务端口不带 token 请求核心接口 + 篡改身份标识重放。两个动作各 5 分钟。

### P2：只测能不能进来，不测进来后能拿多少

拿到未授权访问就报「高危」，却不评估影响面 —— 是返回脱敏摘要，还是能导出几十万条身份证号。定级失真，要么过度反应，要么真问题被排到后面。

**破解**：每个越权缺陷补三问 —— 能读多少条、能读哪些字段、能不能写。用**影响面**而不是**漏洞类型**定级。

### P3：把 AI 代码审计的「无高危」当安全结论

扫一遍没报高危就写「已完成安全审计」，而工具漏报的往往是跨文件污点传播这类真正危险的模式，报出来的多半是低价值告警。这比不做审计更危险 —— 它给了虚假的安全感。

**破解**：先测**召回**（用注入已知缺陷的靶场代码看命中几个），再对报出的每条做**可利用性**复核。报告里写「工具覆盖范围 + 人工复核条数」，不写绝对结论。
