## 性能测试

### 1. 容量的三个交付口径

**Q：压到 TPS 8000、错误率 12%，这套系统到底能扛多少？**

- 8000 不是容量，是**打崩前的瞬时值**。失败请求往往比成功返回得更快，会把 TPS 抬高。
- 交付时给三条线一起定：**有效 TPS**（只算成功）、**错误率阈值**（一般 0.1%，核心链路 0）、**响应时间拐点**（P95 突抬的那个并发点）。
- 表述模板：「在错误率 0.1% 以内、P95 小于 500ms 的前提下，单机稳定承载约 N TPS，建议按 70% 做容量规划」，并注明数据量、机器规格、下游配置三个前提。

**判据**：给区间与前提，不给孤立的单点数字。

### 2. 拐点的三个判定信号

| 信号 | 表现 | 单独出现时的含义 |
| --- | --- | --- |
| TPS 走平/下降 | 加压后吞吐不再线性增长 | 可能只是抖动 |
| 响应时间拐点 | P95 从平缓突然抬升 2 倍以上 | 可能只是长尾波动 |
| 错误率抬头 | 超时、5xx、连接拒绝上升 | 可能是下游瞬时故障 |

三者**同时出现**才判定为容量拐点；拐点前最后一个稳定点才是可交付容量，通常再打 70% 折扣。

### 3. 平均值失真的三种形态

- **长尾被稀释**：1% 请求慢 10 倍，平均值只涨几个百分点。
- **双峰分布**：一半 10ms、一半 500ms，平均 255ms，但没有任何用户感受到 255ms。
- **样本量不足**：只跑 100 个请求，几个超时就把均值拉偏。

对策固定为：**平均值用于汇报，P50/P90/P99/P999 与直方图用于排查**。

### 4. 并发、RPS 与思考时间的换算

- **Little's Law：并发数 ≈ RPS × 平均响应时间**；含用户思考时间时为 **RPS ×（响应时间 + 思考时间）**。
- 漏掉思考时间，会把「800 并发」估成「只有几十个真正在发请求」，压测结论虚高。
- 反向使用：要验证「1000 并发下响应时间达标」，先算出对应 RPS，再用恒定 RPS 模式压，比直接 1000 线程硬怼更接近真实。

### 5. 数据库瓶颈的四个观测点

1. **慢查询**：按**总耗时**排序（不是单次耗时）——一条 20ms 但每秒 500 次的 SQL，危害大于偶发 2 秒的。
2. **活跃连接与锁等待**：大量 Sleep 但连接不降 = 泄漏；大量 Waiting for lock = 锁竞争。压测期间的 DDL 会伪造出「性能问题」。
3. **磁盘 IO 与刷盘**：写入瓶颈时 binlog sync、redo 刷盘是天花板，加索引无效。
4. **连接数上限**：max_connections 或代理层上限先满，表现为应用侧「获取连接超时」而数据库 CPU 很低。

**判据**：数据库 CPU 低 + 应用报连接超时 → 查连接池与连接生命周期，不要去看慢查询。

### 6. 深分页与索引失效的区分

- 两者都表现为「数据量越大越慢」，区别在根因：**深分页**是 `limit offset` 必须扫描并丢弃前 offset 行；**索引失效**是条件用不上索引（前导模糊、函数包裹字段、隐式类型转换、or 混用）。
- 共性判据：**看 explain 的 rows 是否随数据量线性增长**。
- 改法：游标分页（`where id > last_id`）或延迟关联；不要用「加机器」掩盖。

## 大模型与推理性能

### 7. 推理服务的四个核心指标

| 指标 | 含义 | 决定什么 |
| --- | --- | --- |
| TTFT | 首 token 时间 | 用户觉得「卡不卡」 |
| TPOT / ITL | 每 token 输出时间或间隔 | 用户觉得「流不流畅」 |
| 吞吐 | tokens/s、requests/s | 成本与容量 |
| 并发承载 | 在 TTFT/TPOT 达标下能服务多少请求 | 容量规划 |

四者互相制约：并发抬高通常牺牲 TTFT，batch 变大提升吞吐但拉长尾延迟。报告必须写「在什么并发下、达到什么指标」。

### 8. 非确定性输出的统计口径

- 三条处理：**控制变量**（固定 max_tokens、temperature=0、统一 prompt 长度）、**按 token 归一化**（报 tokens/s 与每千 token 耗时）、**分长度档给分位数**。
- 反例：A 单次 2.1 秒输出 38 token、B 单次 4.3 秒输出 180 token，按 tokens/s 折算后 B 反而更快（42 vs 18），结论会反转。
- 报告必须注明**输出长度分布**，否则不可比。

### 9. 流式与非流式的口径差异

- 非流式：一个完成时间点，看总耗时与 QPS。
- 流式：完成是一条曲线，必须按 chunk 计时，分别统计 TTFT、TPOT 波动、总时长、断流率。
- 三个实现坑：**不能等响应体读完才算完成**（否则测不出首字延迟）；**长连接占用并发额度**（1000 个流式并发 = 1000 条长连接）；**必须测客户端中途取消**，验证服务端资源是否及时释放。

### 10. RAG 端到端延迟的五段拆解

| 环节 | 经验耗时 | 备注 |
| --- | --- | --- |
| 查询改写 | 200~500ms | 可能含一次小模型调用 |
| Embedding | 50~200ms | 远程 API 更慢 |
| 向量检索 | 几十毫秒 | 多路召回会上升 |
| Rerank | 300~800ms | 重排 50 条候选，最易被低估 |
| 生成 | 几秒 | 通常占大头 |

不分层就优化，大概率会花一周优化只占 80ms 的检索。首字延迟与总时长必须分开报。

### 11. 上下文变长的三个连带影响

- **预填充**随输入长度增长；**解码**每步都要与全部历史做注意力，上下文越长每 token 越慢。
- **KV cache 随长度线性增长**，显存被吃满会压缩并发，吞吐断崖式下降——最容易被忽略的一条。
- 测试要按 4K/8K/16K/32K 分档给 TTFT、TPOT、单次成本，并测「刚好超长」时的行为（截断、报错还是静默丢弃）。

## Agent 与 AI 工具

### 12. Agent 性能的三层度量

| 层级 | 核心指标 | 用途 |
| --- | --- | --- |
| 任务级 | 完成率、端到端 P95、重试次数 | 用户感知 |
| 步骤级 | 平均步数、工具调用次数、每步耗时、无效步骤占比 | 成本与效率 |
| 资源级 | token 消耗、工具 API 调用量、并发占用时长 | 费用 |

Agent 慢的常见原因不是模型慢，而是**本可并行的工具被串行调用**，或在某个工具上反复重试。还要看**同任务重复执行的耗时方差**，方差大则难以做容量规划。

### 13. 并发 Agent 的隔离性验证

- **唯一标识法**：50 个任务各自在 prompt 内嵌唯一编号，结束后校验输出只含自身编号。出现交叉编号即判定上下文或结果绑定被污染。
- 常见根因：多 Agent 共用同一份 memory / session id；工具结果按「先返回先匹配」而非按调用 id 绑定；共享临时文件路径互相覆盖。
- **并发度-耗时曲线**：分别跑 1/5/20/50 并发，若 5 并发时单任务 P95 涨 3 倍，说明共享了串行资源（模型配额、工具限流），容量要按曲线拐点取。

### 14. AI 辅助瓶颈分析的可信边界

- AI 擅长**扩展排查思路**，不擅长**做最终判断**。
- 三条纪律：① 看是否引用具体 SQL / 方法名 / 占比，没有就是模板话术；② 按验证成本排序，先验 5 分钟能验的；③ 用监控数据反证，数据不支持就否掉。
- 警惕「正确但无用」的建议（加缓存、优化 SQL、加机器），它们在所有场景都成立，等于没给信息；涉及容量换算必须自己重算。

## 测试工程与协作

### 15. 环境保真度对结论的影响

| 差异维度 | 影响 | 是否可迁移 |
| --- | --- | --- |
| 机器规格 | 影响可承载并发 | CPU 密集场景近似线性 |
| JVM / 运行时参数 | 决定停顿与吞吐 | 不一致则 GC 类结论不可迁移 |
| 中间件规格 | 连接数上限、内存容量常先成瓶颈 | 不可迁移 |
| 网络拓扑 | 跨区、经代理增加往返与超时 | 不可迁移 |

结论表达用**单位资源效率**（如单核 TPS）比总量更可迁移，且必须标注哪些参数与生产不一致。

### 16. 超时重试与熔断的验证

- **量化放大倍数**：给下游注入 800ms 延迟，观察下游收到 QPS 是否从 1000 涨到 3000（3 倍放大即需治理）。
- **退避必须带抖动**：无 jitter 时所有客户端会在同一时刻重试，形成尖峰。
- **熔断验证两个边界**：打开是否及时、恢复是否放行探测；恢复瞬间全量打回同样是缺陷。
- **硬约束**：非幂等接口禁止自动重试，否则超时重试会导致重复下单、重复扣款。

### 17. 灰度期的性能判据

- 对比对象是**同流量下的旧版本对照组**，不是和昨天比（跨天比较受流量与数据差异干扰）。
- 卡点分级 1% → 5% → 20% → 50%，每级观察 10~30 分钟。
- 回滚条件要写死成数字与时长，例如「P99 超基线 1.5 倍持续 10 分钟」或「错误率超 1%」。
- 区分**冷启动慢**（JIT 未预热、缓存未填充）与**稳态慢**，前者等预热后再判。

### 18. 压测通过而线上故障的五个归因方向

1. **流量模型**：压测均匀流量 vs 线上脉冲式，开抢瞬间可达均值数十倍。
2. **数据量与分布**：库从百万级到千万级，同一条 SQL 的执行计划都会变；热点集中导致缓存击穿。
3. **下游真实性**：压测 mock 固定 20ms，线上 P95 400ms，超时率会从 0 直接升到 6%。
4. **资源共享**：线上与其他业务共用数据库/集群，压测环境是独占的。
5. **配置差异**：连接池、线程池、JVM 参数、限流阈值不一致。

**产出不是「下次注意」，而是把差异项逐条变成下一轮压测的场景清单。**
