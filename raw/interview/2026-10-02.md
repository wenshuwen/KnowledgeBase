## 一、性能测试

### Q：压测时 TPS 上不去、响应时间也不高，怎么定位？

**结论**：TPS 上不去但 RT 很低，典型是「压力没打到位」，先怀疑压测端而不是被测端。

排查顺序：

1. **压测机自身瓶颈**：CPU 是否跑满、是否只用了单机 JMeter、网络带宽是否打满、是否被 Linux 临时端口耗尽（TIME_WAIT 过多）。
2. **线程模型**：JMeter 线程数是否够、是否用了一问一答的同步模型（RPS 会被 RT 卡住），必要时改用 wrk / k6 或开多机分布式。
3. **服务端入口**：SLB 与 Nginx 的连接数与限流阈值、keepalive 是否关闭导致每请求建连。
4. **中间件水位**：线程池大小、DB 连接池、GC 停顿。

**判据**：压测机 CPU 低于 30% 而 TPS 封顶 → 先查端口耗尽或同步模型；服务端 CPU 很低、RT 也低 → 只是流量太小。

### 知识点：性能测试的三层指标体系

| 层次 | 核心指标 | 用途 |
|---|---|---|
| 业务层 | TPS、QPS、并发用户数、**业务成功率** | 业务是否真的成功（下单成功率比接口成功率真实） |
| 体验层 | RT 均值与 **P95 / P99**、超时率 | 均值被长尾掩盖，必须看分位 |
| 资源层 | CPU、内存、GC 停顿、磁盘 IO、带宽、DB 连接池与慢查询、MQ 积压 | 定位瓶颈在哪一层 |

**联动判断**：RT 抬头但 CPU 平稳 → 问题在等待（锁、IO、下游）；CPU 跑满 → 才考虑扩容或优化算法。

### 知识点：性能拐点与容量水位

- 阶梯加压（约 25% 递增），每级**稳定运行 3~5 分钟**再记录，画三条曲线：并发-TPS、并发-RT(P95)、并发-资源。
- 拐点 = TPS 增速放缓且 RT 开始非线性抬头的那一点。
- 水位取拐点的 **70%~80%**，再在该水位跑 8~24 小时看内存泄漏与 RT 漂移——长时间阶段才是真正暴露问题的阶段。

### 技能：性能测试方案设计与瓶颈定位

**目标三问**：容量水位在哪、瓶颈在哪一层、该怎么改。高级工程师的差别在证据链完整——指标、监控、线程栈、火焰图、SQL 执行计划能串起来。

- 常见工具：JMeter、k6、Locust、wrk、Grafana + Prometheus、Arthas、async-profiler。
- 关键动作：阶梯加压找拐点，绝不一步到位压高并发；压测数据要预热，否则第一轮全是冷启动噪声。
- 产出物：水位建议 + 优化项，而不是只报一个 TPS 数字。

### 坑点：只看平均响应时间，不看 P95 / P99

- **现象**：平均值被大量快请求拉低，掩盖长尾；用户体感差往往来自那 5% 的慢请求。
- **破解**：报告至少给出 P95 与 P99 并关注超时率；P99 超过均值 5 倍以上，说明存在排队、锁竞争或 GC 停顿，要单独定位。

## 二、数据库

### Q：缓存与数据库的一致性，怎么验证？

**结论**：一致性问题的本质是「写路径的顺序与时序」，测试要主动构造并发与失效场景。

1. **更新后立即读**：写库成功但删缓存失败 → 读到旧值；验证是否有补偿（延迟双删、消息重试）。
2. **缓存穿透**：查不存在的数据是否直穿 DB，验证布隆过滤器或空值缓存是否生效。
3. **缓存击穿**：热点 key 过期瞬间并发打 DB，验证互斥锁或逻辑过期是否生效。
4. **缓存雪崩**：大批 key 同时过期，验证过期时间是否加了随机抖动。
5. **并发更新**：两个写请求交错，验证最终值是否为最后提交的那个（避免旧值覆盖新值）。

**断言方式**：并发执行后比对「数据库真值」与「缓存值」，并观察是否出现长时间不一致。

### 知识点：读写分离下主从延迟对测试结论的影响

- **刚写入立刻查不到**：多半是读到延迟的从库，不是数据丢了。验证方式是写后立即读主库，再轮询从库直到可见。
- **自动化用例随机失败**：写入后马上断言，赶上复制延迟就红。应在断言前等待主从同步位点（对比 binlog 位点与从库执行位点），而不是固定 sleep。
- **脏缓存（最难查）**：写库成功 → 删缓存成功 → 读从库旧值又写回缓存。
- **压测结论失真**：写流量大时从库延迟上升，读接口 RT 抬高，容易误判为读性能差。
- **测试动作**：明确每个接口走主还是走从，把延迟纳入断言条件，并在报告标注结果是否受主从延迟影响。

### 坑点：用真实手机号、身份证、银行卡做测试数据

- **风险**：一旦造成真实用户被短信轰炸、被扣款，就是生产事故；数据泄露还要承担合规责任。
- **破解**：一律使用**符合校验规则但无效**的假数据（Faker 类规则 + 自写校验位算法）；手机号用测试号段；库表层面再加脱敏，导入生产数据必须先脱敏。

## 三、AI / Agent 测试

### Q：Agent 调用工具失败或超时，怎么做降级测试？

**结论**：核心是「不因为一个依赖挂掉就整条链路崩，也绝不假装成功」。故障注入场景：

- **超时**：验证是否重试、重试次数是否有限、是否最终给出明确失败提示。
- **报错**：区分可重试与不可重试；不可重试应立即停止而不是反复尝试。
- **脏数据**：字段缺失、类型不符、空结果——验证 Agent 是否会校验并拒绝使用，而不是硬编一个结果。
- **部分失败**：多工具流水线第 2 步失败，验证已完成步骤是否有回滚或补偿。
- **资源耗尽**：token 超限、步数超限、并发限流，验证熔断与降级话术。

**断言重点**：最终状态必须可解释（明确成功或明确失败），**不出现静默失败**——这是 Agent 最危险的失败模式。

### 知识点：RAG 的两层指标（检索层 / 生成层）

- **检索层**：Hit Rate（相关文档是否在 Top-K）、Recall、MRR / NDCG（排序质量）、上下文精确度（召回的噪声比例）。
- **生成层**：忠实度 Faithfulness、答案相关性、引用正确率（引用段落是否真的支撑结论）。
- **分层判断**：忠实度低 → 生成与 Prompt 问题；Hit Rate 低 → 分块、Embedding 或 Top-K 问题。
- **常见坑**：分块切断语义（表格、流程图被切开）、Top-K 太大引入噪声、文档更新未重建索引。
- **工具**：Ragas 可直接计算上述指标，适合接入 CI 做回归。

### 技能：Agent 轨迹测试与安全护栏验证

Agent 的能力来自「自主决策 + 调用工具」，风险也来自这里。只看最终回答会漏掉绝大部分问题。

- **轨迹断点**：工具选择、参数合法性、调用序列与次数、步数上限、终止条件、写操作幂等。
- **手段**：为工具做 Mock（可记录调用、可注入故障），精确断言调用序列；护栏必须在**代码层**强制，不能只写在系统提示词里。
- **成本维度**：统计任务成功率、平均步数、平均 token，并设阈值告警。

### 坑点：Agent 的重试没有上限，一次故障就让成本失控

- **现象**：工具持续报错时反复重试或在工具间来回试探，单任务步数从正常 6 步涨到上百步，token 成本成倍上升，用户侧表现为长时间无响应。
- **破解**：重试设硬上限与指数退避，区分可重试与不可重试错误；设置最大步数、单任务 token 预算与整体超时，超限即熔断并返回明确失败；把单任务步数与 token 分布纳入监控告警。

## 四、安全测试

### 技能：业务逻辑漏洞与攻击链验证

扫描器只理解技术模式，不理解业务不变量，而资损恰恰来自业务规则被绕过。

- **先列业务不变量**：金额非负、库存非负、优惠不可叠加、一人一单。
- **典型漏洞**：负数下单、只改前端价格、优惠券叠加、流程跳步（未付款直接发货）、重复领取、自己给自己审批。
- **方法**：针对每条不变量设计绕过尝试，用参数篡改与并发去冲击它——**不变量清单才是业务层安全测试的用例来源**。
- **工具**：Burp Suite、OWASP ZAP、Mitmproxy、JWT 调试工具。

## 五、测试环境与 CI/CD

### 坑点：测试环境直连第三方生产接口

- **风险**：真实调用短信 / 支付 / 物流接口，产生真实费用、骚扰真实用户，还可能被第三方风控封禁 IP 或封号。
- **破解**：测试与压测环境统一走挡板（WireMock 等）或第三方沙箱；对「发送类」接口在网关层强制拦截并留痕；挡板响应与服务商契约保持同步版本管理，避免「Mock 通过、真连失败」。开关类配置变更需同步给出回滚方案。

### 坑点：发布后只看到 HTTP 200 就认为部署成功

- **现象**：部署返回成功不代表页面与资源都更新到位。曾出现过「JS 是新版、CSS 块缺失」的半新半旧发布，页面样式全乱但接口仍是 200。
- **破解**：发布后做端到端核验——拉取关键静态资源与数据文件**比对哈希**（带时间戳绕过缓存）、检查核心交互是否可用、核对页面关键文案；把「部署成功」与「功能可用」拆成两个独立校验步骤。
