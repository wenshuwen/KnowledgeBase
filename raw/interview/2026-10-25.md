## 一、面试题精选

### Q1：测试什么时候能停？「测得差不多了吧」怎么回答？

**答**：先立一个前提——**穷尽测试不可能**，输入组合指数爆炸加上时间成本，任何项目都测不完。所以「停」是一个**风险决策**，不是技术结论。

三层回答结构：

| 层次 | 内容 | 判据 |
|---|---|---|
| 准出标准 | P0/P1 用例 100% 通过、新增需求覆盖率达标、遗留缺陷按严重级有上限 | 可逐条勾选，不靠感觉 |
| 残余风险 | 没测的是哪块、概率多大、影响是钱还是合规还是口碑 | 能写成三句话 |
| 停止信号 | 缺陷发现速率曲线走平、缺陷聚簇区域已覆盖 | 有趋势数据支撑 |

**表达要点**：不要只说「差不多了」，要说「还有 3 个 P2 没修、支付对账这块没覆盖，风险是会漏单，我建议先上但要加监控」。把依据给足、决策权交回去，这才是专业表达。

> 归入方向：测试理论 —— 「停止判据是风险决策，不是覆盖率达标」

### Q2：接口返回 200 就一定成功吗？断言怎么设计？

**答**：200 只说明 HTTP 这一层通了。断言要分四段：

1. **状态与结构** —— 状态码、业务 code、返回体 schema（字段名、类型、必填是否齐全）；
2. **数据正确性** —— 不和「我以为的值」比，而是和数据库或上游对账。金额、数量做**守恒校验**：下单前库存 100、下单 3 件，下单后必须正好 97；
3. **副作用** —— MQ 有没有发、审计日志有没有落、缓存有没有刷；这些接口不返回但业务依赖；
4. **负向断言** —— 不该出现的字段不能出现（手机号明文返回就是缺陷）、没权限的账号拿不到数据。

**最容易漏的一种**：200 + 空数据。列表接口返回空数组在协议上合法，但业务上「本该有数据却没有」是缺陷，必须靠**前置造数**来区分，否则这条用例永远是绿的。

> 归入方向：接口测试 —— 「断言的四段结构：状态、数据、副作用、负向」

### Q3：Agent 有写权限，能改配置、发消息、下单，怎么做安全验证？

**答**：核心思路是**验证「限制生效」而不是「它不会做」**——因为它一定会做出格的事，只是概率问题。

| 检查面 | 做法 | 判据 |
|---|---|---|
| 权限边界 | 拿它用的那个 token 直连接口，试越权访问未授权资源 | token 本身权限不能过大，否则上层限制是纸糊的 |
| 参数约束 | 白名单不只限工具名，还要限参数范围 | 退款金额上限、可退订单范围必须**服务端**校验 |
| 确认机制 | 高危动作（删除、退款、发外部消息）设人工确认点 | 不确认就**真的执行不了**，不是弹个框后端已经跑了 |
| 幂等与回滚 | 重试会不会重复下单、出错能不能回滚 | 失败后不留不可清理的中间态 |
| 注入穿透 | 在它读取的内容（网页、文档、邮件）里埋指令 | 不会被诱导去调高危工具 |

**验收标准写死一句**：即使模型完全被劫持，也不能产生不可逆的资金或数据损失。

> 归入方向：AI Agent 测试 / 安全测试 —— 「限制放在模型之外」

## 二、知识点精选

### K1：覆盖率的四种口径与各自的盲区

| 口径 | 要求 | 强度 | 盲区 |
|---|---|---|---|
| 语句覆盖 | 每行执行过 | 最弱 | 只证明跑过，证明不了判断走对 |
| 分支覆盖 | 每个 if 的真假都进过 | 中 | 覆盖不到条件内部的组合 |
| 路径覆盖 | 所有执行路径都走到 | 最强 | 循环与嵌套下组合爆炸，实际不可行 |
| 条件组合覆盖 | 复合条件里每个子条件的取值组合 | 较强 | 组合数随子条件数量指数增长 |

**四者的共同盲区**：没有断言也算覆盖。用例把接口调一遍、代码全绿，但一行断言都没写，覆盖率依旧能到 90% 以上。

**结论**：覆盖率是**下限指标**，低于阈值说明有代码没跑过，肯定漏；高于阈值只说明「没漏在这」，不说明「测对了」。要配合无断言用例统计或变异测试才有意义。

> 归入方向：测试理论 —— 「覆盖率是下限，不是质量结论」

### K2：「测过了」的三种含义：执行过、断言过、验证过

同一句「这条测过了」，在三种口径下含义完全不同：

1. **执行过** —— 用例跑了没报错。只能证明代码没崩，连功能对不对都不知道；
2. **断言过** —— 跑了并且对返回值做了断言。能证明返回值符合预期，但证明不了**副作用**（数据库、MQ、缓存）对不对；
3. **验证过** —— 返回值、副作用、边界、异常路径都被独立核对过。

**缺陷逃逸的常见根因**，就是把第 1 种当成第 3 种来交付。

**可量化的抓手**：统计**无断言的用例占比**，这个数不为零，说明「测过了」里有水分。评审时问「这条的断言写在哪儿、验了几个面」，比问「测了没有」有效得多。

> 归入方向：测试理论 —— 「测过了」的口径分级

### K3：Agent 失败分级——什么没做、做了一半、做错了

Agent 的失败不能只统计「成没成」，要按**副作用**分级：

| 级别 | 形态 | 副作用 | 容忍阈值 |
|---|---|---|---|
| 一 | 什么都没做，识别出做不到就停 | 无 | 可接受，体验差 |
| 二 | 做了一半，中途失败留下中间态 | 有，可清理 | 需要清理能力兜底 |
| 三 | 做错了且产生副作用（退了不该退的款） | 有，往往不可逆 | 接近零容忍 |
| 四 | 报告成功但实际没做 | 隐性，最危险 | **零容忍** |

第四类为什么最危险：它终结了人工兜底的机会，用户以为完成了，事后才发现什么都没发生。

**度量方式**：四类分开统计，后两类单独设阈值。单一成功率会把严重性完全抹平——85% 的成功率听起来不错，但如果 15% 里有 5% 是假报成功，实际风险远大于数字给人的感觉。

> 归入方向：AI Agent 测试 —— 「按副作用分级，而不是按成败二分」

## 三、技能精选

### S1：准出标准与风险接受单的设计

**要解决的问题**：准出标准写不清楚，发版就永远变成「谁嗓门大谁说了算」，而且是测试独自背锅。

**三件产出**：

1. **可判定的准出条件** —— 把「功能测试完成」拆成硬指标：P0 用例 100% 通过、P1 通过率不低于 98%、遗留 P1 缺陷为 0。发版前逐条勾选，不靠口头确认；
2. **未达标项的风险接受单** —— 每个未达标项写清：影响范围、触发概率、止损手段、责任人、有效期。由产品与研发共同签字，测试不单独承担决策；
3. **标准的定期复核** —— 质量水位变化后调整门槛，并记录调整依据与生效版本，避免标准变成一成不变的形式。

**配套工具**：准出检查清单、风险接受单模板、Jira 版本报告、质量看板、发版评审纪要。

> 归入方向：测试理论 / 沟通 —— 「让上线决策留痕」

### S2：接口异常注入与故障面覆盖

**要解决的问题**：正向用例谁都会写，接口真正的质量问题集中在异常路径；而线上故障九成出在异常路径。

**枚举方式**：按「谁可能出错」列，而不是按接口列——调用方传错、被调方处理错、下游超时或脏数据、中间件不可用、网络抖动。每一类至少一条用例，并明确期望行为（返回什么码、数据回不回滚、要不要重试），而不是只写「不崩」。

**典型注入场景**：

- 给下游注入 3 秒延迟 → 上游应返回 504 并带可重试标记，本地事务已回滚、无残留记录；
- 下游返回缺少关键字段的响应 → 上游应告警并降级为待确认状态，不能空指针 500，也不能静默当成功；
- 同一幂等键并发 20 次 → 数据库只产生 1 条订单，20 个响应里 19 个返回同一单号。

**配套工具**：Toxiproxy、WireMock、Chaos Mesh、pytest + responses、mitmproxy。

> 归入方向：接口测试 —— 「按故障面枚举异常路径」

### S3：Agent 失败模式的分级归类

**要解决的问题**：只报成功率的 Agent 评测是失真的，真正的事故几乎都藏在「假报成功」和「做错有副作用」里。

**落地方式**：

1. 采集完整 trace（每步的输入、输出、耗时），按四类打标；
2. **对每个声称完成的任务回查目标系统实际状态**——这是识别「假报成功」的唯一办法，不能看模型自己怎么说；
3. 单独构造「中途失败」用例，检查是否留下中间态、有没有清理任务兜底；
4. Dashboard 按类分项统计，后两类单独设阈值。

**配套工具**：Langfuse / Phoenix（trace 采集）、自定义失败分类表、人工标注评测集。

> 归入方向：AI Agent 测试 —— 「四类失败分开统计」

## 四、坑点精选

### P1：预期结果写「与上次一致」，等于没写预期

**坑在哪**：用例的预期结果写「返回和上一次一样」「数据正确」，执行时全靠人脑判断。这种用例既不能自动化，也没法交给别人跑，过一段时间连作者自己都说不清什么算通过。

**破解方法**：预期必须是**可判定的具体值或条件**——金额 100 变 80、状态从待支付变已支付、响应时间小于 300ms。写完自查一遍：这条用例的预期，能不能写成一行 assert？换个人来执行，结论会不会一样？

> 归入方向：测试理论 —— 「预期可判定是可自动化的前提」

### P2：备份每天成功，但从来没恢复过一次

**坑在哪**：监控上备份任务全绿，团队默认数据是安全的。真出事那天才发现备份文件损坏、版本不兼容、或者恢复要八小时，而承诺的恢复时间是半小时。

**破解方法**：把**恢复演练**放进季度计划，在隔离环境完整还原一次；核对比行数更细的指标（金额汇总、最大 id、外键完整性）；记录恢复耗时，用这个数字校准对外承诺。**没有演练记录的备份不算备份**，这句话要写进值班手册。

> 归入方向：数据库 / 测试环境 —— 「备份的价值不是有备份，是能回来」

### P3：只统计 Agent 的成功率，不看失败留下了什么

**坑在哪**：成功率 85% 写进汇报，看起来还不错。但那 15% 里有一部分是「做了一半留下脏数据」和「做错了但报成功」，实际影响远大于 15% 这个数字给人的感觉。

**破解方法**：按副作用分四类统计（没做、做一半、做错有副作用、假报成功），后两类的容忍阈值应该是零；专门构造「声称成功但目标系统无记录」的场景来识别假报成功。**单一成功率不能用于对外汇报**。

> 归入方向：AI Agent 测试 —— 「成功率要拆，副作用要数」
