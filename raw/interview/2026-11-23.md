## 一、多 Agent 链路上的消息契约

单点都对、整体错，多半错在传递：丢了没人发现、重发了没人拦、乱序了拿旧结果下判断。

### 1. 题：三个 Agent 串起来，怎么测消息没丢、没乱序

**Q：规划、执行、校验三个 Agent 串起来做一件事，你怎么验证它们之间的消息没丢、也没乱序？**

先把契约钉死：每条消息必须带**角色、意图、载荷、追溯 id** 四样，再加**单调序号**与**幂等键**。然后分三层测：

| 层次 | 做法 | 期望 |
|---|---|---|
| 单跳契约 | 畸形载荷打一遍（缺字段、类型错、枚举越界） | 明确拒绝，不静默降级 |
| 多跳顺序 | 混沌层把某步延迟 0.5~3 秒、复制 5% 消息 | 校验方识别序号倒挂并等待，不用旧结果下判断 |
| 缺失与重复 | 丢 1 条、重发 1 条 | 靠序号发现缺口并重放，重发不产生第二条副作用 |

**判据**：凭 trace id 能拼出完整链路；重发不产生第二条副作用；最终状态与单 Agent 直跑逐字段一致。

### 2. 知识点：消息契约的四要素

1. **追溯 id**：贯穿全链路的 trace id，跨进程、跨语言都要能串上。
2. **单调序号**：同一会话内递增，缺号即缺口，不靠时间戳（时钟漂移会骗人）。
3. **幂等键**：由业务语义生成，重投时下游能识别「这条我处理过」。
4. **状态机约束**：哪一步允许被重放、哪一步只允许前进不能回退，要显式定义。

四者缺一，对应的失败模式就是「查不出、判不出、去不掉重、说不清」。

### 3. 技能：多 Agent 协作链路的可观测验证

核心思路是**先让它可见，再谈断言**。

- 每条消息打 trace id + 单调序号 + 幂等键，落成可查询链路；
- 测试对象是契约与链路，不是「最终答案看起来对」；
- 混沌注入必须可控可复现：固定 seed、固定丢包比例，否则跑不出结论；
- 对账口径固定为「最终状态与单 Agent 直跑结果逐字段比对」。

常用工具：OpenTelemetry（链路埋点与上下文传播）、LangSmith / Langfuse（Agent 调用链与中间步留痕）、Jaeger（分布式追踪查询）。

## 二、Agent 的记忆与缓存

记忆和缓存的共同点是**写进去容易，错在里面很难发现**。

### 1. 题：Agent 把临时结论写进长期记忆，后面几轮一直带着错前提

**Q：Agent 有长期记忆，它把中途的临时结论也写进去了，后面几轮都带着这个错前提往下走，怎么测？**

核心是**写入准入**，不是「发生过就记住」。三条最小规则：只写用户明确确认的事实（带来源消息 id 与时间戳）、不写推测与临时中间态、冲突时以最新确认覆盖并保留旧值可追溯。

用例怎么造：

1. 先说「按月统计」，第三轮改「按周」→ 期望只留「按周」，旧值可查到是谁改的；
2. 让它自己编一个工具没返回过的结论 → 期望不落库。

**判据落在 dump 出来的记忆上**：跑 10 轮后条目数不超过预期、无「推测」类标记、每条都能追到来源消息。只测第一轮准确率是测不出这个问题的。

### 2. 知识点：记忆写入的四条准入规则

1. 只写**已被确认**的事实，推测与中间态不落库；
2. 每条记录带**来源**（消息 id、工具调用 id）与时间戳，能追溯也能撤回；
3. 同一事实冲突时以最新确认覆盖，**旧值保留为历史**而非直接删除；
4. 写入有**配额与去重**，避免同一结论反复写入把上下文挤满。

最常见缺陷是「写了但没来源」——等到要回溯为什么它记住了错误前提，无从下手。

### 3. 坑点：记忆写了就不管来源

**现象**：记忆条目越多越像「懂业务」，实际上没有任何一条能追到是哪句话、哪次工具返回让它记住的。
**破解**：把「可追溯率」做成指标（有来源的条目 ÷ 总条目），低于阈值即视为缺陷；写入路径上强制带来源字段，缺失就拒写，而不是事后补。

## 三、Agent 的完成度判定

「做完了」是模型的一句话，不是事实。要把这句话变成可核对的证据。

### 1. 题：Agent 说完成了，其实只做了一半

**Q：Agent 回「任务完成了」，但实际只做了一半。你怎么测它的完成度判定？**

把「完成」从模型的一句话变成**可核对的证据**：给每类任务定义验收条目，要求结束时输出「做了哪些动作 + 每条验收对应的证据」（文件路径、接口返回、测试结果摘要），测试侧只认证据不认声明。

两个方向的用例：

- 故意让它少做一步（只生成代码没跑测试）→ 期望自报未完成，或证据缺失被外层拦下；
- 给它一个「假成功」返回（HTTP 200 但 body 是错误码）→ 期望它识别成失败。

**判据**：20 个任务里「声称完成但证据不全」的比例为 0。这个数比问它「你觉得完成了吗」可靠得多。

### 2. 技能：AI 产出的可追溯与可核验

- **可执行**：生成的定位器、脚本、用例当场跑通才入库；
- **可核对**：结论要带行号、字段名或请求标识，只说「可能有问题」等于噪声；
- **可度量**：注入已知缺陷算召回率与误报率，按缺陷类型看分布，召回低的类型只做提示不做门禁。

### 3. 坑点：Agent 的完成声明当成事实

**现象**：回一句「已完成」就认为成功，实际上只生成了代码没跑测试，或调用的工具返回错误码它没看；等下游用到产物才发现是半成品。
**破解**：完成度 = 验收条目 + 证据。测试只认证据，并专门造「少做一步」和「假成功返回」两类用例，看它会不会自报未完成。

## 四、评测集与结论的可靠性

模型评测的两类致命错误：尺子本身不准、把噪声当提升。

### 1. 知识点：标注一致性与评测集可信度

多人独立标同一批样本，算 Cohen's Kappa（两人）或 Fleiss' Kappa（多人）。**0.6 以下**说明口径本身有分歧，此时模型分数再高也只是拟合了某个人的偏好。

配套还要看四项：类别比例是否与线上一致、有无重复样本、与训练集是否重叠、难易分桶是否均衡。任何一项失守，**先修数据再调模型**。

### 2. 技能：评测集质量与差异显著性

先确认尺子准不准，再谈模型好不好——否则 3 个点的提升可能只是噪声。

- Kappa 低于 0.6 先修数据，别调模型；
- 评测集类别比例要与线上对齐；
- 同批样本比较用**配对检验**，不用两个独立比例；
- 分歧样本逐条看，那里藏着新缺陷模式。

操作口径举例：3 人标 200 条得 Kappa 0.52 → 先统一口径重标；线上 88% 是简单问题而评测集只占 30% → 按线上比例重采样对照集，两份分数差超 15 个点即说明评测集偏离；两个模型在 1000 条上 82% 与 85%，配对后「B 对 A 错」38 条、「A 对 B 错」8 条 → 才够得出显著结论。

### 3. 坑点：拿一个总分当模型结论

**现象**：准确率 90% 就认为可上线，没看样本构成、标注一致性与难易分布；上线后线上反馈很差，因为线上 60% 是评测集里几乎没有的多轮追问。
**破解**：分数必须配三样——标注一致性（Kappa）、类别比例与线上的偏差、分桶后的分数。上线决策看**高风险类目**的分数，不是总分。

## 五、环境差异与执行面

「环境不一样」是最常见的甩锅理由，也是最容易变成可核对项的地方。

### 1. 知识点：环境变量优先级链与覆盖排查

典型顺序：进程环境 > CI 平台注入（secrets 优先于普通变量）> 项目 .env > 镜像默认值。各家平台不完全一致，不能靠记忆。

**排查手法**：把「变量名 + 来源 + 是否被覆盖」打成指纹，本地与流水线各跑一次对照。最隐蔽的坑是 .env 被打进镜像，把 CI 注入的凭据悄悄替换掉——表现为连对了地址但权限报错。

### 2. 技能：环境指纹与差异定位

把「环境不一样」从口头解释变成可核对的指纹比对。

- 启动时自动采集指纹（版本号、关键参数、变量来源、依赖清单），不靠人记；
- 基线用**生产环境的真实值**，不是文档里的值；
- 差异要能定位到具体变量与其来源；
- 自检失败**阻断**回归，而不是记一条日志。

### 3. 坑点：环境差异用口头解释

**现象**：本地绿灯、流水线红灯，结论是「环境问题」，然后各自散去，下一轮同样卡在这里。
**破解**：把指纹比对做成回归的前置步骤（不一致直接红灯），差异表随失败报告一起输出。解释变成数据后，这类争论基本消失。
