## 一、面试题精选（3 条）

**Q：你们怎么落地测试左移？别讲概念，讲具体做了哪几件事。**

落到工程上通常就三件事。一是需求评审带测试用例骨架去，评审时就把验收条件和边界摆出来，大量歧义在这一步消掉；二是接口契约先定后写，前后端在编码前对齐字段、错误码、分页方式，联调阶段吵的次数明显下降；三是单测与静态检查进提交门禁，让问题在提交那一刻暴露而不是等到提测。判断左移是否真的有效，看一个指标就够：提测后第一个版本就被打回的缺陷占比。左移做得好，这个占比会下降，因为大量问题在编码前就被挡住了。左移的关键不是流程名词，而是把质量活动落到具体的检查点上。

**Q：幂等性接口，测试上你会重点验证什么？**

幂等不只是「调两次结果一样」，要验四个点。其一，重复提交只产生一次副作用——同一个请求 ID 连发三次，库存只扣一次、订单只生成一条。其二，响应一致性——重复请求返回首次结果还是重复提交错误，两种都可以，但必须与接口约定一致、不能随机。其三，并发下的幂等——两个请求几乎同时到达，靠串行测试永远测不出来，必须用并发工具同时打。其四，幂等键的边界——键为空、键过期、用别人的键，这些异常路径最容易被漏掉。核心认知：幂等在串行测试里永远是好的，只有并发才暴露它其实没生效。

**Q：需求紧急、明天上线，只来得及测一遍，你怎么安排？**

时间不够时，测试的价值体现在排序而不是全测。先划核心链路，这次改动影响的用户主路径必须一条不漏；再按「影响面 × 出错概率」排优先级，改动大、逻辑复杂、历史高发的先测，纯展示无逻辑的放后面；能用接口层批量覆盖业务逻辑就不要走页面，接口比 UI 快得多也稳得多。最关键的一步是明确写出「这次没测什么」——把未覆盖范围与对应风险显式列出，请产品或主管确认接受，而不是自己默默承担。上线出问题时，白纸黑字的风险清单既保护自己也推动团队正视取舍。测试不能保证没有风险，只能保证风险被看见。

## 二、核心知识点（3 条）

**1. 准出标准的五个维度**

「测完了」不能靠感觉，用五个维度给准出设闸。覆盖维度：需求点覆盖率，以及需求之外补充的异常场景是否覆盖；质量维度：用例通过率、未关闭缺陷的等级分布；回归维度：核心链路是否全绿、本次改动影响范围内用例是否都跑过；性能维度：关键接口响应时间与吞吐是否达到基线；风险维度：已知未修问题与未覆盖范围，是否已列出并被业务方确认接受。要点：准出是「风险已知且被接受」，不是「零缺陷」。把遗留风险摆到台面上请业务确认，比追求零缺陷更现实也更负责。

**2. 鉴权形同虚设的五种写法**

越权能得手，往往是鉴权「写了但没生效」，常见的失效写法有五：只在网关鉴权，服务之间内网互调时却默认可信；只校验身份不校验归属，确认了「你是登录用户」却没确认「这条资源是不是你的」；前端控权，按钮藏了菜单灰了而接口没做校验；信任前端传值，身份、角色、金额、状态由请求体传入且后端照单全收；令牌校验不完整，只验签名不验有效期，已登出或已吊销的令牌仍可用。要点：鉴权要问三句——在哪儿校验、校验了什么、能不能绕过。只看页面表现等于没测。

| 失效写法 | 验证手段 | 判据 |
|---|---|---|
| 只在网关鉴权 | 绕过网关从内网直连服务 | 服务自身能否拒绝无凭据请求 |
| 只验身份不验归属 | 替换资源 ID 打接口 | 非所属资源是否被拒 |
| 前端控权 | 隐藏入口后直接构造请求 | 接口是否独立校验 |
| 信任前端传值 | 篡改请求体中的身份/金额字段 | 后端是否忽略前端传值 |
| 令牌校验不完整 | 用过期或已吊销令牌访问 | 是否被拒绝 |

**3. RAG 的两段式评估口径**

RAG 的答案质量由「检索」和「生成」共同决定，必须分段评估。检索段看召回率（该召回的有没有召回）、准确率（召回的有没有无关内容）、切片质量（关键知识有没有被切断），这一段决定回答上限；生成段看忠实度（是否严格基于检索内容、不引入范围外事实）、抗干扰（拿到无关上下文会不会被带偏）、拒答能力（该说不知道时是否老实说）；端到端看整体准确率、幻觉率、拒答率。要点：答错先分层定位——召回错是检索或切片问题，召回对但答错是生成问题。不分段就会出现「明明检索没问题却一直在调模型」这种低效排查。

## 三、测试技能（3 条）

**1. 测试策略制定与风险排序**

在有限时间和人力下判断「该重点测什么、可以少测什么」，并把风险显式摆出来。常用工具/方法：需求评审、风险矩阵、用例分级、思维导图。要点：先按「业务影响 × 出错概率」排风险，而不是按功能顺序平推；把不做或少做的部分显式写进策略，风险要摆在明面上；策略随进度滚动更新，不是评审时定完就锁死。这一项是高级测试工程师与普通测试的分水岭——全覆盖是伪命题，策略的本质是做取舍并把取舍讲清楚。

**2. Agent 轨迹与工具调用验证**

从「结果、轨迹、副作用」三层验证 Agent 行为，重点覆盖工具失败与终止条件。常用工具：LangSmith、LangFuse、OpenTelemetry，以及可注入失败的 mock 工具服务。要点：断言工具调用顺序与参数正确性，而非只看最终输出；每个工具路径都要有失败注入用例，主动验证容错；必须设置步数与重试上限并验证其真的生效。Agent 的产出是一串动作与状态变化而不是一段文本，只看最终答复会漏掉大量过程风险。

**3. AI 辅助测试工具的效果评估**

用对照实验与量化指标判断 AI 测试工具是否真的提升效率，而不是凭感受下结论。常用工具/方法：用例生成工具、代码辅助工具、缺陷预测、指标看板。要点：先定指标（有效率、召回增益、成本）再做实验；必须设人工对照组，否则无法排除任务难度差异；把复核成本算进去，生成一堆需要重修的内容是负收益。价值公式：AI 测试工具的收益 = 多发现的缺陷 + 省下的时间 − 校验与维护成本，四项不量化，PoC 永远得不出结论。

## 四、面试坑点（3 条）

**1. 把「用例都执行完了」当成测试做完了**

执行完用例只说明走完了流程，不代表需求被真正理解、盲区被覆盖。用例本身可能就漏掉了一整类场景，执行得再整齐也只是把漏测跑了一遍。破解：结项时多问一句「需求里还有哪块我没测到」，把未覆盖部分显式列出，而不是用「用例全过了」掩盖。

**2. 接口测试看到 200 就断言通过**

HTTP 200 只代表请求被成功处理，业务可能已经失败——业务码是错的、数据没落库、状态没流转，看状态码全都「通过」。破解：断言必须穿透到业务层，业务码、关键字段值、必要时查库确认副作用；把「响应成功」和「业务成功」当成两件事分别验。

**3. Prompt 改动不走版本和回归**

Prompt 能改变线上行为，却经常被当成「改个文案」随手改掉，试完忘记回退，线上跑着没人评审过的版本，出问题也追溯不到改了什么。破解：Prompt 按代码变更管理——版本化留存、过评测集回归、灰度上线、可热回滚；后台可改必须配套版本记录与权限，避免无人评审的版本长期在线。
