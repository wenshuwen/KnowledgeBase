## 一、面试题精选（3 条）

**Q：线上偶发慢查询，测试环境完全复现不出来，你会怎么排查？**

先把「复现不了」转成「差异可控」，而不是反复在测试环境重试。步骤是：先列环境差异（数据量级、索引统计信息、并发数、参数配置、是否有其他负载）→ 用 `explain` 看执行计划 → 把测试环境数据量灌到同一量级对比执行计划是否变化 → 执行计划一致但线上仍慢时，看扫描行数与回表次数。同时临时调低慢查询阈值抓现场，拿到真实 SQL 与执行时长再决定优化手段。

**Q：Linux 上你排查服务 CPU 飙高的第一组命令是什么？**

标准套路是「先全局后局部」：`top` 看整体负载 → `top -H -p <pid>` 展开线程 → 十六进制 tid 去 `jstack` 匹配栈。若 CPU 空闲但负载高，优先怀疑 IO 瓶颈，用 `iostat -x 1` 看 %util 与 await，配合 `free -m`、`vmstat 1` 看内存与上下文切换。核心是先定位到进程和线程再谈优化。

**Q：MySQL 四种隔离级别分别解决什么问题？**

读未提交有脏读；读已提交解决脏读但可能不可重复读；可重复读保证事务内多次读取一致，但间隙锁外仍有幻读可能；串行化最严格并发最低。MySQL InnoDB 默认可重复读，且通过间隙锁（next-key lock）在很大程度上抑制幻读 —— 面试里说「默认级别能防幻读」时补一句「靠的是间隙锁而非 MVCC 本身」，这个细节能拉开差距。

## 二、核心知识点（3 条）

**1. 执行计划里最该看的三个字段**

`type` 判断访问类型（const / ref / range / index / ALL，出现 ALL 即全表扫描，需结合扫描行数判断）；`rows` 是预估扫描行数，与实际差距大说明统计信息过期；`Extra` 重点盯 `Using filesort` 与 `Using temporary`，出现即意味着额外排序或临时表。

**2. 内存排查里最容易被误读的两个指标**

`free` 值低不等于内存不足 —— Linux 会把空闲内存用作缓存，应看 `available` 列；CPU 使用率与负载不是一回事，负载高常因等 IO 或等锁而非 CPU 不够，必须把 CPU、IO、上下文切换三个维度一起看。

**3. SQL 优化的固定排查顺序**

先看执行计划确认是否走索引 → 看扫描行数与回表次数判断索引质量 → 看排序与临时表（能用覆盖索引消掉最好）→ 看返回行数是否远超需要 → 最后才考虑改表结构与分库分表。把低成本手段先用完，避免把简单问题复杂化。

## 四、面试坑点（3 条）

**1. 用测试环境的执行计划直接推断生产表现**

测试库数据量小，优化器往往选全表扫描反而更快，于是测试看不出问题，上量后执行计划切换、扫描行数暴涨才暴露。
→ **破解**：性能相关用例必须把数据量显式参数化，至少小中大三档，观察趋势而不是只看单点结论。

**2. 接口返回 200 就认为功能正常**

很多系统把业务失败包在 200 的响应体里，只看状态码会漏掉大量异常分支。
→ **破解**：断言要同时校验状态码、响应结构、业务码和关键字段取值，形成多层断言。

**3. 自动化用例不稳定时用重跑当通过**

不稳定用例会让红灯失去意义，团队逐渐忽略失败，真实缺陷也会被一起放过。
→ **破解**：把失败分类为「用例问题」与「产品问题」，前者必须修稳定性；重跑机制要保留首次结果不覆盖。
