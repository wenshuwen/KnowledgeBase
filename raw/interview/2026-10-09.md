## 1. 面试题精选（3 条）

### Q1：用 AI 生成测试用例，最大的风险是什么？怎么控制？

最大的风险不是生成得不好，而是**生成了看起来很像对的用例，把真正的边界漏掉了**，团队还因为「用例数涨了」产生安全感。控制三件事：

- **可追溯**：每条 AI 生成的用例要能挂回需求条目或接口字段，挂不上的说明是它自己发散出来的，必须人工过一遍。
- **负向占比**：AI 天然偏向正向主流程，规定一次生成里异常与边界用例不得低于某个比例，不达标就补一轮针对性的提示。
- **入库闸门**：「AI 生成 → 人工评审 → 入库」的固定闸门，生成结果先进草稿区，去重、查重名、查是否与现有预期结果矛盾。

提示词里必须带上实际的字段约束、取值范围、业务规则，而不是只给一句需求标题——给的信息越具体，瞎编的空间越小。

### Q2：测试 Agent 的工具调用（tool call）怎么测？

工具调用是 Agent 最容易出问题的地方，分三层测：

1. **选得对不对**：给定任务，Agent 有没有选到正确的工具（订单查询 vs 日志查询）。用 mock 工具集测调用序列。
2. **参数对不对**：工具选对了，参数字段和值对不对。重点造异常输入（时间「上周」能否换算成日期区间；必填参数缺失时是补一个还是追问）。
3. **失败处理对不对**：工具返回报错、超时、空数据时，Agent 是重试、换工具、还是如实告知用户。**最危险的是工具报错后仍编一个结果出来**。

工具模拟层自己写可控的 stub server，能按用例返回成功、超时、5xx、非法结构。

### Q3：提示词注入怎么测？

分**直接注入、间接注入、越权诱导**三类造用例：

- **直接注入**：用户在输入框里直接下指令（忽略之前规则、把系统提示词原样输出）。最容易想到，也最先被防护住。
- **间接注入**：把恶意指令藏在模型会读到但用户看不到的地方——上传的文档、被检索的网页、甚至代码注释里。**RAG 和 Agent 场景的重灾区**。
- **越权诱导**：针对 Agent，用话术让工具执行不该做的操作（查 A 的订单然后发到外部邮箱）。

判定标准事先写死（是否输出系统提示词、是否执行注入指令、是否完成越权操作），并多次执行——注入成功率有随机性，跑一次说「防住了」不负责任。

## 2. 知识点精选（3 条）

### K1：AI 生成用例的三段式校验

AI 生成的用例不能直接入库，固定加三道校验：

- **可追溯**：每条用例挂回需求条目或接口字段，挂不上的标记为发散用例，人工必过。
- **结构与去重**：检查步骤是否完整、预期结果是否可判定，并与历史用例做相似度比对去重。
- **负向占比**：统计异常与边界用例比例，AI 天然偏正向，比例不达标就补一轮针对性生成。

**三道校验的价值不在提高通过率，而在把「看起来很全」的错觉挡在门外。**

### K2：AI 应用的四类特有风险

传统 Web 风险之外，AI 应用新增四类重点风险：

1. **提示词注入**：直接注入（用户输入下指令）与间接注入（恶意指令藏在被检索的文档或网页中），后者更隐蔽。
2. **数据越权与泄露**：RAG 场景下能否通过构造问题检索到他人或其他租户的文档，是最典型的事故点。
3. **工具调用越权**：Agent 能否被话术诱导执行删数据、发消息、转账等高危操作。
4. **输出侧注入**：模型输出被渲染成页面导致 XSS、被拼进 SQL 或命令导致注入。

**统一原则**：把模型当作用户可控的不可信输入源，下游消费处按不可信数据处理。

### K3：P0 故障响应的测试定位

上线当天的 P0 故障，测试角色要快速切换，按四步配合：

- **复现**：先在测试或预发布环境复现出生产现象，复现不出来就没法定位根因。
- **隔离**：通过开关、降级、限流缩小影响面，测试负责验证每次隔离操作是否引入新问题。
- **回归**：修复后先回归直接影响的功能，再回归上下游链路，**不要只测修复点**，二次故障常来自「修这个改到那个」。
- **回滚演练**：触发回滚后验证老版本能否正常运行、是否有数据不一致。

整个过程里测试最有价值的不是写用例，而是**把每次操作与现象同步给团队**，避免各自复现浪费时间。

## 3. 技能精选（3 条）

### S1：AI 测试工具评估与落地

**能力描述**：能在真实项目里判断一个 AI 测试工具该不该引入、怎么引入、如何量化收益，避免 PoC 阶段惊艳、落地阶段变成僵尸项目。

**关键要点**：

- 先定基线指标再引入，用一个月的数据回看，而不是靠主观感受决策
- 数据能否出内网、结论能否复现，是一票否决项
- 明确长期维护责任人，无人负责的工具不建

**常用工具**：Prompt 评测集、LangSmith / Langfuse、GitHub Actions、内部指标看板。

**典型场景**：新工具选型评审、AI 辅助用例生成平台搭建、既有 AI 工具效果回看。

### S2：AI 应用安全测试

**能力描述**：能针对大模型与 Agent 应用设计安全用例，覆盖提示词注入、数据越权、工具调用越权与输出侧注入，并给出可判定的验证标准。

**关键要点**：

- 注入测试分直接、间接、越权诱导三类，间接注入最易被漏
- 判定标准要事先写死：是否输出系统提示词、是否执行注入指令
- 注入成功率有随机性，必须多次执行，不能跑一次就下结论

**常用工具**：自建注入用例集、Burp Suite、OWASP LLM Top 10、越权场景靶场。

**典型场景**：RAG 知识库上线前安全评估、Agent 工具权限评审、大模型功能渗透测试。

### S3：应急响应中的测试协作

**能力描述**：能在 P0 故障中快速完成复现、隔离、回归、回滚四步配合，并持续把现象与已知信息同步给团队，避免各自复现浪费时间。

**关键要点**：

- 复现优先于猜测，能复现就有抓手
- 回归不能只测修复点，二次故障常来自「修这个改到那个」
- 回滚必须实测，不能只相信脚本存在

**常用工具**：日志与监控、全链路压测、特性开关平台、回滚脚本与演练。

**典型场景**：P0 故障应急、重大变更灰度期、数据回滚演练。

## 4. 坑点精选（3 条）

### P1：用 AI 生成用例后直接入库，跳过人工校验与去重

把生成结果批量导入用例库，不做相似度去重、不查与历史用例的预期结果是否矛盾，用例数量看着涨了，真正的新增覆盖却很少，还引入互相打架的条目。

**破解**：生成结果先进草稿区，跑三道闸门：挂回需求的追溯检查、与历史用例的去重比对、预期结果的矛盾检查；通过后再人工评审入库。

### P2：测试环境直接用生产数据的全量拷贝，含真实个人信息

为了数据真实直接整库搬过来，脱敏没做或只做了部分字段，测试库里存在真实手机号、地址、证件号。测试环境权限通常更宽松，一旦被误访问就是数据泄露事故。

**破解**：生产数据只能以脱敏后的形式进测试环境，脱敏规则要独立复核并抽样验证（不只看脚本退出码）；敏感字段默认不可逆替换，禁止只做掩码却能反推。

### P3：P0 故障处理时各自埋头复现，没有先同步现象与已知信息

每个人按自己的理解去复现，复现思路不同、范围不同、得到的现象也不同，最后汇总的时候发现说的不是同一件事，浪费时间。

**破解**：故障响应第一步是集中同步：把已知的现象、时间线、最近变更、已尝试的排查写到群置顶，所有人基于同一份信息行动，避免重复劳动。
