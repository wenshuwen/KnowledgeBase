## 一、环境能不能代表线上：可核验的判据（env / theory）

### 1. 题：「机器配置一样，TPS 只有五分之一」的定位顺序

**Q：测试环境和线上机器配置一致，压测 TPS 只有线上五分之一，从哪里开始查？**

不要从「代码有没有性能问题」开始，先按**三段顺序**排除环境侧因素：

| 顺序 | 检查项 | 判据 |
|---|---|---|
| 1 | 容器 CPU 配额是否限流 | `cpu.stat` 的 `nr_throttled` / `throttled_time` 持续增长即配额不足 |
| 2 | 连接池与线程池默认值 | `池上限 × 副本数` 是否小于压测并发数 |
| 3 | 硬件代际差异 | 老机器单核性能低 20%~30% 属正常区间 |

关键认知：**CPU 使用率 40% 不等于没到瓶颈**——使用率按宿主机核数计算，配额只有 1 核时线程仍在排队。

> 结论口径：三段都排除后才允许怀疑代码；反过来，只要第 1 段命中，后面所有性能结论都不成立。

### 2. 题：「测试 50ms、线上 3 秒」为什么不是同一件事

**Q：同一条 SQL 在测试库 50 毫秒，线上要 3 秒，怎么解释？**

执行计划由三个输入决定：**统计信息**（行数、字段区分度）、**数据分布**（某值占比 1% 还是 90%）、**数据库版本**（优化器规则随版本变化）。小数据量环境里优化器倾向走索引，大数据量下同一索引反而更慢，优化器改走全表扫描。

验证方式是比 `explain` 的 `rows` 估算，而不是比耗时：

> **测试环境测出的「慢」可以参考，测出的「快」不能证明线上快。** 两者不可比时，结论只能是「测试环境通过」，不能是「线上无风险」。

### 3. 题：mock 与真实接口的契约漂移怎么防

**Q：上游在测试环境是 mock，怎么保证 mock 不偏离真实接口？**

mock 的固有风险是**它永远返回你想要的结果**，所以必须把契约本身当成被测对象：

1. **单一来源**：mock 由 OpenAPI / pact 生成，禁止手写响应 JSON；
2. **定期录制真实响应**，做结构比对，比对点固定四个：字段名与层级、字段类型、必填与枚举、错误语义；
3. **错误分支也要造**：只返回 `200` 的 mock 等于没测错误路径；
4. **契约变更即用例变更**：契约比对先红，用例跟着改。

## 二、知识点：把环境差异显式化（env）

### 4. 环境保真度的六个维度

判断测试环境能否代表线上，不看「像不像」，看六项可勾选：

| 维度 | 典型差异 | 影响面 |
|---|---|---|
| 版本 | 应用提交、中间件大版本、OS | 行为与性能结论 |
| 配置 | 池大小、超时、开关、字符集 | 功能与容量结论 |
| 数据 | 量级、分布、脏数据比例 | 性能与边界结论 |
| 拓扑 | 单机/集群、有无网关与缓存 | 容量与故障传播 |
| 资源 | CPU/内存/磁盘 IO | 性能结论 |
| 外部依赖 | 真实服务还是 mock | 功能与异常路径 |

每项标「一致 / 已知差异 / 未知差异」，**未知项即风险项**。落地时做成脚本采集 + 与基线比对，差异进构建日志。

### 5. 配置漂移的四种来源

| 来源 | 表现 | 治理 |
|---|---|---|
| 手工热改 | 救火时直接改机器，未回写 | 变更必须改基线文件再同步 |
| 默认值兜底 | 某项没配就走代码默认值 | 启动打印生效值 |
| 继承层级混乱 | 公共/环境/实例三层覆盖 | 固定覆盖优先级并只留两层 |
| 开关长期未清 | 临时开关变永久差异 | 开关清单 + 过期时间 |

### 6. 复现线上问题的四个前置条件

复现不出来通常不是运气问题，是四项没凑齐：**代码版本**（是否就是出问题的 commit）、**配置**（开关、超时、池大小）、**数据**（那条记录的字段值，空值与超长最常触发）、**时序与并发**（竞争窗口单人操作永远复现不了）。

四项补齐仍不行，转**线上旁路取证**：加日志、影子流量、只读副本重放。复现的目的是定位，不是必须在测试环境完成。

## 三、技能：把环境当工程资产（env / devops / python / agent）

### 7. 容器化环境的资源核算

三个必算的数：**配额**（CPU limit / memory.max）、**实际峰值**、**池上限 × 副本数**。

- 压测前：内存峰值已到 limit 的 85%，先扩内存再压，否则 RT 里混着页缓存回收开销；
- 压测中：`nr_throttled` 增量超千次即配额不足，TPS 曲线会提前走平；
- 定容量：连接池上限 × 副本数 = 数据库最大连接，压测并发超过它就是池子在排队。

### 8. 零依赖环境自检脚本

现场排查最怕「脚本跑不起来因为缺包」，所以只用标准库：

| 检查项 | 实现 | 说明 |
|---|---|---|
| 端口连通 | `socket.create_connection` | 3 秒超时 |
| HTTP 健康 | `urllib.request` | 只看状态码与前 200 字节 |
| 配置一致性 | `json` 读基线比对 | 输出差异项 |
| 并发控制 | `concurrent.futures` | 20 目标并行，整体 5 秒内 |

输出固定四列「检查项 / 目标 / 结果 / 耗时」，退出码 0 全通、1 有失败，流水线可直接消费。保持单文件，用配置管理工具的 script 模块推送执行。

### 9. Agent 自助环境的权限边界

把「别乱删」写进提示词没有用，要写进系统约束，四道边界：

| 边界 | 做法 |
|---|---|
| 权限 | 只绑定专属 namespace 的 edit 角色，跨 namespace 删除应返回 403 |
| 资源 | 配额上限写死（副本数、CPU、存储） |
| 动作 | 部署前强制 dry-run，输出将变更的资源清单，出现非白名单资源即中止 |
| 时间 | 环境带到期时间自动销毁；任务设最大步数与超时，防死循环烧钱 |

配套留全量操作日志与快照回滚。**敢放它跑的前提是「它跑坏了能五分钟恢复」。**

## 四、坑点：三条反复踩的（env / scene）

### 10. 用测试环境的执行计划推线上

在万行级测试库上 `explain` 看到走索引、耗时 50ms，就断定线上无问题。线上百万行时优化器可能改走全表扫描，结论完全反过来。

**破解**：性能结论必须比 `explain` 的 `rows` 估算量级；量级差一个数量级以上，只能说「测试环境通过」，不能说「线上没问题」。

### 11. 演示前临时改环境配置

演示前一晚为「效果更好」调参数或换数据，引入未验证变更，现场出现谁也没见过的问题，且没有时间回滚。

**破解**：提前 24 小时冻结环境；要改就在另一套环境改好再整体切换；准备主备两套演示数据与快照，出问题 2 分钟内恢复。

### 12. 给 Agent 环境管理员权限

为了让它「自己搞定」，直接给集群管理员角色，一次误判就删掉别人的环境，或循环创建资源把集群撑爆。

**破解**：权限收口到专属 namespace、高危动词不给、部署前强制 dry-run 预览、配额与步数双上限、临时环境带到期时间自动回收。
