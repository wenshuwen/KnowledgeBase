# 性能瓶颈定位的分层排查路径

## 回答思路先摆出来

**先分层，再定序，最后才动手。** 面试里最容易失分的答法是"先看 CPU"——因为 CPU 是表面上最好看的指标，但它经常只是受害者而不是元凶。正确的起点是 I/O，因为它最容易制造假象。

## 四步排查顺序

```
收到"系统慢了"
   ↓
① 磁盘 I/O —— iostat -x 1
   %util > 80% 或 wa > 10% ？ → 是：直接解决磁盘问题，结束
   ↓ 否
② 内存 —— free -h / vmstat
   有 Swap 活动 / 内存不足？ → 是：解决内存问题，结束
   ↓ 否
③ CPU —— top
   us 高 → 查 SQL 与算法热点
   sy 高 → 查锁竞争与连接数
   wa 高 → 回到第 ① 步（说明漏判了 I/O）
   ↓ 否
④ 网络 —— 带宽 / 重传 / 建连时间
   打满或延迟高 → 优化拓扑、升级带宽、检查连接池
```

**为什么这个顺序**：I/O 和内存的问题会以 CPU 指标的形式表现出来（`wa`、`sy` 偏高）。先排掉它们，后面的判断才干净。

## 每层的动作清单

| 层 | 第一步命令 | 看什么 | 常见误判 |
|---|---|---|---|
| 磁盘 | `iostat -x 1` | `%util`、`await` | 把 `wa` 高当成 CPU 问题 |
| 内存 | `free -h`、`vmstat 1` | Swap 活动、`si/so` | 忽略 GC 停顿，只看使用率 |
| CPU | `top`、`top -Hp PID` | `us`/`sy`/`wa` 三者比例 | 只用总利用率下结论 |
| 网络 | `mtr`、`tcpdump` | 重传率、建连时间 | 忘了检查连接池是否耗尽 |
| 数据库 | `EXPLAIN`、慢查询日志 | `type`、`key` | 索引失效（函数操作列、隐式类型转换、前导模糊匹配） |
| 应用 | `jstack` | 线程池队列、阻塞点 | 只调线程池大小，不查阻塞源 |
| 中间件 | Kafka Lag、`kubectl top pod` | Lag、CPU Throttling | 忽略容器 Limit 过低 |

## 优化策略：五个方向，按代价从低到高

| 方向 | 核心思路 | 适用场景 |
|---|---|---|
| 减少需求 | 缓存热点、减少重复计算、合并请求 | 读多写少 |
| 改善分布 | 负载均衡、读写分离、分库分表 | 单点过载 |
| 减少同步 | 异步化、消息队列解耦、无锁设计 | 高并发竞争 |
| 优化代码 | 算法优化、批量处理、消除 N+1 查询 | 应用层瓶颈 |
| 增加资源 | 扩容 CPU/内存、换 SSD | 确实的硬瓶颈 |

**先测后优**：没有基准测试的优化都是瞎猜。先压出瓶颈点，再针对性优化——反过来做，改了一堆地方却不知道哪个起了作用。

## 一个容易漏掉的环节

**先确认压测机自己不是瓶颈。** 判断方法：线程/并发翻倍后 TPS 不成比例增长，且服务端资源水位不高——那大概率是压测机先到极限。解法是分布式压测，或先跑一次压测机空载基准。
