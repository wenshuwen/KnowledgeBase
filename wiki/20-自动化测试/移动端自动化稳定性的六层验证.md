# 移动端自动化稳定性的六层验证

## 一句话

**「跑一次通过」不叫稳定。** 稳定性要一级一级加压力来证明：从单动作能不能重复执行，
一直到异常注入后脚本能不能自愈。跳过中间层级直接宣称稳定，等于什么都没证明。

## 展开

| 层级 | 要回答的问题 | 通过标准 |
|---|---|---|
| **L1 单动作验证** | 定位器与单步动作能不能重复稳定执行？ | 同一动作连续 N 次结果一致 |
| **L2 单流程冒烟** | 最短主路径能不能一次跑通？ | 串联逻辑无断点，无人工干预 |
| **L3 全链路端到端** | 完整闭环 + 终态断言，结果真的一致吗？ | 终态业务断言通过，不只是界面到位 |
| **L4 长稳运行** | 连续 N 小时 / M 轮之后还稳吗？ | 成功率与耗时无累积漂移 |
| **L5 异常注入** | 断网、杀进程、弹窗、来电、切后台、低电之后能自愈吗？ | 自动恢复成功率达到预设线 |
| **L6 覆盖度核对** | 主要路径真的都覆盖了吗？ | 无空白格，缺口显式列出 |

### L4 要看的六个指标口径

| 指标 | 定义 | 为什么要单列 |
|---|---|---|
| 全链路成功率 | 成功轮次 / 总轮次 | **必须区分业务失败与脚本失败**，混在一起算等于没算 |
| 无故障连续轮次 | 中途不人工干预的最长连续成功轮次 | 比成功率更能暴露累积性漂移（页面栈、内存、登录态） |
| 假失败率（flaky） | 同一用例重跑结果不一致的比例 | 这个数高说明**等待策略**有问题，不是被测对象有问题 |
| 单步 P95 耗时 | 每个动作从发起到确认的耗时分布 | 只看均值会漏掉卡顿型问题 |
| 自动恢复成功率 | 异常注入后脚本能自愈的比例 | 直接决定要不要人守着 |
| 定位漂移率 | 元素定位失败次数 / 总定位次数 | 版本迭代后**第一个恶化**的指标，是回归预警 |

### L6 覆盖度怎么证明

1. **建页面-状态图**：每个页面指纹 = 一个节点，每个动作 = 一条边。**先画图再写脚本**，不是写完脚本再补文档。
2. **做需求↔步骤映射矩阵**：每条业务需求 → 对应脚本步骤号 → 对应断言点。缺口在矩阵里是空白格，必须显式列出而不是等别人发现。
3. **三方交叉验证**：脚本日志 vs App 埋点/服务端日志 vs 录屏抽检。**三者对不上，就是脚本在骗你**——最典型的形态是脚本一路绿、服务端根本没收到请求。

## 落地到测试动作

### 阈值怎么定

| 环节 | 口径与依据 |
|---|---|
| **依据/假设** | 指标定义与分级来自本页方法论推演；具体数值**没有在任何真实环境跑过**，属于量级建议。 |
| **建议值** | 就绪等待超时 **3–10 秒区间**；界面快照一致次数 **2 次**；单步重试上限 K **2 次**；L4 长稳先跑 **2 小时 × 20 轮**作基线再逐步延长。**以上全部需实测确认。** |
| **待复核** | ① 四个数值都是口径建议而非实测结论；② 长稳时长与业务周期强相关，无通用值；③ 自动恢复成功率的合格线取决于被测对象的关键程度，需按业务定。 |

### 判断脚本质量的三个反常识点

- **成功率漂亮但假失败率高** → 优先修等待策略，不要先怀疑被测对象。
- **L1 不过就直接搭闭环** → 后面所有层级都会在"定位失败"上反复翻车，且无法区分是谁的问题。
- **不做 L5 就上生产定时任务** → 一次弹窗就能让整晚的任务空跑。
