# 移动端 App 自动化的三条技术路线

## 结论

移动端自动化不是「选一个框架」的问题，而是**先选驱动躺在哪里**。按驱动位置只有三条路线：
PC 侧驱动、设备内驻留、云真机托管。三者的差别不在 API 好不好用，而在
**能不能脱离主机长期跑**——这一个维度就直接把可选项砍掉一半。

三条路线的可达上限并不对等：

| 路线 | Android | iOS |
|---|---|---|
| PC 侧驱动 | ✅ | ✅（WDA 必须先用 Mac 签名构建一次） |
| **设备内驻留** | ✅ 可打包 APK 脱离主机 | ❌ 非越狱下不成立 |
| 云真机托管 | ✅ | ✅ |

> **iOS 侧的硬边界**：非越狱 iOS 下，一个 App 无法操作另一个 App 的 UI——这是沙箱的设计前提。
> 现成方案的实质是「Mac 构建一次 WDA + 主机持续发指令」。Sonic 文档只说「构建成功后可以脱离
> **Mac**」，脱离的是 Mac，不是主机。
>
> 出处：Sonic 部署文档（iOS device access）、Mobilerun iOS 指南、Appium XCUITest 驱动
> System Requirements——三处对「WDA 必须由 macOS 构建」以及「免费 Apple ID 签名 7 天过期、
> 最多 3 台设备；付费开发者账号解限」的描述一致。

## 对比表

| 维度 | PC 侧驱动 | 设备内驻留 | 云真机托管 |
|---|---|---|---|
| 代表实现 | adb + uiautomator2；Appium 2/3（UiAutomator2 / XCUITest 驱动） | AutoJs6 / AutoX.js；自研 AccessibilityService App | 机架 + ATX / WDA，远程调度 |
| 驱动位置 | 主机进程 → 设备端服务 | 完全在设备内 | 厂商机房 |
| 能否脱离主机常驻 | ❌ | ✅（Android） | ❌（但主机在厂商侧） |
| 事件注入通道 | 无障碍 / 调试注入 | 无障碍 | 无障碍 / 调试注入 |
| 首次构建成本 | 低（插线即用） | 中（要打包签名） | 低（托管） |
| 长期运维成本 | 主机必须在线、设备固定 | 要对抗厂商省电策略 | 成本、网络延迟、数据合规 |
| 多机并发 | 要自己搭调度 | 天然分散 | 开箱即用 |
| 主要风险 | 主机故障即全线停 | 保活失败、无障碍被检测 | 数据出域 |

## 各自的适用场景

- **PC 侧驱动**适合：进 CI 做回归、需要看 UI 层级调试、双端要一套代码。这是**唯一一套代码跑双端**的路线（Appium 的价值就在这里）。
- **设备内驻留**适合：要长期无人值守、要脱离电脑、只覆盖 Android。**这是 Android 上唯一能真正做到"装完就走"的路线。**
- **云真机托管**适合：机型矩阵覆盖、大规模并发、团队没有设备运维能力。

## 反例与陷阱

- **把「图像识别」当成第三条事件通道**：图像识别只是"找目标"的方法，找到之后仍要落到
  无障碍或调试注入通道之一。用它绕开无障碍检测是**做不到**的。
- **把「离线」当成一个词**：设备本地跑、主机常驻调度、云真机托管是三档不同的目标，
  混在一起谈会得出互相矛盾的结论。
- **只看框架能力，不看签名/证书期限**：iOS 侧的失败通常不是脚本写错，而是签名过期或
  会话中断后无法自动拉起。
