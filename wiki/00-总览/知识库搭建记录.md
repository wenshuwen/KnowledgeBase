# 知识库搭建记录

## 一句话
2026-09-10，用 16 个澄清问题把「我想搭个自生长知识库」这句模糊诉求，翻译成了一套可施工的三层架构，并落地为本地 Git 仓库。

## 背景
诉求的服务对象是软件测试领域，首要用途是**经验图谱**——让项目复盘、踩坑、排障经验通过双向链接连成网，而不是散落的笔记。选择 Karpathy 的 llm-wiki 模式而非 RAG，理由见 [[编译式wiki与RAG的选型对比]]。

## 澄清是怎么做的
没有直接开始搭，而是先用五个维度、16 个问题把需求钉死。这套问法后来证明比架构本身更有复用价值，已抽成独立页：[[需求澄清的五维度框架]]。

关键结论（完整 16 题答案见 `raw/notes/2026-09-10 知识库搭建会话要点.md`）：

| 决策点 | 结论 | 对架构的直接影响 |
|---|---|---|
| 用途 | 经验图谱优先 | `## 相关` 段设为硬要求，lint 重点盯孤页 |
| 规模 | 1000 页+ | 分层索引 + 标签双索引；向量留接口不启用 |
| 编译 | 单源精读 | ingest 串行化，禁止批量 |
| 隐私 | 只存脱敏经验 | 脱敏从"记得做"变成流程步骤 |
| 备份 | 每周 lint + 本地 Git | 落成定时自动化任务，历次体检结果见 [[体检报告-2026-09-14]] |

## 最终架构

三层：`raw/`（不可变原料）→ `wiki/`（LLM 编译维护）→ `meta/` + `WIKI-SCHEMA.md`（规范）。

三个反直觉的取舍，也是这套架构真正的承重墙：
1. **`raw/` 严格不可变** —— 它是唯一能回答"这个结论从哪来"的地方，允许回改就退化成聊天记录
2. **不给向量库** —— 0 页起步时它是纯负债，千页以内分层索引够用
3. **单源精读不让步** —— 批量投喂看着快，代价是交叉引用崩塌，而交叉引用正是图谱的全部意义

## 落地顺序（P0–P4）
- **P0 骨架** ✅ 三层目录 + schema + 索引 + 模板 + lint 规则 + Git
- **P1 首批内容** —— 不追量，只求任意一页 2 跳内可达领域地图
- **P2 自动化与接入** —— skill + 每周体检任务
- **P3 规模化** —— 标签收敛到 15–25 个
- **P4 长期演进** —— 300 页评估图谱视图、800 页评估向量接入

## 如果重来
会早一点把"位置"定下来。这次在「放进 Obsidian 库」和「放进工作区」之间来回改了一次，原因是没先问清楚"你到底会不会真的打开图谱视图看"——如果先问这个，能省一轮。教训：**取舍类的选项，要问它对应的使用动作会不会真的发生，而不是问偏好**。
