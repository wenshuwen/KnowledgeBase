# 面试助手升级与部署记录

## 一句话
把本地知识库变成面试助手的底层数据源：架构核心**一行未改**，新增一条平行数据通道；每日自动化的抓取内容被限制在原料层，不污染经验图谱。

## 背景
原有面试助手是单文件静态站点（`index.html`，含内嵌内容 + 运行时拉取云端内容包），每天由定时任务生成复习内容并部署到公网链接。升级诉求是让它以本地知识库为数据源，并支持每日抓取。

## 最初的四项需求与判断

| 需求 | 判断 |
|---|---|
| 接入知识库为数据源 | 可行，需加构建步骤（浏览器读不到本地文件系统） |
| 每天抓取写入知识库 | **照字面做会毁库**，见下方 |
| 静态站点渲染 | 已具备 |
| 多端浏览 | 已具备 |

### 为什么"每天抓取写入知识库"必须改造
知识库的铁律是单源精读、自动抓取须过人工确认闸门、页面须有交叉引用。每天自动往 `wiki/` 灌素材的后果可预测：一年 3000+ 条外部内容淹掉个人经验图谱；自动内容不产生交叉引用，批量制造孤页，击穿"孤页率 <5%"的健康指标。

**改造方式**：抓取素材只落 `raw/interview/`（原料层），编译进 wiki **每日限 1–2 页**。流水层与沉淀层分离——这正是知识库三层架构本来就该有的用法。

## 实施结果

| 阶段 | 产出 |
|---|---|
| 知识库准备 | schema 升 v0.2 写入渲染契约；6 个模板扩展字段；旧库 67 篇导入 `raw/legacy/` |
| 构建脚本 | `build_kb.py`：wiki/ → kb.json，构建期过滤 publish:false，内容哈希进版本号 |
| 首批内容 | 从旧库编译 3 页性能方向内容，互相成网，知识库 5 → 8 页 |
| 站点改造 | `index.html` 六处改造，核心结构未动 |
| 自动化 | 每日任务扩展为三段：抓取落 raw → 精选 1–2 页编译 → 重建产物并部署 |

## 如果重来
两件事会做得更早：

1. **先确认"本地知识库"指哪一个。** 这台机器上同时存在旧 Obsidian 库（91 篇真内容）和新建的编译式库（当时 4 页全元内容）。方案里"接入知识库"一度等于接了一堆空数据。**歧义点要先消除再谈可行性**——这比多问几个技术细节重要得多。
2. **先断言"内容不进前端"再谈过滤逻辑。** `publish: false` 如果在前端过滤，开关就是摆设。这个认知应该在做方案时就说清楚，而不是实施时才写进硬性要求。
