# 个人知识库搭建方案全景对比

> **一句话结论**：七类主流方案里，**现金成本最低是「本地 Markdown + Git」**（趋近 0 且迁移成本实质为 0），**最推荐是「本地 Markdown 单源 + Git + LLM 辅助编译，按需挂静态站」**；没有一种方案能同时占住「高自持 + 高协作」，选型的第一步是先认下这个互斥。

> 价格口径：2026-09 量级估算，1 USD ≈ ¥7.1，仅为选型参考，实际以各产品官网为准。

## 问题背景

- **触发场景**：要为自己搭一套长期使用的知识库，市面上的工具与方案太多（本地笔记、云端 SaaS、自建服务端、企业平台、RAG 平台），功能清单看完仍然不知道该选哪个。
- **原始诉求**：需要一份**按成本结构分层**的方案全景，而不是按功能数量罗列的工具清单；并要一个明确的「最省成本」和「最推荐」结论。
- **约束 / 上下文**：个人使用为主；重视数据自持与长期可维护性；需要与 AI / agent 协作（让模型能直接读写知识）；工作目录是本地 Git 仓库。

## 解决结论

- **根因**：所有方案本质上都在回答两个问题——**数据存在哪、归谁控制**（自持度），以及**谁来维护、几个人同时用**（协作度）。这两条轴一旦画出，成本结构就自动显现：自持度高则现金成本低、时间成本高；协作度强则省人力、但订阅费与供应商锁定成本随规模线性增长。
- **做法**：分三步定方案，**不要从工具清单出发**。

  **第一步，钉住两条轴的位置。** 个人 + 自持 → 落在右下象限（本地优先）；团队 + 协作 → 落在左上象限（云端 / 服务端）。当前工具生态下，同时做到「高自持 + 高协作」的方案还不存在，别去找。

  **第二步，按「谁维护」倒推成本大头。** 现金支出通常不是主项，**人力才是**：自建 Wiki 的软件是免费的，但一年运维折算 ¥3 万–10 万；本地 Markdown 几乎零现金，代价是自己整理的时间。判断标准是——你要的是「付租金」，还是「存资产」。

  **第三步，选一个能渐进升级的数据层。** 数据层（存成什么格式）一旦定错，上层换多少次工具都救不回来；数据层定对，上层可以随时换。

- **为什么有效**：方案的优劣不在功能多少，而在**它把成本放在哪一类里**。现金成本、时间成本、迁移成本、认知成本四者互斥——把成本放在「自己的时间」上时，这份投入会随内容积累产生复利；放在「订阅费」上则是纯支出，且随时间被涨价、改版、停服持续侵蚀。

### 七类方案速查

| 方案 | 代表工具 | 主要优势 | 主要劣势 | 适用人群 | 年现金成本 |
|---|---|---|---|---|---|
| 本地纯文件 / 本地优先 Markdown | Obsidian、思源、纯文件夹 | 零订阅；纯文本任意编辑器可读；**迁移成本 <5%**；离线；可 Git | 实时协作≈0；插件折腾耗时；移动端一般 | 个人沉淀、开发者、喂 AI | ≈ ¥0 |
| docs-as-code | Git + MkDocs / Docusaurus | 文档与代码同流程（PR/CI）；发布即静态站；天然版本化 | 写作门槛（Markdown + Git）；非技术同事难用 | 工程团队、对外技术文档 | ¥0–300 |
| 云端笔记 SaaS | Notion、语雀、飞书 | 开箱即用；协作与权限成熟；视图模板丰富 | 数据不在自己手里；**迁移成本 20–40%**；按人头涨价 | 协作优先、不愿运维 | 个人 ¥0–850；含 AI ≈ ¥1,700 |
| 自建 Wiki 服务端 | Wiki.js、BookStack、Outline、Docmost | 自持与协作兼得；权限/SSO/搜索可控；Git 后端双写 | DevOps 成本真实（Outline 要 4 个服务）；升级备份全归你 | 10–100 人技术团队 | ¥1,000（个人）– ¥4,200（小团队）+ 人力 ¥3–10 万 |
| 企业级项目知识库 | Confluence、飞书企业版、SharePoint | 合规审计；权限体系；与工单/CI 打通；厂商 SLA | 贵、重、僵化；**迁出很难**；小团队用不动 | 中大型企业 | ¥100–500/人/年起（首年常 10 万+） |
| AI 原生 / RAG 知识库 | Dify、RAGFlow、FastGPT、MaxKB | 自然语言问答；自动切片建索引；可接 Agent | **质量取决于原料质量且答错难察觉**；切片重建是持续运维；本质是问答引擎非知识本体 | 需要问答入口的团队 | ¥2,000–3 万 |
| LLM 编译式 wiki | llm-wiki 范式 | 投喂即编译，回答带来源；纯 Markdown 天然自持；agent 直读文件系统 | 依赖「单源精读」纪律，批量灌入即崩；强依赖可靠 agent | 个人精耕、要经验图谱 | ¥300–1,500（模型 token） |

### 两个明确结论

- **综合成本最低**：**本地 Markdown 纯文件 + Git**。现金趋近 0；无服务器、无订阅、无供应商绑定；备份即复制目录；迁移成本实质为 0（本身就是标准格式）。关键不只是省钱——**其他方案都有某个环节会随时间变贵或不可用**（涨价、改版、停服、升级路径断裂、导出丢关系），它是唯一没有这个风险项的。
- **最推荐**：**本地 Markdown 单源 + Git + LLM 辅助编译**，需要分享时再挂静态站。理由四条：
  1. **成本结构最优** —— 付的是自己的时间，而这份时间会复利（越积越厚、越互链越值钱）；订阅制付固定租金，不产生资产。
  2. **格式最优** —— 纯文本是唯一能被所有编辑器、所有模型、所有未来软件读取的格式；一份数据同时是知识库、是喂 AI 的语料、是简历素材。
  3. **可渐进，不必推倒重来** —— 要图谱挂 Obsidian，要对外挂静态站，要问答加检索，要协作再上 Wiki.js / Outline；**数据层全程不动，只换上层**。
  4. **唯一短板（实时协作）恰好是个人场景最不需要的**，不要提前为它付成本。

### 最小可行起步

```bash
# 成本 0 元的最小知识库：纯 Markdown + Git，不装任何软件也能开始
mkdir -p ~/kb/{raw,wiki,meta}      # raw 不可变原料 / wiki 编译产物 / meta 规范
cd ~/kb && git init                # 版本历史即备份，误删可回退
printf 'raw/\n.DS_Store\n' > .gitignore
git add . && git commit -m "init: 知识库骨架"
# 编辑器任选：Obsidian 只是「更好看的文件夹浏览器」，不装也不影响这套结构
```

## 适用场景

- **适用**：为个人或小团队做知识库选型决策时；被工具清单淹没、需要按成本结构横向比较时；已有库需要评估「要不要迁移 / 升级方案」时。
- **不适用 / 边界**：需要多人**实时**协同编辑（如团队共同维护 SOP）时，本地优先路线不适用，直接看自建 Wiki 或云端 SaaS；原料以海量非结构化数据（会议录音、聊天日志）为主且只做一次性问答时，看 RAG 或 NotebookLM 类工具。
- **前置依赖**：能接受 Markdown 与 Git 的基本操作；选本地优先路线还需要一个可靠的 agent / 模型来完成编译与检索。

## 反例与陷阱

- **陷阱一：把「笔记工具」当「知识库」选。** 选型问题实际是「数据存哪、谁维护」，如果只对比插件数量和界面美观度，会选出一个三年后搬不出来的工具。**先问数据能不能整体搬走**。
- **陷阱二：只算现金成本，不算人力。** 自建 Wiki 的软件免费，但运维一年折算 ¥3 万–10 万；「免费」在这里是认知陷阱。反过来，若自身时间本来就要投入，本地路线的「时间成本」其实是资产而非支出——两者不能直接比大小。
- **陷阱三：认为 RAG 能替代知识库。** RAG 是「问答引擎」，回答用完即弃，不会积累出交叉引用网络；原料质量差时它会稳定地给出错误答案且**很难被察觉**。它适合做知识库的**前端入口**，不适合当本体。
- **陷阱四：为「以后可能有团队」提前上重方案。** 协作能力是本地路线唯一短板，但这个短板只在真的出现第二个人时才会痛；提前付这笔成本的代价是日常效率与现金双输。
- **陷阱五：把「迁移成本低」当成「不用备份」。** 纯文件的优势是可迁移，不是不会丢——仍需 Git 或异地副本，否则误删照样不可逆。
