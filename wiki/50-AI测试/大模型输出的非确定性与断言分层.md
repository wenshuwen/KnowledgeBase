# 大模型输出的非确定性与断言分层

## 一句话
大模型应用不能断言「输出等于什么」，只能断言「输出必须满足什么约束」——按成本从低到高分四层；且**评测用的那把尺子本身也会漂移**，必须与模型一起锁版本。

## 展开

**先分清三个来源**（来源不同对策就不同，不能笼统归成「模型不稳定」）：

| 来源 | 表现 | 对策 |
|---|---|---|
| 采样随机性（temperature / top_p） | 输入完全相同，输出仍不同 | 固定参数 + 多次采样 + 比例判定（N 次中达标次数不低于阈值） |
| 上下文变化 | 历史消息、召回片段、系统时间、工具返回值都会变 | 把上下文当输入的一部分固化——用例存完整消息数组，而不是一句话 |
| 上游模型升级 | 供应商静默更新或主动切版本，输出分布整体漂移 | 固定模型版本号 + 建立回归基线，每次切版本跑全量评测集对比涨跌 |

**断言四层**，从便宜到贵——能早失败就不要拖到语义层：

1. **硬约束断言**：长度范围、能否解析、字段是否齐全、枚举值是否在允许集合内、有无敏感词。这些是确定性的，直接断言。
2. **结构化断言**：要求输出 JSON 时用 schema 校验，不合规即判失败，必要时触发自动重试。
3. **语义断言**：用向量相似度或另一路模型做裁判，判「是否覆盖要点」而非「字面是否一致」。
4. **多次采样 + 比例判定**：参数固定、跑 N 次，以「达标率不低于阈值」作为通过条件，同时把每次输出留档，便于对比版本漂移。

**为什么必须把「结构合法性」与「内容正确性」分开断言**：结构（JSON 可解析、字段齐全）是确定性的，可以硬断言、能让用例尽早失败，省下后面昂贵的语义判定成本；只有内容正确性才是概率性的、才需要统计口径。两者混在一起，失败时既不知道是格式坏了还是答错了。

**最容易漏的一条——裁判自身也会漂移**：评测模型必须锁版本、锁 prompt，并定期用人工标注的小样本校准判准。否则等于用一把会伸缩的尺子去量另一个不稳定的对象，两次评测的分数根本不可比。

## 落地到测试动作
- **用例资产的形态变了**：从「一句话 + 期望输出」改成「完整消息数组 + 约束断言 + 采样次数」。上下文不固化，结论就不可复现。
- **把模型调用当接口测**，分两层：契约层（返回结构、超时、限流与失败异常路径）硬断言、失败即拦；质量层（格式合法率、要点命中率、拒答正确率）用通过率加样本量表达。分层参照 [[接口测试知识地图]]。
- **阈值必须与产品一起白纸黑字写进验收标准**。数据不好看时应反馈给产品调预期，而不是自己在断言上不断放宽——放宽断言正是 [[假阴性漏测的六大来源]] 里第 6 条的 AI 变体。
- **多轮判定接 trace 与多次统计**：与 [[Agent任务成功率的分层口径]] 同一口径纪律——报告「N 次运行中的成功率」，禁止用单次最好成绩汇报。
- **常见误用**：把「两次答案不同」直接提成缺陷。先区分**非确定性**（采样带来的合理差异）与**错误**（不满足业务约束）：前者改断言口径，后者才是缺陷。曾经出现过测试与开发在这件事上来回扯皮、缺陷被挂起、评测进度也停摆的情况。
