# Harness 工程

## 一句话
**Agent = Model + Harness**。Harness 是模型之外让 Agent"能做事、做得对、出问题能被发现"的整套工程外壳，而测试新手最容易犯的错，就是只盯着模型不看 Harness。

## 展开

Harness 直译"驾驭装置"。模型负责"想"和"生成"，Harness 负责其余的一切工程能力，包括：

- **工具封装**——把外部 API 包成模型可调用的工具，含参数校验与结构化错误返回
- **上下文管理**——历史消息的窗口、截断与传递策略
- **权限控制**——模型能调哪些工具、以什么身份调
- **重试熔断**——失败重试策略、最大迭代上限、循环检测
- **日志监控与回滚**——全链路可观测，出问题能退回

**和测试的关系特别直接**：一个测试用例 Agent 越跑越不稳定，问题往往**不在模型，而在模型之外的 Harness**——比如上下文无限增长、工具权限没收敛、没有失败兜底。所以测 Agent 不能只盯着 prompt 和回答质量，要把 Harness 当被测对象：工具调用链路、状态管理、失败恢复，都得有验证手段（具体测法见 [[Agent工具调用测试]]）。

**延伸——Agent 自进化的新风险**：当 Agent 被允许修改自己的提示词或配置时，会出现三类新问题——行为漂移（几十轮自修改后行为不可预测，说不清是哪次改动引起的）、依赖污染（自主安装的插件可能带恶意代码）、回滚失败（修改链一长，反向操作不完备）。应对思路是版本快照、关键操作熔断、全链路可观测，把每次自修改记录成可审计的变更。

## 落地到测试动作

- 拿到不稳定的 Agent 用例时，**先查 Harness 再怀疑模型**：上下文有没有膨胀、权限有没有收敛、失败有没有兜底
- 测试范围里显式加入 Harness 组件：工具调用的结构化错误返回、迭代上限触发、上下文截断后关键信息是否丢失
- 对自进化型 Agent，验证版本快照可恢复、自修改有审计记录、关键操作有熔断
