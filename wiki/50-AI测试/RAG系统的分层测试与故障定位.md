# RAG 系统的分层测试与故障定位

## 一句话
RAG 要**拆四层测**（数据 / 检索 / 生成 / 端到端），各层指标完全不同；线上答错时靠「把召回的片段和最终回答一起打出来」这一步判断锅在哪一层。

## 展开

| 层 | 测什么 | 主要指标 |
|---|---|---|
| ① 数据层（入库） | 文档解析是否正确（表格、扫描件、多栏排版是重灾区）、切分是否切断完整语义、元数据（来源 / 版本 / 权限）是否带全 | 解析正确率、切分完整率、元数据齐全率 |
| ② 检索层 | 多路召回融合后的排序是否合理 | Recall@K / Precision@K（用「标准问题 → 应召回文档」的标注集算） |
| ③ 生成层 | 答案是否忠于召回内容（是否幻觉）、引用是否指向正确片段、格式是否合规 | 忠实度、引用正确率、格式合法率 |
| ④ 端到端 | 用户视角能不能解决问题 | 任务完成率 + 人工抽检 |

**定位判据（把「答错了」拆成两种归因）**：

- 召回里**本来有**正确答案、生成却答错 → **生成层**问题（prompt 或模型）；
- 召回里**根本没有**正确答案 → **检索层或数据层**问题（切分粒度、embedding、或权限过滤把正确内容滤掉了）。

这一步是整页的关键：不做「召回片段 + 最终回答」联合打印，就只能在「模型不行」和「知识库没这条」之间猜。

**最易漏的一层——权限过滤**：不同角色的用户问同一个问题，召回范围必须不同。这类用例必须单独造，一次泄漏就是事故。

**生成层怎么深入：幻觉的三种成因与对应手段**。幻觉不可能被消灭，只能被圈定并持续监控。

| 成因 | 抑制手段 | 验证手段 |
|---|---|---|
| 知识缺失型（模型本来没有这块知识） | 接检索（RAG）+ 系统提示限制「只依据给定资料回答」 | 忠实度评测：把答案拆成原子陈述，逐条判断是否被召回内容支持，算支持率 |
| 上下文冲突型（召回资料互相矛盾或已过期） | 数据治理：资料带版本号与生效时间，检索时先过滤 | 构造含新旧版本冲突的用例，断言模型采用现行版本 |
| 指令泛化型（为回答完整而自行补全细节） | 输出约束：要求逐句引用来源，无依据时明确输出「不知道」 | 拒答评测：造一批知识库无答案的问题，看是否老实说不知道 |

**拒答率的双向含义**：过高说明业务可用性差，过低说明幻觉风险大——**两个方向都是问题**，必须一起看，不能只盯一个方向调优。

**长期观测**：线上把「未命中知识库但仍给出确定性回答」的请求单独打标并人工抽检。

## 落地到测试动作
- **断言方式接 [[大模型输出的非确定性与断言分层]]**：结构合法性硬断言、内容正确性用比例判定。别写一条用例断言「模型必须回答 X」，单条通过就当整体合格。
- **权限类用例并入越权测试矩阵**：检索层的召回必须按当前身份过滤，而不是在生成层用 prompt 约束——prompt 约束不是权限控制，见 [[越权访问与IDOR]]。
- **数据层回归要留旧版本文档样本**：解析与切分的问题往往在「文档更新后」才暴露，只在最新语料上测会漏。
- **指标先定再选工具**：想清楚要回答「涨了多少 / 降了多少 / 哪些用例回归了」，再决定用哪套评测工具。
