# Agent 任务成功率的分层口径

## 一句话
只报一个「成功率」数字没有信息量——必须**分四层统计**，且立场明确：**中间步骤再漂亮，最终目标没达成就是失败**。

## 展开

四层口径，从产品视角到工程视角逐层收窄：

| 层 | 口径 | 用途 |
|---|---|---|
| ① 任务级成功率 | 用户目标是否达成 | **唯一对外汇报的口径** |
| ② 过程级正确性 | 工具选择是否正确、参数抽取是否准确、步骤是否多余或缺失 | **只用于定位失败的环节**，不用于判定成败 |
| ③ 失败归因分类 | 规划错误 / 工具错误 / 参数错误 / 知识缺失 / 幻觉 / 超限（步数、token、超时） | 没有归因的成功率只是一条曲线，有归因才能指导优化 |
| ④ 效率与成本口径 | 平均步数、工具调用次数、token、端到端 P95 | 「成功但用了 40 步、花了 8 毛钱」在很多场景等于不可用 |

**必须单独统计的一类：「编造的成功」比「诚实的失败」危害大得多**——Agent 没调工具、凭记忆编了个看起来对的答案，被计入成功率后，换一个输入必然失败。要从成功率里挑出来单列。

**统计纪律**：
- 评测集必须带**标准答案与标准步骤**，否则过程级判定无从谈起；
- Agent 有随机性，**同一任务跑多次、报告「N 次里的成功次数」**，而不是挑最好一次；
- 每次运行的步骤序列、工具入参出参、耗时、token 必须**落库（trace）**，否则无法归因也无法复现。

与 [[Agent工具调用测试]] 的衔接：过程级正确性正是其「四层测试法」中①②层的判定结果；「编造的成功」对应其异常处理层的「诚实性」检查——两者是同一套 trace 在「判定口径」与「测试方法」两个视角的展开。

**为什么「跑多次、报比例」不是权宜之计**：随机性有三个来源（采样参数、上下文变化、上游模型版本），都不在测试的控制面上。来源与对策的系统展开见 [[大模型输出的非确定性与断言分层]]——参数与模型版本不固定，成功率这个数字本身也不可比。

## 落地到测试动作

- 评测脚本按四层分别出数：任务成功率对外、归因分布对内、效率成本做容量与选型依据；
- 过程判定接 trace 落库：把实际步骤序列与标准步骤比对，识别「侥幸成功」（结果对但工具用错/参数错/凭记忆作答）并纳入归因分类；
- 报告口径固定为「N 次运行中的成功率 + 归因分布 + 成本」，禁止用单次最好成绩汇报；
- 把「编造的成功」做成独立指标：抽查「未调用任何工具却给出答案」的样本，验证诚实性。
