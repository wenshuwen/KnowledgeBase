# Agent 工具调用测试

## 一句话
把 Agent 的工具调用拆成**四层**分别验证——选对工具、参数合法、失败有兜底、组合调用有序；死循环防线是三层防御设计，测试要专门构造持续故障来验证熔断真的生效。

## 展开

**四层测试法**：

| 层 | 测什么 | 判据 |
|---|---|---|
| ① 工具选择准确性 | 构造需要不同工具的任务集，看 Agent 选没选对 | **选错率是核心指标**，不看单次对错看分布 |
| ② 参数正确性 | 生成参数过 JSON schema 校验 | 重点测缺字段、类型错、枚举值越界 |
| ③ 异常处理 | 工具超时、返回错误码、返回空结果时 Agent 的反应 | 是重试、换工具，还是诚实汇报失败？死循环防护必须设最大迭代次数 |
| ④ 组合调用 | 多步任务里工具的调用顺序与上下文传递 | 前一步的输出有没有正确进入下一步 |

**死循环的三层防御**（大厂高频考题：Agent 调用三个工具后就死循环了，兜底机制怎么设计）：

1. **工具层硬隔离**：每个外部工具调用都包 try-catch，且不能只吞异常——要返回结构化错误给 LLM，例如 `{"status":"failed","error_type":"Timeout","retry_after":5}`，让模型知道失败了、该等多久、能不能重试；
2. **推理层熔断**：同一工具连续失败 3 次或检测到循环调用，强制中断——必须实现 Max Iteration 上限和 Loop Detection；
3. **规划层自我修正**：更高级的做法是让 Agent 反思"刚才哪里做错了、要不要换个工具"，即 Reflection 模式。

**跨域风险——参数注入**：用户输入直接拼进工具参数时，可能被用来执行越权操作。这是注入类攻击在 AI 系统上的延伸，测试要与安全测试联动（思路同 [[Web安全测试地图]] 的输入注入类）。

## 有副作用的工具怎么测（2026-10-12 补）

> 更新：2026-10-12 源自 `raw/interview/2026-10-07.md`——工具调用里「查订单、发短信、退款」这类**有副作用**的调用，测法与只读工具不同：断言重点从「有没有真的执行」转为「有没有以正确参数、在正确时机发起调用」。

1. **环境隔离**：测试环境下游全部指向沙箱或 mock；做不到时至少让下游能识别测试标记并走干跑分支。
2. **工具层打桩 + 断言调用意图**：桩记录「被调用的工具与参数」，断言参数正确性与调用时机，而不是真实副作用。
3. **幂等与并发验证**：Agent 有重试机制，最易出的事故是重复执行——必须验证「重试、超时、并发下会不会重复发短信、重复退款」，**判据是幂等键与落库流水，不是工具返回成功**。
4. **两类必须单独测的越界**：**金额越界**（100 算成 1000、部分退款执行成全款）与**权限越界**（Agent 以服务身份调用，天然高权限，一次提示词注入就可能变成任意工具调用）。建议给高风险动作配「动作确认网关」（资金、外发消息、删除数据），并专门验证网关拦得住。

与本页四层测试法的关系：第 ①② 层管「工具选对了没、参数对不对」，本段管「副作用本身会不会被触发两次或超出范围」；第 ③ 层的诚实性检查对应 [[Agent任务成功率的分层口径]] 里的「编造的成功」。权限越界的授权侧整改见 [[越权访问与IDOR]]。

## 落地到测试动作

- 为每一层各准备一组用例：任务集断言工具选择、schema 校验断言参数、故障注入断言异常行为、长链路断言组合顺序
- **验证熔断必须用持续故障**：专门构造"工具持续超时""返回格式异常"的用例，确认 Max Iteration 与 Loop Detection 真的触发，而不是只看代码有没有写
- 异常处理断言里加"诚实性"检查：任务无法完成时，Agent 是编造结果还是明确交代失败
- 对接安全测试：对工具参数做注入类用例（越权指令、特殊字符），确认参数构造环节不会把用户输入当成指令执行
