# 多 Agent 消息契约的四要素

## 一句话

多个 Agent 串起来「单点都对、整体错」，病灶几乎都在**传递层**：消息丢了没人发现、重发了没人拦、乱序了拿旧结果下判断。治法是先把消息契约钉死成四要素（追溯 id、单调序号、幂等键、状态机约束），再按单跳、多跳、缺失重复三层去测。

## 展开

单 Agent 的失败看得见——它答错了。多 Agent 的失败看不见——每一步都返回了合理结果，错在把哪一步的结果交给了下一步。所以测试对象不是「最终答案看起来对不对」，而是**消息本身是否可追溯、可判定、可去重、可限序**。

四要素各自封掉一种失败模式：

| 要素 | 定义 | 缺了它的失败模式 |
|---|---|---|
| 追溯 id | 贯穿全链路的 trace id，跨进程、跨语言都能串上 | **查不出**：出问题不知道是哪一跳断的 |
| 单调序号 | 同一会话内递增，缺号即缺口 | **判不出**：序号倒挂时下游拿旧结果当新结果 |
| 幂等键 | 由业务语义生成，重投时下游能认出「这条处理过」 | **去不掉重**：重发产生第二条副作用 |
| 状态机约束 | 显式定义哪一步允许重放、哪一步只允许前进不能回退 | **说不清**：重放一个已完成步骤，语义未定义 |

**为什么进度不能靠时间戳判**：分布式节点时钟会漂，同一毫秒内的两条消息、跨机房的 NTP 回拨，都会让「按时间排序」得出错误顺序。单调序号是逻辑时钟，不依赖物理时钟——这是本页最容易被跳过、也最容易在联调后期返工的一条。

**三层测法**（顺序从内到外，先保证单跳契约成立，再谈多跳）：

| 层次 | 做法 | 期望 |
|---|---|---|
| 单跳契约 | 畸形载荷打一遍：缺字段、类型错、枚举越界 | 明确拒绝，**不静默降级**成默认值 |
| 多跳顺序 | 混沌层把某一步延迟 0.5~3 秒、复制 5% 消息 | 校验方识别序号倒挂并等待，不用旧结果下判断 |
| 缺失与重复 | 丢 1 条、重发 1 条 | 靠序号发现缺口并重放；重发不产生第二条副作用 |

**判据三条**，缺一条都只能算「跑通了」：① 凭 trace id 能拼出完整链路；② 重发不产生第二条副作用；③ 最终状态与该任务单 Agent 直跑的结果**逐字段一致**。第 ③ 条是口径锚点——没有它，「多 Agent 更好」这句话无法验证，也无法证伪。

**混沌注入必须可控可复现**：固定 seed、固定丢包比例、固定延迟区间。否则一次「没复现」既不能证明没问题，也不能证明有问题，只是浪费一轮。

**工具定位（不是本页重点，只标位置）**：链路埋点与上下文传播用 OpenTelemetry；Agent 调用链与中间步留痕用 LangSmith / Langfuse；分布式追踪查询用 Jaeger。三者是「先让它可见」的手段，可见之后再谈断言。

**与单 Agent 工具调用测试的边界**：那边测的是「工具选对没、参数对不对、失败有兜底」，被测对象是**一次调用**；本页测的是**调用之间那一段**——上下文有没有正确、完整、按序地传过去。边界上重叠的一块是第 ④ 层组合调用（前一步输出是否进入下一步），本页把它拆成了可判定的四要素。

## 落地到测试动作

- **把契约写成接口文档级的产物**，四要素逐条落字段名与取值规则，再据此生成畸形载荷用例；口头约定等于没有契约。
- **混沌用例进流水线**：延迟、复制、丢包三组参数固定成用例集，每次回归都跑，不靠临时手工注入。
- **对账口径固定**：同一任务分别用「单 Agent 直跑」与「多 Agent 链路」各跑 N 次，最终状态逐字段比对；差异要先归因到某一跳（靠 trace 与序号），而不是笼统记「多 Agent 不稳定」。
- **常见误用**：拿最终答案的文本相似度当链路正确性判据。答案对不代表链路对——链路错但被模型「圆」回来的情况，正是本页要抓的那类缺陷。
- **常见缺口**：只测正常链路，不测「序号倒挂」与「重投」。这两个才是线上真实故障形态，而它们在 happy path 上永远不出现。
