# llm-wiki 编译式知识库

| 项 | 内容 |
|---|---|
| 定位 | 让 LLM **增量编译并持续维护**一套结构化 markdown wiki，替代 RAG 式的"提问时现查" |
| 类型 | 知识库构建模式（不是软件产品，无安装包） |
| 提出者 | Andrej Karpathy |
| 原始说明 | gist.github.com/karpathy/442a6bf555914893e9891c11519de94f |
| 本库使用版本 | 模式本身无版本；本库 schema 为 v0.1 |

## 我为什么用它
核心诉求是经验图谱，需要"知识之间已经连好"这件事本身。RAG 每次现查现拼，永远攒不出一张网；这个模式在投喂时就把链接和矛盾处理完了。选型推演见 [[编译式wiki与RAG的选型对比]]。

## 关键能力

- **三层分离**：`raw/`（不可变原料）/ `wiki/`（LLM 编译产物）/ schema（规范）——对测试工作的直接意义是**结论可追溯**，任何一句结论都能回到原始日志或记录
- **单源精读**：一次编译一个源，一个源通常触及 10–15 个既有页面——保证交叉引用密度
- **好答案回填**：查询产生的横向对比、新连接固化成新页面，不留在对话历史里——对测试工作的意义是**排障经验不会随对话丢失**
- **lint 周期体检**：查矛盾、孤页、缺链、缺口——对应测试里的"回归"，防知识腐化
- **纯 markdown + Git**：无锁定，换任何编辑器都能读

## 踩过的坑

- **"自生长"容易理解成"自动生长"。** 实际上生长动力来自人持续投喂，LLM 只负责编译质量。投喂断档库就停滞——所以要把投喂门槛降到"口述两句话也算一次"。
- **不设边界会污染。** 自动抓取若不设人工确认闸门，一周就能灌进几十页低价值内容，把图谱冲淡。本库的解法是落 `raw/inbox/` 待确认。
- **规范只写在文档里会被跳过。** 必须包装成可调用的 skill，否则换个会话 agent 就不按规范干活。

## 上手最小示例

```
目录骨架（三层）：
raw/     ← 不可变原料：inbox / notes / files / clippings / assets
wiki/    ← LLM 维护：领域目录 + index.md + log.md
meta/    ← 规范：templates / lint-rules.md

一次 ingest 的七步：
读源 → 复述要点确认 → 落盘 raw/ → 建页 → 抽实体页 →
补全库交叉引用 → 更新 index.md → 追加 log.md
```
