# 覆盖率口径与测过了的三层含义

## 一句话
覆盖率是**下限指标**不是质量结论；同一句「测过了」分执行过 / 断言过 / 验证过三层，缺陷逃逸的常见根因就是把第一层当第三层交付。

## 展开

### 覆盖率的四种口径与共同盲区

| 口径 | 要求 | 强度 | 盲区 |
|---|---|---|---|
| 语句覆盖 | 每行执行过 | 最弱 | 只证明跑过，证明不了判断走对 |
| 分支覆盖 | 每个 if 的真假都进过 | 中 | 覆盖不到条件内部的组合 |
| 路径覆盖 | 所有执行路径都走到 | 最强 | 循环与嵌套下组合爆炸，实际不可行 |
| 条件组合覆盖 | 复合条件里每个子条件的取值组合 | 较强 | 组合数随子条件数量指数增长 |

**四者的共同盲区：没有断言也算覆盖。** 用例把接口调一遍、代码全绿，一行断言没写，覆盖率照样能到 90% 以上。所以：

- 覆盖率**低于阈值**说明有代码没跑过，肯定漏；
- 覆盖率**高于阈值**只说明「没漏在这」，不说明「测对了」。

要让它有判定力，必须配合**无断言用例占比统计**或变异测试——存活变异体就是断言弱点清单，这是 [[假阴性漏测的六大来源]] 治理主线里的第二条。

### 「测过了」的三层含义

同一句「这条测过了」，在三种口径下含义完全不同：

| 层 | 含义 | 能证明什么 |
|---|---|---|
| ① 执行过 | 用例跑了没报错 | 代码没崩，功能对不对不知道 |
| ② 断言过 | 跑了且对返回值做了断言 | 返回值符合预期，副作用（数据库 / MQ / 缓存）对不对不知道 |
| ③ 验证过 | 返回值、副作用、边界、异常路径都被独立核对过 | 完整的交付口径 |

**缺陷逃逸的常见根因，就是把①当成③来交付。** 可量化的抓手：统计**无断言用例占比**——这个数不为零，说明「测过了」里有水分。评审时问「这条的断言写在哪儿、验了几个面」，比问「测了没有」有效得多。

### 预期可判定是最低门槛

预期结果写「与上次一致」「数据正确」等于没写预期——既不能自动化，也没法交给别人跑，过段时间连作者自己都说不清什么算通过。预期必须是**可判定的具体值或条件**：金额 100 变 80、状态从待支付变已支付、响应时间小于 300ms。

自查两问：这条用例的预期能不能写成一行 assert？换个人执行，结论会不会一样？

预期值写到哪几层（协议 / 业务 / 数据 / 副作用），接口场景的系统展开见 [[接口断言的四个层次]]。

## 落地到测试动作

- 流水线里覆盖率只做下限卡点（如语句覆盖低于阈值阻断合并），不做质量结论的依据；
- 每轮回归统计无断言用例占比，非零进质量周报，趋势看收敛；
- 用例评审固定问三句：断言在哪、验了几个面（返回值 / 副作用 / 边界 / 异常）、预期可否写成一行 assert；
- 「与上次一致」类预期一律打回重写。
