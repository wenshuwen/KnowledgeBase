# Mock 接口桩的设计模式

## 一句话
自研 Mock 桩的价值不在"能返回假数据"，而在**能按需制造你想测的那种响应**。五种响应模式覆盖了接口测试绝大多数的依赖替代需求。

## 五种响应模式

| 模式 | 动态依据 | 适用场景 |
|---|---|---|
| **请求参数匹配** | URL 参数 | 按不同 ID 返回不同数据（正常/异常路径） |
| **请求体解析** | POST 内容 | 按业务类型分支返回（如普通订单 vs VIP 订单） |
| **场景模拟** | 请求里的 `scenario` 字段 | **测异常处理逻辑**：超时、错误码、余额不足 |
| **通用 Mock** | 请求体指定 `status_code` / `delay` / `response` | 不改代码就能构造任意响应，最灵活 |
| **规则引擎** | 预定义规则表 | 多条件匹配的复杂业务场景 |

**第三种和第四种是测试视角下最有价值的**——它们把"制造异常"从"改代码"变成了"改请求"，异常用例的编写成本直接降一个量级。

## 实现要点（Flask 方案）

一个最小可用的桩用 Flask 就够了：路由接收请求 → 根据参数/请求体/scenario 字段分支 → 返回不同 JSON。50 行以内能覆盖前三种模式。

## 什么时候该换专业工具

| 需求 | 该用什么 |
|---|---|
| 录制回放、契约测试 | WireMock、Mountebank、mitmproxy |
| 简单接口桩、异常场景构造 | 自研 Flask 方案足够 |

**判断标准**：当"维护桩本身"开始比"写用例"更耗时，就该换工具了。

## 最容易犯的错：把"Mock 通过"当成"接口没问题"

这是接口测试里最典型的假阳性来源：

- **契约偏离**：Mock 返回的字段名/类型和真实服务不一致，用例全绿，上线后立刻挂
- **行为偏离**：Mock 不校验权限、不做参数边界检查，掩盖了真实的鉴权缺陷（比如 [[越权访问与IDOR]] 在 Mock 环境下根本测不出来）
- **状态偏离**：Mock 无状态，测不出并发、幂等、事务回滚这类问题——**「幂等在 Mock 上通过」是没有证据价值的**，因为 Mock 压根不落库、不存在唯一键冲突，也不存在并发窗口。幂等的真实战场见 [[幂等的两种语义与并发验证]]

**破解方式**：Mock 只用于**隔离被测接口的外部依赖**，被测接口自身的逻辑必须跑真实实现；关键链路（鉴权、支付、状态流转）不允许全程 Mock 通过就算完。

**判据层面的补充（2026-10-19）**：Mock 环境能覆盖的只有 [[接口断言的四个层次]] 里的①②层（协议与业务）；③数据层的精度、空值语义，④副作用层的「只发生一次」，都必须跑真实依赖。
