# 接口断言的四个层次

## 一句话
断言不是「返回 200 就算过」，而要按**检查对象**分四层：协议层、业务层、数据层、副作用层——层次越往后越容易漏，而线上事故几乎都出在后两层。

## 展开

四层的检查内容与最常被漏掉的部分：

| 层 | 断言什么 | 常见漏测 |
|---|---|---|
| ① 协议层 | 状态码、响应头（`Content-Type`、缓存控制、`Content-Length`）、响应体能被按声明格式解析 | 只断 200，不断 4xx / 5xx 分支；不断 `Content-Type`，HTML 错误页被当 JSON 解析「成功」 |
| ② 业务层 | 业务码、`message` 语义是否与场景匹配、失败原因是否可区分 | 不同失败原因返回同一句模糊文案，用例只能断言「失败」，无法断言「因为什么失败」 |
| ③ 数据层 | 字段类型、金额精度、空值语义（`null` / 不返回 / 空串）、时间格式与时区、大整数 ID 精度 | 全层最容易整体漏掉：字段多一个少一个、精度被四舍五入、时间少 8 小时都不报 |
| ④ 副作用层 | 数据库、缓存、消息、下游调用**是否发生、且只发生一次** | 全层最容易整体漏掉：接口答了 200，但数据没落、落了两条、下游没收到 |

**为什么要分层，而不是「多写几个 assert」**：分层决定了失败时你能否立刻定位。混在一起的断言只告诉你「这个用例挂了」，分层后能直接说「协议对、业务对，数据层金额精度错了」。

另一层理由与成本有关：**确定性强的层要早失败**。协议与数据层是确定性判定，跑得快、误报低，应该挡在最前面；业务语义与副作用核对更贵，放在后面。这与 [[大模型输出的非确定性与断言分层]] 是同一套思路，但两者维度不同——那边按**约束强度**分层（硬约束 → 结构化 → 语义 → 比例判定），这边按**检查对象**分层，可以叠加使用：同一份数据层断言在两边都成立。

**典型反例（本源最具代表性的一个）**：下单接口返回 200 且 `code=0`，但库存扣减是异步的，前端立刻查订单查不到。只断言响应体的用例全绿，用户却下不了单。正确做法是补「返回后轮询查最终状态」的断言——**有界等待 + 超时即判失败**，而不是固定 `sleep` 几秒。

**一条判据**：断言「用户能感知到的结果」，而不是「接口自己说了什么」。接口说成功不算成功，用户能看到、能查到、且只发生一次才算。

**另一条容易被忽略的纪律**：期望值必须来自需求或契约（OpenAPI、JSON Schema、产品验收标准），**不能拿被测实现的实际返回来反向生成基线**。否则第一次运行就把 bug 写进了期望值，之后每次运行都在验证「bug 还在」。

## 落地到测试动作

- **按层建断言工具**：`assert_protocol` / `assert_business` / `assert_data` / `assert_side_effect` 各一个 helper，用例里显式调用；失败信息带层名与期望/实际，避免只留下一句 `assert 200 != 500`。
- **负向用例要断言错误结构**：不只断言「非 200」，还要断言错误码、字段级错误信息、是否有敏感信息泄露（错误栈、SQL、内部路径）。
- **异步与最终一致场景**：断言终态，用有界轮询（如最多 30 秒、每 500ms 一次），超时判失败；禁止 `sleep` 固定秒数——它既慢又不稳。
- **契约来源固定**：数据层结构断言走 OpenAPI / JSON Schema；字段集合变化应触发用例失败并人工确认，而不是自动跟随线上。
- **控制断言数量**：只断言契约内字段与语义稳定字段；不要断言自增 ID、时间戳、不稳定排序、日志原文——这类断言维护成本高、误报多，属脆弱断言。
- **常见误用**：把 Mock 环境下的全绿当成接口通过。Mock 无状态、不校验权限，副作用层根本测不出来，见 [[Mock接口桩的设计模式]] 的「状态偏离」。
