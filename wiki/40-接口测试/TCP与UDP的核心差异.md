# TCP 与 UDP 的核心差异

## 一句话
两个传输层协议的分歧是**设计哲学**：TCP 是追求数据完整性的"完美主义者"，UDP 是追求极致速度的"极简主义者"。选型不是看谁高级，而是看业务容得下丢包还是容得下延迟。

## 核心对比

| 维度 | TCP | UDP |
|---|---|---|
| 连接方式 | 面向连接（三次握手、四次挥手） | 无连接，知道 IP+端口直接发 |
| 可靠性 | 不丢、不重、不乱序（序列号 + ACK + 超时/快速重传） | 尽力交付，丢包不管 |
| 传输形式 | 面向字节流，**无边界 → 粘包/拆包要应用层自己处理** | 面向数据报，保留消息边界 |
| 速度 | 较慢（确认、重传、拥塞控制的开销） | 极快 |
| 首部开销 | 20~60 字节 | 固定 8 字节 |
| 通信对象 | 仅一对一 | 一对一/一对多/多对多（广播、组播） |
| 典型场景 | 网页（HTTP）、文件传输、邮件、支付 | 音视频通话、实时游戏、直播、DNS |

**选型原则**：要求数据 100% 完整、能容忍延迟 → TCP；实时性优先、能容忍少量丢包 → UDP。反例值得记住：射击游戏如果用 TCP，重传旧包反而导致画面卡死——丢一帧比卡一秒好。

## 面试三大追问点

**一、三次握手为什么不能是两次？**
两次无法防止**历史失效的 SYN** 造成错误连接：旧 SYN 迟到到达时，服务端在两次握手下会直接建连并分配资源傻等；三次握手下服务端等不到第三次 ACK 会超时释放。四次则纯属浪费——第三次已把 ACK 和 SYN 合并。

**二、四次挥手为什么是四次？**
TCP 是**全双工**的。客户端发 FIN 只代表自己发完了；服务端可能还有数据没发完，必须先回 ACK（进入半关闭），等数据发完再发自己的 FIN。ACK 和 FIN 在时间上被拆开，所以多了一次。

**三、TIME_WAIT 状态的作用？**
① 确保最后一个 ACK 能到达对方（丢了对方会重发 FIN）；② 让旧连接的残留报文在网络中自然消失（等待 2MSL）。

## 测试视角的落点

- **压测时看到大量 TIME_WAIT** → 说明是短连接高频交互，压测机和被测端都可能耗尽端口/连接资源。优先确认客户端连接池是否复用连接（Keep-Alive），而不是急着调内核参数
- **自定义 TCP 协议的接口要专门测粘包/拆包**：TCP 无消息边界，收包方按固定长度或分隔符切分——构造"一次发半条、一次发两条"的用例
- **HTTP/3 基于 UDP（QUIC）**：升级后"连接复用、弱网重传"类用例要重测，行为与 TCP 版本不同（见 [[HTTP协议要点与状态码]] 的版本演进）
