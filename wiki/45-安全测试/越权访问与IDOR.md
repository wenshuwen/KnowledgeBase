# 越权访问与 IDOR

## 一句话
攻击者篡改请求里的资源标识符，访问到**本不属于自己的数据或功能**。水平越权是"同级别之间横向跨越"，垂直越权是"低权限向高权限提升"。

| 类型 | 通俗说法 | 核心危害 |
|---|---|---|
| 水平越权 | 普通员工 A 看到员工 B 的工资条 | 数据泄露 |
| 垂直越权 | 普通员工执行了管理员的删除操作 | 功能滥用 |

## 系统化测试方法

### 水平越权

**双账号对比法（黄金标准）**：同时登录 A 和 B → 用 A 抓取所有带资源 ID 的请求 → 把 ID 换成 B 的 → 用 **A 的 Token** 重放。

> **关键判断：返回 200 ≠ 越权成功。** 必须对比响应体内容，确认返回的确实是 B 的数据。很多接口在无权限时返回 200 但内容为空或为占位数据，只看状态码会误报。

**ID 遍历策略**：自增 ID 直接递增；雪花算法 ID 分析时间戳+机器 ID 缩小范围；UUID 从列表接口、历史记录、分享链接收集已知值当种子。

**⚠️ "用了 UUID 就安全"是误区。** UUID 只是增加猜测难度，一旦从列表接口、分享链接、邮件通知或前端 JS 源码暴露，照样可被利用。

### 垂直越权

- **权限矩阵枚举法**：列出所有角色 × 所有接口，逐格验证实际访问结果是否符合预期
- **接口发现优先于权限测试**：爬前端 JS / Swagger / OpenAPI 提取全部路径，关注 `/admin/*`、`/internal/*`、`/manage/*`、`/config/*`，用目录爆破找未文档化接口
- **降级测试**：用高权限账号抓请求，逐步降低 Token 权限重放，看在哪一级开始返回 403——确认权限边界是否清晰
- **区分功能级与数据级**：能调用接口 vs 只能操作自己管辖范围的数据，两者要分别测

## 容易被漏掉的四种变体

1. **参数位置**：不只测 Query，还要测 JSON Body、XML Body、自定义 Header、Cookie 里的标识符
2. **批量赋值**：`PUT /api/user/profile` 里额外传 `user_id`、`role`、`is_verified`，若服务端自动绑定就中招
3. **二阶 IDOR**：A 无权直接访问 B 的订单，但能访问自己的收货地址，而收货地址接口返回了关联的 `order_id` → 间接拿到 B 的订单
4. **前端隐藏 ≠ 后端校验**：`v-if="user.role === 'admin'"` 只是 UX，攻击者直接构造 HTTP 请求即可

## 测试心法

**越权测试的核心不是工具，是业务理解。** 测试前必须画出用户角色图、数据实体关系图、业务流程图——**不知道"应该怎样"，就无法发现"不该怎样"**。

水平越权测试**务必用两个真实账号**，单账号无法区分"正常返回自己的数据"和"越权返回他人的数据"。

**越权漏洞往往成群出现**：发现一个点，说明整个模块的权限模型可能有系统性缺陷，应扩大测试范围，报告写"权限模型问题"而不是"这一个接口问题"。

## 服务端鉴权验证（2026-09-21 补）

> 更新：2026-09-21 源自 `raw/interview/2026-09-21.md`——把「怎么证明鉴权真的在服务端做」的验证动作系统化。

立场先行：**前端隐藏按钮只是体验优化，不是安全控制**（即上文第 4 变体的正面验证法）。验证只有一个原则——**绕过界面，直接打接口**：

1. **抓包改字段重放**：普通账号正常操作后，把请求里的用户 id / 订单 id / 租户 id / 角色 code 改成别人的重放，看服务端是否拒绝；
2. **低权限 token 直调高权限接口**：前端有路由守卫、后端完全没校验是高频漏洞形态；
3. **删掉前端限制**：disabled 按钮改成可点、直接 URL 打开被隐藏菜单，验证「UI 不可见但接口可达」的路径；
4. **看响应体泄露**：即使返回 403，错误信息带出他人数据片段或敏感字段同样是缺陷。

**矩阵化组织**：「角色 × 资源归属 × 操作」三维矩阵（自己的 / 同租户他人 / 跨租户 × 查改删导出），每格一条断言，期望结果明确写成「403 或 404，且不返回任何业务数据」。矩阵化才能保证覆盖完整、后续版本可回归。

**两个高频盲区**：① **多租户**（同角色不同数据域——权限模型完全相同，差别只在数据归属）；② **批量接口的部分执行**——传 10 个 id、9 个自己的 1 个别人的，必须验证服务端是整体拒绝还是部分执行，而不是只测单条。

## 旁路入口与解析不一致（2026-09-28 补）

> 更新：2026-09-28 源自 `raw/interview/2026-09-27.md`——补齐水平越权必测的五类入口里，上文尚未覆盖的部分。

**只测「查详情」远远不够**，水平越权必测的五类入口按优先级：

1. **写操作（改、删）**——危害最大，优先级最高先测；
2. **批量接口**——即上文「批量接口的部分执行」盲区，手法是传 `[自己的ID, 别人的ID]` 看是否两条都成功；
3. **导出接口**——直接按查询条件出数据，绕过列表页的权限过滤，最经典的重灾区；
4. **旁路入口**——分享链接、附件下载 URL、消息跳转、图片直链、打印页、二维码：**经常压根不做鉴权，只靠「URL 猜不到」当安全**；
5. **二次入口**——列表页过滤了、详情页没过滤；详情页过滤了、编辑页没过滤。顺着资源 ID 遍历所有能访问它的接口。

**参数污染**：同参数传两次（`id=1&id=2`）、传数组、加空格与编码变形。成因是**校验逻辑只作用于第一个参数，而业务逻辑取了最后一个值**（解析不一致）。配合小范围 ID 遍历（连续扫 100 个）判断是偶发还是批量泄露。

**效率工具**：Burp Autorize 插件可自动重放全部请求并替换为低权限身份，越权测试效率提升一个量级——但判定仍要人工比对响应体。

**根因层面的整改建议（写进报告）**：越权反复出现几乎都是因为**鉴权写在控制层、数据归属校验写在业务层，两层没对齐**。正确做法是所有带资源 ID 的接口在数据访问层强制附加「当前用户 ID」条件（**行级权限**），而不是依赖业务代码记得判断。

## 模型与检索场景下的越权（2026-10-12 补）

> 更新：2026-10-12 源自 `raw/interview/2026-10-07.md`——越权在 AI 应用上有两个新形态，判定逻辑与上文完全一致，只是「谁在发起请求」与「被访问的资源」换了主体。

1. **检索层的权限过滤（RAG 场景）**：不同角色的用户问同一个问题，**召回范围必须不同**，这类用例要单独造——一次泄漏就是事故。注意这里**不能用提示词约束替代权限控制**：在系统提示里写「只回答你有权看的内容」不是鉴权（本质是上文「前端隐藏 ≠ 后端校验」把前端换成了提示词）。
2. **Agent 的权限越界**：Agent 以服务身份调用工具，**天然是高权限身份**，一次提示词注入就可能变成任意工具调用。因此可调用的工具集合必须最小化，写操作（下单、发消息、删数据）必须有确认或幂等保护，并给高风险动作配「动作确认网关」，专门验证网关拦得住。

判定口径不变：**返回 200 且带出别人的数据绝对不行**；差别只在检查对象从 HTTP 响应体扩展到了「召回片段」与「工具调用参数」两处。

## 列表接口与拦截位置（2026-10-19 补）

> 更新：2026-10-19 源自 `raw/interview/2026-10-18.md`——补两个上文没单独展开的点：**列表接口的量级差异**与**拦在哪一层**。

**一、列表接口的漏测后果比详情接口大一个量级。** 详情接口一次泄露一条，列表接口若「不按当前用户过滤」，一次返回全站数据。所以水平越权的用例清单里，列表 / 导出 / 搜索这三类必须与详情同优先级——它们常共用同一个查询构造器，改一处漏一处。

**二、只验证「被拦住了」不够，要看拦在哪一层。** 同一请求可能被网关的鉴权中间件拦住，也可能进了业务层才被数据归属校验拦住。前者一旦有旁路入口（分享链接、内部调用、老版本接口）就整条失守；后者才是真正的防线。判定方法是**绕过网关直连内网服务**重放同一请求，或查日志确认拒绝发生在哪个环节。

**三、判定口径写成三段**（可直接进报告模板）：

| 实际结果 | 判定 |
|---|---|
| 200 + 业务码表示「无权限」 | 通过（接口设计如此，需确认前端也不渲染数据） |
| 200 + 返回他人数据 | **高危，阻塞发布** |
| 403 / 404 但错误信息带出他人数据片段 | 缺陷（信息泄露） |

第三段最容易被放过：状态码是拒绝，但错误文案里回显了对方昵称、手机号尾号或内部 ID。**状态码只是线索，不是结论**——这条与 [[接口断言的四个层次]] 的「协议层通过不代表接口没问题」是同一条纪律在安全场景的投影。
