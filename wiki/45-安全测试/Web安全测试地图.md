# Web 安全测试地图

## 一句话
安全测试的坑位不是按"漏洞名字"记的，而是按**攻击者从哪里进入系统**分成三类：往输入里塞东西、借用你的身份、骗服务器去请求。记住入口，比记住 payload 有用得多。

## 三类入口

| 类别 | 攻击者利用什么 | 代表漏洞 | 测试的共性动作 |
|---|---|---|---|
| **输入注入类** | 用户输入未经处理就被拼进解释器（SQL、HTML、HTTP 头） | [[SQL注入测试]]、[[XSS跨站脚本测试]]、[[CRLF注入测试]] | 找全用户可控输入点 → 塞特殊字符 → 看输出位置 → 按输出上下文调整 payload |
| **身份与会话类** | 系统信任了客户端传来的身份或凭证 | [[CSRF跨站请求伪造测试]]、[[越权访问与IDOR]] | 准备两个账号 → 篡改身份标识 → 重放 → **比对响应体内容而非状态码** |
| **服务端请求类** | 服务端代替攻击者发起请求 | [[SSRF服务端请求伪造测试]] | 找"从 URL 取资源"的功能点 → 逐级探测回环/内网/云元数据 |

## 三个跨类别的通用原则

**一、前端控制不是安全措施。** 隐藏按钮、前端校验、UUID 难猜——都只是 UX 或增加难度，不构成防护。判断标准永远是"直接构造请求会怎样"。

**二、状态码不等于判定结果。** 越权测试里返回 200 不代表成功越权，必须对比响应体内容是否真的是别人的数据；SSRF 里超时也不代表不可达，可能是被防火墙静默丢弃。**判定依据要落在内容上。**

**三、找到一个，就扩大范围。** 越权漏洞往往成群出现——发现一个说明整个权限模型可能有系统性缺陷。安全测试的报告方式应该是"这个模块的权限模型有问题"，而不是"这一个接口有问题"。

## 测试视角的落点

在测试用例设计里，这三类对应三种**必测的异常路径**：

- 输入注入 → 每个输入框、每个 Header、每个排序/分页参数，都要有一条"特殊字符"用例
- 身份会话 → 每个涉及资源 ID 的接口，都要有一条"换一个账号的 ID"用例
- 服务端请求 → 每个"填 URL"的功能，都要有一条"填内网地址"用例

**常见误用**：只在功能测试阶段用现成的扫描器跑一遍。扫描器能覆盖输入注入类的大部分，但**越权和业务逻辑类的漏洞几乎全靠人工理解业务才能发现**——工具不会知道"这个订单不该被这个用户看到"。
