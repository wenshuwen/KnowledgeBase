# SSRF 服务端请求伪造测试

## 一句话
服务端提供"从指定 URL 取资源"的功能却不校验目标地址，攻击者就能**让服务器替他发请求**——而服务器在内网里，能碰到攻击者碰不到的东西。

SSRF 的危害等级比多数 Web 漏洞高，因为它把攻击面从"公网可达"扩展到了"整个内网 + 云元数据"。

## 高危功能点（测试入口清单）

- URL 预览 / 链接分享解析
- 图片抓取 / 头像上传 / **PDF 生成**（很隐蔽，本质是服务端去取图片）
- Webhook 回调地址配置
- XML/JSON 外部实体引用（XXE）
- 导入远程资源（RSS、CSV、模板）
- SSO / OAuth 回调验证
- 云服务元数据接口调用

**找 SSRF 入口的通用方法**：搜代码/接口里所有"用户填了个地址，服务端去访问"的地方。

## 逐级探测 payload

| 级 | Payload | 目的 |
|---|---|---|
| 1 | `http://127.0.0.1:80/` | 探测本地回环 |
| 2 | `http://169.254.169.254/latest/meta-data/` | **云元数据服务**（AWS/阿里云） |
| 3 | `http://192.168.1.1:8080/admin` | 探测内网 Web 后台 |
| 4 | `file:///etc/passwd` | 伪协议读本地文件 |
| 5 | `http://internal-redis:6379/` | 探测内部服务端口 |

## 危害等级差异很大

| 利用方向 | 危害 |
|---|---|
| 内网端口扫描 | 中（只是信息收集） |
| 读取本地文件 | 高（敏感文件泄露） |
| **攻击内网服务**（Gopher 协议打 Redis） | **极高，可实现 RCE** |
| **窃取云元数据**（`/iam/security-credentials/`） | **极高，可接管云账号** |

面试里如果只答"能探测内网"，深度是不够的——**能打通云元数据直接接管账号**才是 SSRF 被列为高危的原因。

## 修复方向
白名单（推荐，只允许预批准的域名/IP）优于黑名单（易绕过）；**限制伪协议**只留 `http`/`https`；服务端禁止重定向（防跳转绕过）+ 设超时；**统一访问入口**——不让用户传完整 URL，改成传资源 ID 由服务端映射到固定路径，这是最彻底的解法。

## 绕过手法与三层防御（2026-10-19 补）

> 更新：2026-10-19 源自 `raw/interview/2026-10-18.md`——上文只说「黑名单易绕过」，这里补齐具体绕过形态与可验收的修复层级。

**常见绕过形态**（全部要进回归用例集）：

- **IP 表示的变形**：十进制 / 八进制 / 十六进制 IP、`0.0.0.0`、IPv6 映射地址；
- **DNS 重绑定**：域名第一次解析到公网、校验通过；服务端实际请求时解析到内网；
- **302 跳转**：入口 URL 合法，跳转目标指向内网；
- **URL 解析歧义**：`http://expected.com@169.254.169.254/`、`#` 与 `?` 位置的利用——校验器与请求库解析出不同 host。

**三层防御，按验收顺序**：

1. **协议白名单**：只允许 `http` / `https`，禁 `gopher` / `file` / `dict`；
2. **解析后校验真实 IP**：DNS 解析**只做一次**，用解析结果做内网 / 回环 / 链路本地段校验，再把该 IP 交给请求库——校验与请求必须用同一个解析结果，这是防重绑定的关键；
3. **统一出网代理 + 域名白名单**：所有服务端出站走同一代理，代理侧再拦一次。

**一个容易误判的判据**：**「拒绝」与「超时」必须区分**。超时可能意味着请求已经发出、只是没有回显（内网端口过滤、服务不返回），此时不能判「防御有效」，要结合服务端出网日志、代理访问日志确认。这是本源在测试方法上最容易出错的一处。
