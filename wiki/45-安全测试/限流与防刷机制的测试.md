# 限流与防刷机制的测试

## 一句话
只验证「超过阈值返回 429」是典型的测了表面、没测机制——核心是验证**拦得准不准、兜得住兜不住、被绕过时损失有多大**，共五个层次。

## 展开

**层次一：阈值准确性。** 打到第 N 次、第 N+1 次看是否被拦，并额外验三件事：

- **计数窗口边界**：固定窗口在切换瞬间可能放过 2 倍请求，滑动窗口不会——重要验证点；
- **计数维度**：按用户 / 按 IP / 按接口 / 按用户+接口组合，配置了哪个维度就验哪个；
- **限流粒度优先级**：单接口限流与全局限流同时命中时哪条先生效。

**层次二：绕过尝试（最有安全价值）。** 攻击者不会老老实实从一个 IP 一个账号发请求：

- **换 IP**：只按 IP 限流 + 代理池即可绕过 → 高危发现；
- **换用户标识 / 不带登录态**：未登录路径的限流最常被漏；
- **伪造头部**：系统若信任客户端传的 `X-Forwarded-For`，攻击者可随便伪造 IP 绕过——非常经典的高危缺陷，必测；
- **换入口**：同一业务能力有 H5 / APP / 小程序 / 开放接口 / 内部接口多个入口，往往只在主入口做了限流。

**层次三：降级与体验。** 正确行为是 429 + `Retry-After` 头 + 明确文案，而不是 500 或静默失败；还必须验**正常用户会不会被误伤**——按 IP 限流时同一出口 IP 下的公司/学校用户会互相拖累，这是上线后投诉的主要来源。

**层次四：高并发下的准确性（真正难点）。** 用 200 并发同时打，实际通过数是否接近阈值？远超阈值说明计数器有竞态（如 Redis get-then-set 非原子）——隐蔽但很常见。同时验**限流器自己不能成为瓶颈或单点**：它挂了应降级为放行而非阻断。这层已跨入性能域，排查思路见 [[性能瓶颈的分层模型]]。

**层次五：防刷的业务侧兜底（必测）。**

- **短信/验证码接口**（被刷直接资损）：有效期、一次性使用、同号/同 IP 频率、图形验证码触发策略；
- **登录接口**：失败锁定、锁定后能否改大小写/加空格绕过、**锁定机制能否被用来恶意锁定他人账号（拒绝服务）**；
- **下单/领券**：并发下超卖或超领（并发+限流交叉场景，必须单独测）；
- **接口枚举**：遍历 ID 能否批量获取数据（绕过手法同 [[越权访问与IDOR]]）。

## 落地到测试动作

- 工具选择：JMeter / k6 / Locust 做精确计数与并发验证，**k6 的 constant-arrival-rate 执行器最适合「严格每秒 N 次」**；Burp Intruder 做绕过试探；
- 压测执行纪律：**先小并发验证脚本与计数口径，再逐步加压**；
- 验收标准一句话：**拦住攻击者的同时不误伤正常用户，并且被绕过时有第二道防线**。
