# 编译式wiki与RAG的选型对比

## 结论先行
**在"知识要反复复用、需要跨条目建立联系"的前提下选编译式 wiki；在"原料海量、只做一次性事实问答"的前提下选 RAG。**
个人测试经验库属于前者，因此选了 [[llm-wiki 编译式知识库]]。

## 背景与约束
- 使用者 1 人，无团队协作需求
- 起步 0 页，长期预期 1000 页以上
- 核心诉求是**经验图谱**：踩坑记录、排障路径、选型依据之间要能互相引用
- 本机运行，可接受 Git 但不想额外维护模型服务

## 对比维度

| 维度 | 编译式 wiki | RAG |
|---|---|---|
| 处理时机 | 投喂时编译（写时） | 提问时检索（读时） |
| 产物 | 持久页面，交叉引用已就位 | 临时上下文，用完即弃 |
| 矛盾处理 | 写入时就标注、标 superseded | 每次检索都可能拿到互斥的两段 |
| 合成能力 | 综述随所有材料持续更新 | 只对当次召回的片段做合成 |
| 冷启动成本 | 高（每次投喂要精读、要补链） | 低（丢进去建索引即可） |
| 维护成本 | 中（需定期 lint 防漂移） | 低（但要维护向量库与模型） |
| 检索体验 | 千页内靠分层索引 + 标签够用 | 语义检索，海量原料下更强 |
| 失败模式 | 投喂断档 → 库停滞 | 召回不准 → 答非所问，且难以察觉 |

## 决策依据
按权重排序的三个理由：

1. **图谱必须先存在才能被查。** 编译式在投喂时就把链接、矛盾、综述都做完了；RAG 每次现查现拼，永远不会积累出"一张网"。
2. **个人规模不需要语义检索。** 千页以内，`index.md` 分层目录 + frontmatter 标签 + `rg` 全文的命中率足够，省掉向量库的模型依赖和索引重建成本。
3. **矛盾可见性是刚需。** 测试经验经常出现"以前这么写、后来发现不对"，编译式能把旧结论标成 `superseded` 并指向新页，RAG 做不到。

## 事后验证
待验证（2026-09-10 刚上线）。验证信号：
- 若 300 页时仍需频繁全文搜索才能找到东西 → 分层索引设计有问题，要重构目录
- 若 800 页时搜索命中率明显下降 → 该启用预留的向量接入位

## 什么情况下这个结论会翻转
- 变成多人协作、需要检索大量非结构化原料（会议记录、聊天日志）
- 知识以"查得到就行"的一次性事实为主，无复用需求
- 库规模远超个人量级（万页以上）
