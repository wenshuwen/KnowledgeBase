# 静态站点接入本地知识库的架构决策

## 结论先行
**在"已有单文件静态站点、要接本地知识库当数据源"的前提下：新增一条平行数据通道 + 一个构建步骤，不改站点的既有数据通道。**

具体三条：
1. 构建期把知识库编译成 `kb.json`，**不往已有内容包里塞**
2. 站点新增第二个 fetch 目标，与原有通道**互不依赖**
3. `publish: false` 的过滤只发生在构建脚本里，**绝不放前端**

## 背景与约束
- 站点是单文件 `index.html`（含内嵌兜底内容 + 运行时拉取云端内容包），已有版本比对、旧版归档、移动端与微信内核兼容层
- 浏览器读不到本地文件系统，所以任何"本地数据源"都必须先经过构建
- 已有内容包 145KB，微信 X5 首屏解析能力弱
- 站点是公网可见的

## 备选方案

| 方案 | 做法 | 否决/采纳理由 |
|---|---|---|
| A. 扩已有内容包 | 把知识库条目塞进 `content.json` 的 data 里 | ❌ 主包已 145KB，再扩拖慢首屏；两条业务线的更新互相牵制 |
| B. 平行产物 + 平行通道 | 新建 `kb.json`，站点二次 fetch | ✅ **采纳**。隔离、可独立更新、零回归风险 |
| C. 运行时直读知识库 | 站点直接请求知识库文件 | ❌ 需要知识库本身可被公网访问，等于把整个知识库暴露，且违背"构建期过滤"安全模型 |
| D. 服务端聚合 | 加一层后端渲染 | ❌ 为一个个人站点引入服务端，维护成本不成比例 |

## 决策依据

**一、隔离优先于简洁。** 方案 B 多了一个文件和一个 fetch，换来的是：知识库编译失败不影响每日内容管道；两条通道可独立发布；主包零改动即零回归。对一个每天自动更新、出错会影响你复习的站点来说，这个交换划算。

**二、安全边界必须在构建期。** 静态站点的前端过滤是**假过滤**——内容已经下载到浏览器，拿到链接的人看一眼源码就能绕过。所以"哪些内容不上站"这个判断只能发生在构建脚本里。这条决定了方案 C 不可行，也决定了 `publish` 字段必须由 `build_kb.py` 消费而不是由 JS 消费。

**三、失败要静默降级。** 新增通道的入口默认隐藏，只有拉取成功才放出。实测在取不到产物的环境下，主功能完全不受影响。**新功能不该以"可能弄坏老功能"为代价上线。**

## 一个可复用的细节：分类键映射层
知识库用长分类键（`performance-testing`），站点用短键（`perf`）。**不要改数据去迁就站点，也不要改站点去迁就数据**——在渲染前加一层映射常量（`KB_CAT_MAP`），直接复用站点既有标签样式，零样式改动，两边各自保持自洽。

## 事后验证
待验证（2026-09-10 刚上线）。观察信号：
- 若每日自动化更新知识库产物时主内容管道出现过中断 → 说明隔离不彻底
- 若 `kb.json` 超过 200KB → 需要按分类分片、按需加载

## 什么情况下这个结论会翻转
- 站点需要按知识库内容做全文检索或复杂筛选 → 单文件产物可能不够，要考虑分片或专门的检索索引
- 知识库本身要对外开放 → 方案 C 反而成立，且能省掉构建步骤
