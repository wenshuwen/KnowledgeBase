# 静态站点按日归档与漂移发布

## 结论先行
无后端的内容站，数据组织用「**日期 × 组 + 索引**」，发布用「**漂移判据**」，内容流转用「**流水与图谱分层**」。三个决策共同针对同一类失效：**内容明明更新了，用户看到的却是旧的**。

1. 内容按「日期 × 组」组织，索引记录「日期 → 所在文件名」，前端只读索引、不拼路径
2. 发布判据是"本地与线上哈希不一致"，不是"某条数据通道变化了"
3. 每日流水与知识图谱分层：归档不直接进图谱，经原料层由低频编译消化

## 背景与约束
- 单文件静态站点、纯静态托管、无服务端；内容由定时任务每日生成
- 知识库（wiki）是低频编译的图谱：每个新页要抽实体、补 ≥2 条出链、控制孤页率
- 用户通过移动端与微信内访问，首屏解析能力弱，页面体积敏感

## 备选方案

| 决策点 | 备选 | 结论 |
|---|---|---|
| 内容组织 | A. 单一平铺内容包 | ❌ 无法支撑"按日期回看历史"，也撑不起"每组展示不同集合"的轮换需求 |
| | B. 日期 × 组 + 索引 | ✅ **采纳**。索引是唯一事实来源，归档策略变化不动前端 |
| 发布判据 | A. "某条数据通道变化了才发布" | ❌ 页面代码、构建脚本的更新被排除在外，永远不会上线（真实发生过） |
| | B. 本地与线上哈希比对 | ✅ **采纳**。与实现无关的客观事实，不需要理解"这次改了什么" |
| 内容流转 | A. 每日归档直接写进知识图谱 | ❌ 图谱每页要抽实体补链，流水一天上百条且隔天过时，直接灌入冲垮图谱 |
| | B. 归档 → 原料层（精选落盘）→ 低频编译 | ✅ **采纳**。每日只做"落原料"（只增不改、脱敏、标注来源日期），图谱按自身节奏消化 |

## 决策依据
- **索引为什么记文件名**：按日切片后，跨月合并会让同一天从 `2026-09-30.json` 换到 `2026-09.json`。猜路径的前端在合并当天全线 404；索引改为唯一事实来源后，归档策略再怎么变都不用动前端
- **漂移为什么可信**：文件哈希比对不依赖"这次改了什么"的判断，天然覆盖所有通道。代价是发布工具必须支持同目录重复发布，且发布后必须复核（只看 HTTP 200 会漏掉「JS 新、CSS 旧」的半新半旧推送）
- **分层为什么必要**：见 [[编译式wiki与RAG的选型对比]] —— 图谱的价值在"写时编译"，流水灌入等于退化成读时检索

## 代价与边界
- 归档体积逐日增长 → 用"当月按日、跨月合并月文件"收敛；合并逻辑必须幂等，且**必须同步改索引指向**（漏了这一步等于制造全线 404）
- 漂移判据依赖发布工具的可重复发布能力；平台策略变化（如新增必填参数、域名绑定）会直接打断发布链路，需要有兜底巡检把问题报出来而不是静默
- 两套分类词汇（归档短键 / wiki 长键）并存，必须有一条一致性测试钉住，否则会各自漂移
