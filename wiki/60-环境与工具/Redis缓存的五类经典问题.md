# Redis 缓存的五类经典问题

## 一句话
缓存不是"加一层就快"，它有五种典型失效模式，每一种的表现都是"数据库压力突然变大"，但根因和修法完全不同。

## 五种问题对照表

| 问题 | 现象 | 定位方法 | 修法 |
|---|---|---|---|
| **缓存击穿** | 某个热点 Key 过期瞬间，大量请求直接打到数据库 | 热点 Key 监控 | 热点 Key 设为永不过期；或加互斥锁重建 |
| **缓存穿透** | 查询的 Key 根本不存在，每次都穿透到底层 | 查询日志出现大量 `null` 返回 | 布隆过滤器拦无效 Key；或缓存空值 |
| **缓存雪崩** | 大批 Key 同一时刻集中过期，数据库被瞬时打满 | 观察 Key 过期时间分布 | 过期时间加随机偏移；上多级缓存 |
| **大 Key** | 单 Key 体积过大，读写阻塞、网络传输慢 | `redis-cli --bigkeys` | 拆分大 Hash/List；压缩 value |
| **热 Key** | 单个 Key 的 QPS 异常集中，压垮单分片 | 监控 QPS 集中度 | 本地缓存 + Redis 二级；Key 拆分（`key_1` ~ `key_10`） |

## 还有一层：Redis 自身的单线程瓶颈

Redis 命令执行是单线程的。当 `INFO` 里的 `instantaneous_ops_per_sec` 接近单实例上限时，加机器不如改用法：

- **集群分片** —— 把压力摊到多个实例
- **读写分离** —— 读走从节点
- **Pipeline 批量操作** —— 减少往返次数，这是性价比最高的一招

## 测试视角的落点

这五种问题在测试里对应的是**缓存失效场景的用例设计**，不是功能用例：

- 击穿 → 用例要覆盖"热点 Key 刚好在压测过程中过期"
- 穿透 → 用例要覆盖"随机不存在的 ID 高频查询"
- 雪崩 → 用例要覆盖"批量写入后同时到达过期点"
- 大 Key → 用例要覆盖"单个 Key 接近 512MB 上限"
- 热 Key → 用例要覆盖"单 Key 占 80% 流量"

**常见误用**：把缓存问题的验证放在功能测试阶段做一遍就算完。这些问题只在**并发**下暴露，功能环境单请求跑一万遍也测不出来。
