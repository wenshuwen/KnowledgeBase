## 一、今日高频面试题

**题目：你们项目接了 RAG（检索增强生成）系统，怎么做端到端的测试与评估？**

**口语化参考答案：**

这题在 2026 年的 AI 岗面试里基本是必问，但大部分候选人上来就说"我用人工抽样看几个问答评估一下"——这种回答只能算入门。面试官真正想听的是**分层、可量化的工程评估体系**。

**第一步：别上来就评"答案对不对"，先把 RAG 拆成两段来看**。RAG 系统天然有两个独立故障面——**检索器（Retriever）** 和 **生成器（Generator）**。一个问题答错了，可能是检索召回错了 chunk，也可能是模型拿到了对的 chunk 却没正确引用。**一个端到端的正确率指标无法定位是哪个环节出了问题**，所以我的做法是分两段拆指标。

**第二步：检索阶段看四个核心指标**。第一个是 **Recall@K**，向量的检索里我通常用 K=5 或 K=10，就是回答这个问题需要的所有相关 chunk 里，有多少排在了 top-K；第二个是 **MRR（Mean Reciprocal Rank）**，第一个相关 chunk 排得越靠前分越高；第三个是 **Context Precision**，检索回来的 chunk 里有多少是真的有用的；第四个是 **Context Recall**，该召回的 chunk 召回回来了多少。这四个指标都靠 ground-truth 的"问题—相关 chunk"对照表来算，这套对照表要花 2~3 天从真实用户问题里挑 200~500 条做出来，不能用合成数据替代。

**第三步：生成阶段看三个核心指标**。最关键的是 **Faithfulness（忠实度）**，把模型生成的答案拆成一条一条 claim，每条 claim 检查能不能从检索回来的 context 里推导出来——分数低就说明模型在**瞎编**，这是幻觉检测的硬指标，企业级一般要求 0.90 以上。第二个是 **Answer Relevancy（答案相关性）**，模型答的内容到底是不是在回答用户的问题—— faithfulness 高不代表 relevancy 也高，比如检索回了一堆相关文档，模型答了一个擦边但没正面回答的问题。第三个是 **Citation Accuracy**（引用准确率），每条引用指向的文档里是不是真的有这个 claim，这个在医疗、法律、金融领域特别敏感，行业基线 95%+。

**第四步：实测我用工具链跑**。主流框架是 **Ragas**（开源最常用，支持这五个核心指标），它的原理是用一个更强的 LLM 当裁判（LLM-as-Judge），把答案拆 claim 再比对 context。我自己项目里是这样做的：用 Ragas 跑离线评估集，出报告；线上每条用户请求记录 query、检索的 chunks、模型输出、用户反馈四元组，每天抽样 50~100 条喂给 LLM-judge 看 faithfulness 和 answer relevancy 的均值，跟基线对比超过 5% 退化就告警。除了 Ragas，还有 **TruLens**（带 trace 的评估）、**Langfuse**（带可观测性的评估）、**DeepEval**（pytest 风格集成），CI 里跑就用 DeepEval 最顺手。

**真实坑点补充**：我踩过的最贵的坑是——LLM-as-judge 本身的偏差。裁判模型偏好长答案、偏好自己写的风格，而且同一份输入跑两次可能不一样。我的破解方法：**judge 模型固定 + temperature=0 + 配 rubric prompt 锚定评分标准 + 关键决策必须配人工抽检**。这两个加在一起，工程上才稳。

**收尾点一句深度**：RAG 评估不是一次性的事，是**反馈回路**——评估集要持续从线上流量里补新问题，指标要持续监控，单次离线跑得好不代表线上不漂移。能讲出这层，工程视角就立起来了。

## 二、今日知识点总结：RAG 评估的分层指标体系

RAG 的质量不是单一指标能衡量的，**必须按检索 / 生成 / 端到端三层拆开看**：

| 层级 | 指标 | 看什么 | 需要 ground-truth？ | 工程基线 |
|---|---|---|---|---|
| **检索** | Recall@K | top-K 里召回了多少相关 chunk | ✅ | > 0.85 |
| 检索 | MRR | 第一个相关 chunk 的排名 | ✅ | > 0.80 |
| 检索 | Context Precision | 召回的 chunk 有多少是有用的 | ✅ 或 ref-free | > 0.80 |
| **生成** | Faithfulness | 答案的 claim 是否都来自 context（反幻觉） | ❌ | > 0.90 |
| 生成 | Answer Relevancy | 答案是否在回答用户的问题 | ❌ | > 0.85 |
| 生成 | Citation Accuracy | 引用是否真的指向支撑文档 | ✅ | > 0.95 |
| **端到端** | Answer Correctness | 答案最终是否正确（vs 真值） | ✅ | 视业务定 |
| 业务 | Resolution Rate | 用户问题一次解决的比例 | 反馈数据 | 业务定 |

**关键认识**：
- 检索指标低 → **改 embedding / chunking / 检索策略**
- Faithfulness 低、Recall 高 → **改 prompt 模板 / 换更强生成模型**
- Faithfulness 高、Answer Relevancy 低 → **改 Query Rewrite / 检索排序**
- 一个指标好不等于系统好，**至少看 faithfulness + relevancy + 召回三项联动**才能定位瓶颈。

## 四、今日面试坑点

**坑点：「RAG 评估只测端到端正确性，不分阶段定位问题」**

很多候选人被问"你怎么评估 RAG 系统"时，立刻答"我用人工抽几个问题看看答案对不对"。这种回答在 2026 年的 AI 测试岗面试里**几乎必败**。

面试官的真正考点是：

> **你怎么定位"答案错了"到底是检索层还是生成层的锅。**

**破解方法**：
- **必须分层答**：检索（Recall@K / Context Precision）→ 生成（Faithfulness / Answer Relevancy）→ 端到端（Answer Correctness）
- **必须报具体基线**：不说"越高越好"，说"Faithfulness >0.90、Answer Relevancy >0.85、Context Recall >0.75 是工程基线"
- **必须说 LLM-as-Judge 的隐患与对策**：judge 模型的偏差、温度、rubric 校准
- **必须提反馈回路**：评估集要持续从线上流量扩充、指标要长期监控、单次跑分不代表系统稳定
- **收尾补一个真实反思**："这套体系踩过什么坑、后来怎么改"——比"我都用得很熟"加分 10 倍

**反例**：凭感觉抽样看几个问答。
**正解**：分层指标 + 工程基线 + LLM-judge 校准 + 反馈回路 + 真实反思。

## 五、每日自测题

**题目**：在 RAG 系统的分层评估指标里，「Faithfulness」与「Answer Relevancy」最本质的区别是？

- A. Faithfulness 看答案长度，Answer Relevancy 看答案语种
- B. Faithfulness 看答案的每一句 claim 是否都能从检索回来的 context 里推导出来（反幻觉），Answer Relevancy 看答案是否在回答用户的问题（不偏题）
- C. Faithfulness 用 embedding 模型算，Answer Relevancy 用 LLM 算
- D. 两者完全等价，叫法不同而已

**正确答案：B**

**解析**：
- **A 错**：Faithfulness 衡量的是答案对检索上下文的"忠实度"，跟答案长度、语种没有任何关系。
- **B 对**：这是两个最容易被混淆也最关键的区别——**Faithfulness 是反幻觉指标，对抗"模型瞎编"**；**Answer Relevancy 是相关性指标，对抗"模型答非所问"**。一个高一个低是非常常见的现象：检索回了一堆相关文档，模型忠实引用了（faithfulness 高），但答的是擦边内容（answer relevancy 低）。
- **C 错**：Ragas 里这两者**都是 LLM-as-Judge 算的**，差异在 judge prompt 的 rubric，不在用哪种模型。
- **D 错**：两者不仅不等价，而且是 RAG 评估里必须分开看的两个独立维度，混淆了就没法定位故障点。
